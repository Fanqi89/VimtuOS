# 网络与浏览器生态攻坚计划（v0.12.2 起）

> [← 返回主页](../README.md) · VimtuOS 文档体系

本文是「网络与浏览器生态」阶段的**事实盘点 + 分期计划**。所有结论都带代码位置或实测判据；
凡没做到的，直接写"没做"，不写成"计划中"。

- 阶段起点：v0.12.1（`7069df7e`），本版目标版本 **0.12.2**
- 本文三件事：**① 现状到底是什么**（两条独立网络栈）→ **② `ping 域名` 为什么报错**（根因逐条）
  → **③ 分期怎么打**（L4 硬化 → DNS → TLS → 浏览器移植 → 外壳）

## 0. 一句话结论

| 问题 | 结论 |
|---|---|
| TCP/大文件 | 内核 socket 层的 TCP 原来**不校验序号**、**不认窗口**、**不做数据段重传** —— 局域网能通，多兆下载**会坏**（重复数据入缓冲 / 丢数据被静默跳过）。v0.12.2 已按序号收 + 真窗口 + 校验和 + 单段重传，见 §3 |
| DNS | `ping baidu.com` 报错有**两个**代码根因，都已定位：① 卷上**没有 `/etc/resolv.conf`**（musl 的 getaddrinfo 没有内置默认 nameserver）；② `poll()` 对 socket handle 一律回 `POLLNVAL`（handle 不在 fd 表里），musl 等 DNS 回包时直接失败。v0.12.2 两条都修 |
| HTTPS | **一行 TLS 都没有**。现代站点全 HTTPS，所以"能上网"必须先把 mbedTLS 移植进来（§6） |
| 浏览器 | 仓库里**已经没有浏览器**（v0.5.x 那版 `/bin/browser` 源码已删）。按战略方向改成**移植 NetSurf**（§7），不自研引擎 |
| 工作量 | L4+DNS 是工程活（本版已做）；TLS 是中等移植（§6）；NetSurf 是**大移植**（9 个依赖库 + 前端 + fetcher），必须分阶段（§8） |

## 1. 现状盘点：仓库里有**两条**各自独立、互不复用的网络栈

这是理解一切的前提 —— 它们**不是**同一份代码的两个入口。

| | **A. 内核 socket 层**（真实应用走这条） | **B. Ring 3 网络守护 `netd`**（自带栈的演示/工具） |
|---|---|---|
| 代码 | `kernel/net64.cpp`（ARP/ICMP/IPv4 收发）+ `kernel/sock64.cpp`（TCP/UDP/raw ICMP socket）+ `kernel/e1000_64.cpp` | `user/net/netd.c`（1,700 行，**自拼每一个字节**，只用内核号 53 收发原始帧） |
| 谁在用 | busybox `ping`/`wget`/`nslookup`、musl 的 `getaddrinfo`、任何 Linux ABI 程序 | 只有 `/bin/netd` 自己（CLI：ifconfig/dhcp/ping/dns/tcp connect/listen/selftest） |
| 能力 | 客户端 TCP/UDP/raw ICMP；**无** listen/accept | ARP/IPv4/ICMP/UDP/**DHCP**/DNS(A)/TCP（客户端 + 监听回显） |
| 验收 | `net64_test`、`netping64_test` | `netuser64_test` |

**结论**：浏览器（ring3 程序）只能走 A。所以「能让开源浏览器跑起来」= **必须把 A 做到工业级**，
B 的能力（DHCP、DNS 客户端）应当**下沉成 A 的公共设施**，而不是让浏览器自己去实现协议。

> 如实说明：v0.12.2 **没有**把 B 合并进 A（那是一次架构级重构，见 §8 P1）。本版只把 A 的
> TCP/DNS 短板补齐到"能下载、能解析域名"。

## 2. `ping baidu.com` 报错：三个根因（两个代码、一个环境）

| # | 根因 | 证据 | 本版处置 |
|---|---|---|---|
| ① | **没有 `/etc/resolv.conf`**。musl 的 `getaddrinfo` **不内置**默认 nameserver：`__res_msend_rc` 只读 `/etc/resolv.conf`，文件不存在 → 直接失败（EAI_NONAME）。仓库里 `tools/**` 从来没写过这个文件（旧日志 `grep resolv.conf` = 0 命中） | `tools/store_pack_win.py` 原来只种 `/etc/fonts.conf` 与 `/etc/vpkg/provides` | **已修**：构建期预置 `/etc/resolv.conf`（`nameserver 10.0.2.3`，0666，改完立即生效） |
| ② | **`poll()` 看不见 socket**。musl 发完 DNS 查询后 `poll()` 等回包，而 socket handle = `200+idx` **不在 fd 表里**，旧 `lx64_poll_core64` 一律回 `POLLNVAL` → 解析必然失败 | `kernel/syscall64.cpp` 旧 `lx64_poll_core64` 只调 `fd64_ready64` | **已修**：新增 `sock64_ready64()`，poll 核心按 socket 类型分派 |
| ③ | **环境**：QEMU 用户网络（slirp）只对**网关 10.0.2.2** 回 ICMP echo；对公网地址 ping **不会**有 reply（slirp 不转发 ICMP） | QEMU 文档 + `netping64_test` 之所以只 ping `10.0.2.2` | **不是代码缺陷**。真机/桥接下 `ping baidu.com` 才会"变绿"；slirp 下只能证明**域名解析成功**（回复里的 `from <解析出的IP>` 行） |

所以本版的验收判据拆成两条（不混为一谈）：
- **解析成功** = `nslookup baidu.com` 打出 A 记录 / `ping` 打出 `PING baidu.com (110.242.x.x)`；
- **回声成功** = 只对 10.0.2.2（slirp 网关）断言 `0% packet loss`。

## 3. 大文件传输：内核 TCP 的 6 个真缺陷（v0.12.2 修法）

旧实现（v0.7.4 起未变）在 `kernel/sock64.cpp`，对**小请求/小响应**没问题，对多兆下载会坏：

| # | 缺陷（旧代码） | 真实后果 | v0.12.2 修法 |
|---|---|---|---|
| ① | 收到数据段**不校验序号**：`if (dlen > 0) { append; rcv_nxt = seq + dlen; }` | 对端重传一次 → **同一段数据被追加两遍**，文件比源大且内容错位 | 只有 `seq == rcv_nxt` 入缓冲；`seq < rcv_nxt` = 重复（只回 ACK，计数）；`seq > rcv_nxt` = 乱序（丢弃 + 立即 dup ACK 促快速重传） |
| ② | 窗口**写死 4096**；缓冲满时静默丢数据**却仍推进 rcv_nxt** | 丢的那段**永不重传** → 文件中间整段缺失 | 每次 ACK 报真实剩余空间（64 KiB 缓冲），收满报 0 且不推进 `rcv_nxt` |
| ③ | 收到段**完全不验 TCP 校验和** | 坏段被当数据收下 | 伪首部 + 段整体算和，非 0 丢弃并计数 `badsum` |
| ④ | 数据段**发了就不管**，没有重传 | 丢一个段 → 连接永久卡住（上传/请求头/大 POST 都会踩） | 单段在途 + RTO 500 ms 指数退避到 4 s，收到 ACK 才清 |
| ⑤ | SYN **不带选项** → 对端只能按 MSS 536 发 | 吞吐约为应有的 1/2.7 | SYN 带 `MSS=1460` |
| ⑥ | `recv` 超时返回 **0**（与 EOF 不可区分） | 慢下载停 3 秒 → 被当成"文件结束" → **截断文件** | TCP/UDP 超时返回 `-EAGAIN`；只有 `FIN`/`RST` 才返回 0（EOF） |

配套：缓冲 4 KiB → **64 KiB**；`recv` 取走数据后**立即重发 ACK 通告新窗口**（否则对端按旧窗口停住，
这是"下载中途不动了"的经典原因）；新增判据计数器 `sock64_retx64 / rx_dup64 / rx_ooo64 /
rx_badsum64 / rx_winzero64`，验收脚本据此断言"真的按序号收了、真的重传了"。

**仍然没有的（如实）**：listen/accept、IPv6、IP 分片重组、SACK/时间戳/窗口缩放、拥塞控制
（固定 RTO，无 cwnd/RTT 估计）、乱序缓存（丢乱序等重传）、Nagle/延迟 ACK、`SO_RCVTIMEO`。

### 3.1 追加发现（第一次真连网络时抓到的两个线上 Bug）

上面 6 条是"看代码就能看出来"的；真跑 `nslookup example.com` 时又抓到两条**只有真发包才会暴露**的：

| # | 缺陷 | 实测现象 | 修法 |
|---|---|---|---|
| ⑦ | **UDP 根本没包头**：`sock64_send64` 的 UDP 分支把用户 payload 直接交给 `net64_send_ipv4`，而 `net64_send_ipv4` 只补 Ethernet + IPv4 头 —— 对端看到的"目的端口"其实是 payload 的前两个字节（DNS 报文里是事务 ID） | `[SOCK64] create type=2` → `arp reply 10.0.2.3` → `sendto ret=0x1D`（29 字节发出去了）→ 下一次 `poll` **直接超时** → `nslookup: can't resolve` | 新增 `s64_build_udp()`：补 8 字节 UDP 头（源/目的端口、长度、校验和=0） |
| ⑧ | **端口/窗口在线上字节序写反**：`wr16(htons(port))` 双反，收包侧 `htons(rd16(...))` 又反回来 —— 内部自洽、逻辑自检全绿，但**线上 53 变成 0x3500=13568** | 与 ⑦ 叠加：即使补了 UDP 头，对端仍不认为这是发往 53 端口的查询 | 本层端口统一**主机序**保存，`s64_wr16/s64_rd16` 直接做大端读写；删掉 `s64_htons`。自检新增判据：`rport=53` 时线上必须是 `0x00,0x35`（写反必红） |

> 这两条的教训写进纪律：**"逻辑自检全绿"不能证明"线上字节对"** —— 凡是协议字段，必须有"把字节算出来断言"的判据。

```
P0  L4 硬化 + DNS 打通              ← v0.12.2（本版）
      ├─ TCP 序号/窗口/校验和/重传/MSS
      ├─ poll 看得见 socket
```

## 6. mbedTLS 移植评估（P2 的核心）

| 项 | 实测/事实 |
|---|---|
| 上游 | `github.com/Mbed-TLS/mbedtls`（v3.x，Apache-2.0 / GPL-2.0 双许可；商用友好） |
| 仓库体积 | GitHub 报告 **145,319 KB**（含 tests/framework 子模块）；**只需要 `library/*.c` + `include/mbedtls`**，实际编进系统的约 **50–60 个 .c**，静态链接后预计 **~250–400 KB**（未实测，移植后按 `nm`/文件大小给硬数字） |
| 依赖 | 只需要 C89/C99 运行时 + 我们自己的 musl 交叉工具链（与 busybox/lua/tcc 同一套）。**不需要 pthread**（`MBEDTLS_THREADING_C` 默认关） |
| 需要的系统能力 | `read/write/close`（有）、`fcntl`（有）、`poll`（**本版起对 socket 生效**）、`getrandom`（有号 318，但**目前是非密码学安全**）、`clock_gettime`（有）、`snprintf`（musl 有） |
| **必须先补的前置** | **密码学级熵源**。现在的 `getrandom(318)` 自述"伪随机（非密码学安全）"——**TLS 用弱随机等于没有加密**。方案：CPUID 探 `RDRAND`/`RDSEED`（`CPUID.01h:ECX bit30`），有则直采；无则 TSC/中断抖动 + 内核池做 CSPRNG（ChaCha20/DRBG，mbedTLS 自带 `ctr_drbg`） |
| 配置裁剪 | 只要 TLS 1.2/1.3 客户端 + X.509 校验 + AES-GCM/ChaCha20-Poly1305 + SHA-256/384 + ECDHE（P-256/X25519）+ RSA 签名验证；关掉 DTLS/PSK/SSLv3/服务端/自检/测试套件 |
| 风险 | ① 证书时间校验需要我们提供**可信的 RTC 时间**（本内核 RTC 从 CMOS 读；无 NTP），系统时间错 → 证书"过期/未生效"判定错。方案：先做 **SNTP/HTTP Date 校时**或允许"时间未知"降级并**大声打点**（不许静默跳过校验） |
| 判据 | `https://` 握手成功 + 对**故意错证书**的站点**必须失败**（负向对照，不许假设通过） |

## 7. NetSurf 移植评估（P3 的核心）

**为什么选 NetSurf**：纯 C、自带 HTML/CSS 排版引擎、有可替换的 **frontend API** 与 **fetcher API**，
静态链接后体积可控；`mbedTLS` 官方受支持（`nssslcert`/`mbedtls` 后端）。它不要求 X11/GTK。

依赖（GitHub 实测仓库体积，均 MIT）：

| 库 | 体积(KB) | 作用 |
|---|---|---|
| `netsurf-browser/netsurf` | 28,332 | 引擎本体 + 各前端（我们只取 `content/` `render/` `desktop/` 等核心） |
| `libwapcaplet` | 151 | 字符串驻留 |
| `libparserutils` | 600 | 字符集/输入流 |
| `libhubbub` | 3,395 | HTML5 解析 |
| `libcss` | 8,428 | CSS 解析/选择器/层叠 |
| `libdom` | 5,496 | DOM |
| `libnsgif` / `libnsbmp` / `libsvgtiny` | 833 / 1,208 / 1,542 | 图片解码 |
| `libnsutils` / `libnspsl` / `libnslog` | 40 / 1,635 / 93 | 杂项 / Public Suffix List / 日志 |

**必须自己写的两块**（这正是"用我们的外壳"的落点）：

1. **fetcher**（`content/fetchers/vimtu.c`）：用我们的 socket 层实现 `FETCHER_HTTP`（+ mbedTLS 的
   `FETCHER_HTTPS`）。NetSurf 的 fetcher 接口很小（`setup/start/abort/finalise/poll`），
   比移植 libcurl 省一个数量级的依赖。
2. **前端**（`frontends/vimtu/`）：以 NetSurf 自带 `framebuffer` 前端为模板，把 `gui_table`
   （窗口/绘图/字体/位图/剪贴板）实现在 **`wl_surface`** 上；`plot` 走我们内核的
   `gfx64`（抗锯齿、圆角、阴影都是现成的）。字体用系统已有的 Noto Sans / Sarasa / Unifont。

**外壳（我们自己实现，不沿用 NetSurf 的旧 UI）**：标签页 + 地址栏（输入即搜索，默认 `bing.com`）+
前进/后退/刷新/主页 + 下载管理（进度条、取消、落点选择）+ 状态栏。用现有的 Token 表
（`gui_rs` 生成的圆角/间距/动效）画，风格与桌面一致。

**风险（如实，按严重度）**：
1. **字体度量**：NetSurf 需要 `font_plot_style`/字形度量与 kerning 查询；我们的字体是"构建期子集 4 个面"，
   缺字形只能回落，**排版精度会明显低于桌面浏览器**。方案：先保证"能读、能点、不崩"，不承诺像素级对齐。
2. **libcss/libdom 的规模**：这两个库比其余六个加起来还大，是编译期的主要工作量（交叉编译 + 配置）。
3. **页面兼容性**：NetSurf 的 JS 支持是空的（`libdom` 无 JIT）。现代站点大量依赖 JS →
   **本阶段目标是"能打开、能读、能点下载"，不是"能跑 Gmail"**。这条必须写进产品文案，不许吹。
4. **时间**：不是一个版本能完的。按 P3.1（库编译打通）→ P3.2（fetcher + 简单页面渲染）→
   P3.3（外壳与交互）→ P3.4（下载管理）四步走。

## 8. 明确不做的事（避免"手搓引擎"的老路）

- **不自研 HTML/CSS 引擎**（用户已定死方向：移植）。
- **不移植 Chromium/Gecko**（体积与内存模型都不匹配 15 MiB 内核 + ring3 1008 MiB 窗口的约束）。
- **不把 TLS 自己写一遍**（除必要的最小胶水：熵源、时间、socket 回调）。
- **不在内核里解析 HTTP/TLS**（格式解析器不拿 ring0 权限 —— 与 ext4 放 ring3 同一条纪律）。

## 9. 验收方法（每个阶段都要有可复核的判据）

| 阶段 | 判据 | 不许怎么做 |
|---|---|---|
| P0 | `[SOCK64] fin … dup=/ooo=/badsum=/retx=` 打点；`ping -c 3 10.0.2.2` 0% loss；`nslookup` 打出 A 记录 | 不许拿"能连上"当"传对了" |
| P1 | 客人 `sha256sum` 与宿主 `sha256` **逐字节一致**；4 MiB / 16 MiB 两档 | 不许只比文件大小 |
| P2 | 真站点握手成功；**错证书站点必须失败** | 不许跳过证书校验换"通过" |
| P3 | 打开 `example.com` 后**屏幕像素**有正文墨迹；点链接能触发下载 | 不许用"进程没崩"当渲染成功 |

## 10. 现场（本版起点）
```
HEAD（阶段起点） = 7069df7e（v0.12.1 发版回读）
本版目标         = 0.12.2
内核映像基线     = 3,575,808 B（15 MiB 闸门：15,728,640 B）
两条栈           = kernel/net64+sock64（应用用）/ user/net/netd.c（自带栈演示）
DNS 上游常量     = 10.0.2.3（slirp）；网关 10.0.2.2；本机 10.0.2.15/24（静态，无 DHCP）
```
