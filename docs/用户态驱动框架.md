# 用户态驱动框架（VimtuOS ring3 驱动框架 + 零拷贝通道 + 内核监督重启）

> 版本：v0.9.33。署名：Fanqi89 主导设计。
> 这份文档只写**已经跑通并有串口证据**的东西；没做到的写在 §7「诚实边界」里，一条不留。

---

## 1. 一句话

**把"文件系统协议"搬进 ring3，把"总线/DMA"留在 ring0。**

* ring0 只干三件非它不可的事：**按盘上的字节探出这是什么文件系统**、**按 PRDT 发 DMA**、**监督服务进程生死**；
* ring3 的驱动服务在自己的地址空间里解析 ext4，它拿到的数据是 **DMA 直接写进它映射着的共享页**（0 次 memcpy）；
* 它崩了只死一个进程 —— 内核监督器会把它重新拉起来；拉不起来就**如实放弃**，卷退回只读安全态。

第一个真驱动是 `/usr/bin/ext4svc`（ext4 只读），配套看门狗观察进程 `/usr/bin/drvwatch`。

---

## 2. 为什么（取舍，不是口号）

### 2.1 为什么不把 ext4 写进内核 —— 不是放不下，是不该放

内核当前 `kernel64_os.bin` 约 3.17 MB，硬闸门 15 MiB（`ML64_KERNEL_SECTORS=30720`），余量 12 MB 以上。
所以"塞不进"不是理由。真正的理由是：

> 文件系统解析器是**最容易被畸形磁盘镜像打崩**的那一类代码 —— 它按盘上的字节做链式解引用、算偏移、
> 跟整数溢出搏斗。留在 ring0，一张坏 U 盘能拖垮整机；放到 ring3，最坏结果是"那个服务进程死了"。

这条判断有前例可循：VimtuFS2（自家格式）留在内核里是因为**我们能约束格式**；ext4 是外来格式、外来数据，
攻击面完全不同。

### 2.2 为什么 DMA 目标必须是服务的共享页，而不是内核缓冲

内核缓冲那条路要多一次 `for (i..) dst[i] = src[i]`。64 MiB 就是 64 MiB 的 CPU 拷贝 —— 在 QEMU/TCG 下
这笔开销甚至比磁盘本身还贵。

而 AHCI 的 PRDT 允许"一帧一项"：只要内核知道共享对象的**物理帧号**
（`proc64_shm_view64` 能给），就能让 DMA 引擎自己把数据放进服务已经映射好的页里 ——
那一次拷贝**根本不需要发生**。

### 2.3 为什么监督器在内核里，而不是"用户态看门狗进程去重启别人"

一个 ring3 进程连"另一个进程还活着没有"都要靠内核告诉它。让它去重启别人，是把可靠性倒着设计。

所以分工是：**内核执行（respawn），ring3 观察（取证）**。
`/usr/bin/drvwatch` 周期读 `/proc/vimtu/drivers`，把状态机打到串口，让验收脚本能抓到"服务在不在、
重启过几次、零拷贝搬了多少字节"。它不是执行者。

## 3. ABI：两条系统调用入口 + 一块共享对象

### 3.1 入口必须分清（这点搞错，调用号一定错）

| 入口 | 号段 | 本批用到 |
|---|---|---|
| `int $0x80` | VimtuOS **自有**（`V64_NR_*`） | `13 shm_create` / `14 shm_map` / `1 write` / `5 sleep_ms` / `4 ticks` |
| `syscall` | **Linux x86_64** + 私有追加号 | `0 read` / `1 write` / `2 open` / `3 close`，以及本批 `1029..1035` |

同一个数字在两条路径上含义不同（`2` 在自有 ABI 是 exit，在 Linux 是 open）。见
`kernel/syscall64.cpp` 文件头与 `user/drivers/r3drv.h`。

### 3.2 私有 syscall（只许追加，不许改旧号）

| 号 | 名字 | 参数 | 返回 |
|---|---|---|---|
| 1029 | `r3drv_register` | `(name, proto, disk, shm_id, bytes)` | 槽号 / 负错误码 |
| 1030 | `r3drv_beat` | `()` | 0 = ok |
| 1031 | `r3drv_kick` | `(shm_id)` | 处理的 SQE 条数 / 负 |
| 1032 | `r3drv_dma` | `(shm_id, obj_off, lba, secs)` | 落地字节数（单发零拷贝） |
| 1033 | `r3drv_copy` | `(shm_id, obj_off, lba, secs)` | 落地字节数（单发**拷贝对照**） |
| 1034 | `r3drv_status` | `(slot, out R3drvInfo, len)` | 0 / -ENODEV |
| 1035 | `r3drv_route` | `(disk, lba)` | `0=driver / 1=read-only / 2=unknown-ro` |

### 3.3 共享对象布局（`kernel/r3drv_abi.h`，内核 C++ 与用户态 C **共用这一份**）

```
[0   , 56 )                R3drvRing  环控制块（magic/slots/head/tail/kicks/dma_bytes/copy_bytes/errs/ver）
[64  , 320)                R3drvSqe[8] 请求数组（32 B/条，**就地完成**）
[4096, obj_bytes)          数据区 —— **只有这一段能当 DMA 目标**
```

* 一帧（4 KiB）= 8 个 512 B 扇区，所以 `obj_off` 必须 4096 对齐；
* 服务的提交姿势：填 SQE → **最后**写 `state=R3DRV_SQ_PENDING` → `head++` → 调一次 `kick`（门铃）；
* 内核消费完**就地**把 `state` 改成 `DONE(2)` / `FAILED(3)`，并把实际字节数写进 `bytes`；
* 所以"环"是控制面（每批一次 syscall），"对象的帧"是数据面（DMA 直达）。

为什么没有独立 CQ 环：省一个环、省一次内存序协商；代价是同一槽在下一次提交前必须已被消费
（服务侧用 `head - tail < 8` 自然节流）。

## 4. 零拷贝到底哪一步省掉了拷贝

```
服务: shm_create(2 MiB) -> shm_map -> 拿到 VA（用户可读写）
服务: r3drv_register(name, proto=ext4, disk, shm_id, bytes)
              |
内核: 槽位记下 (pid, shm_id)，核对该 shm 句柄真的属于调用者
              |
服务: 在环里放 SQE{lba, secs, obj_off=4096}
服务: kick(shm_id)   <-- 唯一一次系统调用
              |
内核: proc64_shm_view64(shm_id) -> **物理帧号数组**
内核: ahci64_read_frames64(disk-8, lba, secs, &frames[1], npages-1, &bytes)
              |                       ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^
              |                       一帧一项 PRDT（一条命令 ≤16 帧 = 64 KiB = 128 扇区）
              v
      AHCI 引擎把盘上扇区 **直接写进服务的页**（没有任何内核缓冲参与）
              |
服务: 自己的 VA 上已经能看到数据，直接解析（ext4 超级块/inode/extent/目录项）
```

三个必须说清的细节：

1. **x86 上不需要任何 cache 刷新**：无 IOMMU 时 DMA 与 CPU 缓存一致（MESI），数据落地即可读。
2. **页池不保证连续**，所以"一帧一项 PRDT"是唯一正确的做法（不是优化，是必需）。
   对照路径（`R3DRV_F_COPY`）里那个内核 64 KiB 暂存也踩过同一个坑：最初只记首址 `g_kbuf` 就当连续用，
   会写坏页池里别人的页；现在改成**逐页记地址 + 探测连续段长度**（`g_kbuf_pg[]` / `g_kbuf_run`）。
3. **零拷贝只在 AHCI 上成立**。PATA 是 PIO，没有 DMA 可达的目标地址；其它总线（NVMe/USB）尚未接。
   非 AHCI 盘会自动退到拷贝路径。

## 5. 状态机：注册 / 心跳 / 重启 / 只读回退

```
                  autostart（/etc/r3drv.conf）
                          |
                 按分区类型探卷 r3drv_probe_proto64
                    |                    |
              认得出 ext4           什么都不是
                    |                    |
        route = read-only         route = unknown-ro
        reason=no-driver          （只读裸卷，不假装能写）
                    |
        r3drv_start_service64  -> 状态 DYING
                    |
        服务 register      -> 状态 RUN（route 升级为 mode=driver）
                    |
            beat 每秒若干次（超时 = beat_ticks，默认 250 tick = 1 s）
                    |
        进程消失 / 心跳超时 / 拉起后不注册
                    |
        service died  -> 收尸（proc64_destroy64）-> 状态 STALE
                    |
        restarts < 3 ?  -> 重启（service restart attempt=N）
                    |                    |
                   是                   否
                    |                    |
                回到 DYING        状态 FAILED（reason=restart-limit）
                                        -> 该协议的卷退回只读安全态
```

* **注册是幂等的**：同名重复注册 = 更新（重启后的新进程重新认领同一个槽，`mode=update`）。
* **收尸是必须的**：`proc64_destroy64` 把进程槽与地址空间收回来，否则重启三次就把 `PROC64_MAX(16)` 耗干。
* **监督器不做磁盘 I/O**（只有"拉起"那一瞬要读 ELF），所以它挂在 `kheart` 内核线程（约 1 秒一次），
  **不挂 GUI 帧循环** —— 帧循环里做 ELF 加载会撞看门狗。
* **★ v0.9.34：死亡检测与拉起拆成两步，各自有确定的时间上界**
  * 死亡检测 = **同一拍**：`proc64` 的退出漏斗（`p64_exit64`，`#DE/#PF/...` 与应用 `exit()` 都走它）
    直接调 `r3drv64_on_die64(pid)`，只认领槽 + 打时间戳（`g_die_tick`），**不做任何 I/O**；
  * 拉起 = **下一个 60 ms 切片**：`kheart` 的循环从"1 秒一次"改成 `PIT_HZ/16 ≈ 60 ms` 一片跑
    `r3drv64_tick64()`（心跳打点仍是 1 秒一次，日志格式不变）。原来只在 1 秒的 beat 里跑，
    "崩了多久才被拉起"既不可观测也不好保证；
  * 两行都带 **`lat_ms=`**（PIT 250 Hz -> 1 tick = 4 ms，从"死亡那一拍"算起），
    于是"1 秒内拉起"是**内核自己报出来的数**，不是主机侧猜的时间。

## 6. 本次验收实测

`py -3 tests/drv64_test.py` → **38/38 PASS**。关键数据（同一块 64 MiB ext4 镜像、同一台 QEMU、同一条通道）：

| 指标 | 实测 |
|---|---|
| 端到端 | 内核探到 `disk=8 lba=0 proto=ext4` → 拉起 `/usr/bin/ext4svc` → `shm_create/map(2 MiB)` → `register`（`mode=new`）→ 零拷贝读 → 用户态解析 ext4 |
| 路由两态 | 服务起来前 `route … mode=read-only reason=no-driver`；注册后 `route … mode=driver slot=0` |
| 零拷贝正确性 | 服务在自己地址空间里对卷首 4 KiB 算 CRC32 = `0xb5d452d3`，与宿主侧对同一镜像算出的 **0xB5D452D3 逐位相等** |
| 文件内容 | `/hello.txt` 13 B `0x1b00f179`｜`/big.bin` 100,000 B `0x92858800`｜`/sub/data.bin` 5,000 B `0x4d71c181` —— 三个都与宿主侧一致 |
| 64 MiB 顺序读（机制，确定性） | 零拷贝路径内核报 `copied=0`（命中 4 条）；对照路径内核报 `copied=2093056`（每块，2168 B 控制页之外全拷）；两条路径读到的总字节数都是 67108864 |
| 64 MiB 顺序读（计时，仅作数据） | 零拷贝 81~91 MB/s、对照 80~88 MB/s（七次取样；最后一次 87 vs 84，也曾出现反向 82 vs 88） |
| 崩溃重启 | `crash=1` → 服务写空指针 → 内核 `service died … pid=25 beats=1 restarts=0 reason=exit`（**同一拍就发现**）→ `service restart attempt=1 pid=27 ok` → 新实例 `restarts=1` 重新注册并把 ext4 又解析了一遍；整机继续心跳 |
| 只读回退 | `autostart=0` → 只打 `autostart skipped reason=off`，全程无 `[R3DRV] start`、无 `[EXT4SVC]` |
| 合成节点 | `[DRVWATCH] slot0 name=ext4svc proto=1 disk=8 st=2 pid=25 beats=141 rst=0 dma=125952 cpy=0`（`dma=` 与内核 `[R3DRV] kick … dma_bytes=` 对得上） |

**关于吞吐这条，必须说实话 —— 这是本批最容易自欺的地方**：

省掉的是 64 MiB 的 CPU memcpy，但在 QEMU/TCG 下 **AHCI 命令的模拟开销远大于真实硬件**，
它把 memcpy 那点差距压平了，甚至会被抖动盖过去（实测出现过零拷贝 82 MB/s 反而低于对照 88 MB/s）。
所以本批**不拿吞吐排序当判据**（测试里也不断言它），只拿两条确定性证据：

1. 内核自己报告**它拷了多少字节**（零拷贝 `copied=0` / 对照 `copied=64 MiB`）—— 不受计时抖动影响；
2. 两条路径**读到的字节数相同**（67108864），内容 CRC 与宿主一致 —— 证明省掉的只是拷贝，不是数据。

"零拷贝让 CPU 少干 64 MiB×2（读+写）的活"是**代码结构事实**（`ahci64_read_frames64` 里没有一处 memcpy）；
"省了多少时间"在这台模拟机上**测不出来**，正确的度量是"每 GB 的 CPU 周期数"—— **本批没测，记为未验证**。

## 7. 诚实边界（一条都不许抹）

1. **完全只读**：框架没有写路径。`r3drv_*` 里没有任何写盘接口，ext4svc 也不实现 WRITE。
   这是有意的：只读驱动不可能弄坏用户数据。
2. **零拷贝只在 AHCI**：`disk >= ATA64_AHCI_BASE` 才走散列 DMA；其它总线退到拷贝路径并打点。
3. **没有驱动隔离/权限模型**：能 `register` 的进程就能对该盘发**任意 LBA** 的读请求（只读，但信息面很宽）。
   真正的沙箱（只允许读自己声明的卷）需要"设备归属仲裁"，本批没做。
4. **完成是就地写 SQE.state**，没有独立 CQ 环、没有中断/事件驱动；门铃是一次系统调用（不是纯共享内存轮询）。
5. **ext4 只支持 extents**：不支持间接块（老 ext3 风格）、不支持 64bit 块号、不支持 `metadata_csum` 校验、
   不做 journal 重放。extent 索引树只做到 `depth ≤ 1`，遇到更深的**如实拒绝**（返回 `unsupported depth`）。
6. **一次 kick 最多消费 8 条**（环深），超出的留给下一次。
7. **监督重启**只覆盖"进程没了 / 心跳停了"，不覆盖"进程活着但算错了"（那需要协议层校验和；
   ext4 的 CRC32 只证明**数据**一致，不证明解析没漏）。
8. 服务的**常驻策略是有限时长**（`ext4svc` 每 40 ms 一次心跳、跑 1500 轮 ≈ 60 秒后退出）。
   真实发行版应当做成常驻守护，本批为了保证验收可复现，故意做成有界。
9. **"每 GB 的 CPU 周期数"没测**（见 §6 末段）：零拷贝省掉一次拷贝是结构事实，"省了多少"没有硬数字。

## 8. 怎么验收

```powershell
py -3 tests/drv64_test.py            # 4 个阶段，全自动（约 4~6 分钟）
```

它做的事：

1. 用 `tools/mkfs_ext4_win.py` 生成 **64 MiB 真 ext4 夹具**（4 KiB 块、extents、FILETYPE 目录项、真实位图与 inode 表），
   并在生成时用**独立的读取器**自校验（`SELFCHECK OK`）；
2. 把 `build64/sysdisk.img` 复制到临时目录（**绝不直接开机 sysdisk.img** —— 开机过程会往里写 `/etc/users.db` 等文件），
   把它当第一块盘（PATA 0），把 ext4 夹具当第二块盘挂在 **AHCI**（`ich9-ahci` + `ide-hd,bus=ahci.0`）上；
3. 四个阶段靠**等长字节替换** `/etc/r3drv.conf` 切换（`autostart=1→0`、`bench=0→1`、`crash=0→1`）——
   不改内核、不重编；
4. 每个断言都对应一条串口行，失败时把那一行原样打出来（便于定位"是没跑还是跑错了"）。

## 9. 下一步（按价值排序）

1. **写路径**（ext4 只读 → 可写需要 journal 与 bitmaps 的写回，风险高于读，必须单独一批）。
2. **设备归属仲裁**：让 `register` 声明"我只服务这块卷"，内核拒绝越界 LBA。
3. **通道改事件驱动**：接 AHCI 中断 → 完成时置 SQE 而非依赖服务轮询（与 xHCI 的补中断同一条路）。
4. **NTFS/FAT 驱动服务**：同一套 ABI，只换 `proto` 与服务 ELF；这正是"框架"相对"一条硬编码路径"的价值。
5. **把 `/proc/vimtu/drivers` 接进任务管理器**（现在只是文本节点 + `drvwatch` 读取）。
