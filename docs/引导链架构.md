# VimtuOS 引导链架构（位宽说明）

本文件回答一个问题：**这套系统的各部分到底是什么位宽？** 结论先给：

| 部分 | 位宽 | 说明 |
|------|------|------|
| 内核（`kernel/*`，64 位构建） | **纯 64 位** | 全部目标文件 ELF64 / x86-64，入口 `0x100000` 即长模式 |
| 内核入口 `entry64.asm` | **64 位** | `bits 64`，第一条指令就是 64 位代码 |
| 中断桩 `isr_stubs64.asm` | **64 位** | `iretq` / `push` r64 语义 |
| 上下文切换 `switch64.asm` | **64 位** | 与中断帧同构 |
| 驱动/图形/安装程序（fb/font/input/ata64/setup64/x86_64） | **64 位** | 用 `clang --target=x86_64-elf` 编译 |
| 引导加载器 `loader64.asm` | 16 + 32 + **64** | 见下方"三段"说明，业务逻辑全在 64 位 |
| MBR 引导扇区 `boot.asm` | 16 位 | BIOS/MBR 的物理要求（CPU 复位后就是实模式） |

## 1. loader64.asm 的三段构成

```
[bits 16]  第 1..934 行   实模式准备（BIOS 只能在这里用）
    · 串口初始化、开启 A20
    · INT 15h E820 内存地图
    · INT 10h VBE 模式设置 + 读 EDID
    · 写 BootInfo 到 0x1000
    · lgdt + 置 CR0.PE → 远跳 0x08:pm_ata_load 进保护模式

[bits 32]  第 935..1038 行   ★ 只有"进入长模式"所必需的指令
    · pm_ata_load：设置段寄存器/栈，写一个 'P' 标记，直接跳 lm64_enter_long
    · lm64_cpuid：检查 CPU 支持 LM + PAE
    · lm64_build_paging：建 0..4GB 恒等映射页表（PML4/PDPT/4×PD，2MB 大页）
    · lm64_enter_long：CR4.PAE=1 → EFER.LME=1 → CR0.PG=1 → 远跳 64 位代码段
    这些指令**必须在加载 64 位代码段之前执行**（CPU 架构规定），因此无法用
    64 位代码完成；执行一次后永不回到 32 位。

[bits 64]  第 1039 行起      ★ 其余全部在 64 位长模式里
    · 初始化串口、打印阶段标记
    · 用 ATA PIO 把内核从 LBA 9 读进 0x100000（**这段原来在 32 位，现已搬到 64 位**）
    · 跳转 0x100000 进内核入口
```

也就是说：引导链里**没有 32 位业务代码** —— 读盘、输出、跳转都是 64 位的；
32 位那一段只有"进长模式"这一件事，约 50 条指令。

## 2. 实测证据

```
# 64 位构建的全部 19 个目标文件
ata64.o  builtins64.o  entry64.o  fb.o  font*.o  icon*.o
input.o  isr_stubs64.o  kernel64.o  logo_rgba.o  setup64.o  switch64.o  x86_64.o
→ 全部 Class: ELF64 / Machine: Advanced Micro Devices X86-64

# 内核 ELF 头
Class: ELF64     Machine: x86-64     Type: EXEC     Entry point: 0x100000

# 引导链位宽分布（loader64.asm）
81:[bits 16]     935:[bits 32]     1039:[bits 64]
loader64.bin = 2826 bytes（MBR 只能读 8192 字节，余量充足）

# 内核运行期自证（串口日志）
[LM64] ENTERED LONG MODE efer=0000000000000500   ← EFER.LMA(bit10)+LME(bit8) 都是 1
[LM64] ptr_bits=64 cr3=0000000000040000 cr4=0x20  ← CR4.PAE=1
[LM64] PIT IRQ OK ticks=12 irq_total=13
```

自动验收：`python tests/boot64_assert.py --stage m1` → PASS；
`python tests/screen64_probe.py` → PASS（安装界面 5/5 像素断言）。

## 3. 为什么还留着 16 位那一段？

**x86 CPU 上电/复位后一定处于 16 位实模式**，这是硬件规定，任何操作系统都绕不过去
（Windows x64 的 MBR 引导也是 16 位；Linux 的 `boot/header.S` 同样如此）。BIOS 的
INT 10h/INT 15h/INT 13h 也只在实模式可用。

**唯一能让引导链完全 64 位的方式是 UEFI**：x86_64 平台上的 UEFI 固件本身就跑在长模式，
`EFI/BOOT/BOOTX64.EFI` 是纯 64 位可执行文件 —— 那样连 16 位和 32 位都不需要。
这正是本项目 M3（UEFI 双模式 ISO）要做的内容；做完之后，"引导"这一段就可以是
**100% 64 位**，MBR 那条路只作为兼容保留。

## 4. 与 32 位旧工程的关系（已退役）

本项目**只保留 64 位构建**：`build64.sh` 是唯一构建脚本，产物只有
`vimtu64-64.img`（安装介质）与 `vimtu64-64.iso`（光盘/U 盘引导 ISO）。

原先那套 32 位工程（`build.sh` + 32 位专用内核源码，产出 `vimtu64.img`）已整体移入
`legacy32/`，**不参与构建、也不被 64 位代码引用**：

* `legacy32/build32.sh`（原 `build.sh`）—— 已退役，保留仅供历史参考
* `legacy32/kernel/` —— 32 位专用内核源码（`kernel.cpp`、`gui.cpp`、`task.cpp`…），
  将来把桌面栈移植到 64 位时可作为参考实现
* `legacy32/boot/` —— 32 位 loader 与文本安装器
* `legacy32/artifacts/` —— 32 位时代的镜像产物（`vimtu64.img`、`vimtu64-install.iso`…）
* `legacy32/uefi/` —— 早期 gnu-efi 草稿（Linux 工具链路径，从未接入构建）

详见 `legacy32/README.md`。整个 `legacy32/` 目录可以直接删除，不影响 64 位构建。
