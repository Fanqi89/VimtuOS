### 批次 v0.9.20：ENABLE 卡点修掉（启动不再停）+ PRIME 跨进程 + 事件投递 —— `v0.9.20`

> 上一批把 ENABLE 之后的"启动停在桌面之前"写成**证据**留给本批。这一批先把它修掉，
> 再把用户清单里的"dma-buf/fence 跨进程"和"事件通知"两块真正补上。

* **卡点根因（一次证据定案）**：加 `[VMWARE] stage1 a=pre / b=fifo-ok / c=enable-written / d=update-enter /
  e=update-done`（带 `i=` 序号）后，VMware 一次就跑到 `e=update-done` —— 说明**不是**卡在注册/几何/ENABLE，
  而是卡在 `vw_fifo_update()` 的等待里：v0.9.19 的 `vw_wait_idle()` 是"2,000,000 次 spin、每次一次 `outl+inl`"，
  而 VMware 上**每次端口 I/O 都是一次 VM-exit**（真机 1~10 µs）→ 几十秒到几分钟的**假卡死**。
  修法：① 两次端口读之间插 **65,536 次 `pause`**（纯 CPU，不进 hypervisor）② 上限 2,000,000 → **2,000 次读**
  （≈60 ms 封顶）。修后实测 `[GUI64] ready` 与 `[UI] perf` 都在 `[VMWARE] svga enable=1` **之后**出现。
* **顺手修的自伤病**：ENABLE / CONFIG_DONE 之后 host 会把 `FIFO[NEXT_CMD]` 复位到头部保留区，
  原来的 `if (next < MIN) return 0;` 让 `SVGA_CMD_UPDATE` **根本没进 FIFO**却只打一行 `sync=TIMEOUT`
  （看起来像 host 不回 SYNC，其实是自己提前退了）。现在越界从 `MIN` 重新开始，并把 `next=` / `max=` 打进日志。
* **新量出来的能力边界（如实）**：`refifo … sync=ok` 证明 ENABLE 之后 SYNC/BUSY 握手仍可用，
  但 `SVGA_CMD_UPDATE` 入队（`next` 16→21）之后 host **不再回 SYNC** → **3D 命令通路仍未验证**。

### 批次 v0.9.16：DRM 属性系统（14 个属性 + blob）+ atomic commit —— `v0.9.16`

> v0.9.15 补完非 atomic 路径之后，wlroots 的 DRM 后端还差最后一层：**属性系统**与 **atomic commit**。
> 它们不是"多几个 ioctl"，而是一种模型 —— 对象（CRTC/connector/encoder/plane/fb）各自有一组**属性**，
> 一次 `MODE_ATOMIC` 请求要改一批对象的批属性，**要么全成要么全不成**。本批把这个模型落地。

* **8 个新 ioctl**（号由 `DRM64_IOWR(nr, type)` 用 sizeof 算，与 Linux 逐个相等）：
  `GETENCODER` `0xC01464A6` / `GETPROPERTY` `0xC04064AA` / `GETPROPBLOB` `0xC01064AC` /
  `OBJ_GETPROPERTIES` `0xC02064B9` / `OBJ_SETPROPERTY` `0xC01864BA` / `ATOMIC` `0xC03864BC` /
  `CREATEPROPBLOB` `0xC01064BD` / `DESTROYPROPBLOB` `0xC00464BE`。累计 **24 个 DRM ioctl**。
* **14 个固定属性**（名字/标志/可挂对象都在 `D64_PROPS` 一张表里，标志取 Linux 位值）：
  CRTC 的 `ACTIVE`/`MODE_ID`；plane 的 `type`(immutable)/`FB_ID`/`CRTC_ID`/`SRC_X/Y/W/H`/`CRTC_X/Y/W/H`/
  `IN_FORMATS`(immutable)；connector 的 `CRTC_ID`。SRC_* 是 **16.16 定点**（Linux 口径），CRTC_* 是像素。
* **blob**：两个**固定** blob + 4 个用户槽。`MODE_ID` 走 `CREATEPROPBLOB`（libdrm 的
  `drmModeCreatePropertyBlob` 就把 68 B 的 `drm_mode_modeinfo` 塞进去）；`IN_FORMATS` 按 Linux 的
  `drm_format_modifier_blob` 布局拼（header 24 B + 2 个 fourcc + 1 条 linear modifier，共 56 B）——
  这是 wlroots 判断 plane 能接哪些格式的依据。
* **atomic commit 的语义（做到哪儿就说到哪儿）**：
  * 请求里 `objs_ptr` / `count_props_ptr` / `props_ptr` / `prop_values_ptr` 四组数组全部做用户范围校验，
    对象数 ≤ 8、属性数 ≤ 32（超了如实 `-EINVAL`），`reserved` 必须 0。
  * 每个属性先做**归属校验**（这张属性能不能挂在这个对象上）与 **immutable 校验**；
    然后做语义校验：`MODE_ID` 必须是本内核那一个模式（换分辨率 → `mode-unsupported`）、
    `SRC_*` 只支持 0 偏移、`SRC_W/H` 与 `CRTC_W/H` 不相等就 `no-scaling`、矩形越出屏/越出 fb 各自报错。
  * `TEST_ONLY`（0x100）：全部校验通过后**直接返回，一个像素都不动**。
  * 真提交：`ACTIVE=0` 或 `FB_ID=0` → 真清屏（整屏填黑并提交）；否则按 `CRTC_X/Y` 贴图上屏，
    `g_crtc_active`/`g_fb_on_screen`/`g_last_*` 一起更新，之后 `GETCRTC`/`GETPLANE`/`OBJ_GETPROPERTIES`
    读到的都是新状态。
  * `NONBLOCK`（0x200）/`ALLOW_MODESET`（0x400）接受但语义上仍是同步提交（如实写在头文件里）；
    `PAGE_FLIP_EVENT`（0x1）等**一律 `-EINVAL`** —— 本内核不投递事件，不假装能投。
* **对象 id 的如实说明**：本内核 CRTC / connector / encoder / primary plane 的 id 都是 1（Linux 里它们
  是不同命名空间、可以是不同数字）。属性归属靠"属性表里的 types 位"判定，所以 id 撞车不影响语义，
  这一点写进了 `d64_atomic_apply64` 的注释。
* **判据加强（45 → 65 条）**：①b 的号表 16 → **24 个**、双头文件比对的结构体 17 → **25 个**；
  新增 11 条 ring3 阶段断言（encoder / 属性两阶段枚举 12 项 / `FB_ID` 名字与标志 0x12 / IN_FORMATS 56 B /
  MODE_ID blob 68 B → id 768 / atomic 缩放反例 / 事件反例 / TEST_ONLY / 真提交 / 提交后
  `GETPLANE`+`GETCRTC` 报同一个 fb / DESTROYBLOB），外加 9 条内核侧证据断言。
  **"TEST_ONLY 没动像素"用的是 present 计数差 == 1**（提交自己那次）—— 比"看着像没动"强。
* 实测（本批构建产物）：`drm64_test` **65/65**、`wl64_test` **91/91**、`gpu64_test --only std` **40/40**、
  `proc64_test` **67/67**、`fd64_test` **34/34**、`status_report` **95 / 0 / 0**。
* 体积：内核 3,046,768 → **3,054,560 B**（+7,792 B；闸门 3,116,544 B，余量 **61,984 B**）。
* 串口实证原文：
  `[DRM] encoder id=1 type=2 crtc=1 possible_crtcs=0x1`、
  `[DRM] prop obj=1 type=0xeeeeeeee count=12`、`[DRM] prop get id=4 name=FB_ID flags=0x12 values=0`、
  `[DRM] blob read id=513 len=56`、`[DRM] blob create id=768 len=68`、
  `[DRM] atomic FAILED reason=no-scaling err=22`、`[DRM] atomic FAILED reason=flags err=22`、

### 批次 v0.9.15：DRM 属性面（ADDFB/ADDFB2/SETCRTC/GETPLANE）+ 进程回收 hook —— `v0.9.15`

> v0.9.14 把 ABI 对齐做完了，但 wlroots 的非 atomic 路径还缺三样：**fb 对象**（`drmModeAddFB2`）、
> **`drmModeSetCrtc`**、**plane 枚举**（`drmModeGetPlaneResources`/`drmModeGetPlane`）。本批补齐这三个，
> 并把"进程异常退出不 DESTROY_DUMB 就永久占页"这个欠账清掉。

* **五个新 ioctl**（`ADDFB` 0xAD / `ADDFB2` 0xAE / `SETCRTC` 0xA2 / `GETPLANE` 0xB5 / `GETPLANERES` 0xB6），
  号由 `DRM64_IOWR(nr, type)` 用 sizeof 算出来，**与 Linux 逐个相等**：
  `0xC01C64AD` / `0xC06864AE` / `0xC06864A2` / `0xC02064B5` / `0xC01064B6`。
  两个 struct 的**对齐陷阱**写进注释了：`drm_mode_fb_cmd2` 的 `modifier[4]` 与
  `drm_mode_get_plane_res` 的 `u64+u32` 都**不能 packed**（packed 会给出 100 / 12 字节，号就错）。
* **fb 与 dumb 是两套号**（Linux 也这样）：fb id 从 `0x100` 起、dumb handle 是 `1..4`；
  fb 只是"dumb handle 的薄包装"（不复制像素）。`dumb 被销毁 / 被进程回收时，引用它的 fb 一起消失` ——
  否则 fb id 会指向已经还给页池的物理页（那等于把任意内存显示到屏上）。
* **`SETCRTC` 语义**：`fb_id = 0` 是**真清屏**（整屏填黑并提交，不假装关掉）；
  `mode_valid = 1` 时校验模式（本内核只有 1 块屏 1 个模式，换分辨率如实 `-EINVAL reason=mode-unsupported`）；
  `x/y` 真的生效（呈现函数从 `[0,0,w,h)` 改成 `[x,y,w,h)`，越界自动裁）。
* **`GETPLANE`**：`primary`(1) / `cursor`(2)；primary 报当前在扫出的 fb，format 表 = `XRGB8888`/`ARGB8888`；
  cursor 只报告**不接管硬件**（如实写在证据里）。
* **进程回收 hook**：`proc64` 的 `p64_exit64` 与 `proc64_destroy64` 两处按**弱符号**调

  把该 pid 名下没 DESTROY 的 dumb 全部收走并打一行聚合账
  `[DRM] release pid=<n> fbs=<n> pages=<n> free_pages=<n>`。

  新增 11 条断言：plane 资源/格式、`ADDFB2` 成功行、**`ADDFB2` 的 NV12 反例必须 `-22`**、
  `SETCRTC` 成功行（`mode=ok path=cpu`）、`[DRM] release … fbs>=1 pages>=1`、

* 实测（本批构建产物）：`drm64_test` **45/45**、`wl64_test` **91/91**、`gpu64_test --only std` **40/40**、
  `proc64_test` **67/67**、`taskexit64_test` **PASS**、`fd64_test` **34/34**、

### 批次 v0.9.14：DRM ABI 与 Linux `drm.h` 逐字节对齐（11 个 ioctl 号 + 5 个 struct） —— `v0.9.14`

> v0.9.12 交付了 DRM/KMS 门面，但 ABI 是"我们自己算的"：`DRM64_IOWR(nr, type)` 的 size 位就是
> `sizeof(struct)`，所以我们那 5 个 struct 的尺寸与 Linux 差 4/4/16/16 字节，ioctl 号也跟着差。
> 本批把 struct 改成与 `include/uapi/drm/drm.h` **逐字节相同**，11 个 ioctl 号于是全部落回 Linux 的数值 ——
> 下一批接真 libdrm 本体时不用再动 ABI。

* **必须一次改齐**（v0.9.13 试过只改头文件：`kernel/drm64.cpp` 立刻编译不过，只能回滚）。
  本批是 7 个文件同一提交：`kernel/drm64.h` + `kernel/drm64.cpp` + `user/lib/drm64.h` +

* `drm_version` 60→**64**：3×`int` + **自然对齐的 4 B padding** + 6×8。这里**必须去掉 `packed`** ——
  packed 不插 padding，会永远停在 60 字节（上一版文档误写成"56 → 64"，56 是错的）。
* `drm_mode_modeinfo` 72→**68**：`clock` 在前、`name[32]` 挪到**最后**、`hskew/vscan` 回到 Linux 位置。
* `drm_mode_crtc` 108→**104**（内含 68 B 的 mode，偏移 36）。
* `drm_wait_vblank` 40→**24**：`u32 type; u32 sequence; i64 tval_sec; i64 tval_usec`。
  **Linux 这个 union 里没有 `crtc_id`** —— 原先拿它做 CRTC 校验，现在不校验（本内核只有 1 个 CRTC），

### 批次 v0.9.12：DRM/KMS + evdev 内核门面（ring3 打开 /dev/dri/card0 与 /dev/input/event*） —— `v0.9.12`

> 目标只有一个：让 ring3 能**枚举显示模式、建一块 CPU 可写的 dumb buffer、page-flip 上屏、等 vblank、
> 读键鼠原始事件** —— 也就是 Wayland 需要的"内核态抽象层"最小可验证子集。libdrm/libinput/wlroots 是下一批。

* **两个设备特判**（与 `/dev/console` 同一套做法，不查盘、不建文件）：`/dev/dri/card0` → DRM 门面、
  `/dev/input/event0|1` → evdev 门面；`read`/`write` 的语义如实（DRM 不可读、两者都不可写 → `-EINVAL` 并打 `[FD64] deny`）；
  `ioctl(16)` 在 **tty 分支之后**按 fd 类型分派（syscall 号、wl64 的 15–21/22–26、9/10/11、48 **一个都没动**）。
* **dumb buffer 怎么让 ring3 可写（全批最关键）**：`CREATE_DUMB` 用 `page_alloc_64()` 逐页分配（页帧表在内核状态里，
  不要求物理连续）；`MAP_DUMB` 把**同一批物理页**逐页挂进当前进程页表（`user64_map_phys_page64`），窗口 =
  A1 帧缓冲映射区 `USER64_FB_VA64` 的后半段（`[+8MiB, +40MiB)` = 4 槽 × 8 MiB）—— 它在 PDPT[5]，
  进程回收只走 PDPT[4]，所以这些页不会被当成"进程自己的页"还回页池。`MAP_DUMB.offset` 返回的就是那个用户 VA
  （Linux 那边是 mmap 的偏移，语义差异写死在头文件里）。**不新增 syscall 号**。
* **混合呈现**：ring3 负责光栅化（直接写 dumb buffer）；内核 `page_flip` 只做传输与扫描输出 ——
  先把这块缓冲逐行拷进既有后备缓冲，再 `vgpu64_blit64()`（virtio-gpu 2D：TRANSFER_TO_HOST_2D + RESOURCE_FLUSH）
  → `path=gpu`；它返回 0（无设备/降级/超时）就 `fb_soft_flip_region64()` 逐行写 LFB → `path=cpu`。
  **本层不碰任何厂商 GPU 寄存器**，两条都是既有函数。
* **vblank**：复用 `fb.cpp` 既有的 VGA 回扫探针/等待（新增两个薄导出，一处实现两个调用方），不可用时按 16 ms
  软兜底并如实打 `mode=soft`；序列号单调递增（`WAIT_VBLANK` / `CRTC_GET_SEQUENCE` 都返回它）。
* **evdev**：数据源是既有的每进程事件队列（`input64.h`），转成 24 B `struct input_event`（与 Linux x86_64 同尺寸）；
  键鼠分流的"非本设备事件"进 8 条待取缓冲，**不静默丢事件**；`EVIOCGNAME/GVERSION/GBIT` 认，其余 `-ENOTTY`。
* 启动期自检（`[DRM] selftest … ok=1`）建 dumb → 写 8 条彩条 → **内核读回核对像素** → page flip → 等 vblank →
  把开机画面快照翻回来 → 销毁；**自检失败不算启动失败**，只留一行 `FAIL reason=`。
* ring3 验收程序 `/bin/drmdemo.elf`（`user/apps/drmdemo.c`）：open → version → getresources → getconnector →
  建 dumb → 映射 → 画 8 条 64px 彩条 → page_flip → wait_vblank → `badcmd rc=-25`（反例）→ 读一次键事件 →
  销毁 → `done ok=1`；**opt-in**（卷里有 `/etc/drm64_probe` 才跑，默认启动不多画一个像素）。
* 交付：`docs/Wayland基础抽象层.md`（四条内核态逐条对照 + 下一批 libdrm/libinput/wlroots 的前置）、
  `tests/drm64_test.py`（含"两份头文件逐值比对""vblank 序列号单调""非黑像素比例 > 0.3"）。

### 批次 v0.9.11：AMD 多核启动修复（INIT 前刷缓存 + 时序下限 + SIPI 重发 + A20 保护） —— `v0.9.11`

> 用户交叉实测：**AMD + VMware 2 核以上直接三重故障复位；Intel i3 正常。**

* 先排除"写死 Intel APIC 地址"：MADT 的 LAPIC 地址一直读表（`acpi64.cpp` 取 `MADT.lapic_address` + type 5 覆盖），
  BSP 基址读 `MSR 0x1B`，`apic64.cpp` 自检里还有"LAPIC 基址 == MADT 记录"一位。
* 真因①（主因）：**发 INIT 前没有刷缓存**。跳板/共享块/GDT 拷贝源是 BSP 经缓存写进 `0x8000` 的，AP 出 INIT 时
  `CR0.CD=1` 读内存 → 读到旧内容（SeaBIOS 跳板区残留）→ 执行垃圾指令 → 实模式无 IDT → 三重故障。
  修：`smp64_flush_trampoline64()`（`mfence`+逐行 `clflush` 整页+`wbinvd`+`mfence`），拷完跳板与**每次写共享块后**都调。
* 真因②：`out 0x92`（A20 fast gate）没清 bit0 —— 读回 bit0 若已是 1，这一句就是 **fast reset**（表现同三重故障）。
* 真因③：INIT 后 10ms 只靠 `g_ticks64`（IF=0 时 tick 不涨 → 实际远短于 10ms），且 SIPI 不重发。
  修：`smp64_delay_min_ms64()`（TSC 下限按最坏 6.5GHz 折算）+ SIPI 重发循环（≤5 次）+ 每次写 ICR 后等投递完成。
* 诊断新增：AP **进度面包屑**（跳板在 16 位/pm32/lm64 各写一次 `stage`，超时行 `timeout stage=<0|1|2|3>`）、
  `[SMP] cpu vendor=<AuthenticAMD|GenuineIntel>`；GDTR 描述符挪到页内 `0x50` 给 16 位段腾地方（blob 234→242 B）。
* 证据：`smp64_test` **52/52**（含 `-smp 2` / `-smp 4`）；QEMU 默认 CPU 的厂商串就是 `AuthenticAMD`，这轮就是"AMD 身份"跑通的。

**① pipe 默认阻塞（POSIX）+ `fcntl(72)` + `statfs(137)/fstatfs(138)`（批次 pipe/statfs）**：先前 pipe 是"非阻塞 + 短写"，
消费者不重试 -> `ls|grep|wc` 这类真管线拿不到数据。本版：读空 / 写满一律 `task_sleep_ms64` 让出睡等（不忙等），
**有界**（单次等待上限 `FD64_PIPE_WAIT_MS=30,000 ms`；源码注释写明 5 s 会误伤正常管线）、**可被对端关闭打断**

`fcntl(72)`：`F_GETFL(3)`/`F_SETFL(4)`（只认 `O_NONBLOCK`/`O_APPEND`，非法位 `-EINVAL`）+ `F_GETFD(1)`/`F_SETFD(2)` 的
**`FD_CLOEXEC` 真实现**（每个 fd 槽一位；execve 成功后关闭），open 的 `O_CLOEXEC` 落地。
`statfs(137)/fstatfs(138)`：x86_64 的 `struct statfs` = 120 B、字段偏移按 Linux；数据源 = `drive64`->`fs64`->`vfs64`（现数位图）。
**顺带修两处真缺陷**：① **pipe 池无条件复用 0 号槽** —— 第二条管道把第一条清零并把数据串过去（实测 `ls|grep|wc` 的输出
跑进上一条 `echo hi|cat` 的落盘文件）；修 = 找空闲槽（`used==0`），池满 `-EMFILE`。② **pipe 对象两端引用计数吞掉中间释放**
（`refs>1` 直接 return）-> 用完的管道对象不回收；修 = 每次释放逐项 -1、归零才 `used=0`。
证据（宿主侧逐字节 + 同刻对照）：`ls -l /tcc/demo | grep hello | wc -l` == **b"2\n"**（真值 hello.c + hello.lua）、
`echo hi | cat` == b"hi\n"、`cat lines.txt | sed s/beta/BETA/` 五行逐字节、`cat big64.txt | wc -c` == **b"300\n"**
（300 B 过 64 B 环：分次写完不丢字节 + EOF）；阻塞等待打点 12 次（pid 真值 / `why=empty|full` / ticks 齐全），
最长 1412 ticks（≈5.6 s）未撞 30 s 上限；busybox `df` 行 `/dev/sda2 12379 6829 5550 55% /`、`df -h` 行 `12.1M 6.7M 5.4M`
（= statfs `blocks=24758 bfree=11100` 的 1K 块 / 可用）；statfs 行 `blocks=24758 bfree=11100 files=512 ffree=126`
== 同刻 `[DRV64] total_kb×2 / free_kb×2` == 宿主侧独立解析卷 inode 表 512/126。
**边界（如实）**：**不投递 `SIGPIPE`**（读端全关的 write 只回 `-EPIPE`）；ring3 端到端 `F_SETFL` 证据缺位

**⑤ virtio-gpu（2D）+ 显示后端切换（驱动线 3）**：PCI **`0x1AF4:0x1050`**（现代非过渡）+ capability +

512×512 **247 µs → 18 µs（13.7×）**；**beta18 复测（同机并发跑核心集、宿主负载更高）**：整屏 **600 µs → 119 µs**、
512² **259 µs → 81 µs**、128×128 **20 µs → 72 µs（反而更慢）** —— 绝对耗时随宿主负载变化，**交叉点实测比文档口径的

**边界（如实）**：没有 3D/virgl、单一格式（XRGB8888）、`TRANSFER_FROM_HOST_2D` 对非 blob 的 2D 资源**不回写**
（报告里如实标 `GAP`）、没有 cursor 平面 / 多输出、`reconfigure` 未实测。

**⑥ 本批两处修复（都有回归断言）**：
* **`unlink` 栈泄漏**（`kernel/vfs64.cpp` 的 `vfs64_unlink64`）：删除文件时把一个**未清零的 128 B 栈缓冲**交给
  `inode_store()` 落盘 —— ① 内核栈字节泄漏到磁盘；② 卷里留下垃圾名（实测 `rec[0]=0xC8`、`namelen=0x34`），
  宿主造卷器解析该槽会 `UnicodeDecodeError`。修法：删除/回收 inode 槽**先 `zero_bytes` 再落盘**
  （`unlink64` 与 `rmdir64` 两条路径，`zero_bytes(empty, VFS64_INODE_BYTES_MAX)` 命中 2），零槽 =
  干净"已释放"记录（`type=FREE(0)` + `namelen=0` + 保留区全 0，`inode_ok()` 认它）。
  **宿主侧证据**：同一夹具盘上 `rm` 前后逐槽比对 —— 被删槽 `type=1 namelen=19 name='zc_unlink_probe.txt' size=5`
  → **整槽 64 B 全零**；全卷 229 个空槽**全部全零**（非零空槽 0），**非 ASCII/越界名 0**；
  `tests/status_report.py` 把这条做成可跑断言（源码层 + 字节层）。防御没删：`tools/tcc_pack_win.py` 的
  残留槽过滤（`namelen` 越界 / 非 ASCII / UnicodeDecodeError 兜底）与**幽灵 inode** 判定仍在。
* **1024×768 面板锚点**（`kernel/panels64.cpp`）：`[PANEL64] selftest FAIL mask=1024` 的算式 —— 1024 宽下
  `sm_x=(1024-400)/2=312`、菜单右边缘 712、右侧可用 `1024-4-(712+8)=300 < NOTIF_W(320)`；旧逻辑把面板翻到左侧
  （`312-8-320=-16`）再 `clamp` 到 4 → 面板 `4..324` 与菜单 `312..712` **重叠 12 px**，且"通知面板必须在菜单右边"
  的断言必然不成立。修法：**按屏宽钳制**（优先侧放得下 = 旧行为逐字节不变；放不下就把宽度缩到该侧可用宽度，
  同宽优先侧；下界 `PANEL64_MIN_W=208`），并在自检里加**虚拟分辨率断言**（1024×768 与 1280×800 的锚点/限界都验）。
  **证据**：`[PANEL64] selftest PASS mask=0 w=1024 h=768 virt=1024x768,1280x800 ok`（`-vga virtio`）与
  `… w=1280 h=800 …`（`-vga std`）。
