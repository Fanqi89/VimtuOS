  截断（MBR+loader 在、内核区不在）启动，必须打 `[LM] int13 read FAILED ah=0x0C …` 后停机，

* **item 5b 根因（实测，别再踩）**：旧代码把 AHCI 命令头写错 —— `PRDTL` 写到 DW1、`CTBA` 写到
  DW3/DW4；HBA 读出的命令表地址 = `0x…0500_00000000` → DMA 映射失败 → **命令被静默丢弃**
  （`PxCI` 挂着、`PxIS`/`PxTFD` 不动、trace 里一个命令事件都没有）。正解：**PRDTL 放 DW0 的
  bits[31:16]**（DW1 是 HBA 回填的 PRDBC）、**CTBA/CTBAU 放 DW2/DW3**；PRDT 的 **DBC 在 +0x0C**
  （+0x08 是保留 DWORD）。定位手法与全部证据见 `kernel/ahci64.cpp` 顶部“实测踩坑记录”J/K
  （★ QEMU 里"命令被跳过"的 trace 事件叫 `handle_cmd_*`，只开 `ahci_*` 会被滤掉）。
* 补充：**引导层磁盘路径已经不依赖 PATA PIO**（改走 BIOS INT 13h，见上一条），
  "装到 SATA 盘再重启"现在有两种验法：① `ahci64_test.py --sata-install`（把装好的盘按 IDE
  兼容方式再挂一次）② **`disk_boot_test.py`（把装好的盘只挂 AHCI 启动 —— 这才是纯 SATA 机器的形态）**。

## 批次 E（"U 盘形态 × 双固件"验证 + 安装时在目标盘建 ESP/GPT）—— 2026-09-20 实测

本批次的目标（用户需求）：**安装 U 盘在新设备（UEFI 64 位）和老设备（BIOS/CSM）上都能启动，
装好的系统也要在两代设备上都能启动**。分两半：

### ① "U 盘形态 + UEFI"验证（`tests/usb_boot_both_fw_test.py`）

同一个 `vimtu64-64.iso` 当磁盘/U 盘引导，四档全 PASS 且都**进到安装向导第一屏**：

| 形态 | 固件 | 关键打点 |
|---|---|---|
| ISO 挂 `usb-storage`（UHCI + `bootindex=1`） | UEFI（OVMF） | `S12345J` → `U:====` → `U:loaded KERNEL64.BIN/SYSTEM.IMG` → `[LM64] ENTERED LONG MODE` → `[SETUP] 磁盘枚举完成` |
| ISO 当 IDE 盘 | UEFI（OVMF） | 同上（不支持 USB 启动的固件的等价形态） |
| ISO 挂 `usb-storage` | BIOS（SeaBIOS） | `I:boot dl=` → `I:hdd mode (USB/disk)` → `I:jump loader64` → `L:media=ram` → 向导第一屏 |
| ISO 当 IDE 盘 | BIOS（SeaBIOS） | 同上 |

**结论：UEFI-USB 这条组合原生就通**（不需要改 `tools/make_iso64.py`）——ISO 里
El Torito 0xEF 项 + GPT + FAT32 ESP（48MB）三者齐全，OVMF 用 GPT 路径就能找到 `EFI/BOOT/BOOTX64.EFI`；
MBR 里还有 0xEF 项兜底。 BIOS 侧走 hybrid MBR → cdiso 桩 → INT 13h 搬内核/载荷。
脚本末尾另有"安装介质 sha256 未变"断言（真 U 盘/光驱是只读的）。

### ② 安装时在目标盘建 ESP + GPT（`kernel/fat64.{h,cpp}` + `kernel/part64.cpp`）

以前安装只写"MBR + 固定 LBA 引导区"→ UEFI 固件在装好的盘上找不到任何 FAT 卷 →
装完的盘在 UEFI 机器上起不来。现在安装收尾会写：

* **48MB FAT32 ESP**（盘尾）：内嵌最小 **FAT32** 写入器，卷参数与构建期 `tools/make_esp.py`
  **逐条对齐**（512B 扇区 / `SPC=1` / **32 个保留扇区**（1=FSInfo、6=备份引导扇区）/ 2 份
  **32 位** FAT / 根目录 = 从簇 2 开始的**簇链** / 簇数硬断言 `>= 65525`）。
  ESP 里放 `EFI/BOOT/BOOTX64.EFI`（内嵌桩字节）+ `UEFI64.BIN`（内嵌引导器）+
  `KERNEL64.BIN`（**直接读目标盘 LBA 9..8008 的 4MB 内核区**，这样安装程序内核不必内嵌 4MB 副本）。
  **为什么是 48MB**：FAT32 的簇数硬下限 65525（少于这个数就该被当作 FAT16，固件会按 16 位读
  我们的 32 位 FAT 表 → 多簇文件报 EFI_VOLUME_CORRUPTED）；SPC=1/512B 扇区时数据区至少
  65525 扇区（32MB），加保留扇区与两份 32 位 FAT，卷下限约 33.5MB —— 取 48MB（96736 簇）。
* **混合 MBR**：`0xEF` 引导区（活动，9+8000）+ `0x07` 主分区 + `0xEF` ESP（盘尾）。
  故意**不写 `0xEE` 保护项**（EDK2 见到 `0xEE` 会放弃 MBR 解析路径）。
* **盘尾备份 GPT**：主 GPT 头的规范位置 LBA 1 被 `loader64.bin` 占着（`boot.asm` 从 LBA 1 读 8 扇区），
  所以只写备份头 + 备份项数组；UEFI 规范要求"主头无效时用备份头"，EDK2 实测如此
  （OVMF 从这块盘启动成功，且启动后 LBA 1..8 的 loader 字节**未被改写**）。
* `boot/efi/uefi64.c`：`SYSTEM.IMG`（安装载荷）改成**可选**（装好的盘上没有它；
  跳过并写 `U:missing SYSTEM.IMG (optional, skipped)` + 介质描述符 `kind=0`），安装介质路径不变。
* 小盘（`< 8009 + 8MB + 48MB + 33 = 122730 扇区 ≈ 59.9MiB`）不建 ESP，只写老 MBR 布局并在串口打
  `[INSTALL] esp skipped (disk too small)` —— 既有的 16MB 回归目标盘字节级断言因此原样保持。

**字节级 + 双固件验收（`tests/esp_install_test.py`，64MB 目标盘挂 AHCI）**：


### 踩坑记录（值得记住）

* **FAT（16/32）自检不能碰真盘**：第一版把"切 I/O 后端"写进了 `format` 内部（强制 `g_ram=false`），
  于是自检的 format 落到了 `drive 0` —— 实测把安装介质 ISO 的前 2.5MB 覆盖成 FAT 卷，
  表现为"后续 BIOS 从 ISO 启动一片空白（0 字节串口）"，而**当轮串口侧完全看不出来**。
  修法：`format_volume()` 只做实现、`fat64_format64()` 显式切真盘后端、自检显式切内存后端；
  并给 `tests/usb_boot_both_fw_test.py` 加了"介质 sha256 未变"断言兜住同类问题。
* **GPT 头的 CRC 要"把 HeaderCRC32 字段当 0"再算**（UEFI 规范；EDK2 与 `tools/make_iso64.py` 都这么做）——
  写测试脚本时若直接 `crc32(header)` 会误报"头 CRC 不符"。
* **ESP 的末尾要避开盘尾 33 扇区的 GPT 备份表**：ESP 结束于 `总扇区 - 34`，备份项数组在 `-33`，头在 `-1`。

## 批次 F（item 6：NVMe 驱动 —— 能装到 NVMe 盘、UEFI 从这块盘启动）—— 2026-09-20 实测

### ① 最小 NVMe 驱动（`kernel/nvme64.{h,cpp}`，新建）

* **PCI**：扫 class `0x01` / subclass `0x08` / prog-if `0x02`（= class_code `0x010802`）；只在自己找到的
  功能上开 MEM + BUS MASTER；读 **BAR0**（偏移 `0x10`；bit2=1 表示 **64 位 MMIO BAR**，高 32 位在 `0x14`）。
  实测两种环境都过：BIOS 下 `bar0=0x00000000FEBF0000`、**UEFI 下 `bar0=0x000000C000000000`**（4GB 以上，
  64 位 BAR 的高位处理真的被用上了）。
* **控制器初始化（严格照规范顺序）**：`CC.EN=0` → 等 `CSTS.RDY=0` → `INTMS=0xFFFFFFFF`（**全程轮询**，
  与 AHCI 一致）→ `AQA`（ASQS/ACQS 0-based）→ `ASQ`/`ACQ`（**页对齐物理地址**，页池低内存 PA==VA）→
  `CC`（CSS=0 NVM / MPS=0 4KB / IOSQES=6 64B / IOCQES=4 16B / EN=1）→ 等 `CSTS.RDY=1`（`CSTS.CFS` 检查）。
* **Admin 队列（qid 0）**：Identify Controller（`CNS=0x01`，型号/序列号）→ Identify Namespace
  （`CNS=0x00`，NSID=1，取 `NSZE` + `LBAF`→LBA 字节数）→ Create I/O CQ（`0x05`）→ Create I/O SQ（`0x01`）
  （PC=1 连续、IEN=0 不开中断、QD=8）。
* **I/O（qid 1）**：Read `0x02` / Write `0x01`：`NSID` + `SLBA` + `NLB（0-based）` + PRP1/PRP2；
  提交敲 **SQ tail 门铃**（`0x1000 + 2*qid*stride`），完成轮询 **CQ 的 phase 位**，然后敲 **CQ head 门铃**
  （`0x1000 + (2*qid+1)*stride`，`stride = 4 << CAP.DSTRD`）。`SC`/`SCT` 非 0 一律打点返回失败。
* **传输上限与分块**：一条命令 **≤ 128 扇区（64KB）**（与 `part64` 的 `INSTALL_CHUNK_SECTORS` 同值），
  更大的请求由驱动**内部按 128 扇区分块**，上层不用管。PRP 规则（**这里是本次的真坑**）：
  PRP1 之后剩余 ≤1 页 → 只用 PRP1；**刚好两页 → PRP2 = 第二页页基址（直接指针）**；
  ≥3 页 → PRP2 = 页对齐的 PRP 列表（项 = 第 2..N 页页基址）。DMA 缓冲地址算不出来时走**暂存页**兜底。
* **超时双保险**：`g_ticks64`（250Hz，1s）+ 自旋上限（IF=0 时 tick 不前进），绝不挂死；
  失败一律 `[NVME64]` 打点并如实返回 false。

### ② 接入磁盘层（`kernel/ata64.{h,cpp}`，上层一行未改）

* 驱动器号方案：`0..3`=PATA、`8..15`=AHCI 盘、**`16..`=NVMe 命名空间**（`ATA64_NVME_BASE = 16`，
  数组尺寸用 `ATA64_MAX_DRIVE64`）。
* `ata64_drive_count64()` = `4 + ahci64_count64() + nvme64_count64()`；`ata64_slot_to_drive64()` 依序给号；
  `ata64_identify/read/write` 内部按号分派到 `nvme64_*`。`ata64_init64()` 里 `nvme64_init64()`
  + `nvme64_selftest64()`（幂等；没控制器只打 `[NVME64] not found`）。
* **上层（setup64 / part64 / vfs64 / store64 / fat64）的实现代码没动**：`setup64.cpp` 只把磁盘表的
  数组尺寸从 `ATA64_AHCI_BASE + AHCI64_MAX_DEVS` 改成 `ATA64_MAX_DRIVE64`（**必须改，否则 16 号盘会被
  `d >= kDiskSlots` 静默跳过 = 装不进去**），并把向导/串口的 bus 标签从"AHCI/PATA"扩成三项
  （16 号盘打 `bus=NVMe`）；其余全是注释/证据行。

### ③ 硬件报告页（`kernel/hwui64.cpp`）

* 存储区块不再写"NVMe 本系统不支持"：找到控制器时显示 **PCI 位置 / bar0 / qd / 命名空间数 / 控制器型号**，
  每个命名空间作为一行设备（`NVMe drive16 … 扇区 / 容量`）列出；没找到才写 `NVMe：未检测到`；
  有 class 01/08 但初始化失败时如实写"没初始化成功（看串口 [NVME64] 行）"。
* 行数上限 `HWUI64_MAX_LINES` 34 → 40（加了 NVMe 控制器行 + 命名空间行后 34 会正好挤满，
  满了会覆盖最后一行）；报告页实测 `[HWUI] report lines=34 storage=3 controllers=3`（NVMe 3 设备场景）。

### 踩坑记录（新增，值得记住）

* **PRP2 的两种含义别写混**（本次定位到的真缺陷）：PRP1 之后剩余数据 **刚好 ≤ 1 页**时，PRP2 必须是
  **第二页的页基址（直接指针）**，**不是** PRP 列表；只有剩余 > 1 页才用列表。把"两页"也写成列表时，
  QEMU 会把**列表页的第一个 8 字节**当作第二页的数据地址 —— 症状是"**前半段对、后半段错**"：
  ESP 里 `BOOTX64.EFI`（2560B，嵌在安装程序内核 .rodata 里、起始地址不在页边界上）只写对了前 848
  字节（= PRP1 覆盖的部分），其余全错，OVMF 直接 `BdsDxe: failed to load … Load Error` 掉进 EFI Shell；
  而 4MB 的 `KERNEL64.BIN`（缓冲页对齐）一直是对的，所以只看大文件根本发现不了。
  **回归网**：`nvme64_test.py` 把 ESP 三文件与构建产物逐字节比对（这一档就是抓这个 bug 的那一档）。
* **Identify Namespace 的 CNS 是 `0x00`，不是 `0x02`**：`0x02` 是 **Active Namespace ID list**；
  用它读 `NSZE` 只会拿到命名空间 ID 列表（QEMU 实测表现为 `nsid=1 not present (NSZE=0)`，
  而命令本身是"成功"的 —— 因为响应确实是合法的空列表）。改成 `CNS=0x00` 后 NSZE 立刻正确（131072）。
* **QEMU 的 NVMe 需要"真的有一个命名空间"**：`-device nvme,drive=…` 与显式 `nvme-ns` 两种挂法都
  实测可用（都能枚举到 NSID 1）；但只有控制器没有命名空间时，Identify Namespace 返回的是全 0 列表，
  表现为 `nsid=1 not present (NSZE=0)` —— 打点里区分得出来。

加 `nvme64.o`）—— 两者都远低于 4,096,000 B 上限；loader **4,010 B**（未动）；UEFI64.BIN 36,864 B。

### 如实边界（本批次没做/没验的）

* **真机未测**：全部证据来自 QEMU 11.1（`-device nvme`）+ OVMF/SeaBIOS；真机 NVMe 需按
  `docs/真机验证指南.md` §3 复验（报告页 + 串口 `[NVME64]` 行）。
* NVMe 侧只做**单控制器 / 单 I/O 队列对（QD=8）/ 单命名空间（NSID=1）/ 全程轮询**（无中断、无 MSI-X、
  无 CMB/PMR、无门铃优化）；只支持 **512B 逻辑块**（别的 LBA 尺寸如实打点并**不给驱动器号**）；
  单条命令 ≤ 64KB；PRP 列表上限 17 项。
* **BIOS 从 NVMe 启动取决于固件**：QEMU 11.1 的 SeaBIOS 实测支持（能起来），但 BIOS 的 INT 13h 盘号
  来自固件自己的驱动表 —— 很多真机 BIOS 不认 NVMe，**推荐 UEFI 引导**。
* 没有 Trim/Flush/Format NVM/SMART；没有多路径/命名空间管理；没有掉电保护语义。

## 批次 G（VimtuFS2 v3 目录树 + 盘符/驱动器枚举层 —— "此电脑"的地基）—— 2026-09-20 实测

**需求**：做一个类似 Windows 10 的"此电脑 + 文件资源管理器"。本批次只做**地基（不含 UI）**：
① VimtuFS2 目录树 ② 盘符/驱动器枚举层 ③ inode 时间戳与类型识别；UI 留给下一批。

### ① VimtuFS2 v3：真正的目录树（`kernel/vfs64.{h,cpp}`）

* **卷版本 3**（`vfs64_format` 产出）：inode 记录 **128B/个**（每块 4 个）、名字上限 **31B**、
  **多级路径**（`/dir/sub/file`，`.`/`..`，根的父亲还是根）；inode 里新增
  **mtime**（`(年-2000)<<26|月<<22|日<<17|时<<12|分<<6|秒`，RTC 打包）、**nlink**、**kind**（类型判定）。
* **目录表示**：名字仍存在 inode 里（目录没有数据块）——"目录" = `parent` 指向它的 inode 集合；
  取舍写在 `kernel/vfs64.h` 文件头。查名字/列目录是 O(inode 数)，用一个"当前 inode 扇区"缓存把读盘降到 1/4。
* **新 API**：`vfs64_stat64` / `vfs64_list64`（路径版 + 游标分页）/ `vfs64_opendir64+readdir64+closedir64` /
  `vfs64_mkdir64`（多级）/ `vfs64_create64` / `vfs64_write64` / `vfs64_read64` / `vfs64_unlink64` /
  `vfs64_rmdir64`（**空**目录）/ `vfs64_tree_dump64`（有界目录树打印）/ `vfs64_pack_time64` 等工具函数 /
  `vfs64_probe_volume64` + `vfs64_mounted_volume64`（只读卷探测）。
  **旧单层 API 全部保留成兼容包装** —— `fd64`/终端/`app64`/`elf64`/`store64`/`sysstate64`/`update64` 一行未改；
  `fd64_norm_path64` 升级为多级路径（保留"空白截断/根目录拒绝"的旧行为），`FD64_PATH_MAX` 32→64。
* **v2 兼容**：v2 卷（64B inode、名字 ≤27B、无 mtime/kind）**照常挂载**（`VFS_LAY_V2`），按单层语义工作；
  现有 Python 夹具（`proc64_test._vimtufs2_format` 等）都不用改。
* **自检**：`vfs64_selftest64` 新增 bit8（多级目录树）/ bit9（路径语义）/ bit10（mtime + 类型判定）/
  bit11（代际几何 + 重挂载持久化 + 空目录删除）；真盘侧仍是只读探测。
* **踩坑**：旧自检在 bit5 注入坏 inode 时把 inode 表**第一个扇区**整体清零 —— 那里面正好是根目录 inode，
  于是后面的目录树自检全废。现在注入前先备份整扇区、做完原样写回（并断言根目录还在）。

### ② 盘符/驱动器枚举层（`kernel/drive64.{h,cpp}`，新建）

* `drive64_scan64`（幂等）/ `count64` / `info64` / `by_letter64` / `selftest64` / `dump64` / `kind_name64`。
* **C: 的判定依据**：`vfs64` 当前**真正挂载**的卷的 `(drive, start_lba)`（系统内核用
  `app64_main_part_lba64(0)` = MBR `0x07` 项作挂载参数）；没挂载时退化为 drive 0 的 MBR `0x07` 项，
  再退化为第一个可浏览卷。其余可浏览的 VimtuFS2 卷依次 `D:`、`E:`…（A:/B: 不分配）。
* **跳过项不占字母但要列出**：ESP（type `0xEF`）、未知文件系统、未分区盘 → `letter=0` +
  `[DRV64] skip lba=<n> type=<0xEF|unknown> reason=<esp|no-fs>`。
* **FAT 只识别不浏览**（BPB 指纹 → "EFI 系统分区"/"FAT 卷"，`browsable=false`）：本内核只有 FAT32 写入器。
* 每项给显示名 / 文件系统字符串 / 驱动器号 / MBR 项号 / 起始 LBA / 扇区数 / 总容量 / 可用容量
  （`total_known`/`free_known` 标明未知）/ 是否可浏览 / 是否系统盘 / 卷版本。

### ③ 验收（`tests/fs_tree_test.py`，新增，84 条断言，全 PASS）

安装到 128MB 盘 → **向导里格式化主分区得到 v3**（`[VFS64] format ok ... version=3 inode=128`）→
多级 `mkdir /efi` `/apps` `/apps/demo` → 在子目录里 `write /apps/demo/demo.txt hello` →
**冷启动同一块盘**后 `[VFS64] tree /apps/demo/demo.txt type=file size=5 mtime=0x.. ymd=.. hms=.. kind=text`、
`cat` 读回 5 字节、`rm` 删掉；坏路径（父目录不存在 / `/../..` / 32B 超长段）全被拒且不崩；
盘符表断言 `letter=C: disk=0 part=2`、`letter=D: disk=1 part=1`、ESP 被 skip、`free ≤ total`；
再用一块 16MB 小卷断言 **drive64 的容量与终端 `df` 同口径一致**。

### 如实边界（本批次没做/没验的）

* **UI 一行没做**：桌面"我的电脑"窗口仍是**静态统计页**（`gui64.cpp` 的 `mypc_draw`，本批次刻意没碰）；
  文件管理器窗口、右键菜单、盘符树留给下一批。
* **单文件上限没提高**（仍 67584B）：v3 没有加二级间接块；提高它需要新的块索引层。
* **FAT 不能浏览**：只有 BPB 指纹识别 + 显示名，没有 FAT 目录解析（`fat64` 仍只有写入器）。
* **目录删除只支持空目录**（`vfs64_rmdir64`）；非空目录必须先自己清空；`rmdir`(84) 号段仍是 `-ENOSYS`
  （没接进 syscall，本批任务范围外）。
* **盘尾备份 GPT 不解析**：枚举以 MBR 的 4 个分区项为准（本安装器写的 MBR 与备份 GPT 内容一致）。
* **`sysstate64` 的卷探测位图上限 8 块**：因此 >32MB 的主分区上终端 `df` 会报"没有卷"（既有行为，
  本批次没改那个文件）；fs_tree_test 用 16MB 小卷来验证"盘容量与 df 一致"。
* **终端里的提示文案仍写着 single-level**（`terminal64.cpp` 不在本批次允许改动的文件里）；
  实际能力已是多级路径，文案随下一批 UI 一起改。
* **真机未测**：全部证据来自 QEMU（BIOS）。新代码只读枚举 + 写盘都走既有 ata64 通路，真机复验见
  `docs/真机验证指南.md`。
