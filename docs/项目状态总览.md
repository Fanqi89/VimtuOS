* **屏幕硬件检查报告**（`kernel/hwui64.{h,cpp}`）：真机没有串口时的唯一诊断画面。内容全部真探测：
  CPU（hwinfo64）/内存（E820+页池+堆）/固件与地址空间（BIOS vs UEFI、页表 isolated/shared）/

  **EHCI/xHCI 标“不支持”**）/ACPI（自己只读遍历根表：表数、FACP、PM1a_CNT 软关机）/网络（e1000）。
  三处展示：① 启动期约 5 秒（任意键跳过）② 安装程序找不到磁盘时画在向导列表区 ③ 设置应用第 5 页
  “硬件检查”。打点 `[HWUI] report lines=<n> storage=<n> controllers=<n>` /
  `[HWUI] report shown ms=<n> skipped=<0|1>` / `[HWUI] selftest PASS`。
* **验收**：`tests/ahci64_test.py`（默认档 14 项断言 PASS）：控制器/ABAR/端口数/HBA 复位/端口有设备
  （`port=0 det=3 sig=0x…101 kind=ata`）/报告打点 + **截图像素**（黑底 13686/20400、区块色块 5866、
  文字 436）/无 PANIC；`--strict-dma` 档另要 `[AHCI64] selftest PASS` + `[AHCI64] drive 8 model=…
  sectors=…` + `[AHCI64] read lba=0 count=1 ok` + `kind=ata`（**现在 PASS**）；
  `--sata-install` 档再走一遍"在 SATA 盘上装系统 + 重启进桌面"（`[PART] … drive=8`、
  `[INSTALL] 完成：已写 8073 扇区`、`[AHCI64] write lba=0 count=1 ok`、
  `[AHCI64] write lba=0 count=1 ok (first write since init)`、`[LM] disk boot via INT 13h dl=0x80`、
  `[OS] booted from installed disk`、`[GUI64] desktop init 1280x800`）。
* **★ 引导层改 BIOS INT 13h 扩展读（SATA/任意 BIOS 可见盘可直启）**：`boot/loader64.asm` 的
  *磁盘启动路径*不再用自写 PATA PIO（只认 0x1F0/0x170 后面的 IDE 兼容盘，AHCI 模式下读不到内核），
  改成 **INT 13h AH=0x42 + DAP**：驱动器号用固件传进来的 `DL`（`boot/boot.asm` 显式透传；不是
  猜 0x80，若 DL 不是硬盘号则回退 0x80 并在打点里写 `(fallback)`）→ 每次 64 扇区（32KB，**不跨
  64KB 边界**、≤127 扇区上限）读进低内存暂存区（段:偏移 `0x2000:0x0000` = 物理 `0x20000`；
  实模式 段×16+偏移 到不了 `0x100000`，所以每批 13 块再进一次保护模式用 4GB 平坦段
  `a32 rep movsd` 搬到 `0x100000`）→ 失败复位磁盘重试 3 次 → 仍失败打
  `[LM] int13 read FAILED ah=0x.. lba=… retry=…` 并**停机**（绝不静默失败）。
  光盘路径语义不变（仍是 `cdiso.asm` + `loader64_atapi.inc` 的 ATAPI，打点 `[LM] cd boot via ATAPI`），
  RAM 源（hybrid/U 盘）也不变。loader64.bin **4090 → 4010 字节**（删掉整段 PIO + VBE 调试打印，
  腾出空间给 INT 13h 与打点；上限 4096 不变）。
* **验收**：`tests/disk_boot_test.py` —— 先用 AHCI 路径把系统装到 16MB SATA 盘上，
  然后**只把这块装好的盘挂在 `ich9-ahci` 上启动**（没有 IDE 兼容盘、没有安装介质），断言
  `[LM] disk boot via INT 13h dl=0x80`、`[LM] int13 read lba=… count=… ok`、
  `[OS] booted from installed disk`、`[GUI64] ready`；另有一段**失败路径**验收：把装好的盘
  截断（MBR+loader 在、内核区不在）启动，必须打 `[LM] int13 read FAILED ah=0x0C …` 后停机，
  且**不许**出现 `[LM64] ENTERED LONG MODE` / `[OS] booted`。
* **item 5b 根因（实测，别再踩）**：旧代码把 AHCI 命令头写错 —— `PRDTL` 写到 DW1、`CTBA` 写到
  DW3/DW4；HBA 读出的命令表地址 = `0x…0500_00000000` → DMA 映射失败 → **命令被静默丢弃**
  （`PxCI` 挂着、`PxIS`/`PxTFD` 不动、trace 里一个命令事件都没有）。正解：**PRDTL 放 DW0 的
  bits[31:16]**（DW1 是 HBA 回填的 PRDBC）、**CTBA/CTBAU 放 DW2/DW3**；PRDT 的 **DBC 在 +0x0C**
  （+0x08 是保留 DWORD）。定位手法与全部证据见 `kernel/ahci64.cpp` 顶部“实测踩坑记录”J/K
  （★ QEMU 里"命令被跳过"的 trace 事件叫 `handle_cmd_*`，只开 `ahci_*` 会被滤掉）。
* 补充：**引导层磁盘路径已经不依赖 PATA PIO**（改走 BIOS INT 13h，见上一条），
  "装到 SATA 盘再重启"现在有两种验法：① `ahci64_test.py --sata-install`（把装好的盘按 IDE
  兼容方式再挂一次）② **`disk_boot_test.py`（把装好的盘只挂 AHCI 启动 —— 这才是纯 SATA 机器的形态）**。

## 批次 E（"U 盘形态 × 双固件"验证 + 安装时在目标盘建 ESP/GPT）—— 2026-09-20 实测

本批次的目标（用户需求）：**安装 U 盘在新设备（UEFI 64 位）和老设备（BIOS/CSM）上都能启动，
装好的系统也要在两代设备上都能启动**。分两半：

### ① "U 盘形态 + UEFI"验证（`tests/usb_boot_both_fw_test.py`）

同一个 `vimtu64-64.iso` 当磁盘/U 盘引导，四档全 PASS 且都**进到安装向导第一屏**：

| 形态 | 固件 | 关键打点 |
|---|---|---|
| ISO 挂 `usb-storage`（UHCI + `bootindex=1`） | UEFI（OVMF） | `S12345J` → `U:====` → `U:loaded KERNEL64.BIN/SYSTEM.IMG` → `[LM64] ENTERED LONG MODE` → `[SETUP] 磁盘枚举完成` |
| ISO 当 IDE 盘 | UEFI（OVMF） | 同上（不支持 USB 启动的固件的等价形态） |
| ISO 挂 `usb-storage` | BIOS（SeaBIOS） | `I:boot dl=` → `I:hdd mode (USB/disk)` → `I:jump loader64` → `L:media=ram` → 向导第一屏 |
| ISO 当 IDE 盘 | BIOS（SeaBIOS） | 同上 |

**结论：UEFI-USB 这条组合原生就通**（不需要改 `tools/make_iso64.py`）——ISO 里
El Torito 0xEF 项 + GPT + FAT32 ESP（48MB）三者齐全，OVMF 用 GPT 路径就能找到 `EFI/BOOT/BOOTX64.EFI`；
MBR 里还有 0xEF 项兜底。 BIOS 侧走 hybrid MBR → cdiso 桩 → INT 13h 搬内核/载荷。
脚本末尾另有"安装介质 sha256 未变"断言（真 U 盘/光驱是只读的）。

### ② 安装时在目标盘建 ESP + GPT（`kernel/fat64.{h,cpp}` + `kernel/part64.cpp`）

以前安装只写"MBR + 固定 LBA 引导区"→ UEFI 固件在装好的盘上找不到任何 FAT 卷 →
装完的盘在 UEFI 机器上起不来。现在安装收尾会写：

* **48MB FAT32 ESP**（盘尾）：内嵌最小 **FAT32** 写入器，卷参数与构建期 `tools/make_esp.py`
  **逐条对齐**（512B 扇区 / `SPC=1` / **32 个保留扇区**（1=FSInfo、6=备份引导扇区）/ 2 份
  **32 位** FAT / 根目录 = 从簇 2 开始的**簇链** / 簇数硬断言 `>= 65525`）。
  ESP 里放 `EFI/BOOT/BOOTX64.EFI`（内嵌桩字节）+ `UEFI64.BIN`（内嵌引导器）+
  `KERNEL64.BIN`（**直接读目标盘 LBA 9..8008 的 4MB 内核区**，这样安装程序内核不必内嵌 4MB 副本）。
  **为什么是 48MB**：FAT32 的簇数硬下限 65525（少于这个数就该被当作 FAT16，固件会按 16 位读
  我们的 32 位 FAT 表 → 多簇文件报 EFI_VOLUME_CORRUPTED）；SPC=1/512B 扇区时数据区至少
  65525 扇区（32MB），加保留扇区与两份 32 位 FAT，卷下限约 33.5MB —— 取 48MB（96736 簇）。
* **混合 MBR**：`0xEF` 引导区（活动，9+8000）+ `0x07` 主分区 + `0xEF` ESP（盘尾）。
  故意**不写 `0xEE` 保护项**（EDK2 见到 `0xEE` 会放弃 MBR 解析路径）。
* **盘尾备份 GPT**：主 GPT 头的规范位置 LBA 1 被 `loader64.bin` 占着（`boot.asm` 从 LBA 1 读 8 扇区），
  所以只写备份头 + 备份项数组；UEFI 规范要求"主头无效时用备份头"，EDK2 实测如此
  （OVMF 从这块盘启动成功，且启动后 LBA 1..8 的 loader 字节**未被改写**）。
* `boot/efi/uefi64.c`：`SYSTEM.IMG`（安装载荷）改成**可选**（装好的盘上没有它；
  跳过并写 `U:missing SYSTEM.IMG (optional, skipped)` + 介质描述符 `kind=0`），安装介质路径不变。
* 小盘（`< 8009 + 8MB + 48MB + 33 = 122730 扇区 ≈ 59.9MiB`）不建 ESP，只写老 MBR 布局并在串口打
  `[INSTALL] esp skipped (disk too small)` —— 既有的 16MB 回归目标盘字节级断言因此原样保持。

**字节级 + 双固件验收（`tests/esp_install_test.py`，64MB 目标盘挂 AHCI）**：

```
[FAT64] selftest PASS
[INSTALL] esp: lba=32735 sectors=98304 fs=FAT32 clusters=96736 fat_ok=1
[INSTALL] esp files: BOOTX64.EFI=2560B UEFI64.BIN=36864B KERNEL64.BIN=4096000B
[INSTALL] gpt written (main + esp), pmbr ok main=8009+24726 esp=32735+98304 backup_hdr_lba=131071

     + 三文件与构建产物逐字节一致

```

### J3. 剪贴板模型（写清楚，免得后来人猜）

* 剪贴板 = 最多 8 条 `(卷槽, 完整路径)` + 操作（复制/剪切）——**不是文件内容快照**（粘贴时现读现写；源被删掉就失败并计入 `skipped`）。
* **跨卷**（C: ↔ D:）：源用 `vfs64_*_on64(源槽)` 读、目标按**界面盘符**写（`exp_ensure_volume()` 保证"当前卷 = 用户看到的盘"），
  所以复制/粘贴与"当前卷恰好是哪块盘"无关。
* **目录递归复制**：支持（`exp_copy_tree`，深度 ≤4、整棵 ≤96 条，单层一次列 16 条；超限/失败如实计入 `skipped`），
  并且**拒绝把目录复制进自己的子树**（`path_is_ancestor_pure` 防自喂）。
* **重名策略**：粘贴 / 新建文件夹撞名时**自动追加 `(2)`、`(3)`…**（最多到 32 次；插在扩展名之前）；
  **重命名不自动改名**：用户明确输入的名字撞名一律拒绝（`rename … rc=1`）。
  ⚠️ 与 Windows 不同的是**后缀不带空格**（`readme(2).txt`）：VimtuFS2 的名字只允许 `0x21..0x7E`，**空格不合法**，
  带空格的候选名会被盘上的校验直接拒掉（这是本批实测踩到的坑：`paste ok n=0 skipped=1`）。
* **剪切** = 复制成功后删源（**先全部复制成功再删**；某条失败就保留它的源，绝不半删），成功后清空剪贴板（Windows 语义）。

### J6. 本批次留下的边界（**如实**）

* **没有递归删除**（非空目录只能自己先清空）；没有跨目录移动/拖拽（`vfs64_rename64` 不搬 `parent`）。

### 踩坑记录（值得记住）

* **FAT（16/32）自检不能碰真盘**：第一版把"切 I/O 后端"写进了 `format` 内部（强制 `g_ram=false`），
  于是自检的 format 落到了 `drive 0` —— 实测把安装介质 ISO 的前 2.5MB 覆盖成 FAT 卷，
  表现为"后续 BIOS 从 ISO 启动一片空白（0 字节串口）"，而**当轮串口侧完全看不出来**。
  修法：`format_volume()` 只做实现、`fat64_format64()` 显式切真盘后端、自检显式切内存后端；
  并给 `tests/usb_boot_both_fw_test.py` 加了"介质 sha256 未变"断言兜住同类问题。
* **GPT 头的 CRC 要"把 HeaderCRC32 字段当 0"再算**（UEFI 规范；EDK2 与 `tools/make_iso64.py` 都这么做）——

## 批次 F（item 6：NVMe 驱动 —— 能装到 NVMe 盘、UEFI 从这块盘启动）—— 2026-09-20 实测

### ① 最小 NVMe 驱动（`kernel/nvme64.{h,cpp}`，新建）

* **PCI**：扫 class `0x01` / subclass `0x08` / prog-if `0x02`（= class_code `0x010802`）；只在自己找到的
  功能上开 MEM + BUS MASTER；读 **BAR0**（偏移 `0x10`；bit2=1 表示 **64 位 MMIO BAR**，高 32 位在 `0x14`）。
  实测两种环境都过：BIOS 下 `bar0=0x00000000FEBF0000`、**UEFI 下 `bar0=0x000000C000000000`**（4GB 以上，
  64 位 BAR 的高位处理真的被用上了）。
* **控制器初始化（严格照规范顺序）**：`CC.EN=0` → 等 `CSTS.RDY=0` → `INTMS=0xFFFFFFFF`（**全程轮询**，
  与 AHCI 一致）→ `AQA`（ASQS/ACQS 0-based）→ `ASQ`/`ACQ`（**页对齐物理地址**，页池低内存 PA==VA）→
  `CC`（CSS=0 NVM / MPS=0 4KB / IOSQES=6 64B / IOCQES=4 16B / EN=1）→ 等 `CSTS.RDY=1`（`CSTS.CFS` 检查）。
* **Admin 队列（qid 0）**：Identify Controller（`CNS=0x01`，型号/序列号）→ Identify Namespace
  （`CNS=0x00`，NSID=1，取 `NSZE` + `LBAF`→LBA 字节数）→ Create I/O CQ（`0x05`）→ Create I/O SQ（`0x01`）
  （PC=1 连续、IEN=0 不开中断、QD=8）。
* **I/O（qid 1）**：Read `0x02` / Write `0x01`：`NSID` + `SLBA` + `NLB（0-based）` + PRP1/PRP2；
  提交敲 **SQ tail 门铃**（`0x1000 + 2*qid*stride`），完成轮询 **CQ 的 phase 位**，然后敲 **CQ head 门铃**
  （`0x1000 + (2*qid+1)*stride`，`stride = 4 << CAP.DSTRD`）。`SC`/`SCT` 非 0 一律打点返回失败。
* **传输上限与分块**：一条命令 **≤ 128 扇区（64KB）**（与 `part64` 的 `INSTALL_CHUNK_SECTORS` 同值），
  更大的请求由驱动**内部按 128 扇区分块**，上层不用管。PRP 规则（**这里是本次的真坑**）：
  PRP1 之后剩余 ≤1 页 → 只用 PRP1；**刚好两页 → PRP2 = 第二页页基址（直接指针）**；
  ≥3 页 → PRP2 = 页对齐的 PRP 列表（项 = 第 2..N 页页基址）。DMA 缓冲地址算不出来时走**暂存页**兜底。
* **超时双保险**：`g_ticks64`（250Hz，1s）+ 自旋上限（IF=0 时 tick 不前进），绝不挂死；
  失败一律 `[NVME64]` 打点并如实返回 false。

### ② 接入磁盘层（`kernel/ata64.{h,cpp}`，上层一行未改）

* 驱动器号方案：`0..3`=PATA、`8..15`=AHCI 盘、**`16..`=NVMe 命名空间**（`ATA64_NVME_BASE = 16`，
  数组尺寸用 `ATA64_MAX_DRIVE64`）。
* `ata64_drive_count64()` = `4 + ahci64_count64() + nvme64_count64()`；`ata64_slot_to_drive64()` 依序给号；
  `ata64_identify/read/write` 内部按号分派到 `nvme64_*`。`ata64_init64()` 里 `nvme64_init64()`
  + `nvme64_selftest64()`（幂等；没控制器只打 `[NVME64] not found`）。
* **上层（setup64 / part64 / vfs64 / store64 / fat64）的实现代码没动**：`setup64.cpp` 只把磁盘表的
  数组尺寸从 `ATA64_AHCI_BASE + AHCI64_MAX_DEVS` 改成 `ATA64_MAX_DRIVE64`（**必须改，否则 16 号盘会被
  `d >= kDiskSlots` 静默跳过 = 装不进去**），并把向导/串口的 bus 标签从"AHCI/PATA"扩成三项
  （16 号盘打 `bus=NVMe`）；其余全是注释/证据行。

### ③ 硬件报告页（`kernel/hwui64.cpp`）

* 存储区块不再写"NVMe 本系统不支持"：找到控制器时显示 **PCI 位置 / bar0 / qd / 命名空间数 / 控制器型号**，

### 踩坑记录（新增，值得记住）

* **PRP2 的两种含义别写混**（本次定位到的真缺陷）：PRP1 之后剩余数据 **刚好 ≤ 1 页**时，PRP2 必须是
  **第二页的页基址（直接指针）**，**不是** PRP 列表；只有剩余 > 1 页才用列表。把"两页"也写成列表时，
  QEMU 会把**列表页的第一个 8 字节**当作第二页的数据地址 —— 症状是"**前半段对、后半段错**"：
  ESP 里 `BOOTX64.EFI`（2560B，嵌在安装程序内核 .rodata 里、起始地址不在页边界上）只写对了前 848
  字节（= PRP1 覆盖的部分），其余全错，OVMF 直接 `BdsDxe: failed to load … Load Error` 掉进 EFI Shell；
  而 4MB 的 `KERNEL64.BIN`（缓冲页对齐）一直是对的，所以只看大文件根本发现不了。
  **回归网**：`nvme64_test.py` 把 ESP 三文件与构建产物逐字节比对（这一档就是抓这个 bug 的那一档）。
* **Identify Namespace 的 CNS 是 `0x00`，不是 `0x02`**：`0x02` 是 **Active Namespace ID list**；
  用它读 `NSZE` 只会拿到命名空间 ID 列表（QEMU 实测表现为 `nsid=1 not present (NSZE=0)`，
  而命令本身是"成功"的 —— 因为响应确实是合法的空列表）。改成 `CNS=0x00` 后 NSZE 立刻正确（131072）。
* **QEMU 的 NVMe 需要"真的有一个命名空间"**：`-device nvme,drive=…` 与显式 `nvme-ns` 两种挂法都
  实测可用（都能枚举到 NSID 1）；但只有控制器没有命名空间时，Identify Namespace 返回的是全 0 列表，
  表现为 `nsid=1 not present (NSZE=0)` —— 打点里区分得出来。

### 如实边界（本批次没做/没验的）

* **真机未测**：全部证据来自 QEMU 11.1（`-device nvme`）+ OVMF/SeaBIOS；真机 NVMe 需按
  `docs/真机验证指南.md` §3 复验（报告页 + 串口 `[NVME64]` 行）。

## 批次 G（VimtuFS2 v3 目录树 + 盘符/驱动器枚举层 —— "此电脑"的地基）—— 2026-09-20 实测

**需求**：做一个类似 Windows 10 的"此电脑 + 文件资源管理器"。本批次只做**地基（不含 UI）**：

### ① VimtuFS2 v3：真正的目录树（`kernel/vfs64.{h,cpp}`）

  **mtime**（`(年-2000)<<26|月<<22|日<<17|时<<12|分<<6|秒`，RTC 打包）、**nlink**、**kind**（类型判定）。
* **目录表示**：名字仍存在 inode 里（目录没有数据块）——"目录" = `parent` 指向它的 inode 集合；
  取舍写在 `kernel/vfs64.h` 文件头。查名字/列目录是 O(inode 数)，用一个"当前 inode 扇区"缓存把读盘降到 1/4。
* **新 API**：`vfs64_stat64` / `vfs64_list64`（路径版 + 游标分页）/ `vfs64_opendir64+readdir64+closedir64` /
  `vfs64_mkdir64`（多级）/ `vfs64_create64` / `vfs64_write64` / `vfs64_read64` / `vfs64_unlink64` /
  `vfs64_rmdir64`（**空**目录）/ `vfs64_tree_dump64`（有界目录树打印）/ `vfs64_pack_time64` 等工具函数 /

  `fd64_norm_path64` 升级为多级路径（保留"空白截断/根目录拒绝"的旧行为），`FD64_PATH_MAX` 32→64。
* **v2 兼容**：v2 卷（64B inode、名字 ≤27B、无 mtime/kind）**照常挂载**（`VFS_LAY_V2`），按单层语义工作；

* **自检**：`vfs64_selftest64` 新增 bit8（多级目录树）/ bit9（路径语义）/ bit10（mtime + 类型判定）/
  bit11（代际几何 + 重挂载持久化 + 空目录删除）；真盘侧仍是只读探测。
* **踩坑**：旧自检在 bit5 注入坏 inode 时把 inode 表**第一个扇区**整体清零 —— 那里面正好是根目录 inode，
  于是后面的目录树自检全废。现在注入前先备份整扇区、做完原样写回（并断言根目录还在）。

### ② 盘符/驱动器枚举层（`kernel/drive64.{h,cpp}`，新建）

* `drive64_scan64`（幂等）/ `count64` / `info64` / `by_letter64` / `selftest64` / `dump64` / `kind_name64`。
* **C: 的判定依据**：`vfs64` 当前**真正挂载**的卷的 `(drive, start_lba)`（系统内核用
  `app64_main_part_lba64(0)` = MBR `0x07` 项作挂载参数）；没挂载时退化为 drive 0 的 MBR `0x07` 项，

* **跳过项不占字母但要列出**：ESP（type `0xEF`）、未知文件系统、未分区盘 → `letter=0` +

## 批次 I（多卷挂载 / 盘符切换 —— 每个 VimtuFS2 卷都能浏览与读写）· 2026-09-21 实测

**需求**：文件管理器里"点开 C 盘**或者其他磁盘**"都要能看到里面的文件夹与文件。此前 `vfs64`
**一次只挂一个卷**，只有系统卷 `C:` 能点进去，其余 `D:/E:` 只显示容量卡片。

### ① vfs64 多卷：卷槽表 + 按槽调用（`kernel/vfs64.{h,cpp}`）

* **卷槽表**：`VFS64_SLOT_MAX = 4`，每槽独立保存一份卷几何（drive/起始 LBA/位图/inode/数据区/布局）；
  `g_cur_slot` = **当前卷**，既有的 2000 行实现（路径解析/inode/位图/读写/遍历）通过字段别名
  **逐字不动**地作用于当前卷 —— 切卷 = 改一个下标，没有数据搬运。
* **API**：`vfs64_mount_system64`（系统卷 → 0 号槽 + 登记 + 激活）、`vfs64_mount_slot64`（挂进指定槽，
  **不改变当前卷**）、`vfs64_activate_slot64`、`vfs64_current_slot64`、`vfs64_system_slot64`、
  `vfs64_slot_used/alloc/find/info`、`vfs64_slots_dump64`；旧 API 全部保留为"作用于当前卷"的兼容包装。
* **inode 缓存按 (slot, drive, lba) 三元组键控**：这是切卷最容易出的 bug（只按 LBA 键控会在切盘后
  把上一个卷的 inode 字节当本卷的用）。写盘仍整体失效。**自检 bit12** 专门用"同一块盘上两个不同 LBA
  的卷"覆盖它。
* **on64（固定系统卷）**：`vfs64_*_on64(slot, …)` + `Vfs64SlotGuard`（单次调用内临时切卷、返回前 LIFO
  切回）。`store64`/`config64`/`update64`/`app64`/`elf64`/`proc64`/`sysstate64` **全部**改用
  `vfs64_system_slot64()` —— 这就是"为什么不会写错卷"。
* **目录游标**也带卷身份（slot/drive/start），卷被重挂/换卷时如实报错，不会拿别的卷的 inode 表当目录内容。

## 【批次 L】fileops64 28 条失败的定位与处置 + 11 个脚本补跑（v0.2.1-beta7，2026-09）

**一句话**：① 把上一批遗留的 `tests/fileops64_test.py` 28 条 FAIL 定位到**同一个注入时序问题**
（`/docs` 的双击注入被内核判成两次单击），在**内核**与**测试**两侧修掉，并证明修复前后在同样负载下的差别；
② 补跑 11 个从未跑过的脚本（加 `proc64` 复跑），全部 PASS。

### L1. fileops64 28 条 FAIL：原始证据与定性

* 现象（历史两次运行的串口日志，就是"28 条 FAIL"那两次）：
  `/docs` 的双击只留下 2 条 `[UI] explorer click … hit=item:6`，
  **没有** `[UI] explorer enter name=docs kind=dir`、也没有 `[UI] explorer nav path=/docs`。
  于是后面的动作全部落在**盘根**上：`paste ok n=1 dst=/`（不是 dst=/docs）、框选到 12 条（不是 2 条）、
  `delete confirm n=12 path=/hello.vap`、Ctrl+X 无对象……**一个双击丢了，后面 20+ 条断言连锁失败**。
  两次失败运行都是同一条第一现场（`clicks_item6=2`、`enter name=docs`=0），7 次成功运行都是
  `clicks_item6=2` 且 `enter name=docs`=1 —— 注入的两次按下都到了，只有"判定"这一次不同。
* 定性：**(a) 测试注入时序/抖动**（宿主负载高时 QEMU+PS/2 的两次按下被处理得太慢），不是 UI 语义缺陷。
  量化复现（同一台机器、同一镜像）：
  - 空闲：94/94 PASS；
  - 4 个 CPU 烧机进程：91/94（3 条 FAIL，全是"双击没被识别"：预览/进新目录）；
  - 8 个烧机进程：43/89（46 条 FAIL，第一次双击就丢）；
  - 把 `/docs` 的双击注入**故意拉慢**到两次按下间隔 0.9s（> 内核 500ms 窗口，scratch 副本）：
    93 checks / **29 FAIL**，第一条正是"双击进 /docs（nav path=/docs items=0）"——与历史 28 条同构。
* 根因（代码）：`explorer64` 的双击窗口用的是 **GUI 回调时刻**（`ticks64()` at click callback）。
  主循环虽然很快，但一帧全窗口重绘/调度被拖长时，第二个按下的**回调**可能比第一个晚 >500ms，
  而两次按下的**包到达**只隔 ~200ms —— 用户/注入的双击就这样被吃掉。
* 修复（最小改动）：

## 批次 M：VimtuFS2 大文件（二级间接块，单文件 8 MiB）+ 上层上限对齐（v0.2.1-beta8，2026-09）

**一句话**：给 VimtuFS2 加了**二级间接块**，单文件上限从 67,584 B 提到 **8 MiB（8,388,608 B）**，
并把 fd / 终端 / 文件管理器 / ELF/VAP 上限口径一起对齐；老 v2/v3 卷照旧能挂载读写。

### M1. 格式扩展（一页纸：几何 / 版本 / 兼容）

| 项 | 内容 |
|---|---|
| 直接块 | 4 块（2 KiB），inode 偏移 8/12/16/20 |
| 一级间接 | 1 块 = 128 个块号（64 KiB），inode 偏移 24 |
| **二级间接** | 1 块 = 128 个子块号 × 128 个块号 = 16384 块（8 MiB），inode 偏移 **71**（原保留区首 4 字节） |
| 映射能力 / 上限 | 16516 块 = 8,456,192 B；**对外上限取整到 16384 块 = 8 MiB** |
| inode / 几何 | **仍是 128 B**、每块 4 个、超级块/位图/CRC 规则**未变**（保留区缩到 [75,124)） |
| 卷版本 | **仍是 3**：老 v3 卷该字段恒 0 = "没有二级间接" → 能挂载/能读/能写；**新内核还能在老 v3 卷上写 8 MiB 大文件** |
| 降级 | 老内核读"含二级间接的文件"会拒绝**那一个 inode**（reason=rsvd3），其余文件不受影响（单向升级，如实写清） |
| v2 卷 | 没有 dind 字段 → 上限仍是 **67,584 B**（`vfs64_max_file_bytes64()` 按卷布局返回真实上限） |
| 稀疏 | **不做稀疏文件**：`seek` 过末尾再写 = 中间**补零**；读路径碰到未映射块 = 损坏 -> -1 打点 |
| 回收 | `unlink` / 整体重写释放 数据块 + 一级 + **二级 + 128 个子块**；写-删-写循环空闲块回到基线（有断言） |
| 失败语义 | 超上限 / 空间不足**先失败**（预检）不留半截；建链阶段失败**回滚**新分配的块；指针块已落盘后失败只可能"泄漏块" |

### M2. 读写路径与上层对齐

* `kernel/vfs64.cpp`：新增 `vfs64_read_at64`（按偏移分块读）、`vfs64_write_at64`（部分写/追加 + 空洞补零 + 空间预检）、
  `vfs64_write_stream64`（整体重写，数据由回调给）、`vfs64_blocks_for_bytes64`、`vfs64_max_file_bytes64`
  与按槽变体；`vfs64_write64` 改为"流式建链"（语义不变：先建新链、提交 inode、最后释放旧块）；
  `inode_ok` 增加"指针必须在数据区内 / 有 dind 就必须有 ind"的几何自检。
* `kernel/fd64.{h,cpp}`：**删掉两块整文件读写缓冲**（曾经各 8MiB 级）——读直接读进调用方缓冲、
  写走部分写；`FD64_FILE_MAX = VFS64_MAX_FILE_BYTES`（8 MiB）；`lseek` 64 位偏移、超限 `-EINVAL`。
* `kernel/fs64.{h,cpp}`：`fs64_read_range64` 改成直接按偏移读（不再"整读进 8MiB 静态缓冲再切片"）；
  新增 `fs64_write_at64`（只读卷 `-FS64_EROFS`）。
* `kernel/explorer64.{h,cpp}`：粘贴 = **64 KiB/块复制**（`explorer64_copy_file64`，跨卷/跨文件系统同一份代码，
  也供终端 `bigtest copy` 复用）；空间预检 `vfs64_blocks_for_bytes64(size) + 1`；大于上限的源**整条跳过**；
  大小显示仍是同一个 `fmt_bytes64`（**1.0 MB / 8.0 MB**，一位小数）。
* `kernel/terminal64.cpp`：`cat` 先 `stat` 拿大小、最多打 **4096 B** 并**明确提示截断**（打点 `truncated=1`）；
  `write FILE TEXT` 的说明改成"受命令行长度限制（不是文件上限）"；新增 **`bigtest [1mb|8mb|limit|recycle|copy <src> <盘符>]`**
  （走公共 fd64/fs64/vfs64 路径生成/校验大文件，串口打 `[BIG64]` 行）。
* `kernel/app64.h` / `kernel/elf64.h`：**常量不动**，只把"FS / 用户窗口 / 读盘缓冲"三层上限的归属写进头注释
  （VAP64 代码 32 KiB = 用户窗口；ELF64 读盘缓冲 96 KiB；真正卡住装载的是用户窗口）。

### M3. 自检与端到端验收

* `vfs64_selftest` 假盘从 32KB 扩大到 4MB（前半段跑既有 bit0..bit11/多卷，后半段 2MB 给大文件），新增三个位：
  * bit13(8192) **二级间接块大文件**：流式写 1.5 MB -> 分块读回逐字节 + CRC 一致；断言 inode 的 dind 非 0、
    块数记账 = 数据块 + 一级 + 二级 + 子块；删掉后**空闲块回到基线**；
  * bit14(16384) **回收不泄漏**：写-删 x2 回到基线 + 空间不足**预检直接失败**且不留文件/垃圾块；
  * bit15(32768) **上限边界**：`write_at` 越过上限被拒（不半截）、`write64` 超上限被拒、
    整体重写变小释放块、重写成 0 字节后**全部块回收**。
* 实测串口：`[VFS64] selftest PASS`、`[VFS64] bigfile ok bytes=1572864 blocks=3097 ind=1 dind=1 free_delta=3097
  unlink_back_to_base=1 crc=0xA2EC1872`、`[VFS64] recycle ok rounds=2 free_before=4078 free_after=4078 delta=0`、
  `[VFS64] limit ok max=8388608 over_rejected=2 rewrite_shrink=1 truncate_free=1`。

  然后宿主侧**解析 raw 镜像**沿 直接块 -> 一级 -> **二级间接（127 个子块）** 走一遍，独立重算模式字节的 CRC 比对：
  * `[BIG64] write path=/big1.bin bytes=1048576 blocks=2065 free_before=253836 free_after=251771 crc32=0xA3A93CF1 rc=0`
  * `[BIG64] write path=/big8.bin bytes=8388096 blocks=16512 ... crc32=0x674DEF20 rc=0`
  * `[BIG64] over path=/big8.bin rc=27 size_before=8388608 size_after=8388608 partial=0 crc_ok=1 free=...`

### M4. 如实说明的边界（没做/没验证）

* **没有稀疏文件**（空洞补零，不是 sparse）；**没有任意长度 truncate**（只有"整体重写"与"重写成 0 字节"两种收缩方式）。
* **没有崩溃一致性/日志**：写失败只保证"不指向已释放的块"，指针块落盘后失败仍可能**泄漏块**（与既有口径一致）。
* 单次 `write_at` 没有长度上限（缓冲由调用方给），但**上层建议每次 ≤64 KiB**；`cat` 打屏上限 4096 B。
* v2 卷的大文件（>67,584 B）**不支持**（格式里没有 dind 字段），这是格式决定的，不是 bug。
* 二级间接块链的**碎片化**没做整理：文件仍是"顺序分配块"（`alloc_block` 首次适配），删除后不整理。
