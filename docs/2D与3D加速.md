# 2D 与 3D 加速（v0.9.17）

> 这份文档回答一个问题：**VimtuOS 现在到底有没有 2D/3D 加速？** 每一句后面都有可复跑的证据。
> 先说结论（别被后面的细节淹了）：
> * **2D：有加速，且被量出来了** —— 脏矩形驱动，一次提交只搬改动区域（实测 3,145,728 B → **32,768 B**）。
> * **3D：通路铺通了、但出图还没取证（UNVERIFIED）** —— 主机 virgl 拿到了、上下文/3D 资源/提交/回读全被接受，
>   但**回读像素仍是 0**；QEMU 自己的 stderr 说 `failed to dispatch BIND_OBJECT: 22`。
>   **不假装成功**，如实标 UNVERIFIED 并把根因证据留在下面。

---

## 1. 2D 加速：靠什么、怎么量

### 1.1 为什么"2D 加速"在这个后端上只能省搬运量

virtio-gpu 的 2D 命令集只有三条半：

| 命令 | 作用 |
| --- | --- |
| `RESOURCE_CREATE_2D` | 建一张 2D 资源 |
| `RESOURCE_ATTACH_BACKING` | 把页池的物理页挂成它的后备存储 |
| `TRANSFER_TO_HOST_2D` | 把（一块矩形内的）像素**推给设备** |
| `RESOURCE_FLUSH` | 让设备把这块**扫描输出**到显示器 |

**没有 blit、没有 fill、没有 alpha 混合、没有缩放** —— 所以 2D 加速在这个后端上只有两个落点：
① 扫描输出由设备做（CPU 不逐行写 LFB）；② **只搬改变的那一块**，而不是整屏 3 MiB。

### 1.2 脏矩形（`DRM_IOCTL_MODE_DIRTYFB`，Linux ABI `0xB1`）

```
struct drm_mode_fb_dirty_cmd { __u32 fb_id; __u32 flags; __u32 color; __u32 num_clips; __u64 clips_ptr; };  // 24 B
struct drm_clip_rect        { __u16 x1, y1, x2, y2; };                                                     // 8 B
```

* 内核把它们**并成一个脏矩形**（半开区间），下一次 `PAGE_FLIP` / `SETCRTC` / `ATOMIC` 只搬这个矩形，
  搬完立即失效（一次性消费）。
* `flags` 必须 0（否则 `-EINVAL`）；`num_clips` 1..8；矩形会自动夹到缓冲尺寸内；空矩形跳过。
* 没有脏矩形时报整块（**正确性优先**：宁可多搬，也不能少搬）。

### 1.3 实测（`tests/drm64_test.py` 里就有）

```
[DRM] dirty fb=2 clips=1 dmg=0,0,128,64 bytes=32768
[DRM] present id=2 path=cpu bytes=32768 x=0 y=0 w=128 h=64 seq=…
[DRM] flip a=1 b=2 alt=1 n=1          ← 双缓冲：A/B 两块轮换
[DRM] flip a=2 b=1 alt=1 n=2
```

* 同一帧内容的整块提交是 **3,145,728 B**（1024×768×4），脏矩形那次是 **32,768 B** —— **减少 96 倍**。
* 判据在 `drm64_test.py` 的 ④-d：既要求 `bytes=32768` 这一行，也要求 `alt=1` 出现两次（双缓冲真的在交替）。

## 2. 3D 加速：已经通到哪儿、卡在哪

### 2.1 设计（`kernel/vgpu3d64.cpp`）

virtio-gpu 的 3D 是**另一条通路**（virgl）：guest 把"virgl 命令流"交给 host 的 GL 渲染器执行。完整链路是

1. 设备协商 `VIRTIO_GPU_F_VIRGL`（`virtio_gpu64.cpp` 现在**设备给了就收**，不影响 2D）；
2. `GET_CAPSET_INFO` 拿 virgl capset（版本 + 大小）；
3. `CTX_CREATE` 建 virgl 上下文；`RESOURCE_CREATE_3D` + `ATTACH_BACKING` 建 3D 资源；
   `CTX_ATTACH_RESOURCE` 把资源挂进上下文；
4. `SUBMIT_3D` 提交 virgl 命令流：`CREATE_OBJECT(surface)` → `BIND_OBJECT` → `SET_FRAMEBUFFER_STATE` → `CLEAR`；
5. `TRANSFER_FROM_HOST_3D` 把渲染结果**读回 backing 页**，逐像素核对清屏色。

### 2.2 已经取证的部分（这些是**真的**）

| 环节 | 证据（串口原文） | 结论 |
| --- | --- | --- |
| 特性协商 | `[VGPU] feature dev_lo=0x30000013 … ok_lo=0x1` | ✅ VIRGL 位收下了 |
| 主机有 virgl | `[GPU3D] capset id=1 ver=1 size=308` | ✅ 主机侧 GL 渲染器在场（capset 大小 308 字节） |
| 上下文 / 3D 资源 / 挂载 | 6 条命令全部 `resp=0x1100`（无 `cmd FAIL`） | ✅ 设备全接受 |
| `CREATE_OBJECT` 编码 | 三轮阶梯：`len=6/7` → `22`；`len=5` → **通过** | ✅ 负载就是 5 个 dword（handle, res, format, level, first_layer） |
| 提交 + 回读 | `TRANSFER_FROM_HOST_3D` 执行完、backing 页可读 | ✅ 通路是通的 |
| **出图** | `[GPU3D] selftest … ok=0 px=0x0 want=0xff4080bf` | ❌ **UNVERIFIED** |

### 2.3 卡点（QEMU 自己的 stderr，不是我的猜测）

```
context 1 failed to dispatch BIND_OBJECT: 22
vrend_decode_ctx_submit_cmd: context error reported 1 "vimtu3d" Illegal command buffer 67586
vrend_renderer_transfer_iov: context error reported 1 "vimtu3d" Illegal resource 2
```

`vrend`（host 侧渲染器）拒绝我们的 `BIND_OBJECT`。**六种编码都试过了**（这些尝试是内核里的一轮阶梯，
每次换一个独立上下文 —— 一条命令被判错，那个上下文就废了）：

| # | surface 句柄 | `BIND_OBJECT` 编码 | 结果 |
| --- | --- | --- | --- |
| 1 | 1 | 头部 obj=8，负载 `[h]` | `EINVAL(22)` |
| 2 | 1 | 头部 obj=0，负载 `[h, 8]` | `EINVAL` |
| 3 | 1 | 头部 obj=8，负载 `[h, 8]` | `EINVAL` |
| 4 | 0x100 | 头部 obj=8，负载 `[h]` | `EINVAL` |
| 5 | 0x100 | 头部 obj=0，负载 `[h, 8]` | `EINVAL` |
| 6 | 0x2000 | 头部 obj=8，负载 `[h]` | `EINVAL` |

**为什么先停在这儿**：继续往下需要反查 virglrenderer `vrend_decode_bind_object` 的确切校验条件
（它同时看"对象是否在该上下文的对象表里"与"类型是否匹配"），而我们手上没有该版本的源码；
盲试的每一轮都要一次 ~18 分钟的全量构建，收益/成本已经很差。所以本批**如实记为 UNVERIFIED**，
并把整条阶梯留在内核里：**一旦哪天编码对了，`[GPU3D] selftest … ok=1 px=0xff4080bf` 就会自己出现**，
不需要改判据（`tests/gpu3d64_test.py` 对两种结论都认，但只有 ok=1 才算"出图通过"）。

### 2.4 复跑方式

```bash
py -3 tests/gpu3d64_test.py          # 13 条断言：通路 + 诚实结论 + 无 VIRGL 时的降级
```

它内部起两次 QEMU：

* `-device virtio-vga-gl -display sdl,gl=on` —— 唯一能同时当"主显示 + 带 VIRGL 的 virtio-gpu"的配置
  （Windows 上的 QEMU 只有带 GL 的显示后端才能建 GL 设备；`-display none` 会直接报
  "display backend does not have OpenGL support"）。
  > 顺带记一条坑：`-vga std -device virtio-gpu-gl-pci` 这个组合**我们的驱动认不出来**
  > （`[VGPU] error stage=cap bar unassigned`）—— 双显示设备时 virtio 的 cap 落在未分配的 BAR 上。
* `-vga virtio -display none` —— 没有 VIRGL 时必须只打 `[GPU3D] skipped reason=no-virgl`，**一个 3D 命令都不发**。

## 3. 结论与下一步

* **2D 加速：完成**（脏矩形驱动、可量化、有判据）。
* **3D 加速：通路完成、出图 UNVERIFIED**（根因在 host 侧 `vrend` 对 `BIND_OBJECT` 的校验，证据在上）。

下一步（按顺序）：

1. 找一份 virglrenderer 的 `vrend_decode.c` 把 `vrend_decode_bind_object` 的校验条件读清楚，
   按它的真实编码改 `kernel/vgpu3d64.cpp` 的那一条命令（阶梯已就位，改一处即可）；
2. 出图之后，把 3D 结果接到扫描输出（现在只回读到内存），也就是 `RESOURCE_CREATE_3D + SET_SCANOUT_BLOB`
   等价物；
3. 真 3D 应用还需要 guest 侧 GL（Mesa 的 virgl 驱动）—— 那是独立的一大块；
4. 2D 侧继续做的空间：把 `RESOURCE_FLUSH` 的矩形也交给脏矩形（现在 FLUSH 是整块）；
   dma-buf 跨进程（`PRIME_HANDLE_TO_FD` 等价物）仍在欠账里。

## 4. VMware 侧取证（v0.9.18，用户指定换 VMware 测）

QEMU 的 3D 路是 virgl，卡在 host `vrend` 拒绝 `BIND_OBJECT`（§2.3）。**VMware 不用 virgl，用 SVGA3D** ——
所以按用户要求换 VMware 虚拟机取证：新增 `kernel/vmware64.{h,cpp}`，在 **I/O 端口 BAR** 上读 SVGA 寄存器
（`outl(base+0, idx); inl(base+1)`；**不写 `SVGA_REG_ENABLE`**，唯一一次写是 `SVGA_REG_ID` 版本协商）。

VMware Workstation + BIOS 实测（`tests/vmware_svga64_test.py` **9/9**）：

```
[VMWARE] svga id=0x90000002 caps=0x1f83e2 3d=1 rect_fill=0 alpha=1 gmr=1 screen2=0 fifo_ext=1
         geom=1024x768 max=2560x1600 bpp=32 stride=4096 fb=0xf0000000 vram=134217728
         mem=0xfe000000 memlen=2097152 port=io
[DRM] selftest dumb=ok flip=ok vblank=1 mode=hw ok=1      ← VMware 上是**硬件回扫**
[GUI64] ready
```

* **`3d=1`**：宿主提供 **SVGA3D**（3D 加速的硬件前提，读到了才算数）。
* `alpha=1 gmr=1 fifo_ext=1`：Alpha 混合 / GMR / 扩展 FIFO 都在。
* `mode=hw`：DRM 的呈现与 vblank 在 VMware 上是**真硬件回扫**（QEMU 是 soft 软兜底）。

**仍然不声称"3D 出图已验证"**：`3d=1` 只说明能力存在；SVGA3D 的**命令协议还没实现**
（FIFO 提交 + OT 表 + 着色器 + GMR 映射）。下一步就是它。

## 5. VMware 阶段 1（v0.9.19）：真驱动设备

阶段 0（v0.9.18）只是**读**寄存器。阶段 1 开始**驱动**：配 FIFO、跟 host 做 SYNC/BUSY 往返、试着接管显示。

**两层 opt-in + 三道闸门**（全"不做"而不是"赌一把"）：

| 开关 / 闸门 | 作用 |
| --- | --- |
| `/etc/gpu3d_probe` | 只有它存在才允许碰 FIFO（默认启动一个寄存器都不写） |
| `/etc/gpu3d_enable` | 只有它存在才允许 `ENABLE`（接管显示） |
| `SVGA_REG_FB_START == fb64_lfb_phys64()` | 否则 ENABLE 会换屏 → 可能黑屏，直接跳过 |
| SVGA 几何 `== fb_phys_width/height` | 否则就是"换模式"，跳过 |
| MEM 区在 4 GiB 恒等直映内 | 否则读不了 FIFO，跳过 |

**实测（`tests/vmware_svga64_test.py` 17/17）**

```
[VMWARE] stage1 pre fifo=0xfe000000 memlen=2097152 fb_start=0xf0000000 lfb=0xf0000000
[VMWARE] fifo cfg min=16 max=524288 units=words sync=ok        <- FIFO 被 host 接受，回到空闲
[VMWARE] stage1 fifo sync=ok enable skipped reason=no-marker   <- 默认不接管显示
```

FIFO 在历史上有两种口径（`MAX` 用 word 数或用字节数），实现里**两种各试一次**，哪种 SYNC 通过就用哪种。

**实测卡点（所以要再关一层）**：开 `/etc/gpu3d_enable` 后日志有
`[VMWARE] svga enable=1 w=1024 h=768`，但**随后没有 `[GUI64] ready`、也没有 `[UI] perf`** ——
启动停在桌面之前。说明"接管显示"还要一并处理模式/位深/scanout，或 VGA 回扫探针在 SVGA 模式下的兼容。
**这条留着证据**，下次从这儿接着查（不是重新踩）。

## 6. 四项欠账的逐条审计（2026-11 实测对照）

| # | 需求 | 状态 | 已有的 | 还缺什么 |
| --- | --- | --- | --- | --- |
| 1 | dma-buf / fence 跨进程（`PRIME_HANDLE_TO_FD` 等价物）+ 真双缓冲交替 | **部分** | ✅ 双缓冲 A/B 交替（`[DRM] flip a= b= alt=1`）+ 脏矩形只搬改动区（3,145,728 B → 32,768 B） | ❌ **PRIME 两个 ioctl 没实现**（`0xC00C642D/0xC00C642E`）；❌ 没有 fence 对象；❌ 跨进程共享缓冲（现在还靠"同一进程内映射"） |
| 2 | 事件投递（page flip event / vblank event） | **未做** | ✅ 同步 `WAIT_VBLANK`（软/硬两种模式都实测过） | ❌ **一个事件都不投**：`PAGE_FLIP_EVENT` 位如实 `-EINVAL`；没有 DRM 事件队列、没有 `read()` 事件、没有帧回调 |
| 3 | libinput 的 udev/libevdev 层（`/sys` 枚举、`EVIOCGRAB`/`EVIOCSABS`） | **部分** | ✅ `/dev/input/event0|1` 设备面、24 B `input_event`、`EVIOCGNAME/GVERSION/GBIT` | ❌ 没有 `/sys/class/input` 枚举、❌ `EVIOCGRAB`/`EVIOCSABS`/`EVIOCSKEYCODE`、❌ libevdev/libinput 本体 |
| 4 | GBM + EGL/GLES（需 Mesa） | **未做** | ✅ 3D 的**内核侧**通路（virgl 到 capset 一级；VMware 侧 FIFO 通了） | ❌ GBM 库、❌ EGL/GLES（Mesa）；guest 侧 GL 一行都没有 |

一句话：**双缓冲有了，脏矩形有了，evdev 有了；PRIME / 事件投递 / libinput 的 udev+libevdev / GBM+EGL 都还没有。**
