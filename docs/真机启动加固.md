# 真机启动加固（v0.10.2）

目标：把 v0.10.1 的 ISO 用 Ventoy 烧到 U 盘，在真实 Intel i3 机器上能**安全启动/安装**，
绝不出现"黑屏且一句提示都没有"。

本文件记录：审计出的阻断项、本版修了什么（可复现的打点/判据）、以及**必须在真机上才
能验证的假设**（这些在 QEMU/VMware 上永远是绿的，不能当已验证）。

---

## 1. 审计结论（按"会不会让真机黑屏"排序）

| # | 位置 | 原状 | 真机后果 | 本版 |
|---|---|---|---|---|
| 1 | `boot/efi/uefi64.c` `PAYLOAD_BYTES = 8073*512` | 载荷字节数**写死 4.13 MB**（v0.5.18 的 system.img 大小）；`system.img` 现在 29.3 MB | UEFI 装出来的盘**主分区（LBA 32584 起）整块是零** → 装完重启黑屏 | **已修**：按文件真实大小读（`SetPosition(END)+GetPosition`），扇区数按真实字节数上报 |
| 2 | `boot/efi/uefi64.c` 所有失败路径 | 只写 COM1 串口 | 真机没串口 → 用户看到纯黑屏、无提示 | **已修**：加 ConOut 屏幕输出（`U:no GOP` / `U:image too big` / `U:KERNEL64.BIN missing`） |
| 3 | `kernel/nvme64.cpp` BAR0 | 无 ≥4GiB 检查，随后裸读 `NVME_CAP` | 真机 M.2 NVMe 的 BAR 常在 Above-4G（内核只恒等映射 0..4GiB）→ #PF/黑屏 | **已修**：`[NVME64] skip reason=bar0-above-4g`（拒设备不拒整机） |
| 4 | `kernel/ahci64.cpp` ABAR | 同上 | 同上（PCH AHCI 一般 <4G，但不再赌） | **已修**：`[AHCI64] skip reason=abar-above-4g` |
| 5 | `kernel/fb.cpp` `backbuf_storage[3840*2160]` | `fb_init` 不钳制几何 | GOP 原生模式 4096x2160 / 5120x2880 时第一次清零就**写穿 .bss** | **已修**：按渲染区 + 最近邻放大钳到 3840x2160，`[FB64] geom clamp lfb=… render=… zoom=…` |
| 6 | `boot/uefi64.c` PixelFormat==2（BitMask） | 不解析掩码，bpp 硬写 32 | 少数主板红蓝互换（不是黑屏） | 未修（记录在 §4） |
| 7 | `kernel/gpu64.cpp` iGPU MMIO 裸读 | 不查页表映射 | 若固件没映射 iGPU BAR0 窗口 → #PF | 未修（见 §4：需要真机取证，QEMU 无法复现） |

**已做对、不要再改的地方**（审计确认）：LFB 64 位化（`bootinfo.h` + `fb.cpp`）、LFB 页表
只读走查 + 缺映射自补 + RO→RW 升级、`fb_usable` 闸门覆盖所有 LFB 写点、LFB 改 UC + sfence、
PCI BAR 写全 1 回读确认 + ≥4GiB 直接 ENODEV、AHCI/NVMe/ATA 全部 tick+自旋双上限、
盘探测失败**不 panic**、panic 走 BSOD 且 fb 不可用时不会三重故障。

## 2. 本版修法的可复现判据

UEFI 安装（`tests/uefi64_install_test.py`，判据本轮**加强**）：

```
U:size SYSTEM.IMG = <build64/system.img 的真实字节数>      ← 新增断言
U:payload sectors=<ceil(bytes/512)>                        ← 新增断言（原来是死的 8073）
LBA32584（主分区起点）= system.img 同偏移逐字节一致        ← 新增断言（原来只比前 4MB）
LBA<中段> / LBA<盘尾-2> 同样逐字节一致                     ← 新增断言
目标盘大小 == system.img 大小                              ← 新增断言
```

为什么旧口径不成立：旧断言是 `LBA1..64 = loader64.bin` 与 `LBA65.. = kernel64_os.bin`，
两者都落在**前 4.13 MB** 内 —— 载荷被截断时它们照样全绿（实测就是这样过的 22/22）。

## 3. 必须在真机上验证的假设（UNVERIFIED，别写进"已验证"）

1. 固件页表是否恒等映射 iGPU BAR0 / GTT MMIO（`gpu64.cpp` 与 `intel_gpu64.cpp` 裸读）。
2. 主板是否有 `EFI_EDID_DISCOVERED/ACTIVE_PROTOCOL`（`uefi64.c` 用它拿 EDID）。
3. GOP 当前模式是否 32bpp 线性 + `PixelFormat=1`（`U:bootinfo lfb=… pitch=` 行可读）。
4. LFB 是否在 4GiB 之上（`lfb64=` / `hi=` 两个字段就是给这个的）。
5. "首末页 PTE 可写 ⇒ 真可写"（当前只走页表，没有像素写回验证）。
6. 真机 E820 是否"堆顶到最高可用端连续 RAM"（`mem64.cpp` 页池按最高端一刀切，8~32GiB 只用到 ~2.16GB）。
7. PIT 250 Hz 在真机稳定（所有驱动超时都以 `g_ticks64` 为基准）。
8. Ventoy 的 UEFI 引导会不会把我们的 `EFI/BOOT/BOOTX64.EFI` 换成它的驱动器（Ventoy 有自己的链式加载路径）。

## 4. 明确未做的事

* **PixelFormat==2（BitMask）**：`fb.cpp` 全文没有掩码/BGR 处理，按 B,G,R,X 合成。
  真机若报 BitMask 且 RedMask 在低字节，颜色会红蓝互换（可见，不致命）。要修需要一条
  `fb_fmt` 分支贯穿 fb.cpp 的所有写点，工作量中，留待真机确认是否真的遇到。
* **`gpu64.cpp` MMIO 页表检查**：需要在真机上先抓到"BAR0 地址 + 页表状态"才能定口径
  （`[G64]` 打点里已经有 `mmio=ok/absent`），本轮不盲改。
* **BIOS/VBE 路径的 `int 0x10/4F15`**：`loader64.asm` 调用无法设超时；真机上是
  "固件不返回"的唯一可能点。Ventoy 默认 UEFI 引导，不经过它。
