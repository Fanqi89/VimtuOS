### 1.3 两条用户态 ABI 路径（这是理解一切的钥匙）

```
syscall 指令 ──LSTAR──> syscall64_insn_entry64 (asm)
                         └─> syscall64_dispatch64 (syscall64.cpp:3515)
                              ├─ int_no==INSM_MARK -> syscall64_linux64  【Linux 号段 103 个】
                              └─ 否则(int 0x80)     -> 自有 ABI      【lx64 号段 53 个】

自有 ABI（int 0x80）= 1..26 + 48..53：
  1 write 2 exit 3 getpid 4 ticks 5 sleep_ms 6 open 7 read 8 close
  9 fb_map 10 fb_flip 11 fb_present 12 input_poll 13 shm_create 14 shm_map
  15..21 wl_surface_create/attach/damage/commit/destroy, wl_seat_get, wl_display_dispatch
  22..26 wl_composer_get / surface_export / surface_map / surface_ack / seat_post   ← 合成器专属
  48 pci_map_bar 49 audio_play 50 dir_open 51 dir_read 52 dir_close 53 net_raw
```

两套 ABI **绝不共号**（同号语义完全不同，例如 9 在 Linux 是 `mmap`、在自有是 `fb_map`），
靠帧里的 `int_no` 区分（`syscall_entry64.asm` 填 `0x180`，`int 0x80` 门填 `0x80`）。

## 2. 盘点 B：三个加载器支持到什么程度

### 2.1 原生 ELF64（`kernel/elf64.cpp`，1665 行 / 71 KB）

| 能力 | 状态 | 证据 |
| --- | --- | --- |

| PIE / load bias | ✅ 发行版 PIE 程序能装 | `elf64.cpp:472-495`（`USER64_LOADER_BIG_TOP_VA64`） |
| 大文件分块读盘 | ✅ **16 KiB/次**（`ELF64_READ_CHUNK64`），不再一次性读全文件 | `elf64.cpp:791` |
| 文件大小上限 | 8 MiB（= `VFS64_MAX_FILE_BYTES`） | `elf64.h` `ELF64_MAX_FILE_BYTES64` |
| auxv | ✅ 全套（`AT_PHDR/PHENT/PHNUM/BASE/ENTRY/PAGESZ/HWCAP/UID/EUID/GID/EGID/SECURE/RANDOM`） | `elf64.h` 的 `E64_AT_*` |
| 并发装载保护 | ✅ `E64LoadSpan` 让出式可重入锁（v0.9.41 新增） | `elf64.cpp:1101` 段 |

**解释器窗口两档**（关键设计，决定"能不能跑动态程序"）：
```
span ≤ (4GiB+1MiB − 4GiB+576KiB) = 448 KiB  -> base = 4GiB+1MiB − span      （老档）
span 更大                                    -> base = LOADER_BIG_TOP − span （大档，5.4 MiB 窗）
```
实测：musl 的 `ld-musl-x86_64.so.1` **873,792 B** 与 glibc 的 `ld-linux-x86-64.so.2` **215,000 B**
都走大档装进来了（`[ELF64] interp path=… base=…`，无 `interp reject`）。

### 2.2 Linux ELF

**没有独立的 Linux 装载器**——它复用 §2.1 那一个，差异只在 syscall 层。
这是对的架构选择（构建期没有任何 `*lx*`/`*linux*` 内核源文件）。实测能跑：
- 静态 musl（34,496 B）✅ 退出码 0
- 静态 musl 425,608 B ❌ → 见 §5 根因①
- 动态 musl（`PT_INTERP=/lib/ld-musl-x86_64.so.1`）✅ 退出码 0
- 动态 glibc（Debian bookworm `/usr/bin/hello`，PIE + `ld-linux`）✅ 打印 `Hello, world!`

### 2.4 用户地址空间布局（**这是当前最大瓶颈，务必先看这一段**）

```
4 GiB  ┌─ USER64_CODE_VA64            用户窗口底
       │  +0         .. +64 KiB       老装载区（历史，几乎所有自研程序钉在这）
       │  +64 KiB                    USER64_STACK_VA64   用户栈 16 KiB（4 页）
       │  +256 KiB                   USER64_BRK_VA64     brk 固定区 64 KiB
       │  +576 KiB                   USER64_MMAP_VA64    ← mmap 起点（Linux 9 / vs_mmap）
       │  +1 MiB                     USER64_INTERP_TOP_VA64  解释器老档窗顶（固定）
       │  +998 MiB                   USER64_LOADER_BIG_TOP_VA64  ← 主程序/大解释器装载区顶
       │                              （1008 MiB − 8 MiB − 2 MiB）
       │  +1008 MiB                  USER64_WINDOW_BYTES64 窗口顶 = 0x13F000000
       ├─ 16 MiB 间隙（保证窗口顶严格低于 FB，两条自检与三条 static_assert 钉住）
5 GiB  └─ USER64_FB_VA64             后备缓冲映射 40 MiB
```

**硬数字**：
| 资源 | 大小 | 出处 |
| --- | --- | --- |
| 用户窗口总大小 | **1008 MiB = 1GiB − 16MiB**（v0.9.42；此前 16 MiB，v0.9.10 时 1 MiB） | `kernel/usermode64.h` |
| mmap 可用区 | **≈ 992 MiB**（+576 KiB .. +998 MiB） | 同上 |
| 主程序可装载区顶 | **+998 MiB** | `USER64_LOADER_BIG_TOP_VA64` |
| 单个 surface 像素上限 | **524,288 px**（≈ 896×585 / 1024×512） | `kernel/wl64.h:119` |
| surface 表 | **8** 槽 | `wl64.h:101` |
| 单个 shm 对象 | **2 MiB**（512 页） | `kernel/proc64.h:263` |
| 同时 shm 对象 | **8** | `proc64.cpp:245` |
| 合成器可见区 | 只有 **320×200** 的"外部面板区"（右下角，避开 Dock） | `wl64.h:107-110` |

> **结论（v0.9.42 已按这条结论修掉）**：c/c++ 现代发行版程序的 xz 字典（8 MiB）、大静态 ELF、稍大的 PE 映像，
> 当时都会撞这 5.4/6 MiB。而 4 GiB..5 GiB 之间还有 **~1 GiB 未使用的 VA** —— 所以这是**改常量**级
> 的瓶颈，不是架构问题。实测：窗口放到 1008 MiB 后，425 KB 静态 musl、8 MiB xz 字典、49 条目的 .deb
> 全部通过，**页表/物理页一个都没有预分配**（惰性分配不变，`free_pages` 不变）。
> 为什么不直接取 1 GiB：`USER64_FB_VA64 = 5GiB` 就在 PDPT[4] 顶上，两条运行时自检要求
> `FB_VA > 窗口顶`（**严格**大于），所以窗口顶必须留出间隙；取 16 MiB。

## 4. 盘点 D：图形栈现状（评估图形化 exe 用）

### 4.1 已有三层，不是从零

```
第 3 层  应用：user/browser、user/office、user/store（真 GUI 程序，跑在下面两层之上）
第 2 层  ring3 合成器：/bin/wm（user/wm/wm.c 24.8 KB + wmabi.c/wmpanel.c/wmclock.c）
         · 用 22..26 号从内核拉 surface 表、映射客户端 shm、用户态 blit/遮挡/alpha、fb_flip 上屏
         · 输入做命中测试后 wl_seat_post 投回客户端（等效 PostMessage）
第 1 层  内核：surface 表 + 提交队列 + shm 映射 + seat 路由；**一个像素都不合成**
第 0 层  fb_map(9)/fb_flip(10)/fb_present(11)：整块后备缓冲直接映射给 ring3
```

### 4.2 能直接映射成 Win32 的现成原语

| Win32 概念 | 现有落点 | 差距 |
| --- | --- | --- |
| `HWND` / 窗口对象 | `wl_surface_create`(15) → surface id | 尺寸上限 524,288 px；可见区只有 320×200、2 个槽位 |
| `BitBlt` / 绘制 | 直接写 `shm` 映射 + `wl_surface_damage/commit` | 无 GDI 对象（pen/brush/DC/region） |
| `TextOut` / 字体 | `user/lib/font64.c`（31 KB）+ `stb_truetype.h`（199 KB，真 TTF 光栅化） | 无 `CreateFont`/`LOGFONT` 语义 |
| `GetMessage`/`PeekMessage` | `wl_display_dispatch`(21) → `Wl64SeatEvent`（64 B，含路由 surface/sx/sy/inside） | 无窗口消息分类（WM_PAINT/WM_SIZE/WM_CLOSE） |
| `PostMessage` | `wl_seat_post`(26)（合成器专属） | 无自定义消息号 |

| SEH（`__try/__except`） | 无（我们有 `sig64`，两套模型） | 栈上 `EXCEPTION_REGISTRATION` 链 |

## 5. Linux 侧那 8 条红 = 2 个根因（**v0.9.42 已全部修掉**）

> **★ 修复结果（v0.9.42 实测）**：`linuxapp64_test` **36/36**（原 28/36，缺口清单已空）。
> 两个根因的修法就三处，都在既有通路上小改，没有新架构：
> | 根因 | 修法 | 文件 |
> | --- | --- | --- |
> | ① 装载区顶 6 MiB / mmap 区 5.4 MiB 太小 | 用户窗口 `16 MiB → 1008 MiB`，`LOADER_BIG_TOP` 改为由 `USER64_WINDOW_BYTES64` 推导（原来把 `16ULL*1024*1024` 写死成字面量），并加 3 条 `static_assert` 把"窗口顶严格低于 FB / 不越 PDPT[4] / 4KiB 对齐"钉成**编译期**错误 | `kernel/usermode64.h` |
> | ② `file_pool()` 一次 mmap 1 MiB 失败却报"池满" | 改成**按块增量**（每块 256 条 = 32 KiB），并把"格数用尽"与"mmap 失败"分开如实报（新打点 `chunks=` / `req=`） | `user/store/vs_pkg.c` + `vs.h` |
> | ③（顺带发现的第三处）`close(1)` 返回 -EBADF | fd 0..2 空槽 = 内核控制台虚拟标准流，close 必须成功返回 0（能 write 的 fd 不能说自己不存在）；**不再打 deny**（那是安全闸门打点） | `kernel/syscall64.cpp` |
>
> 附注：③ 的证据链在下面，它才是"Debian hello 打印成功却退出码 1"的真因 ——
> 原先我认为是 `close` 被"误报"，实测证明是**内核语义内部矛盾**：`write(1)` 成功、`close(1)` 却 -EBADF。

### 5.1 修复前的实测（保留原证据，供对照）

命令：`py -3 tools/lxcorpus_build.py`（16 项语料全建成）→ `py -3 tests/linuxapp64_test.py --keep`
结果：**`checks=36 ok=28 fail=8`**

### 根因①（v0.9.42 已修）：主程序装载区顶 6 MiB，撞上 425 KB 程序的 4 GiB+8 MiB

```
[ELF64] exec reject segment va=0000000100800000 reason=outside-user-window
run: /lxcorpus/bighello.elf pid=27 exited code=127
```
- `bighello.elf` 的 5 个 `PT_LOAD` 落在 `0x100800000 .. 0x100867228`（= 4 GiB + 8 MiB 起）；
- 装载器允许的主程序区顶 `USER64_LOADER_BIG_TOP_VA64` = **4 GiB + 6 MiB**；
- 于是"想验的是读盘上限"，**实际撞的是装载区顶**——读盘上限（8 MiB）+ 分块读（16 KiB）本身**是好的**。
- 结论：**测试夹具与装载器上限错位**，但两边都该改；产品侧正确解法是**把装载区顶抬到接近 16 MiB 顶**
  （给 mmap/dev-shm 留 2 MiB 足够），或干脆按 §2.4 扩整个窗口。

### 根因②（v0.9.42 已修）：`file_pool()` 一次 mmap **1 MiB** 失败（`used=0` 却报 pool full）

`user/store/vs_pkg.c:840-844`：
```c
static char (*file_pool(void))[VS_FILE_MAX] {
    if (!g_file_pool)
        g_file_pool = vs_mmap(sizeof(char[VS_FILE_MAX]) * VS_FILE_POOL_MAX);  // 128 × 8192 = 1 MiB
    return g_file_pool;                                                       // 失败返回 NULL
}
```
`vs_inst_file_add` 的 `if (!file_pool()) return VS_E_NOMEM;`（`:861`）→ 打点 `used=0 cap=8192` 报满。
`vs_mmap` 走内核 `mmap(9)`，而 **mmap 可用区只有 ≈5.4 MiB**，且 `vs_mmap` 是 bump 分配**不回收**；
一次装包已经吃掉了：包缓冲 56 KB + xz 输出 256 KB + **xz 声明的 8 MiB 字典**（`dict=8388608`）+ 缓存表，
1 MiB 的池请求自然失败。

### 根因③（v0.9.42 新增发现并已修）：能 write 的 fd 却 close 不了

修复前三段式真证据（`gnuhello` 那一次运行的完整串口原文）：
```
[SYSCALL] insn nr=1  rdi=1 … rdx=0xE ret=0xE        <- write(1,"Hello, world!\n") 成功
[SYSCALL] deny nr=3  arg=1                          <- close(1) 拿 -EBADF
/lxcorpus/gnuhello: write error: Bad file descriptor  <- glibc 的 _IO_cleanup 抱怨
[SYSCALL] insn nr=231 rdi=1                         <- exit_group(1)
```
即：**打印成功了，退出码却是 1**。根因不是"glibc 太挑剔"，也不是"close 被误报"，
而是内核自身的矛盾 —— `write(1)` 落到内核控制台并成功，`close(1)` 却说"没有对象可关 -> -EBADF"。

修法：fd 0..2 的空槽 = **不可关闭的内核控制台流**，close 幂等成功返回 0（不再打 deny）。
取舍如实写清：close 之后 `write(1)` **仍然**可用（a42a64 探针的 `write1_after_close=34` 钉住这条，
本批**没有改它**）。即"关一个不可关的特殊流"，不是真关闭。
配套把 `tests/a42a64_test.py` 的 `close_stdin_unbound` 期望由 `-9` 改为 `0` 并写明理由
（那条期望本身就是旧实现的直译，属于**测试假设随产品语义修正**，不是放宽判据）。

### 两个根因（+ 第三个）的统一解释

> **都是"用户窗口 16 MiB 切得太紧"的同一个后果。**
> 这正是我上版路线图 **L3** 写的东西（"放宽用户窗口，从 0x100010000 扩到几十 GiB"）——
> 当时只做了一半（1 MiB → 16 MiB），够跑 musl/glibc hello，不够跑大 ELF 与大 .deb。
> 而 4 GiB..5 GiB 之间有 **~1 GiB 空闲 VA**，所以这是**改常量 + 扩页表**级的改动，不是重写。

## 6. 架构蓝图

### 6.1 总原则（沿用既有纪律，不破例）

1. **文件系统/格式解析器不拿 ring0 权限**：PE 解析、IAT 填充、Win32 API 桩全部在 **ring3**。
   内核只提供三样：`mmap`（映射节）、`mprotect`（段权限）、进 ring3 的入口。
   → 这条已有先例：`ext4` 解析在 ring3 服务（`user/drivers/ext4svc.c`），内核只转发。
2. **ABI 号只许追加**：Win32 需要的新 syscall 用私有号段续（现有 1024..1036），**绝不改既有号**。
3. **不假 Linux/Win 兼容**：拿不到的语义如实返回专门错误码（沿用 `VS_E_*` / `WL64_E*` 风格）。
4. **判据只许加强**：每条"缺口已修"的断言必须带**失败原文**，不许用"能跑就行"。

### 6.2 Windows 侧：三层结构（而不是"一个 loader"）

```
┌──────────────────────────────────────────────────────────────┐
│ 第 3 层  Win32 实现库（ring3，纯 C，链接进加载器）              │
│   kernel32 子集 / user32 子集 / gdi32 子集 / msvcrt 子集       │
│   · user32/gdi32 的实现体 = 调 wl_*(15..21) + shm 直写像素     │
│   · 每个导出函数用 **Win64 调用约定**（RCX/RDX/R8/R9 + 32B 影  │
│     子空间），由 IAT 直接绑到这些本地实现（**不造真 DLL 文件**） │
├──────────────────────────────────────────────────────────────┤
│ 第 2 层  PE 加载器 + Win32 进程环境（ring3，新增 user/win/）    │
│   · 映射节、DIR64 重定位、**IAT 填充**、TLS 回调、资源段只读索引 │
│   · 每进程造一块 **TEB/PEB** 并写 IA32_GS_BASE（需内核加一条     │
│     "设 GS.base" 的私有 syscall，与现有 158 号 FS.base 对称）    │
│   · 异常：SEH 链 → 最小实现（只支持 `__try/__except` 一层）      │
├──────────────────────────────────────────────────────────────┤
│ 第 1 层  内核（**只加 3 个能力**，不含任何 PE 知识）            │
│   ① 设 GS.base 的私有 syscall（对称于 158 的 FS.base）          │
│   ② mmap 支持"按 PE 节的 ImageBase 偏好地址"映射（已是 bump，需  │
│      加"指定基址 + 冲突检测"）                                  │
│   ③ 用户窗口扩容（§2.4，与 Linux 收尾共用）                      │
└──────────────────────────────────────────────────────────────┘
```

**为什么 IAT 直接绑本地实现、不造真 DLL**：
"极简 exe 单文件小程序"99% 的导入都是 `kernel32/user32/gdi32/msvcrt` 四个系统 DLL。
把这四个名字做成**内置表**（`{"User32.dll","user32.dll"}` 大小写不敏感 → 本地导出表），
`LoadLibraryA("kernel32.dll")` 返回一个假句柄，`GetProcAddress` 查同一张表——
就绕开了"实现一个 PE 格式 DLL 加载器 + 导出表 + 转发器"这整块工作。
真第三方 DLL 等以后再说（可在 W5 之后）。

**★ 实测抓到的真缺陷（已修）**：`peinfo` 一开始**每输出一小段就 write 一次**，而内核在每次
`write` 返回时打一行 `[SYSCALL] insn nr=1 …`，于是 `[PEINFO] nt machine=` 与它的值之间被
内核日志插进去 —— 整行被切成碎片，人看不到、测试也读不出来（第一次跑 17 条红全是这个）。
`union` 那一行之所以完好，正因为它是一次大块 write（这反过来证明解析本身是对的）。
修法：**行级缓冲**（攒到 `\n` 或 4 KiB 满才 flush，一次 write 一整行）。
