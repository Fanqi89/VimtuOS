## 1. 需求与落地映射

| 需求 | VimtuOS 中的实现 |
|---|---|
| 重启流程 RUNNING→STOPPING→STOPPED→STARTING→READY | `kernel/sysstate.cpp` 状态机 + 模块表；由 `sysctl` 任务驱动（`sys_stage_tick()`） |
| 触发方式：按钮 / API / 定时 / 更新后 | 开始菜单・任务管理器・设置页；`sys_request_restart()`；int 0x80 `SYS_RESTART(4)`；终端 `restart --in N`；`update`（`/sys/update.pending`）自动重启 |
| 关闭阶段：拒收新请求、通知模块、状态落盘、关句柄、超时强杀 | `begin_stopping()`：置停靠标志（GUI/监视器停靠、输入闸门丢弃按键）→ 逆序 `stop()` → `session_save()/config_save()/heap_audit()` → 超时 `force_kill_module()` |
| 停止状态：内存/窗口/任务清空，磁盘数据保留 | `STOPPED` 阶段：窗口全销毁、任务可结束、ramfs 的 `/sys`（配置、会话快照）保留 |
| 启动阶段：拉起、重读配置、连子系统、自启、健康检查、ready | `stage_starting()`：逐模块 `init()`（带重试）→ 自启项 → `[READY]` + `[HEALTH]` |
| 对外表现：短暂不可用、自动恢复、日志 shutdown/boot、健康 down→up | 全屏重启页 + `[STAGE]/[BOOT]/[HEALTH]` 日志（debugcon 0x402 → `debug.log`） |
| 软件内容不保存（关闭/重启后不保留上次输入） | `kernel/session.cpp` 会话策略：`session_app_closed()` / `session_reset_all()`；每个应用一个 `reset` 钩子 |
| Windows 10 任务管理器 | `kernel/taskmgr.cpp`：进程 / 性能 / 启动 / 详细信息 四页 + 结束任务 |

## 2. 状态机

### 2.1 系统级

```
冷启动:   [STOPPED] → STARTING → READY → RUNNING
重启:     RUNNING → STOPPING → STOPPED → STARTING → READY(→RUNNING)
硬重启:   … STOPPED → 重启页 → 8042/0xCF9 复位 → 重新引导（日志里 shutdown/boot 成对）
```

* `READY→RUNNING`：完成可用性校验并受理第一个交互（窗口或按键）。
* `RUNNING→READY`：全部窗口关闭且空闲 10 秒（休眠态，仍受理输入与重启请求）。
* 每个模块另有与系统同构的子状态：`MOD_RUNNING→MOD_STOPPING→MOD_STOPPED→MOD_STARTING→MOD_READY`，
  用于"单个服务/任务"作用域（`RM_TASK`/`RM_APP`，见 `sys_request_restart()` 的模式参数）。

### 2.2 模式与原因

| 模式 | 落地 |
|---|---|
| `RM_SOFT` 软重启 | 内核内重建"外壳 + 应用"（不退出 QEMU）；平台层（fb/mem/font/input/x86/sched/sysctl）保持 |
| `RM_HARD` 硬重启 | 走完停止阶段后 8042 0xFE → 0xCF9 → 三重故障；等同 Windows 重启 |
| `RM_SHUTDOWN` 关机 | 同上，最后 ACPI 0x604 断电 |
| `RM_TASK` / `RM_APP` | 任务管理器"结束任务"、模块级重启（细粒度同构状态机） |

原因（`RestartReason`）：`user` / `api` / `timer` / `update` / `recovery` / `panic`，会写进日志与重启画面页脚。

## 3. 模块接口与顺序

```cpp
struct SysModule {
    const char* name;
    uint8_t flags;                 // MOD_CRITICAL | MOD_PLATFORM | MOD_RESTARTABLE
    int  (*init)();                // 0=ok, <0=fail（按 retry_max 重试）
    int  (*stop)(uint32_t deadline);// 0=ok, -1=fail, -2=timeout, -3=仍在进行中（继续等）
    bool (*health)();
    uint16_t timeout_ticks;        // 单模块停止超时（1 tick = 10ms）
    uint8_t  retry_max;            // 启动重试次数
};
int sys_register_module(const SysModule* m);
```

**启动正序（= `kModules[]` 数组顺序）**：

| # | 模块 | 标志 | 超时 | 重试 | 软重启是否保留 |
|---|---|---|---|---|---|
| 0 | fb | 平台·关键 | 50 | 1 | 保留 |
| 1 | mem | 平台·关键 | 50 | 1 | 保留（停止时做堆审计） |
| 2 | vfs | 可重启 | 100 | 1 | 拆（保留 /sys 系统文件） |
| 3 | font | 平台·关键 | 50 | 1 | 保留 |
| 4 | lang | — | 20 | 1 | 重建（从 config 读语言） |
| 5 | config | 可重启 | 50 | 2 | 重建（保存/读取系统设置） |
| 6 | session | 可重启 | 50 | 1 | 重建（保存会话策略） |
| 7 | input | 平台·关键 | 50 | 2 | 保留（停止时清空输入队列） |
| 8 | x86 | 平台·关键 | 50 | 1 | 保留（否则没人再拉起调度器） |
| 9 | task | 平台·可重启 | 100 | 1 | 保留（停止时回收任务槽位） |
| 10 | bootui | — | 20 | 1 | 重建（开机动画只在冷启动播放） |
| 11 | gui | 可重启·关键 | 200 | 2 | 重建窗口管理器/桌面 |
| 12 | apps | 可重启 | 200 | 2 | 关闭所有应用窗口并触发会话清理 |
| 13 | monitor | 可重启 | 50 | 1 | 结束并重建监视器任务 |
| 14 | sysctl | 平台·关键 | 50 | 1 | 保留（它是状态机的执行者） |

**关闭阶段严格逆序**（14 → 0）。平台上模块在软重启时输出 `retained (platform)` 并跳过 stop。

## 4. 超时 / 异常 / 重试 / 幂等

* **超时**：每个模块停止时带 `deadline`；`stop()` 返回 `-3` 表示"还在进行"，状态机每 tick 复查，超过
  `timeout_ticks` 记 `[MOD] xxx stop TIMEOUT -> force kill` 并执行 `force_kill_module()`（窗口直接销毁、
  任务从就绪环摘除并释放栈）后继续，不会卡死流程。
* **异常**：关键模块停止失败（`RM_HARD`）→ 蓝屏 `REBOOT_CRITICAL_FAIL`；关键模块启动重试耗尽 →
  先降级为硬重启（3 次以内），仍失败才 `INIT_FAILED` 蓝屏；非关键模块失败 → `MOD_DEGRADED`，
  系统照常 READY，健康检查显示 `DEGRADED`。
* **重试**：`init()` 失败按 `retry_max` 重试（间隔 50ms），日志 `[RETRY]`。
* **幂等**：①`g_stage_busy` 保证状态机非重入；②请求已排队或状态非 READY/RUNNING 时重复请求一律
  `[REQ] ignored(busy)`（终端 `restart --twice` 可验证）；③每模块带子状态，重复 stop/init 无副作用；
  ④`gen` 代次贯穿日志。
* **看门狗联动**：停止阶段 `wd_suspend()`（GUI 已停靠，不会踢心跳），READY 后 `wd_resume()`，
  避免状态机被自己的看门狗打成蓝屏；蓝屏自动重启也改走同一状态机（`RR_PANIC`）。
* **阶段看门狗**：单阶段超过 10 秒 → `STAGE_STUCK` 蓝屏。
* **复位链**：8042 `0xFE` → PCI `0xCF9`（0x02/0x06）→ 三重故障（`lidt 0; int3`）；关机链：
  ACPI `0x604` → 回落 8042 复位 → 仍失败 `SHUTDOWN_FAILED`。

## 5. 会话策略（"软件内容不保存"）

VimtuOS 的应用是内核内窗口（不是进程），因此"软件内容"= 应用窗口持有的状态：

| 应用 | 内容 | 默认策略下的行为 |
|---|---|---|
| 计算器 | 输入缓冲/累积值/运算符 | 关窗即清 → 重开显示 `0`（不再保留上次的 `1+1`） |
| 扫雷 | 棋盘/难度/计时 | 关窗即清 → 重开是新棋盘 |
| 终端 | 屏幕缓冲与当前命令行 | 关窗即清 → 重开是干净提示符 |
| 任务管理器 | 选中页/选中行/下拉 | 关窗即清 |
| 设置 | —（属于系统设置，不清理） | 系统设置（分辨率/刷新率/缩放/语言/图标位置/自启项）始终保留 |

* 实现：`session_register_app(name, keep_key, reset_fn)` 登记；关闭窗口时 `session_app_closed(id)`，
  停止阶段 `session_reset_all()`；日志证据 `[SESSION] reset app=Calculator reason=close|restart`。
* 策略开关：设置 → **会话 / 应用** 页（全局 `不保存/保存` 单选 + 每个应用"保留内容"复选 +
  `立即清除所有应用数据` + `仅重启外壳（软重启）`）；也可用终端 `session` 查看、`cfg` 查看系统设置。
* 边界（重要）：ramfs 位于内存，因此**软重启**能保留系统设置与策略，**硬重启/断电**后回到默认值。
  要做"硬重启也保留"，需要给内核加可写磁盘驱动（ATA PIO）+ 简单文件系统，属后续工作。

## 6. Windows 10 任务管理器

窗口 780×500（含标题栏），Win10 视觉：顶部菜单行（文件/选项/查看/帮助）、标签行
（进程/性能/启动/详细信息，选中页下 3px 蓝条）、内容区、底部状态栏。

* **进程页**：分组「应用 (N)」= 打开的窗口；「后台进程 (N)」= 内核任务（`TCB`）。
  列：色块图标 / 名称 / 状态 / CPU% / 内存；CPU 单元格按 0、1-9、10-39、≥40 四级热力着色；
  行高 22，悬停浅灰、选中浅蓝；底部「结束任务」。
* **性能页**：CPU 曲线（60 个采样点、1 秒/点、白底网格 + 深蓝折线 + 半透明填充）、内存曲线；
  信息区：CPU 型号 `VimtuOS Virtual CPU (i686) @ 100MHz`、内核数/逻辑处理器、利用率、运行时间、
  进程数/任务数/窗口数/内核堆、上次重启原因与代次。
* **启动页**：系统监视器 / 桌面图标服务 / 健康检查与状态机 三行，可启用/禁用（写回 config，真实生效）。
* **详细信息页**：PID / 名称 / 状态 / CPU 时间(秒) / CPU% / 内存(KB) / 起始 tick，底部「结束任务」。
* **结束任务**：应用 → 关窗 + 会话清理；内核任务 → `task_kill_by_id()`（协作式，任务在检查点 `task_exit()`）；
  gui/sysctl/idle 等关键任务拒杀并显示「拒绝访问：无法结束关键进程」。
* **入口**：开始菜单「任务管理器」（第 7 项）、快捷键 `Ctrl+Shift+Esc`、任务管理器"文件"菜单
  （运行新任务/软重启/重启系统/关机/退出）。
* **数据都是实测**：任务 CPU% 来自调度器每 tick 累加 `cpu_ticks_total`；窗口级 CPU 来自 `rdtsc` 包裹
  draw/key/click 回调；内存来自 `kmalloc` 归属记账（`mem_owner_bytes()`）。
* 键盘：`←/→` 切页、`↑/↓` 选行、`Enter`/`Delete` 结束任务、`F5` 刷新、`Esc` 关闭。

## 7. 触发方式汇总

| 触发 | 入口 | 日志 |
|---|---|---|
| 用户按钮 | 开始菜单重启/关机、任务管理器文件菜单、设置页软重启按钮 | `[UI] reboot button -> state machine rc=0` |
| API（内核内） | `sys_request_restart(mode, reason)` | `[REQ] queued/accepted` |
| API（用户态预留） | int 0x80 `SYS_RESTART`，ebx=mode(0软/1硬)，ecx=reason | 同上 |
| 定时任务 | 终端 `restart --in 15`（`sys_request_restart_in()`） | `[REQ] scheduled in 15s` → `[REQ] timer fired` |
| 更新后自动 | 终端 `update` 写 `/sys/update.pending`；READY/RUNNING 巡检发现即重启 | `[UPDATE] pending update applied -> restart` |
| 故障恢复 | 蓝屏自动重启（`RR_PANIC`）、软重启连续失败升级硬重启 | `[PANIC] auto restart requested` |

## 9. 本次修复的真实内核缺陷（重要）

1. **协作式 yield 的栈帧错位**：`task_switch_yield` 的帧上方多压了 `call` 返回地址，iret 恢复后
   `ret` 弹出 eflags（0x203）→ Invalid Opcode。已改为 `task_yield()` 用"等一个 tick"的抢占式让出。
2. **中断重入破坏切换帧**：保存上下文期间允许 PIT 抢占会覆盖帧槽位，现切换期间保持关中断。
3. **就绪环被破坏导致状态机饿死**：任务退出时未摘链 + 新任务插入依赖会过期的 `ready_head`，
   monitor 重建后把 `sysctl` 挤出环外 → 软重启永久卡在 STARTING。现在环锚点固定为 idle，
   单链插入 + 退出/强杀必摘链。
4. **睡眠任务仍是 ready**：`task_sleep_ticks` 只 hlt 不改状态，睡着的任务被反复调度、
   且会饿死 idle（=冷启动序列）。现睡眠标记 `blocked`，由调度器按 `wake_tick` 唤醒。
5. **复位不清 RAM**：CPU/8042 复位不会清 `.bss`，硬重启后模块表/GUI 状态是上次残留
   （表现为 GUI 任务不再创建、模块表越界、屏幕全黑、健康 DOWN）。现在 `_start()` 第一件事就是清 `.bss`
   （`linker.ld` 提供 `__bss_start/__bss_end`）。
6. **日志被并发拆散**：多字符标记（如 `K:tasks created`）会被任务抢占切成两半，无法用于断言。
   现在 `sys_log/dbg_out` 原子输出（保存并恢复中断状态）。
7. **菜单选中项残留**：开始菜单关闭后未重置选中项，同样的按键序列会落到别的菜单项。
8. **超时注入被提前消费**（测试钩子）：`g_test_timeout_mod` 在处理其它模块成功时被清掉，
   改为"超时真正触发时才消费"。

## 11. 已知限制与后续工作

* 硬重启/断电不保留系统设置（需要可写磁盘驱动 + 文件系统）。
* "结束任务"是协作式的（任务在自己的循环检查点退出）；真正异步杀任务需要用户态进程与地址空间隔离。
* 任务管理器"应用历史记录/服务/用户"页未实现（本机没有对应概念，做了会是假数据）。
* 性能页的磁盘/以太网分区仅占位（无块设备与网络栈）。

## 13. 关键实现

### 13.1 鼠标跟手与脏矩形渲染（需求 1）

* 主循环频率从 22Hz 提升到 **162Hz**：`gui` 任务用 `task_set_slice(pid, 8)` 放大时间片、去掉每帧 `hlt`、
  把 `sysctl` 轮询压到 50ms、`monitor` 压到 100ms；单帧渲染耗时 `frame_us` 实测落在约 1.7~17ms。
* 只把变化区域提交到帧缓冲：窗口移动/缩放/动画、任务栏时钟、开始菜单各自 `gui_dirty()`。
* 空闲 5 秒实测：**整屏提交 0 次（fullflip 31→31），局部提交 +12（region 74→86）** —— 无交互时桌面几乎不重绘。
* 判据（`perf` / `[PERF]`）：`region` 应远大于 `fullflip`，且 `loop` 数量级在百 Hz 以上。

### 13.2 秒级时钟与时间基（需求 2）

* `kernel/timebase.{h,cpp}`：以 PIT 中断为唯一定时源推进时分秒，RTC 只在初始化与每 10 秒重同步时读取；
  重同步只消除 PIT 累积漂移，不跳变（按“真实秒 - 已运行秒”重算基准）。
* 实测 `rtc_reads=10`（启动至今累计），证明时钟不再每帧访问端口（此前的每帧读 RTC 是跟手性瓶颈之一）。
* 任务栏时钟不再使用镜像绘制（文字正向绘制，方向与读数都正确）。

### 13.3 任务管理器数据实时（需求 3）

* 客户区按 250ms 脏刷新：只有数据变化时才提交脏矩形，页面渲染不再依赖整屏重绘。
* 进程数 / CPU% / 内存均来自真实采样；配合需求 5，CPU 型号与机器名不再使用占位串。

### 13.4 硬重启/断电保留设置（需求 4）

* 分层：`kernel/ata.{h,cpp}` 提供 ATA LBA28 PIO 读写与 `IDENTIFY` 能力；`kernel/store.{h,cpp}` 在其上做记录。
* 保留区：镜像尾部 **LBA 5056..5119**，A/B 双副本，每条记录带 CRC32 与 seq，交替写入；掉电最多丢掉最后一次写入。
* 写盘时机：`cfg_set` 标脏 → `store_poll` **2 秒去抖**落盘（由 `sysctl` 周期调用）；`cfg save` 与停止阶段 `store_save()` 立即写。
* 镜像从 4608 扇区扩到 **5120 扇区（2.5MB）**，尾部留给保留区（`build.ps1`）。
* 验收实测：`set display.zoom 125` / `set lang 1` / `cfg save` → `[STORE] saved seq=1 slot=A` → 硬重启 → `[STORE] loaded seq=2`。

### 13.5 硬件型号如实显示（需求 5）

`kernel/hwinfo.{h,cpp}`：CPUID 品牌串 + TSC 校准频率（配合 PIT）+ PCI 枚举 + E820 可用内存 + ATA 磁盘。
QEMU 实测（`hw` 命令 / `[HW]` 日志）：`cpu="QEMU Virtual CPU version 2.5+" mhz≈3614 cores=1`、`gpu=QEMU Standard VGA`、
`disk="QEMU HARDDISK" 5120 扇区 2MB`、`ram≈127MB`、`pci=6`。

### 13.6 应用多开（需求 6）

* 上限：计算器 ≤8、扫雷 ≤4、终端 ≤4、任务管理器 ≤4；达到上限后再“打开”只激活同类最近实例，不新建窗口。
* 实例状态统一挂 `Window::userdata`：关窗时由窗口层自动 `kfree`，关闭单个实例不再清空同类其它实例（会话清理只针对被关的那个）。
* 同类第 2 个实例起窗口依次偏移 **+26/+22**，并在标题上加序号。实测两个实例几何 `(150,80,255,292)` 与 `(176,102,255,292)`。

### 13.7 自由缩放与最大化动画（需求 7）

* 八向边框拖拽缩放，边框命中区 6px；拖拽结束把尺寸写回 `cfg_win_w/h`，下次开窗沿用。
* 双击标题栏 = 最大化/还原；最大化、还原、最小化走同一套 160ms 缓动动画（`begin_geom_anim()` 起动画，`g_anim_frames` 计帧）。
* 实测：拖右下角 +204x+153 → `[UI] resize app=1 x=150 y=80 w=459 h=445`；双击标题栏 → `[UI] max app=1 x=0 y=0 w=1024 h=736`；
  点最大化按钮 → `[UI] restore app=1 x=150 y=80 w=459 h=445`（几何与最大化前完全一致）。

### 13.8 表述统一（需求 8）

* 全篇口径统一：**功能与类型如 Linux**（shell 命令语义、`/sys` 虚拟路径、进程与调度、目录/文件语义），
  **系统界面为 Windows 风格**（开始菜单 + 任务栏 + Win10 风格任务管理器 + 窗口标题栏按钮/双击最大化/边框拖拽缩放），内核为“全手搓自研、无第三方内核代码”。
* 两条口径不冲突：前者说的是**系统类型与功能语义**，后者说的是**图形界面的外观与交互习惯**。

## 15. 本轮缺陷与修复（6 条 + 验收脚本 3 条）

### 15.1 缺陷总表（内核/界面 5 条 + 验收链路 1 条）

| # | 现象 | 根因 | 修法 | 影响 |
|---|---|---|---|---|
| 1 | 光标乱跳：从 (512,384) 跳到 (727,169)，甚至飞出屏幕 | `kernel/input.cpp` 的 `mouse_irq` 每中断只读 1 个字节；8042 输出缓冲积压时丢字节，3 字节包边界错位，解析出 ±127 的假包 | 一次中断循环读空输出缓冲（判断状态端口 0x64：bit0 有数据 + bit5 数据来自鼠标），与键盘 handler 早已采用的“循环读空”写法一致 | 鼠标跟手性与自动化可测性（点选精度） |
| 2 | 终端窗口不响应 Esc，而计算器/扫雷/设置都用 Esc 关窗，行为不一致 | `kernel/terminal.cpp` 的 `term_key` 只处理 `\n`、`\b`、`c>=0x20`，Esc 被忽略 | `term_key` 增加 `if (c == 0x1B) { terminal_close(); return; }` | 四个应用的关窗方式统一 |
| 3 | 窗口几何不可观测：自动化只能靠像素猜 | 窗口移动/最大化/还原没有日志，原有缩放日志缺 x/y | 新增 `[WIN] new`、`[UI] move`、`[UI] max`、`[UI] restore` 日志，并给 `[UI] resize` 补上 x/y | 几何类用例可精确断言 |
| 4 | 开始菜单开/关状态不可观测 | “菜单是否打开”只有像素可判，而窗口会盖住采样点；也没有状态日志 | 新增 `[UI] start menu open/closed (why)`（why ∈ win/btn/activate/esc/outside/reset） | 菜单类用例可断言，不再依赖像素 |
| 5 | 最大化窗口上双击标题栏“还原”时，第一次按下就已静默还原并进入拖拽态：没有 `[UI] restore` 日志、也没有还原动画 | 沿用 Windows 式“按下标题栏准备拖拽”的行为（最大化状态下按下即还原） | 记录当前行为；自动化改用“点最大化按钮”验证还原（该路径有动画与日志） | 双击标题栏的还原路径不可自动断言（见第 18 节） |
| 6 | 本轮验收把批次二的功能判成“假失败 / 假通过”（3 处，见 15.2） | 验收脚本读固定日志文件、`expect` 会匹配历史日志、鼠标助手假设“内核不放大位移” | 改读当前实例日志；`expect` 只匹配本次调用之后的新增日志；点击类用例改为“截图像素反解光标位置 + 闭环逼近”（详见 15.2） | 验收结论的可信度：否则真实缺陷会被误判为通过，正常功能会被误判为失败 |

### 15.2 验收脚本自身的三处缺陷（`_vt_smoke.py`）

| # | 现象 | 根因 | 修法 |
|---|---|---|---|
| a | T11 读到陈旧日志，断言失真 | 断言读的是固定的 `debug_smoke.log`，而持久化用例跑在写盘副本上（日志是 `debug_persist.log`） | 断言改读**当前实例**的日志 |

## 18. 已知遗留风险

1. **TSC 校准偏小**：校准受 4ms tick 粒度影响，频率系统性偏小约 8%；`mhz` 只作参考值，不做绝对精度承诺。
2. **`g_uptime_ms` 回绕**：32 位毫秒计数约 49.7 天回绕（表现为运行时间/时钟基准跳变）。
3. **ATA 写盘期间关中断时间较长**：PIO 轮询在 `cli` 区域完成，落盘窗口内的输入延迟不可忽略（表现为偶发一次点击迟滞）。
4. **保留区会被重建清空**：镜像尾部保留区被 `build.ps1` 重建清空，所以“断电保留”依赖运行期不重建镜像（重建后回到默认值）。
5. **最大化窗口双击标题栏的静默还原**：该路径没有日志与动画（见 15.1 第 5 条），只能用最大化按钮验证。

## 20. 定位口径呼应（§13.8）

* 与 §13.8 完全一致、不冲突：**功能与类型如 Linux**（POSIX 风格 shell、`/sys` 虚拟路径、进程/调度/文件语义），
  **系统界面为 Windows 风格**（开始菜单、任务栏、Win10 风格任务管理器、窗口标题栏按钮/双击最大化/边框拖拽缩放）；
  内核为**全手搓自研、无第三方内核代码**。
* 本批次的两处体现：①显示页的呈现方式沿用 Windows 设置页外观（左导航 + 右侧内容区），
  数据则一律来自内核自述（类 Linux 的“设备信息由内核给出、工具只负责显示”）；
  ②分辨率/刷新率是**硬件现状**，页面上做成**只读字段**，不做假切换（运行期不改模式，见第 24 节）。

## 21. 关键实现

### 21.1 新模块与数据通路（`kernel/display.{h,cpp}`）

* 模块表：本批次新增 `display`（批次一 15 项 + 批次二 4 项 + 本批次 1 项，表内共 **20 项**）；源码顺序在
  `timebase`/`hwinfo` 之后、`gui` 之前（`kernel/kernel.cpp` 第 274~276 行）——它需要 PIT tick、fb 与 `cfg_set`。
* 对外接口：

| 类别 | 接口 |
|---|---|
| 实际画面参数 | `disp_width()` / `disp_height()` / `disp_bpp()` / `disp_pitch()` / `disp_mode_num()` |
| 模式清单 | `disp_mode_count()` / `disp_mode_at(i)`（`BootMode`：模式号/宽/高/色深） |
| 实测刷新率 | `disp_refresh_x10()`（×10）/ `disp_refresh_valid()` |
| EDID | `disp_edid_valid()` / `disp_edid_native_w()` / `disp_edid_native_h()` / `disp_edid_refresh_x10()` / `disp_edid_mfg()` / `disp_edid_name()` |
| 报告 / 轮询 / 格式化 | `disp_report()` / `disp_log_summary()` / `disp_poll()` / `disp_fmt_hex()` / `disp_fmt_hz()` |

* 数据通路（loader → 内核）：`boot/loader.asm` 在 VBE 探测阶段把**真实可用模式**（分辨率 + 色深，最多 16 项、
  每项 8 字节）收集到 `0x7400`；并用 **VBE/DDC（int 10h `4F15` BL=01）** 读 128 字节 EDID 到 `0x7600`
  （失败则 `edid_ok=0`）。`bootinfo.h` 的 `BootInfo` 新增：`mode_num`(0x1C)、`mode_count`(0x1E)、
  `mode_list`(0x20)、`edid_addr`(0x24)、`edid_size`(0x28)、`edid_ok`(0x2A)。
* `disp_poll()` 由 `sysctl` 周期调用（`kernel.cpp` 第 145 行）：一次端口读 + 比较，仅在回扫可计时（真机）时才计数。

### 21.2 按显示器自适应选模式（核心）

* `mode_score`（`boot/loader.asm`）在有 EDID 时：只考虑 **32bpp 且不超过显示器原生分辨率**的模式，
  分数 = **宽×高/1024**（面积越大、越接近原生越优）；其它情况给最低分 **1**，保证仍能选出可用模式
  （不会出现“一个模式都选不中”）。无 EDID 时回退到原有固定优先表（1024x768x32 → 800x600 → …）。
* 实测（QEMU 11.1 + `-vga std`，EDID 默认开启）：EDID 报显示器原生 **1280x800@75**（厂商 `RHT`、
  型号 `QEMU Monitor`）→ loader 选中 **VBE 模式 0x17a = 1280x800x32**，系统实际就以 1280x800 输出
  （帧缓冲行跨距 5120 = 1280×4）。

### 21.3 刷新率来源优先级（`kernel/display.cpp`）

按“能测到什么就用什么、绝不伪造”排优先级：

| 优先级 | 来源 | 采用条件 | 日志（实测） |
|---|---|---|---|
| 1 | **EDID 详细时序** | 其原生分辨率与当前输出一致（此时该时序就是当前模式的时序） | `[DISP] refresh=74.9Hz source=edid clk=107300kHz htotal=1728 vtotal=828` |
| 2 | **0x3DA 垂直回扫计数**（真机路径） | 边沿率落在 10..300Hz | `[DISP] refresh=…Hz source=vretrace frames=… window=…ms` |
| 3 | **CRTC 时序寄存器推算** | 必须先通过自洽检查（CRTC 的水平/垂直显示尺寸与当前实际分辨率一致） | `[DISP] refresh=…Hz source=crtc clk=…kHz htotal=… vtotal=…` |
| 4 | 都不成立 | — | 如实报 `[DISP] refresh n/a (…)`，**绝不伪造** |

* 公式：刷新率 = 像素时钟 ÷ (水平总周期 × 垂直总周期)。EDID 详细时序里的 htotal/vtotal 已经是像素；
  CRTC 寄存器里的 htotal 单位是 8 像素字符（验收脚本按来源区分单位），vtotal 需 +2。
* 实测：EDID 标称 75Hz，按 `clk/(htotal×vtotal)` 精确算出 **74.9Hz**（107300kHz ÷ (1728×828)）。
* 重绘节流：`gui.cpp` 主循环改用**实测刷新率**（`disp_refresh_x10()`；未测出退回 `cfg_hz()`，再不行按 60Hz 兜底），
  输入处理不受节流限制。

### 21.4 启动自适应写系统设置

* `disp_auto_apply()`（一次启动只做一次）按实测值写 `display.width/height/bpp/mode`，缩放 `display.zoom` 按实际
  分辨率自动选定：高度 ≥1600 → 150、≥1200 → 125、≥900 → 110，否则 100；刷新率未测出时**不写**
  `display.refresh`（不伪造）。
* 实测：`[CFG] disp auto width=1280 height=800 refresh=75 zoom=100`。

### 21.5 设置页改造（`kernel/gui.cpp`）

* **显示页**（系统设置 → 显示，page 1）现在显示：

| 字段 | 来源 | 说明 |
|---|---|---|

## 22. 本批次缺陷与修复（5 条）

| # | 现象 | 根因 | 修法 |
|---|---|---|---|
| 1 | QEMU 的 0x3DA 不能用回扫计时 | 实测 350952 次采样得到 175476 个“边沿”（= 读速率）：QEMU 的 VGA 每次读该端口都会翻转状态位 | 只在边沿率合理（10..300Hz，真机情形）时采用回扫计数，否则走其它来源；把 `not usable (read-toggled)` 写进日志作为证据 |
| 2 | CRTC 时序推算会给出错值 | QEMU 的 stdvga 在 VBE 直帧缓冲模式下并未按时序编程 CRTC（读出来仍是旧文本模式的值：水平总周期 100 字符 × 垂直总周期 449 行 → 会算出 78.8Hz 的错误刷新率） | 加自洽检查（CRTC 的显示尺寸必须与当前实际分辨率一致），不通过就拒绝，绝不报错值 |
| 3 | EDID 只能通过 VBE/DDC 拿到 | 直接对 VGA 的 DDC 线做 DDC2B 位操作在 QEMU 上没有任何响应（试了 misc 寄存器的两种 SCL/SDA 组合） | 改用 VBE BIOS 的 `4F15 BL=01`；先用独立引导扇区探针验证可行性：返回 `AX=004F` 且读到的 EDID 头为 `00 FF FF FF FF FF FF 00`、厂商 `RHT`、产品 `0x1234` |
| 4 | loader 汇编里的 `cx` 未保护 → “一个模式都选不中”、启动卡在 VBE 错误路径 | `mode_score` 的新分支用 `cx` 当移位计数器却没恢复，而调用方紧接着用 `cx` 存模式号 → `best_mode` 被写成 0 | 移位前后 `push cx/pop cx`（`read_edid` 也一并保护）；教训：汇编子程序必须遵循寄存器约定 |
| 5 | 验收脚本自身失效 | T8 时钟用例和 T15 的区域/公式都写死过 1024x768 与 CRTC 单位（`htotal*8`），而 EDID 详细时序里的 htotal/vtotal 已经是像素 → 分辨率变成 1280x800 后判据不再成立 | 改成按画面尺寸推导、按来源区分单位（EDID 用 ×1，CRTC 用 ×8） |

## 24. 遗留与限制

1. **“当前模式刷新率”依赖 EDID 的详细时序与当前输出一致**：若显示器 EDID 的原生模式与实际输出不同
   （例如显示器原生 1280x800 而系统输出 1024x768），当前模式刷新率显示为“适配器未报告”，
   此时 EDID 行仍给出显示器自己的能力值。
2. **DDC2B 位操作备份路径**在某些真机/适配器上可能有效，但在 QEMU 上无响应；真机需实测确认。
3. **模式在启动期由 loader 的 VBE/自适应打分决定**，运行期不改模式（Bochs DISPI 的 `fb_set_mode()`
   存在但本轮未启用，避免破坏布局与用例）。
4. **来源标签粒度**（低危，仅文案）：终端 `disp` 的 `Refresh:` 行与汇总日志把非 CRTC 来源统一写成
   “0x3DA vretrace / source=vretrace”；刷新率来自 EDID 时数值仍正确，启动时的 `source=edid` 行才是准确标注。

# 批次四：四个体验缺陷的修复（拖影 / 显示设置可点选 / 图标双击 / 内容自适应）

本轮不改需求，只修缺陷。四个缺陷都有"机制性根因"，不是表面现象掩盖：

## 26. 缺陷根因与修复

### 26.1 某些窗口拖动时有拖影（残影）

**根因（两个条件叠加）**：

1. `gui_draw_all()` 是**按脏矩形重绘**：`draw_desktop()` 只填充本次重绘区域
   （`kernel/gui.cpp:804-806`），`draw_window()` 只绘制与重绘区域相交的窗口（`gui.cpp:994`）。
   提交用 `fb_flip_region(脏区)`，即**只把脏区像素推上屏**。
2. 应用内容**可以画到窗口矩形之外**：`kernel/fb.cpp` 只做"屏幕边界"钳制，没有"客户区裁剪"。
   设置窗的内容按 `SET_W×SET_H = 700×460` 绘制，而客户区只有 `700×436`（少了 24px 标题栏），
   于是每次都往窗口下方多画 24px；显示器窗口的长文本行、缩小后的计算器/扫雷同理。

两者叠加：拖动这类窗口时，脏区（旧位置 ∪ 新位置）把"窗口外的溢出像素"一起提交上屏，
窗口移走后这些像素留在原地 → 看到的就是拖影/残影。

**修复**：

* `kernel/fb.{h,cpp}` 新增客户区裁剪：`fb_set_clip(x,y,w,h)` / `fb_reset_clip()`，
  在 `putpx`、`fb_fill_rect`、`fb_fill_rect_alpha`、`fb_blit_rgba` 四条写像素路径上生效
  （`fb_clear()` 例外：整屏清屏不受裁剪影响）。
* `draw_window()` 在调用应用绘制回调前把裁剪设成客户区 `(bx, by+24, bw, bh-24)`，
  画完复位（`kernel/gui.cpp:1022-1026, 1053`）。
  **这条保证"任何应用都不可能画出自己的窗口"**，是拖影的结构性修法（而不是逐个应用打补丁）。
* 配套把"会溢出"的应用改成按客户区自适应（见 26.4），双保险。

### 26.2 设置 → 显示设置：分辨率/刷新率不能像 Windows 10 一样点击向下选择

**根因**：这两个字段在批次三里被刻意做成**只读文本**（`gui.cpp` 旧 2375-2418 行，
注释写着"硬件现状，不是可选设置"），既没有下拉列表绘制，也没有命中分支；只有"缩放"有下拉。
用户点它没有任何反应。

**修复（按 Windows 10 的交互做成真下拉，且不做假切换）**：

* 三个字段（分辨率 / 刷新率 / 缩放）统一为"可点字段 + 展开列表"，由 `SetGeom`/`set_list_box()`
  统一算几何，**绘制与命中共用同一份计算**（保证"看到的 = 点得到的"）。
* 分辨率候选 = **loader VBE 真实探测到的 32bpp 模式表**（按 w×h 去重、面积降序）；
  刷新率候选 = **显示器 EDID 报告的全部详细时序**（分辨率@刷新率，实测计算：像素时钟 ÷ (htotal×vtotal)）。
* 选择分辨率 → `disp_set_mode()`：写 VBE/DISPI 寄存器 + **回读校验**，成功后同步 display 状态、
  重测刷新率、按新分辨率重算缩放、写回 `display.*` 系统设置；失败/适配器不支持时页面上**红字如实提示**
  （"适配器拒绝运行期切换分辨率"），并在日志留证据；绝不假装成功。
* 选择刷新率 → `disp_apply_timing_range()`：分辨率不同就切到该时序的分辨率并用其实测值核对；
  **同一分辨率下改刷新率需要适配器支持时序编程**（Bochs DISPI 没有该寄存器），此时如实返回
  `-2` 并提示"适配器不支持"。
* 交互细节：同一时刻只展开一个下拉；再点一次字段收起；点窗口其它地方/其它窗口/桌面自动收起
  （`gui_main` 左键分支）；列表空间不够时自动向上展开并滚动（`set_list_box()`）；
  支持键盘上下 + 回车 + Esc。

### 26.3 双击桌面快捷方式图标打不开程序

**根因（单点、可精确复现）**：`gui_main()` 里桌面图标的双击判定写成裸 tick 常量：

```cpp
if (icon_drag_idx == last_icon && now - last_click < 25) open_icon(...);
```

批次二把 PIT 从 100Hz 提到 **250Hz**（1 tick = 4ms），于是 `25` 实际只有 **100ms**，
而人的双击间隔通常 150~500ms（Windows 默认 500ms）——双击几乎永远超时，
`open_icon()` 变成不可达代码；开始菜单是单击路径，所以"菜单能开、图标不能开"。
这是全文件唯一违反 `x86.h` "毫秒必须走 `ms_to_ticks()`" 约定的地方。

**修复**：`ms_to_ticks(500)`（与标题栏双击同一口径）+ 补日志
`[UI] desktop icon open kind=%d name="..." (dblclick)`（此前该路径完全不可观测）。

**同类缺陷一并修掉**：扫雷计时器 `ms_sec()` 里 `(t - start_tick) / 100`（按 100Hz 写的）
→ `/ PIT_HZ`，否则计时快 2.5 倍。

### 26.4 窗口能随意改大小，但窗口里的内容不跟着自适应

**根因**：各应用布局函数写死常量，`apply_resize()` 只改窗口几何、没有任何"内容重排"通知：

| 应用 | 旧行为 | 修复 |
|---|---|---|
| 设置窗 | 内容恒按 `SET_W×SET_H=700×460` 画（右下露白、缩小后越界） | `set_geom()`：导航宽度、字段宽度、行距全部由客户区推导；行距不足按比例压缩；`set_sy()` 让会话页/关于页共用同一映射；下拉列表限制在客户区内并滚动 |
| 扫雷 | 网格固定 30px、难度切换强改窗口尺寸 | `ms_layout()`：格边长 12..30px 由客户区宽高共同决定，网格水平居中、按钮行贴底；难度切换只在"连最小格都放不下"时才长大窗口（`ms_fit_window()`） |
| 计算器 | 固定 255×268 内容，仅居中 | `calc_layout()`：显示屏高度 + 5×4 键位尺寸按客户区缩放（键宽 22..96、键高 14..64） |
| 任务管理器/终端 | 批次二已按客户区推导 | 不变 |
| 默认文本窗/系统监视器 | 文本按宽换行但可能越界 | 由 26.1 的客户区裁剪兜底，不再越界 |

最小尺寸同步校准（`gui_min_size()`）：设置 520×360、扫雷 260×280、计算器 200×240、终端 240×160、
任务管理器 440×300 —— 都是"内容按该尺寸重排后仍放得下"的值。

### 26.5 顺带修掉的 loader 模式表缺陷（为 26.2 服务）

`boot/loader.asm` 的模式清单收集（上限 16 项）**不加 bpp 过滤**，而 VBE 模式表前面
`0x100..0x11x` 全是 8/15/16/24bpp 老模式，于是 16 项上限被它们占满，
真正可用的 **32bpp 模式（0x140+）一个都没进表**——分辨率下拉会只有 1 项。
修：收集时只收 `bpp == 32`（内核整套渲染就是 32bpp LFB），模式表因此恰好等于
"本适配器在 32bpp 下真实支持的显示模式"。实测 QEMU 下得到 16 项：
`320x200 / 640x400 / 640x480 / 800x600 / 1024x768 / 1280x1024 / 1600x1200 / 1152x864 /
1280x768 / 1280x800 / 1280x960 / 1440x900 / 1400x1050 / 1680x1050 / 1920x1200 / 2560x…`。

## 27. 运行期切换的接口（`kernel/display.{h,cpp}`）

```cpp
struct DispTiming { int w, h, hz10; };        // 显示器报告的真实详细时序
int  disp_timing_count();
bool disp_timing_info(int i, DispTiming* out);
int  disp_timing_match(int w, int h);
int  disp_set_mode(int w, int h);             // 0 = 成功（已回读校验）
int  disp_apply_timing_range(int w, int h, int hz10);   // -2 = 同分辨率下适配器不支持改刷新率
void disp_reprobe();                          // 重新测量刷新率（模式切换后）
int  disp_mode_runtime();                     // 1 = 当前分辨率由运行期切换得到
```

刷新率测量抽成 `disp_measure_refresh()`（启动与运行期切换共用同一套优先级：
EDID 详细时序 → 0x3DA 回扫标定 → CRTC 时序推算 → 如实报 `n/a`）。
运行期切模式后，"VBE 模式号"不再代表当前模式，设置页如实显示
`模式：运行期切换（VBE DISPI）` 而不是一个过期的模式号。

# 批次五：刷新率下拉的排序与来源 · 会话页内容修复 · 任务管理器硬件详情（SMBIOS/CPUID 实测）

## 31. 三个问题的根因与实现

### 31.1 设置 → 会话页内容不显示（缺陷）

**根因**：`kernel/gui.cpp` 的 `set_draw()` 里出现了**重复的 `else if` 条件**（上一轮改造时留下的）：

```cpp
} else if (g_set_page == 2) {
    // 会话/应用页：……
} else if (g_set_page == 2) {     // ← 有内容的其实是第二个分支
    …… 全部绘制（策略单选 / 单应用覆盖 / 两个动作按钮）……
} else {
    // 关于页
}
```

第一个分支是**空**的，会话页永远走它 → 客户区一个像素都不画（实测截图里客户区非背景像素 = **0**，而导航栏正常）。
这类缺陷编译器不会报（`-Wall -Wextra` 也不报），只能靠"每个设置页都做像素断言"的验收兜住。

**修复**：删掉重复的空分支；顺带把该页横向分隔线的宽度从旧常量 `SET_W - SET_NAV_W - 52` 改成按客户区推导
`G.cw - G.cx0 - 22`（窗口被拖小时不再溢出）。

### 31.2 显示设置：刷新率下拉的排序与来源（需求）

**要求**（用户原话）：点击刷新率就显示"从上到下、从高到低"的排序；**最高值要按显示器实际刷新率来**。

**实现**：

* 候选来源（全部为显示器/适配器**报告**值，去重后**降序**）：
  1. EDID **详细时序**（DTD）的刷新率；
  2. EDID **标准时序**（byte 38-53，8 组：水平分辨率/8-31 + 宽高比 + 刷新率-60）——本轮新增解析；
  3. 当前**实测**刷新率（EDID 详细时序 / 0x3DA 回扫 / CRTC 推算）。
* **不把 EDID 的"显示范围上限"放进下拉**：描述符 `0xFD` 的 max V rate 只是显示器声称的能力区间
  （实测 QEMU 报 `50..125Hz`），并不代表存在对应具体时序；摆进下拉会让"最高刷新率"虚高到 125Hz。
  该范围改为在页面上**如实展示**：`显示器刷新率范围（EDID）：50-125 Hz  标准时序 6`。
* 非当前分辨率的候选按刷新率**去重并最多留 3 条**，行内标注其分辨率——否则只支持 60Hz 的显示器
  会用一串重复的 60Hz 把列表刷满。
* 下拉的样式、命中判定、键盘操作与**分辨率下拉完全一致**（同一套 `SetGeom`/`set_list_box`）；
  每行只显示 `74.9 Hz` 形式，括号如实标注来源：`（当前）` / `（本分辨率）` / 分辨率。
* 选择行为：与当前分辨率匹配的具体时序走 `disp_apply_timing_range()`（同分辨率改刷新率在
  Bochs/QEMU 上不可行时如实返回 -2 并提示）；范围上限项若被选中，提示"适配器不支持据此改时序"。

### 31.3 任务管理器性能页：点击硬件项显示该硬件详情（需求）

**要求**：点 CPU → 显示实际名称型号、基础速度、实际内核与逻辑处理器、**虚拟化**（Windows 10 同款那一行）；
点内存 → 总容量、已用、**外形规格**（DDR3 就是 DDR3、DDR4 就是 DDR4）。

**实现**：

* 左侧硬件列表 2 项 → **4 项：CPU / 内存 / 磁盘 / 显卡**（`TmState::perf_sel` 0..3）。
  键盘上下键与鼠标点击都能选中，**两者写同一条日志**（可断言）。
* 选中项的详情面板画在列表/曲线下方（`tm_perf_detail()` 生成"字段名 + 实测值"），
  布局按客户区自适应（`tm_perf_layout()`：详情行数 / 曲线高度 / 通用行数按剩余空间分配，
  最小 440x300 也不越界——客户区还有裁剪兜底）。
* 字段（全部实测；取不到就如实写"未报告/固件未提供"）：
  * **CPU**：名称型号（CPUID 品牌串）、基础速度（CPUID `0x16` EAX；为 0 退回 TSC 实测并标注）、
    插槽（SMBIOS Type 4）、内核数/逻辑处理器数（CPUID）、**虚拟化**、SMT、L1/L2/L3 缓存、
    外频、固件标称频率（SMBIOS）。
  * **内存**：总容量（E820）、内存条合计（SMBIOS）、使用中/可用/使用率、
    **外形规格**（SMBIOS Type 17 offset 0x0E：DIMM/SODIMM）、**类型**（offset 0x12：
    `0x18`=DDR3 `0x1A`=DDR4 `0x22`=DDR5…）、速度（configured speed 优先）、插槽占用（Type 16/17）、内核堆。
  * **磁盘**：型号/容量/扇区数（ATA IDENTIFY）+ 读写扇区计数。
  * **显卡**：型号、厂商:设备 ID、显存、帧缓冲分辨率与色深。
* 内核数/逻辑处理器数一律以 **CPUID 为准**：实测 QEMU 的 SMBIOS Type 4 报 `cores=256`（固件占位值），
  与 CPUID 的 1 核冲突——这类异常值不作为主显示，避免误导用户。

## 32. 新增硬件探测（`kernel/hwinfo.{h,cpp}`）

### 32.1 SMBIOS / DMI 实测解析

* 扫描 `0xE0000-0xFFFFF`，**逐字节**寻找入口点（`_SM_` 32 位 / `_SM3_` 64 位），**校验和通过才采用**。
  实测结论：QEMU/SeaBIOS 的入口点在 **0xF5304，不在 16 字节边界上**——按规范建议的 16 字节步长扫描会漏掉
  （这就是最初日志里 `smbios: none` 的原因）；而 ROM 里还有 `_SM3_` 字样（0xF1985），所以校验和过滤是必须的。
* 解析结构：Type 0（BIOS 厂商/版本）、Type 1（系统厂商/型号）、Type 4（处理器：插槽设计名、
  固件标称当前/最大频率、核数、线程数）、Type 16（内存阵列：插槽总数）、
  Type 17（内存条：容量/类型/外形规格/速度/插槽名）。
* 对外接口：`hw_smbios_ok()`、`hw_board()`、`hw_memdev_count()/hw_memdev_at()`、
  `hw_mem_type_name()`、`hw_mem_form_name()`、`hw_mem_slots_total()/used()`、`hw_mem_dev_total_mb()`。
* 实测（QEMU）：`sys="QEMU" product="Standard PC (i440FX + PIIX, 199" bios="SeaBIOS"`、
  `cpu socket="CPU 0" cur=2000 max=2000`、`mem slots=0 used=1 totalmb=128`、
  `mem[0] loc="DIMM 0" size=128MB type=RAM(0x7) form=DIMM(0x9) speed=0`。
  → **外形规格（DIMM）与代数（RAM/DDR3/DDR4/DDR5）读的都是固件报告值**：QEMU 的固件给的是 "RAM"
  （没有标 DDR 代数，页面就如实显示 RAM）；真机固件会给出 `0x18/0x1A/0x22` → 页面自动显示 DDR3/DDR4/DDR5。

### 32.2 CPUID 增强

* `0x16`：基础/最大/外频（MHz）。实测 QEMU 不报告（全 0）→ UI 退回 TSC 实测频率并标注来源。
* 缓存：Intel `0x4` 迭代（ways×partitions×line×sets，取 L1D/L2/L3）+ AMD `0x80000005/6`。
  实测 QEMU：`l1=64 l2=512 l3=32`（KB）。
* **虚拟化**（Windows 10 口径）：`CPUID.1:ECX[31]` = VMX（Intel VT-x）、
  `CPUID.0x80000001:ECX[2]` = SVM（AMD-V）；"已启用"判定用
  `IA32_FEATURE_CONTROL`(MSR 0x3A) 的 lock + VMXON-outside-SMX 位或 `CR4.VMXE`(bit13)，
  AMD 用 `EFER.SVME`(bit12)。
  **只在处理器明确报告 VMX/SVM 时才读对应 MSR**（读不存在的 MSR 会 #GP → 蓝屏），这是安全边界。
  实测 QEMU：`virt=2(VT-x)`（硬件支持 VMX、当前未启用）。

# 批次六：右下角时钟镜像 —— 根因在 8×8 字模表的位序

## 36. 现象与根因

**现象**（用户报告）：任务栏右下角的时间看起来和"镜子里的一样"（数字水平翻转），
而界面上其它文字（开始按钮、窗口标题、任务管理器……）都是正常的。

**根因**：`kernel/font8x8.h` 的 8×8 位图字体，**字形数据是按镜像位序存放的**（bit0 = 最左像素），
而绘制函数 `fb_draw_char()` 按标准位序解释（bit7 = 最左）——两者不匹配，所以"正向绘制"在屏幕上
输出的是**镜像字形**。实证：

| 字符 | 表里的数据（首字节） | 正向绘制结果（bit7 在左） | 标准位序应为 |
|---|---|---|---|
| `A` | `0C` = `00001100` → `....##..`（竖笔偏右） | 镜像的 A | `30` = `..##....` |
| `$` | `0C 3E 03 1E 30 1F` | 镜像的 $ | `30 7C C0 78 0C F8` |

历史包袱正是由此而来：当初发现"时钟是反的"，就把**时钟单独改成 `fb_draw_text_mirror()`**
（把字节先做位反转再画，于是反而正常）——这是"用错误掩盖错误"。后续某轮又把时钟改回正向
并把 mirror 当成历史怪癖删掉，于是镜像现象重新暴露。

**影响范围**：所有走 8×8 位图字体的地方 —— 任务栏时钟（时间 + 日期两行）与 `panic.cpp` 的**蓝屏文字**
（4 处 `fb_draw_text`）；TrueType 字体（`font_draw_text`）不受影响，所以其余界面看着正常。

## 37. 修复（根治，不是再"反着画"）

1. **把 95 个字形全部按位反转**纠正为标准位序（bit7 = 最左）：
   `font8x8.h` 每个字节做 bit-reverse，并在文件头写明位序约定与本缺陷的历史，防止再次被改错。
   转换后 `'A'` 首字节 = `0x30`、`'0'` = `7C C6 CE DE`（标准形状）。
2. **绘制路径保持正向**：`gui.cpp` 的时钟与 `panic.cpp` 的蓝屏都继续用 `fb_draw_text()`，
   现在它输出的就是正确方向（"反着画"的需求不再存在）。
3. **镜像能力保留**：`fb_draw_char_mirror()` / `fb_draw_text_mirror()` 仍然可用（当前无调用点），
   供"确实需要镜像输出"的场景。

## 38. 验收（新增 3 项 + 1 项改写，全量 183/183）

原来的 T8.4 只检查"源码里没有 `fb_draw_text_mirror(` 调用"，抓不到"字模表本身是镜像位序"这类缺陷
（本次缺陷恰好从它眼皮底下溜过去了）。因此新增**真实方向判定**：从截图里把时钟字符位图抠出来，

# 批次七：最小化恢复的几何缺陷 · 系统级预加载

## 40. 缺陷：最小化后从任务栏点开，窗口缩成一条

**现象**（用户报告）：窗口最小化后点任务栏按钮恢复，窗口只剩"任务栏上方露出的一个小条"，
必须再点一下那条才真正打开。

**根因（两处叠加，都在几何复位上）**：

1. 最小化走 `begin_geom_anim(w, x + w/2 - 40, sy - 8, 80, 16, kind=2)`：`begin_geom_anim()` 会把
   `w->x/y/w/h` **立即设成目标几何**（即那个 80x16 的小矩形），只有 `ax/ay/aw/ah` 保存起点。
   动画结束（`anim_kind == 2`）时只做了"隐藏"：
   ```cpp
   w->minimized = true; w->visible = false;
   ```
   **几何没有复位** —— 窗口对象上留下的就是 80x16。
2. 任务栏按钮恢复时只翻转标志：
   ```cpp
   if (tbw->minimized) { tbw->minimized = false; tbw->visible = true; }
   ```
   于是窗口以 80x16 显示 → "只在任务栏上面露出一点"。再点那一下之所以"能打开"，
   是因为小条正好落在最大化/还原按钮的命中区上，触发了另一条路径。

**修复**：

* 最小化动画完成时**复位几何**：最大化过的窗口复位为全屏几何 `(0,0,W,H-taskbar)`（Windows 行为：
  最大化窗口最小化后恢复仍是最大化），其余复位为 `norm_*`；并新增日志
  `[UI] minimize app=N x=… y=… w=… h=…`（复原后的几何）。
* 任务栏恢复时做**"从任务栏弹出"的展开动画**：起点 = 最小化时的小矩形（与最小化动画目标一致，
  位于任务栏上方），目标 = norm（或最大化几何），`begin_geom_anim(kind=1)`；
  并新增日志 `[UI] restore-min app=N x=… y=… w=… h=…`。
* 两条日志都带上"复位后的几何"，让"恢复后尺寸必须等于最小化前"这件事**可自动断言**
  （以前这一整条路径没有任何日志）。

实测：`[UI] minimize app=1 x=150 y=80 w=255 h=292` → `[UI] restore-min app=1 x=150 y=80 w=255 h=292`；
恢复后像素包围盒 `(340,78,69,298)` 与几何（右边界 407 / 顶 80 / 高 292）一致。

**幂等的前提（本轮验收抓到并修掉的又一个真实缺陷）**：预热集必须能**全部驻留** LRU 缓存。
最初 `PRELOAD_CN` 有 **193 个唯一汉字**而 `FONT_LRU_N` 只有 **192** 槽 —— 每轮预热边装边挤，
第二次 `preload run` 仍会重新光栅化 192 个字（`glyphs_new=192`，约 18ms 白干），"幂等"名不副实。
修：① `FONT_LRU_N` 192 → 256（每槽 400B，+25.6KB/face，可接受）；
② preload 启动时**自检并如实写日志**：`[PRELOAD] prewarm set unique=193 lru=256 (fits: idempotent)`，
装不下时写 `WARN prewarm set exceeds LRU capacity … not idempotent` —— 把"容量不够"变成可观测的
一行日志（而不是靠人肉发现）。修后第二次 `preload run`：`glyphs_new=0` ✓；
预热耗时实测 `[PRELOAD] font ascii_new=283 cn_new=193 unique=193 cached=481/1056 us=27657`。

## 41. 需求：系统级预加载（图形化界面用到的重资源）

**做法**（新模块 `kernel/preload.{h,cpp}`，模块表位置：`bootui` 之后、`gui` 之前）：

1. **字形预光栅化**：界面/终端用到的字符在启动阶段提前光栅化进字体缓存，
   此后绘制只做位图混合。覆盖：三个 face（正文/标题/中文）的 ASCII 32..126 +
   界面常用汉字串（菜单、设置页、任务管理器、终端提示等约 230 个高频字）。
   实现上把 `font_draw_glyph`/`font_draw_glyph_cp` 的**缓存填充部分**抽成
   `prewarm_one_ascii()` / `lru_get_slot()` 复用 —— 与绘制结果完全一致，只是提前做；
   新增 API：`font_prewarm_ascii()` / `font_prewarm_ascii_all()` / `font_prewarm_text()` /
   `font_cache_used()` / `font_cache_capacity()`。
2. **桌面图标预缩放**：128×128 的嵌入 RGBA 图标原来是**每次绘制**做最近邻采样 + alpha 判断，
   现在预缩放成 48×48 缓存（`gui_preload_icons()`，由 preload 调用），绘制走"非透明像素直接拷贝"
   快路径（逐像素与原路径等价）。
3. **可观测 + 可控**：
   * 日志（TSC 实测耗时）：`[PRELOAD] init/font/icons/done`；
   * 终端命令 `preload`（查看状态）、`preload run`（手动补预热，幂等：只补没预热的）；
   * 设置 → 系统页新增一行"系统预加载"，显示开关状态 + 缓存字形数/容量 + 缓存图标数 + 上次耗时，
     **点击即可切换**（写入系统设置 `ui.preload`，重启后保持）。

设计取舍：只做"确定性收益"的预热，不做"猜测用户会开什么应用"的提前创建（避免浪费内存与启动时间）；
预热是幂等的，语言切换等场景可以 `preload run` 补。

实测：`glyphs cached=480/864`（容量 = 3 face × (96 ASCII + 64 LRU)）、`icons cached=3`、
`total_us≈42000`（约 42ms 启动一次性成本），`preload run` 第二次执行 `glyphs_new≈0`
（已缓存的不重复光栅化）。

|---|---|
| 重启 | `stage_stopped()` 里 `for (p = 0; p <= 100; p += 5) restart_screen_draw(0, p, 阶段文案)` —— **逐帧**播放（蓝底 + 圆环 + "正在重启" + 进度百分比），共 21 帧 |
| 关机 | 同一处只调了 **一次** `restart_screen_draw(1, 100, "power off")` —— 画一帧静态图就断电，视觉上就是"没有动画" |

另有一段"幽灵代码"：`kernel/gui.cpp` 里存在一个 40 帧、约 2 秒的 `shutdown_animation()`（紫底 + 转圈），
但它**从未被任何地方调用**（编译告警 `'shutdown_animation' defined but not used` 一直在提示这件事），
所以从未出现在屏幕上。

## 46. 实现：关机和重启共用一套逐帧全屏动画

统一到 `kernel/sysstate.cpp`（系统状态机是关机/重启的唯一执行者），新增：

- `pow_begin(int shutdown_style)` —— 进入 STOPPING 时**立刻**开播
- `pow_pump(const char* stage, int percent)` —— 按节拍推进（每 40ms 一帧）
- `pow_finish(const char* stage)` —— 收尾：转满一圈 + 圆环收缩 + 背景淡出到黑
- `pow_frame(stage, percent, fade)` / `pow_lerp(a, b, t, tmax)`（通道插值，无浮点）

**关机画面**（参考 Windows 10/11 关机）：**紫色背景 `0x7C3AED`** + 中央白色 12 点旋转圆环
（连续 4 点亮，Windows spinner 观感）+ "正在关机 / Shutting down" + 副标题
（"正在关闭服务" → "正在关闭电源"，淡紫色）+ 不显示进度条（Win10 关机也没有）。

**重启画面**：蓝色 `0x0078D4` + 同一套圆环 + "正在重启" + 阶段文本 + 进度百分比 +
诊断页脚（gen/reason，保留原有信息）。

**时序**：
1. `begin_stopping()` 里 `pow_begin()` —— GUI 刚停靠、屏幕不会再被界面覆盖，此时立刻画第一帧
   （按下关机马上有反馈，而不是对着冻结的桌面等模块关闭）；
2. `stage_stopping()` 每 tick 调 `pow_pump()`（40ms 节拍）—— 覆盖模块优雅关闭的等待时间；
3. `stage_stopped()`：关机 → `pow_finish("正在关闭电源")`（12 帧转满一圈 + 6 帧收拢/淡出到黑）→ 断电；
   硬重启 → 推进到 100% → `pow_finish()` → 复位；软重启不淡出（转圈画面直接衔接 GUI 首帧，
   像 Windows 重启后桌面直接出现）。

**两个细节（实测踩出来的）**：
- 全屏动画前显式 `fb_reset_clip()` —— 窗口客户区裁剪状态若残留会把动画裁掉；
- **日志顺序很重要**：断电会截断 debugcon 尾部输出（实测 `done` 行经常丢），所以
  `[STAGE] SHUTDOWN` 与 `[UI] power anim finishing` 都在收尾动画**之前**写，保证证据落盘。

**删除死代码**：`gui.cpp` 里从未被调用的 `shutdown_animation()` 已删除（连同它的 unused 告警），
避免"两处动画实现各自漂移"。

## 47. 顺带修掉的一个量纲缺陷

`sys_stage_elapsed_ms()` 原实现是 `(task_get_ticks() - g_stage_start) * 10` —— 按 **10ms/tick（100Hz）**
估算，而 PIT 早已是 **250Hz（4ms/tick）**：所有 `elapsed=` / `cost=` 日志都**高估 2.5 倍**。
修：改用 `ticks_to_ms()`（与 `x86.h` 约定一致）。修后实测 `[STAGE] STOPPED elapsed=648ms`
（此前会显示 1620ms）。

## 48. 日志协议（批次八）

| 日志 | 含义 |
|---|---|
| `[UI] power anim begin style=shutdown bg=7C3AED frame_ms=40` | 动画开播（style ∈ shutdown/restart；bg 为十六进制**大写**） |
| `[UI] power anim finishing style=shutdown frames=N bg=7C3AED` | 收尾开始（N = 已播帧数；**断电前写，一定落盘**） |
| `[UI] power anim done style=… frames=N bg=…` | 收尾完成（断电会截断此行，可能缺失，断言别依赖它） |
| `[STAGE] SHUTDOWN (power off)` | 即将执行 ACPI 断电（现在也在断电前写） |
