# 应用层与系统调用说明（给想给 VimtuOS 写程序的人）

> 适用版本：VimtuOS 0.1.0（Vimtu64，x86_64 long mode）
> 本文所有字段、常量、号段与行为都**逐条从源码核对**（`kernel/app64.h`、`kernel/elf64.h`、
> `kernel/syscall64.h`、`kernel/syscall64.cpp`、`kernel/usermode64.h`、`tools/make_vap.py`、
> `user/*.asm`、`build64.sh`），改动代码时请同步本文。
> 状态：**自有格式应用与自有静态 ELF64 都已实测可安装、可运行**；glibc / 发行版二进制**未验证**。

---

## 1. 一页速览

| 项目 | 结论 |
|---|---|
| 用户态 | ring3，CPL=3，GDT 选择子：内核代码 `0x08` / 内核数据 `0x10` / 用户数据 `0x23` / 用户代码 `0x2B` / TSS `0x30` |
| 用户地址空间 | **一个 1 MiB 窗口**：`4GiB .. 4GiB+1MiB`（所有程序**共用**，没有独立地址空间） |
| 地址空间隔离 | ❌ 没有；也没有 `fork` / `execve` / `clone` / 线程 |
| 系统调用入口 | ① `int 0x80`（Vimtu64 自有 ABI，号段 1..8）② `syscall` 指令（Linux x86_64 号段，25 个号有实现，其余 `-ENOSYS`） |
| 可执行文件格式 | ① **VAP64**（自有，32B 头 + 名字 + 代码段 + CRC32，代码 ≤32KiB）② **ELF64**（静态 `ET_EXEC`/`ET_DYN`、`PT_LOAD`、无 `PT_INTERP`/无重定位） |
| 程序从哪来 | 构建期用 `objcopy` 嵌进**系统内核**，启动时由内核装进 VimtuFS2 的 `/hello.vap`、`/hello.elf`（幂等）；**目前没有"把任意文件拷进 VimtuFS2"的宿主工具**（见 §7 的诚实说明） |
| 怎么启动 | 终端：`run <名字\|/路径>`（按文件头魔数自动分派）/ `elfrun <路径>`（强制 ELF64） |
| 能跑什么 | 自己写的 `-nostdlib` 程序；**不能跑 glibc/发行版二进制**（缺 execve、vDSO、TLS、信号、futex、动态链接、重定位） |

## 2. 用户内存布局（`kernel/usermode64.h`，唯一定义点）

整个用户地址空间 = **4GiB 起、1 MiB 大的一个窗口**（`USER64_CODE_VA64 = 0x0000000100000000`，
`USER64_WINDOW_BYTES64 = 1 MiB`）。窗口内部的分区（**互不重叠**，由 `syscall64_selftest64()` 的 bit0 断言把关）：

| 区域 | 虚拟地址 | 大小 | 权限 | 用途 |
|---|---|---|---|---|
| ELF 装载区 | `4GiB + 0x00000` .. `4GiB + 0x10000` | 64 KiB | 按段（见 §5.2） | ELF64 的 `PT_LOAD` 段落在这里；也是 VAP64 代码页的位置（代码页 R/X） |
| 用户栈 | `4GiB + 0x10000`（`USER64_STACK_VA64`） .. `+0x4000` | 16 KiB（4 页） | `P|U|W|NX` | VAP64 与 ELF64 共用；ELF 的 SysV 初始栈建在这里，`rsp` 16 字节对齐 |
| brk 区 | `4GiB + 0x40000`（`USER64_BRK_VA64`） .. `+0x10000` | 64 KiB | `P|U|W|NX` | Linux `brk(12)` 的固定可写区（首次调用时整块映射） |
| 自检临时页 | `4GiB + 0x80000`（`USER64_TEST_VA64`） | 4 KiB | 临时 | 只给 `user64_selftest64()` 用，用完解除映射 |
| mmap 区 | `4GiB + 0x90000`（`USER64_MMAP_VA64`） .. 窗口末 | 剩余 | `P|U|W|NX` | Linux `mmap(9)` 的 bump 分配器（至少保证 64 KiB 可用） |

要点：

* 用户页要求 **PML4E[0] / PDPTE / PDE / PTE 四级都打开 U/S**；大页会拒绝（`user64_map_page64` 撞大页即失败）。
* 内核自己的映射在 PML4[0] 的低 4 GiB 与 PML4[511] 的高半区，**不套用户权限**；4 GiB 以上在 PML4[0] 里原本是空的，正好当用户窗口。
* `TSS.rsp0` 随任务切换维护（ring3 → ring0 的中断切栈用）；`syscall` 指令**不换栈**，入口切到一份**专用 16 KiB 内核栈**（与 TSS.rsp0 解耦，避免中断帧/syscall 帧互相覆盖）。
* 每个来自用户态的指针都要过 `user64_range_ok64(va, len)`：整段落在窗口内、且四级都是已映射用户页，否则拒（打 `[SYSCALL] deny`）。

## 3. 入口一：`int 0x80`（Vimtu64 自有 ABI）

* 门：`IDT[128]` 装成 `0xEE`（P=1、DPL=3 中断门），ring3 直接 `int 0x80` 即可。
* 寄存器约定：**`rax` = 调用号；`rdi` / `rsi` / `rdx` = 参数 1/2/3；返回值放 `rax`（负数 = 错误）**。
* 号段（`kernel/syscall64.h` 顶部；**这条路径的号段与 Linux 号段完全隔离**）：

| 号 | 名称 | 参数 | 行为与返回值 |
|---|---|---|---|
| 1 | `write` | `rdi`=fd、`rsi`=buf、`rdx`=len | **只支持 fd=1**（输出到**串口 + 屏幕**）；`len` 为 0 或 >1024 → `-1`；buf 不在用户窗口 → `-1`；成功返回写出的字节数 |
| 2 | `exit` | `rdi`=code | 把控制权交回内核（不改写用户帧直接返回 ring0 蹦床）；**不再返回用户态** |
| 3 | `getpid` | — | 当前任务 id（`task_current_id_64()`；没有调度器时 0） |
| 4 | `ticks` | — | PIT tick 数（**250 Hz**） |
| 5 | `sleep_ms` | `rdi`=毫秒 | 睡眠（走 `task_sleep64`；没有调度器时按 tick 忙等 `hlt`）；返回 0 |
| 6 / 7 / 8 | `open` / `read` / `close` | — | **未实现，一律返回 `-1`**（要真实语义请走 `syscall` 指令路径，那边有真文件系统实现） |
| 其它 | — | — | 返回 `-1` |

* 打点（自动验收依赖，别改格式）：只有 `write(1)` 与 `exit(2)` 会打
  `[SYSCALL] nr=<n> rdi=<hex> rsi=<hex> rdx=<hex> ret=<hex>`。

**最小示例（完整可跑的源码见 `user/hello64.asm`）**：

```asm
bits 64
org 0                      ; VAP64 代码段是"平铺二进制、入口在段首"，只能 RIP 相对寻址
_start:
    lea     rsi, [rel msg]
    mov     edx, msg_len
    mov     eax, 1         ; write
    mov     edi, 1         ; fd = 1
    int     0x80
    mov     eax, 2         ; exit
    xor     edi, edi
    int     0x80
.hang:
    jmp     .hang
msg:     db "hello", 10
msg_len  equ $ - msg
```

## 4. 入口二：`syscall` 指令（Linux x86_64 号段）

* 寄存器约定与 Linux 完全一致：**`rax` = 号；`rdi/rsi/rdx/r10/r8/r9` = 参数 1..6；返回 `rax`（负值 = `-errno`）；
  `rcx`/`r11` 被 CPU 覆盖**（易失，Linux 也一样）。
* MSR 现场（`syscall64_init64()` 写入并回读留证）：`EFER.SCE=1`；
  `STAR = (0x1B << 48) | (0x08 << 32)` → `sysret` 的 `CS=0x2B`、`SS=0x23`，`syscall` 的 `CS=0x08`、`SS=0x10`；
  `LSTAR = syscall64_insn_entry64`；`FMASK = 0x700`（入口自动清 TF/IF/DF）。
* 帧标记：`SYSCALL64_INSM_FRAME_MARK64 = 0x180`（`int 0x80` 是 `0x80`），分发器靠它分流，两条路径的号段互不影响。
* 打点：这条路径**每个调用都打** `[SYSCALL] insn nr=<n> rdi=<hex> rsi=<hex> rdx=<hex> ret=<hex>`（方便对照调试）。

### 4.1 号段表（`kernel/syscall64.cpp` 的分发器，逐条核对）

| 号 | 名称 | 实现状态（源码里的真实行为） |
|---|---|---|
| 0 | `read` | **真**：`fd=0` 立即返回 0（EOF，本内核没有键盘输入流）；`fd=3..6` 从 open 时缓存的 **512B 文件窗口**里按 offset 拷给用户；其它 fd → `-EBADF(9)` |
| 1 | `write` | **真**：`fd=1` → 串口 + 屏幕；`fd=2` → 只串口；单次 `len` ≤ **4096**，超限 `-EINVAL(22)`；越界 `-EFAULT(14)` |
| 2 | `open` | **真**（只读语义）：`vfs64_stat` 探存在性 → 分配 fd（**3..6**，共 4 槽）→ 返回 fd；不存在 `-ENOENT(2)`；表满 `-EMFILE(24)`；`flags`/`mode` 忽略 |
| 3 | `close` | **真**：释放 fd 槽 → 0；非法 fd → `-EBADF` |
| 4 | `stat` | **未实现 → `-ENOSYS(38)`**（本阶段没有"按路径 stat"的用户 ABI 需求；用 `fstat` 代替） |
| 5 | `fstat` | **真**：填 144B `struct stat`；fd 0/1/2 → 字符设备最小三字段（`st_mode=0020000|0666`、`st_size=0`、`st_nlink=1`）；fd≥3 → `st_mode=0100000|0444` + 真实大小 |
| 6 | `lstat` | **未实现 → `-ENOSYS`**（与 4 同类） |
| 8 | `lseek` | **真**：fd≥3 在缓存窗口内按 `SEEK_SET/CUR/END` 调 offset；fd 0..2 → `-ESPIPE(29)`；越界 → `-EINVAL` |
| 9 | `mmap` | **真**：用户窗口内的 bump 分配器（从 `4GiB+576KiB` 起），页 `P|U|W|NX`，返回页对齐地址；只看 `MAP_FIXED(0x10)` 的地址提示；`PROT` 参数基本忽略；空间不足 `-ENOMEM(12)` |
| 10 | `mprotect` | **真**：逐页改叶子权限（`PROT_READ=1` → 可读、`PROT_WRITE=2` → 可写、`PROT_EXEC=4` → 清 NX）；范围/页非法 → `-EINVAL` |
| 11 | `munmap` | **真**：逐页解除映射并 `page_free_64` 回收物理页 → 0；未映射/越界 → `-EINVAL` |
| 12 | `brk` | **真**：固定 64 KiB 可写区（`4GiB+256KiB`，首次调用整块映射）；`brk(0)` → 返回当前 brk；区间外 → 返回旧 brk（Linux 同语义） |
| 13 | `rt_sigaction` | **接受但不实施**：不读用户结构、立刻返回 0（内核里没有信号投递路径 —— 用户程序的信号永远不会来） |
| 14 | `rt_sigprocmask` | 同 13（返回 0，不实施） |
| 16 | `ioctl` | **真（最小）**：fd ≤ 2 且请求 `TIOCGWINSZ(0x5413)` → 写回 `25x80`（`row=25 col=80 xpixel=640 ypixel=200`）并返回 0；`TIOCSWINSZ(0x5414)` → 忽略并返回 0；其它 → `-ENOTTY(25)` |
| 20 | `writev` | **真**：fd=1/2，最多 **8** 个 iovec（每个 16B），逐个写；超限 `-EINVAL` |
| 39 | `getpid` | **真**：当前任务 id（`task_current_id_64()`；无调度器时为 0） |
| 60 | `exit` | **真**：把控制权交回内核（帧改写 + ring0 蹦床），返回用户 `exit` 码 |
| 63 | `uname` | **真**：写一份静态 `struct utsname`（6 × 65B）：`VimtuOS` / `vimtu64` / `0.1.0-vimtu64` / `#1 ring3+syscall` / `x86_64` / `(none)` |
| 79 | `getcwd` | **真**：把 `"/"` 写进用户 buf（`size≥2`）并返回 buf 指针（Linux 语义） |
| 102 / 104 | `getuid` / `getgid` | **真**：都返回 `0`（本内核没有用户概念） |
| 158 | `arch_prctl` | **真（部分）**：`ARCH_SET_FS(0x1002)` 把值存进内核变量并返回 0；`ARCH_GET_FS(0x1003)` 写回用户指针；其它 → `-EINVAL`。★ **不写 `IA32_FS_BASE`**：真 TLS 需要 per-CPU/swapgs 那套地基，现在改只会连内核的 FS 基址一起变 |
| 218 | `set_tid_address` | **真（最小）**：返回 0（没有 `clear_child_tid` 唤醒路径） |
| 228 | `clock_gettime` | **真（近似）**：用 `g_ticks64`（250 Hz）造值 —— `tv_sec = t/250`、`tv_nsec = (t%250) * 4000000`（**4 ms 粒度**）；`clockid` 0..3；其它 → `-EINVAL` |
| 231 | `exit_group` | **真**：同 60（本内核是单线程模型，直接当 `exit`） |
| 257 | `openat` | **真**：`open` 的现代入口；`dirfd` 忽略（只支持 `AT_FDCWD`）；相对路径要求以 `/` 开头，否则 `-EINVAL` |
| 其它所有号 | — | **`-ENOSYS(38)`**，并且同一个号只打一次 `[SYSCALL] enosys nr=<n>`（防刷屏） |

**关于号段数量**：源码里**有实现路径的号是 25 个**（表中除 4 / 6 以外的行；其中 13 / 14 是"接受但不实施"），
4 与 6 是显式 `-ENOSYS`，其余全部 `-ENOSYS`。已实现号里做不到的分支一律返回**具体负 errno**
（`-EBADF/-EFAULT/-EINVAL/-ENOMEM/...`），**绝不返回 0 假装成功**。

### 4.2 fd 与文件语义的边界

* fd 表只有 **4 槽**（3..6）；每个 fd 只在**首次读**时把文件最多 **512B** 读进缓存，之后 `lseek`/`read` 都在这 512B 里。
  → 读一个大于 512B 的文件需要重新 `open` 或用 VAP64/内嵌方式。
* 路径必须是**单层绝对路径**（`/name`），名字 ≤27B，且必须是 VimtuFS2 里的**普通文件**；
  目录、深层路径（含 `/`）、`.`/`..` 都不支持（`open` 会 `-ENOENT` 或 `-EINVAL`）。
* `write` 只支持 stdout/stderr；**没有 `write` 到文件**、没有 `mkdir`/`unlink` 的用户入口。
* 没有 `/proc`、没有设备节点、没有管道、没有 socket。

### 4.3 已知边界（别把没做的说成做了）

* 地址空间是**共享**的：`mmap`/`brk`/`mprotect`/`munmap` 都在同一个用户窗口里；没有独立地址空间、没有 `fork`/`execve`。
* glibc / 发行版二进制**没有验证过**：它们依赖的 TLS(FS.base) 真生效、信号投递、vDSO、`futex`、`clone`/线程、
  `/proc`、RELRO/multi-PT_LOAD 保护、IFUNC 重定位等大多不在这里。
  这里验证的是"自有静态 ELF64（`ld.lld -static -nostdlib`）能 load → ring3 → `syscall` → exit"。
* 用户态没有 `swapgs`/per-CPU `gs`，所以 SYSCALL 入口不能用 `gs` 取内核数据；ring3 里 `gs` 基址仍是内核的（用户程序不该依赖它）。
* `syscall` 指令路径因为"每个调用都打串口"，**不适合在循环里高频调用**（将来若要跑真程序，需要先给日志加节流）。

## 5. 可执行格式一：VAP64（Vimtu64 自有）

**为什么自己定义格式**：本阶段只需要"装载一段 ring3 平铺二进制并校验完整性"，
32B 定长头 + 名字 + CRC32 就够；不做重定位 / 导入表 / 多段。

### 5.1 文件布局（唯一定义点：`kernel/app64.h`；打包器 `tools/make_vap.py` 必须逐字段一致）

| 偏移 | 长度 | 字段 | 语义 |
|---|---|---|---|
| 0 | 8B | `magic` | `"VAP64\0\0\0"`（5 个可见字符 + 3 个 NUL） |
| 8 | 4B | `version` | 结构版本 = **1** |
| 12 | 4B | `header_size` | 固定头字节数 = **32**（不含名字） |
| 16 | 4B | `entry_offset` | 代码入口在**文件内**的绝对偏移 = `header_size + name_len`（名字紧跟头后；`hello` 这个 6B 名字 → `38`）。**加载器不接受别的值** |
| 20 | 4B | `code_size` | 代码段字节数：**1..32768**（与 `user64_run_blob64` 的"代码最多 8 页"对齐） |
| 24 | 4B | `code_crc32` | `zlib.crc32(代码段)`（标准 CRC-32：反射多项式 `0xEDB88320`、初值/末异或 `0xFFFFFFFF`，与 vfs64/make_vap.py 同口径） |
| 28 | 4B | `name_len` | 名字字节数，**含结尾 NUL**：1..24（→ 可见字符最长 23） |
| 32 | `name_len` | `name` | 名字（NUL 结尾） |
| `32+name_len` | `code_size` | `code` | 代码段（**平铺二进制，入口在段首**，即第一字节就是第一条指令） |

**文件总长 = 32 + name_len + code_size**（加载器用这条等式做长度一致性校验）。

名字约束（`tools/make_vap.py` 在打包时就拒绝）：必须是可打印 ASCII（`0x21..0x7E`），**不能含 `/` 或 `\`**。

校验与拒绝理由（`app64.cpp`，串口会打 `[APP64] launch FAILED path=<p> reason=<...>`）：
`arg` / `vfs`（读盘失败）/ `size`（>64KB 缓冲上限或长度不一致）/ `magic` / `version` /
`name`（长度或 NUL 不合法）/ `crc` / `user64`（映射或进 ring3 失败）。

### 5.2 运行方式

1. 代码段被拷到 **`4GiB`（`USER64_CODE_VA64`）起的用户页**，映射为 **R/X**（只读可执行，不可写 —— 要写数据请用栈或 `mmap`）；
2. 栈用窗口里的 16 KiB 用户栈（R/W/NX）；
3. `iretq` 进 ring3，入口 = 代码段首字节；程序用 **`int 0x80`** 与内核通信；
4. `exit(2)` 或程序正常走完（后者会走到代码段末尾 —— 一定要显式 `exit`，否则行为未定义）后，内核回收用户页。

## 6. 可执行格式二：ELF64（`kernel/elf64.h` + `kernel/elf64.cpp`）

### 6.1 支持范围（加载器逐条校验，不满足就打 `[ELF64] reject reason=<...>`）

* 魔数 `\x7fELF`、`class=2`（64 位）、`data=1`（小端）、`version=1`、`machine=0x3E`（x86-64）；
* `e_type` = `ET_EXEC(2)` 或 `ET_DYN(3)`；`e_phentsize = 56`；程序头表整段必须落在文件内
  （`e_phoff + e_phnum*56 <= 文件长度`）；**`e_phnum ≤ 16`**（`ELF64_MAX_PHDR64`）；
* **不支持** `PT_INTERP`（动态链接器）、重定位、`PT_GNU_*` 特殊段；加载器**不做任何重定位**；
* 文件总长上限 **96 KiB**（`ELF64_MAX_FILE_BYTES64`，读盘缓冲在 `.bss` 里）；
* 每个 `PT_LOAD`：
  * 目标 `[p_vaddr, p_vaddr+p_memsz)` 必须**完整落在用户窗口的 ELF 装载区**（`4GiB .. 4GiB+64KiB`），否则拒绝（`outside-user-window` / `overlaps-user-region`）；
  * `p_filesz` 字节从文件拷进去，`p_filesz..p_memsz` 清零（`.bss`）；
  * 权限按 `p_flags`：`PF_R` → 加 `P|U`；`PF_W` → 加 `W`；`PF_X` → 不加 NX（不可执行段加 `PTE_NX`）。实现上先统一按 `P|W|U` 映射（否则只读段没法写内容），拷/清零完成后再逐页收紧；**同页多个段取权限并集**（所以各段之间请页对齐）。
* 用户栈：`USER64_STACK_VA64`（`4GiB+64KiB`）起 16 KiB（4 页，`P|U|W|NX`），按 **SysV ABI** 压初始栈：
  `[rsp] argc=1, argv[0]="/hello.elf", NULL, NULL(envp), auxv..., AT_NULL/0`；
  `auxv` 至少含 `AT_PAGESZ(6)` / `AT_PHDR(3)` / `AT_PHNUM(4)` / `AT_ENTRY(9)` / `AT_UID/EUID/GID/EGID(11..14)`；
  进入 `_start` 时 `rsp % 16 == 0`。

### 6.2 运行方式

* 进 ring3 走 `user64_enter_at64()`（同一个用户窗口、同一份 TSS.rsp0 逻辑）；程序用 **`syscall` 指令**与内核通信；
* `exit(60)` 或 `exit_group(231)` 后回收：逐页解除映射 + `page_free_64`（中间页表页保留）；
* 装载与运行是两步：`elf64_load64()` → `elf64_run_loaded64()`（终端与启动路径用合一的 `elf64_run64()`）。

## 7. 怎么编一个能在 VimtuOS 上跑的程序

### 7.1 方案 A：VAP64（`int 0x80` 自有 ABI，最省事）

以仓库自带的示例为准（`user/hello64.asm`）：

```bash
# ① 汇编成"平铺二进制"（NASM -f bin，org 0，入口在段首；只能 RIP 相对寻址）
nasm -f bin user/hello64.asm -o build64/hello64.bin          # 实际产出 202 字节

# ② 加 VAP64 头（32B 头 + 名字 + code CRC32），打包器自带回读自检
py -3 tools/make_vap.py build64/hello64.bin build64/hello.vap hello
#   → [VAP] wrote build64/hello.vap name=hello code=202 crc=0x........
```

**写自己的程序**：把 `user/hello64.asm` 复制成 `user/你的程序.asm`，改逻辑与名字，重复上面两步即可。
`exit(2)` 一定要调；数据放**只读**（代码页不可写），要写缓冲用栈（示例里的 `print_dec` 就是在栈上做十进制转换）。

### 7.2 方案 B：ELF64（`syscall` 指令，Linux 号段）

以 `user/hello_elf64.asm` + `user/hello_elf64.ld` 为准：

```bash
# ① 汇编成 ELF64 目标文件（.text/.rodata/.bss）
nasm -f elf64 user/hello_elf64.asm -o build64/hello_elf64.o

# ② 用仓库自带的链接脚本静态链接（脚本把映像钉在用户窗口里）
ld.lld -m elf_x86_64 -T user/hello_elf64.ld -o build64/hello.elf build64/hello_elf64.o
```

链接脚本的关键点（`user/hello_elf64.ld` 的注释里写得很清楚）：

* `. = 0x0000000100000000 + SIZEOF_HEADERS` —— 让第一个段从文件偏移 0 开始映到 4GiB，
  这样**程序头表本身也在映像里**，`auxv` 的 `AT_PHDR` 才有意义；**默认脚本会把 ELF 头放进 4GB 以内的独立段 → 一定会被加载器拒**；
* 各段之间必须 `ALIGN(4096)`（权限按页给）；
* `/DISCARD/` 掉 `.interp` / `.dynamic` / `.rela*` / `.got*` 等（加载器不做重定位，留着只会让映像非法或变大）。

### 7.3 关于用 C 写（**未验证，谨慎使用**）

仓库里**只带了汇编示例**。理论上可以用 freestanding C 走同一套流程
（`clang -target x86_64 -ffreestanding -nostdlib -static -mno-red-zone -fno-stack-protector ...` +
上面两个入口 ABI 自己写 `_start` 和 syscall 包装），但**本仓库没有 C 用户程序示例、也没有验证过**；
要这么干请自己加一个示例并补验收脚本。

### 7.4 怎么装进去

**当前只有一条路**：把程序**嵌进系统内核**，启动时由内核装进 VimtuFS2（幂等，已存在就跳过）。以 `build64.sh` 为准：

```bash
# VAP64：objcopy 变 ELF64 目标文件（符号名按输入路径生成，必须从仓库根执行）
objcopy -I binary -O elf64-x86-64 -B i386:x86-64 build64/hello.vap build64/hello_vap64.o
# ELF64：同一手法（只嵌进系统内核，安装介质内核不带 ELF64 加载器）
objcopy -I binary -O elf64-x86-64 -B i386:x86-64 build64/hello.elf build64/hello_elf64_elf.o
```

然后把这两个 `.o` 加进 `build64.sh` 的 `SRCS_OS` 链接列表（脚本里已有），重新 `bash build64.sh`。
启动时 `kernel64.cpp` 的 `os_boot_path()` 会：

1. `vfs64_mount(app_drive, app_lba)`（主分区起始 LBA 由 `app64_main_part_lba64(drive)` 从安装器写的 MBR 里解析出来；解析不到退回 `PART_MAIN_LBA`）；
2. `app64_install_builtin64()` → 装成 **`/hello.vap`**；`elf64_install_builtin64()` → 装成 **`/hello.elf`**；
   已经存在就打 `[APP64] install skipped (exists) /hello.vap size=<n>`（**不会重复写盘**）；
3. 串口留证：`[APP64] install ok path=/hello.vap bytes=<n> crc=0x<hex>`、`[ELF64] install ok path=/hello.elf bytes=<n>`。

> **诚实说明**：目前**没有"把任意文件拷进 VimtuFS2"的宿主侧工具**（终端 `write/touch` 写的是内核内 ramfs，
> 不是 VimtuFS2；也没有图片/镜像注入脚本）。所以"装应用"目前等价于"改内核嵌入的文件并重编内核"。
> 给 VimtuFS2 写一个宿主编排工具（或给终端加 VFS 写入命令）是明确的下一步工作。

### 7.5 怎么启动

在桌面终端里：

| 命令 | 行为 |
|---|---|
| `run hello.vap`（或 `run /hello.vap`） | 从 VimtuFS2 读出来 → 按**文件头魔数**分派：`VAP64\0\0\0` → VAP64 路径（`int 0x80`） |
| `run hello.elf`（或 `run /hello.elf`） | 同上，前 4 字节 `\x7fELF` → ELF64 路径（`syscall` 指令） |
| `elfrun hello.elf` | **强制**走 ELF64 加载器（不做魔数分派），用来单独验证 ELF 路径 |
| `run 别的名字` | 名字不带 `/` 会自动补成 `/名字`；VimtuFS2 是单层路径，所以只能找根目录下的文件 |

串口证据（这两条路径成功的判据）：

```
[APP64] load path=/hello.vap via=vfs64_read bytes=240 code=202 name=6 crc=0x........
[APP64] launch ok path=/hello.vap name=hello rc=0
hello from installed app (VAP64 on VimtuFS2)
[ELF64] load path=/hello.elf entry=0x0000000100000190 phnum=6 segs=4 size=<n>
[ELF64] enter ring3 entry=0x0000000100000190 rsp=0x0000000100010000
hello from ELF64 (syscall insn)
pid=<n> / open /hello.elf fd=<n> / read=<n> / sec=<n> / done (exit 60)
[ELF64] back to kernel (ring0) rc=0
[ELF64] launch ok rc=0 path=/hello.elf
```

（`run`/`elfrun` 打的是 `[APP64] run cmd path=<p> rc=<n>` / `[ELF64] run cmd path=<p> rc=<n>`；失败时 rc 为负并打印 `run: failed (see serial log)`。）

## 8. 一分钟自检清单（写程序时最容易踩的坑）

1. **VAP64 代码段是平铺二进制**：`nasm -f bin` + `org 0`，用 RIP 相对寻址，别假设自己被加载到某个固定低地址。
2. **VAP64 代码页是 R/X**：写全局变量会 #PF —— 数据放栈上，或走 ELF64 的 `.bss`/`mmap`。
3. **`int 0x80` 只支持 write(1)/exit(2)/getpid/ticks/sleep_ms**；要文件就用 ELF64 + `syscall`。
4. **ELF64 必须链接在 `4GiB .. 4GiB+64KiB`**，并用仓库的 `.ld` 脚本；段要页对齐；不要 `PT_INTERP`/重定位。
5. **路径是单层绝对路径**（`/name`，≤27B）；`open` 只读、fd 只有 3..6 个、读缓存 512B。
6. **没有 glibc / libc**：`printf`、`malloc`、`memcpy` 都要自己写（内核里也没有 libc 可借）。
7. **`syscall` 路径每个调用都打串口日志**，别写高频调用循环（现在只适合演示/小工具）。
8. **`exit` 必须显式调用**；VAP64 若走到代码段末尾、ELF64 若 `_start` 返回，都没有"正常结束"的语义。
9. **没有地址空间隔离**：你的程序与其它用户程序共用同一个 4GiB 窗口；不要依赖"别的程序看不到我的数据"。
10. **验证手段**：自己加一个 `tests/xxx_test.py`（串口断言 + 必要时 screendump 像素断言），
    并把它加进 `tests/status_report.py` 的 `TESTS`/`CAPS` —— 这个项目里"能被脚本证明"才算完成。
