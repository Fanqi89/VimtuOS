# 应用层与系统调用说明（给想给 VimtuOS 写程序的人）

> 适用版本：VimtuOS 0.1.0（Vimtu64，x86_64 long mode）
> 本文所有字段、常量、号段与行为都**逐条从源码核对**（`kernel/app64.h`、`kernel/elf64.h`、
> `kernel/syscall64.h`、`kernel/syscall64.cpp`、`kernel/usermode64.h`、`tools/make_vap.py`、
> `user/*.asm`、`build64.sh`），改动代码时请同步本文。

## ★ 批次 M：VimtuFS2 大文件（二级间接块）几何与兼容策略（一页纸）

**块链层级**（唯一权威定义：`kernel/vfs64.h` 文件头 + `kernel/vfs64.cpp` 的 `VFS_I_*` / `VFS64_MAX_*`）：

| 层 | fs 块号 | 指针位置 | 覆盖字节 |
|---|---|---|---|
| 直接块 | 0..3 | inode 偏移 8/12/16/20 | 0 .. 2047 |
| 一级间接 | 4..131 | inode 偏移 24（`ind`）：块里 128 个块号 | 2048 .. 67583 |
| **二级间接** | 132..16515 | inode 偏移 **71**（`dind`）：128 个子块号，每个子块再指 128 个块号 | 67584 .. 8455679 |

* **单文件上限 = 16384 块 = 8 MiB（8388608 B）**：映射能力 16516 块（8456192 B），
  对外上限**刻意取整**到 8 MiB（`VFS64_MAX_FILE_BLOCKS = 16384`），留 132 块映射余量。
* **卷版本号不变（仍是 3）**：inode 仍是 128 B、超级块/几何/CRC 规则一个字都没改，
  只是把原保留区首 4 字节（偏移 71）定义为二级间接指针（保留区缩到 [75,124)）。兼容矩阵：
  * 老 v3 卷（批次 M 之前）：该字段恒为 0（当时要求保留区全 0）→ 新内核读作"没有二级间接"，
    **能挂载、能读、能写，而且照样能往上写 8 MiB 的大文件**。
  * 老内核（批次 M 之前）：读"含二级间接的文件"会因保留区非 0 而拒绝**那一个 inode**（`reason=rsvd3`），
    其余文件不受影响 —— **单向升级**，不假装双向兼容。
  * **v2 旧卷没有 `dind` 字段**（32..59 是名字、60 是 CRC）→ 上限仍是 **67584 B**；
    `vfs64_max_file_bytes64()` 返回当前卷的真实上限，超限一律 `-1` + 打点。
* **空间语义**：**不做稀疏文件**（`size` 以内的每个 fs 块都必须有映射块；读路径碰到未映射块 = 损坏 -> `-1`）；
  `seek` 过末尾再写 = 中间**补零**（`vfs64_write_at64` 写实零，与 fd64 既有语义一致）。
* **读写路径**（缓冲区一律由调用方给，内核不再有 8 MiB 级缓冲）：
  * `vfs64_read_at64(path, off, buf, len, &got)`：按偏移分块读（跨三级都对）；
  * `vfs64_write_at64(path, off, buf, len)`：**部分写/追加**（不存在则创建），缺块按需分配、`off > size` 补零；
    **空间预检**（数据块 + 间接块 + 1 块余量）不够就**先失败**，绝不写一半；超上限在任何写盘之前被拒；
  * `vfs64_write_stream64(path, len, src, ctx)`：整体重写（数据由回调给），是 `vfs64_write64` 的底层实现。
* **块回收**：`unlink` / 整体重写会释放 数据块 + 一级间接 + **二级间接 + 它下面 128 个子块**；
  写-删-写循环后空闲块数必须回到基线（`vfs64_selftest` bit13 与 `tests/bigfile64_test.py` 都断言）。
  失败的写：建链阶段失败会**回滚**本次新分配的块；指针块已落盘后才失败只可能"泄漏块"，绝不指向已释放的块。
* **上层对齐**：
  * `fd64`：读写都按偏移（`read` 直读调用方缓冲；`write` 只改被覆盖的块），**删掉了两块整文件缓冲**；
    `lseek` 是 64 位偏移，上限判断用 `FD64_FILE_MAX = VFS64_MAX_FILE_BYTES`。
  * `explorer64`：粘贴 = 64 KiB/块复制（`explorer64_copy_file64`，跨卷同一份代码），
    空间预检用 `vfs64_blocks_for_bytes64(size) + 1`；大于上限的源**整条跳过**（不是截断）。
  * `terminal64`：`cat` 最多打 **4096 B** 并**明确提示截断**（先 `stat` 拿大小，不再读完整文件）；
    `write FILE TEXT` 受**命令行长度**限制（不是文件上限）；新增 `bigtest [1mb|8mb|limit|recycle|copy <src> <盘符>]`。
  * `app64` / `elf64`：**上层上限不动**（VAP64 代码 32 KiB = 用户窗口；ELF64 读盘缓冲 96 KiB），
    只在头注释里写清"FS / 用户窗口 / 缓冲"三层归属。

## 1. 一页速览

| 项目 | 结论 |
|---|---|
| 用户态 | ring3，CPL=3，GDT 选择子：内核代码 `0x08` / 内核数据 `0x10` / 用户数据 `0x23` / 用户代码 `0x2B` / TSS `0x30` |
| 用户地址空间 | **一个 1 MiB 窗口**：`4GiB .. 4GiB+1MiB`（所有程序**共用**，没有独立地址空间） |
| 地址空间隔离 | ❌ 没有；也没有 `fork` / `execve` / `clone` / 线程 |
| 系统调用入口 | ① `int 0x80`（Vimtu64 自有 ABI，号段 1..8）② `syscall` 指令（Linux x86_64 号段，25 个号有实现，其余 `-ENOSYS`） |
| 可执行文件格式 | ① **VAP64**（自有，32B 头 + 名字 + 代码段 + CRC32，代码 ≤32KiB）② **ELF64**（静态 `ET_EXEC`/`ET_DYN`、`PT_LOAD`、无 `PT_INTERP`/无重定位） |
| 程序从哪来 | 构建期用 `objcopy` 嵌进**系统内核**，启动时由内核装进 VimtuFS2 的 `/hello.vap`、`/hello.elf`（幂等）；**目前没有"把任意文件拷进 VimtuFS2"的宿主工具**（见 §7 的诚实说明） |
| 怎么启动 | 终端：`run <名字\|/路径>`（按文件头魔数自动分派）/ `elfrun <路径>`（强制 ELF64）；**桌面文件资源管理器（此电脑）双击**：VAP64 → `app64_launch64`、ELF64 → `elf64_run64`（同一条路径，只是入口从 UI 进） |
| 能跑什么 | 自己写的 `-nostdlib` 程序；**不能跑 glibc/发行版二进制**（缺 execve、vDSO、TLS、信号、futex、动态链接、重定位） |
| 多用户 / 会话身份（批次 P1c） | 用户库 **`/etc/users.db` v1**（加盐 **SHA-256×1000**；普通用户 uid≥1000、`/home/<名>/Desktop`；root **不在登录界面**）；`su - root`/`su -`/`sudo -i` 只改**会话身份**（euid=0，GUI 用户名/头像不变）；**权限位尚未拦截（P4）** —— `getuid/getgid`(102/104) 仍恒 0 |
| Rust 模块（批次 P1） | `gui_rs/`（`#![no_std]`、无 alloc/无浮点）是设计 Token + 主题配色的**真源**，编成 `gui_rs/gui_rs.o` **只链进系统内核**（安装介质 0 个 Rust 符号）；终端 `rust [tokens\|set N]`；C 侧声明在 `kernel/rust64.h` |
| 图像解码（批次 P1） | `kernel/img64.{h,cpp}`：PNG（色型 0/2/3/4/6 + 多块/动态 Huffman）与未压缩 BMP；**JPEG 未支持**；壁纸/头像/Dock 开始按钮图标走"VimtuFS2 文件优先、内置兜底" |

## 2. 用户内存布局（`kernel/usermode64.h`，唯一定义点）

整个用户地址空间 = **4GiB 起、1 MiB 大的一个窗口**（`USER64_CODE_VA64 = 0x0000000100000000`，
`USER64_WINDOW_BYTES64 = 1 MiB`）。窗口内部的分区（**互不重叠**，由 `syscall64_selftest64()` 的 bit0 断言把关）：

| 区域 | 虚拟地址 | 大小 | 权限 | 用途 |
|---|---|---|---|---|
| ELF 装载区 | `4GiB + 0x00000` .. `4GiB + 0x10000` | 64 KiB | 按段（见 §5.2） | ELF64 的 `PT_LOAD` 段落在这里；也是 VAP64 代码页的位置（代码页 R/X） |
| 用户栈 | `4GiB + 0x10000`（`USER64_STACK_VA64`） .. `+0x4000` | 16 KiB（4 页） | `P|U|W|NX` | VAP64 与 ELF64 共用；ELF 的 SysV 初始栈建在这里，`rsp` 16 字节对齐 |
| brk 区 | `4GiB + 0x40000`（`USER64_BRK_VA64`） .. `+0x10000` | 64 KiB | `P|U|W|NX` | Linux `brk(12)` 的固定可写区（首次调用时整块映射） |
| 自检临时页 | `4GiB + 0x80000`（`USER64_TEST_VA64`） | 4 KiB | 临时 | 只给 `user64_selftest64()` 用，用完解除映射 |
| mmap 区 | `4GiB + 0x90000`（`USER64_MMAP_VA64`） .. 窗口末 | 剩余 | `P|U|W|NX` | Linux `mmap(9)` 的 bump 分配器（至少保证 64 KiB 可用） |

要点：

* 用户页要求 **PML4E[0] / PDPTE / PDE / PTE 四级都打开 U/S**；大页会拒绝（`user64_map_page64` 撞大页即失败）。
* 内核自己的映射在 PML4[0] 的低 4 GiB 与 PML4[511] 的高半区，**不套用户权限**；4 GiB 以上在 PML4[0] 里原本是空的，正好当用户窗口。
* `TSS.rsp0` 随任务切换维护（ring3 → ring0 的中断切栈用）；`syscall` 指令**不换栈**，入口切到一份**专用 16 KiB 内核栈**（与 TSS.rsp0 解耦，避免中断帧/syscall 帧互相覆盖）。
* 每个来自用户态的指针都要过 `user64_range_ok64(va, len)`：整段落在窗口内、且四级都是已映射用户页，否则拒（打 `[SYSCALL] deny`）。

## 3. 入口一：`int 0x80`（Vimtu64 自有 ABI）

* 门：`IDT[128]` 装成 `0xEE`（P=1、DPL=3 中断门），ring3 直接 `int 0x80` 即可。
* 寄存器约定：**`rax` = 调用号；`rdi` / `rsi` / `rdx` = 参数 1/2/3；返回值放 `rax`（负数 = 错误）**。
* 号段（`kernel/syscall64.h` 顶部；**这条路径的号段与 Linux 号段完全隔离**）：

| 号 | 名称 | 参数 | 行为与返回值 |
|---|---|---|---|
| 1 | `write` | `rdi`=fd、`rsi`=buf、`rdx`=len | **只支持 fd=1**（输出到**串口 + 屏幕**）；`len` 为 0 或 >1024 → `-1`；buf 不在用户窗口 → `-1`；成功返回写出的字节数 |
| 2 | `exit` | `rdi`=code | 把控制权交回内核（不改写用户帧直接返回 ring0 蹦床）；**不再返回用户态** |
| 3 | `getpid` | — | 当前任务 id（`task_current_id_64()`；没有调度器时 0） |
| 4 | `ticks` | — | PIT tick 数（**250 Hz**） |
| 5 | `sleep_ms` | `rdi`=毫秒 | 睡眠（走 `task_sleep64`；没有调度器时按 tick 忙等 `hlt`）；返回 0 |
| 6 | `open` | `rdi`=path（用户态 `/name`） | **真（批次 B 起）**：走 `kernel/fd64.cpp` 的 FD 层（只读）；成功返回 fd（≥3），失败返回 `-1` |
| 7 | `read` | `rdi`=fd、`rsi`=buf、`rdx`=len | **真（批次 B 起）**：从 FD 层读（单次上限 4096B）并拷进用户 buf；buf 先过 `user64_range_ok64`；fd 非法/越界 `-1` |
| 8 | `close` | `rdi`=fd | **真（批次 B 起）**：释放 FD 层的槽 → 0；fd 非法 `-1` |
| 其它 | — | — | 返回 `-1` |

* 打点（自动验收依赖，别改格式）：只有 `write(1)` 与 `exit(2)` 会打
  `[SYSCALL] nr=<n> rdi=<hex> rsi=<hex> rdx=<hex> ret=<hex>`。

**最小示例（完整可跑的源码见 `user/hello64.asm`）**：

```asm
bits 64
org 0                      ; VAP64 代码段是"平铺二进制、入口在段首"，只能 RIP 相对寻址
_start:
    lea     rsi, [rel msg]
    mov     edx, msg_len
    mov     eax, 1         ; write
    mov     edi, 1         ; fd = 1
    int     0x80
    mov     eax, 2         ; exit
    xor     edi, edi
    int     0x80
.hang:
    jmp     .hang
msg:     db "hello", 10
msg_len  equ $ - msg
```

## 4. 入口二：`syscall` 指令（Linux x86_64 号段）

* 寄存器约定与 Linux 完全一致：**`rax` = 号；`rdi/rsi/rdx/r10/r8/r9` = 参数 1..6；返回 `rax`（负值 = `-errno`）；
  `rcx`/`r11` 被 CPU 覆盖**（易失，Linux 也一样）。
* MSR 现场（`syscall64_init64()` 写入并回读留证）：`EFER.SCE=1`；
  `STAR = (0x1B << 48) | (0x08 << 32)` → `sysret` 的 `CS=0x2B`、`SS=0x23`，`syscall` 的 `CS=0x08`、`SS=0x10`；
  `LSTAR = syscall64_insn_entry64`；`FMASK = 0x700`（入口自动清 TF/IF/DF）。
* 帧标记：`SYSCALL64_INSM_FRAME_MARK64 = 0x180`（`int 0x80` 是 `0x80`），分发器靠它分流，两条路径的号段互不影响。
* 打点：这条路径**每个调用都打** `[SYSCALL] insn nr=<n> rdi=<hex> rsi=<hex> rdx=<hex> ret=<hex>`（方便对照调试）。

### 4.1 号段表（`kernel/syscall64.cpp` 的分发器，逐条核对）

| 0 | `read` | **真**：`fd=0` 立即返回 0（EOF，本内核没有键盘输入流）；`fd≥3` 走 `kernel/fd64.cpp` 的 FD 层（读整文件 + 按游标切片，单次上限 **4096B**）；其它 fd → `-EBADF(9)` |
| 1 | `write` | **真**：`fd=1` → 串口 + 屏幕；`fd=2` → 只串口；`fd≥3` → **真写文件**（fd64，写到游标处并立刻整体落盘）；单次 `len` ≤ **4096**，超限 `-EINVAL(22)`；越界 `-EFAULT(14)` |
| 2 | `open` | **真**：走 FD 层（`/dir/sub/name` **多级路径**，v3 起；`O_CREAT`/`O_TRUNC`/`O_WRONLY`/`O_RDWR` 按 Linux 子集映射；`flags` 不认识的高位忽略）；不存在且没有 `O_CREAT` → `-ENOENT(2)`；表满 `-EMFILE(24)` |
| 3 | `close` | **真**：释放 FD 槽 → 0；非法 fd / 标准流 → `-EBADF` |
| 4 | `stat` | **真（最小，批次 C 起）**：按路径走 `vfs64_stat`，填 144B `struct stat`（目录 `0040000\|0755`、普通文件 `0100000\|0444`）；不存在 `-ENOENT(2)` |
| 5 | `fstat` | **真**：填 144B `struct stat`；fd 0/1/2 → 字符设备最小三字段（`st_mode=0020000\|0666`、`st_size=0`、`st_nlink=1`）；fd≥3 → 走 fd64（普通文件 `0100000\|0444` + 真实大小；目录 `0040000\|0755`） |
| 6 | `lstat` | **部分（批次 C 起）**：与 `stat` 同一实现（本文件系统没有符号链接，因此等价） |
| 8 | `lseek` | **真**：fd≥3 → `fd64_lseek64`（`SEEK_SET/CUR/END`，**64 位偏移**，游标 0..8388608（8 MiB））；fd 0..2 → `-ESPIPE(29)`；越界 → `-EINVAL` |
| 9 | `mmap` | **真（批次 C 起每进程）**：**进程私有** bump 分配器（从 `4GiB+576KiB` 起），页 `P\|U\|W\|NX`；支持 `MAP_FIXED(0x10)`；空间不足 → 已映射页回滚 + `-ENOMEM(12)`。没有进程上下文时退回共享窗口实现 |
| 10 | `mprotect` | **真（每进程）**：逐页改叶子权限（`PROT_READ=1`/`WRITE=2`/`EXEC=4` → 清 NX）；范围/页非法 → `-EINVAL` |
| 11 | `munmap` | **真（每进程）**：逐页解除映射 + `page_free_64` 回收 → 0；未映射/越界 → `-EINVAL` |
| 12 | `brk` | **真（每进程）**：首次调用整块映射 64 KiB 可写区（`4GiB+256KiB`），之后**按进程**维护 brk 端点；`brk(0)` → 当前 brk；区间外 → 旧 brk（Linux 同语义） |
| 13 | `rt_sigaction` | **只记录不投递**：读用户 `struct sigaction` 的 `handler`（32B，过范围校验）存进**进程**；内核没有任何信号投递路径。无进程上下文时只做校验、不记录 |
| 14 | `rt_sigprocmask` | **只记录不投递**：记录屏蔽字（`old` 写回）；语义同上 |
| 15 | `rt_sigreturn` | **`-ENOSYS`**：没有信号帧可恢复 |
| 16 | `ioctl` | **真（最小）**：fd ≤ 2 且请求 `TIOCGWINSZ(0x5413)` → 写回 `25x80`（`row=25 col=80 xpixel=640 ypixel=200`）并返回 0；`TIOCSWINSZ(0x5414)` → 忽略并返回 0；其它 → `-ENOTTY(25)` |
| 20 | `writev` | **真**：fd=1/2，最多 **8** 个 iovec（每个 16B），逐个写；超限 `-EINVAL` |
| 21 | `access` | **真（最小，批次 C 起）**：存在性检查（没有权限模型 → `mode` 忽略，如实注明）；不存在 `-ENOENT` |
| 22 | `pipe` | **真（批次 D）**：`kernel/fd64.cpp` 的管道对象（**64 B 环形缓冲**）+ 读端/写端两个 fd 写进用户给的 `int[2]`。**没有阻塞语义**：写满 → 短写（完全没空间 `-EAGAIN`）；读空且写端还开着 → `-EAGAIN`；写端全关 → 读返回 0（EOF）。`fork` 后父子各持一端即可通信（`user/pipe64.asm` 就是这条证据） |
| 24 | `sched_yield` | **真（批次 C 起）**：`task_yield64()` 让出到下一个 tick；没有调度器时直接返回 0 |
| 32 | `dup` | **真（批次 D 修正语义）**：新旧 fd 指向**同一个打开文件对象**（`OpenFile64`，**共享偏移游标**），引用计数 +1；fd<3 → `-EBADF` |
| 33 | `dup2` | **真（批次 D 修正语义）**：目标 fd≥3 时先关旧目标、再共享同一个对象；目标 ≤2（重定向标准流）→ `-ENOSYS`（标准流是分发器自己认的虚拟流，没有对象） |
| 34 | `pause` | **部分**：本内核不投递信号 → 有界等待 1 秒后返回 `-EINTR(4)`（绝不死等） |
| 35 | `nanosleep` | **真（批次 C 起）**：走调度器睡眠（有界 60 秒，防挂死）；`rem` 忽略 |
| 37 | `alarm` | **只记录不投递**：记进程的 alarm 秒数并返回上一次的值（不投 SIGALRM） |
| 39 | `getpid` | **真**：**进程 pid**（批次 C 起；没有进程上下文时退回任务 id） |
| 56 | `clone` | **部分**：只支持 `flags=0` / `SIGCHLD(17)` 的 fork 语义；`CLONE_VM`/`CLONE_THREAD` 等 → `-ENOSYS` |
| 57 | `fork` | **真**：**整页物理复制**（不做 COW）；子进程从父进程 syscall 的下一条指令继续、`rax=0`；父进程拿到子 pid |
| 58 | `vfork` | **等同 `fork`**（没有"共享地址空间直到 execve"的优化语义，如实注明） |
| 59 | `execve` | **真（静态 ELF）**：释放旧映像 → 复用 ELF64 装载器 → 重建初始栈/auxv → 改写帧直接回到新入口；`argv` 过范围校验；`envp` 恒为空。★ 装载失败会按退出码 127 终止进程（Linux 会保留旧映像继续跑，这是**如实标注的差异**） |
| 60 | `exit` | **真**：把控制权交回内核（帧改写 + ring0 蹦床），进程退出码 = 用户 `exit` 码 |
| 61 | `wait4` | **真**：阻塞轮询（`task_sleep_ms64` + 5 秒有界超时）；`status = (code & 0xFF) << 8`；支持 `pid>0` 与 `-1`（任一子）；`WNOHANG(1)` 支持 |
| 62 | `kill` | **部分**：`SIGKILL(9)`/`SIGTERM(15)` → 立即终止（TERM 记退出码 **143**）；其它信号"记录但不投递"；不允许自杀（`-EINVAL`，如实） |
| 63 | `uname` | **真**：写一份静态 `struct utsname`（6 × 65B）：`VimtuOS` / `vimtu64` / `0.1.0-vimtu64` / `#1 ring3+syscall` / `x86_64` / `(none)` |
| 74 | `fsync` | **部分**：fd≥3 → 0（写路径已**即时落盘**，没有脏页要刷）；fd 非法 `-EBADF` |
| 79 | `getcwd` | **真**：把 `"/"` 写进用户 buf（`size≥2`）并返回 buf 指针（Linux 语义） |
| 82 | `rename` | **`-ENOSYS`**（**批次 J 起内核已有 `vfs64_rename64`（同目录改名，文件管理器 F2 用它），但没有接进这条号段**） |
| 83 | `mkdir` | **真（批次 C 起）**：走 `vfs64_mkdir`（真写盘）；单飞行者：并发调用返回 `-EBUSY(16)` |
| 84 | `rmdir` | **`-ENOSYS`**（`vfs64` 没有删目录原语） |
| 87 | `unlink` | **真（批次 C 起）**：走 `vfs64_unlink`（真写盘）；单飞行者同上 |
| 89 | `readlink` | **部分**：只对 `/proc/self/exe` 返回当前进程的映像路径（不补 NUL，Linux 语义）；其它 `-ENOENT` |
| 96 | `gettimeofday` | **真（批次 C 起）**：用 `g_ticks64`（250 Hz）造 `tv_sec`/`tv_usec`（4 ms 粒度）；`tz` 恒 0 |
| 97 | `getrlimit` | **部分**：没有 per-process 配额 → 返回 `RLIM_INFINITY`（`RLIMIT_STACK`/`RLIMIT_NOFILE` 给常量） |
| 102 / 104 | `getuid` / `getgid` | **真**：都返回 `0`（本内核没有用户概念） |
| 110 | `getppid` | **真（批次 C 起）**：**进程 ppid**（没有进程上下文时 0） |
| 158 | `arch_prctl` | **真（批次 C 起写 MSR）**：`ARCH_SET_FS(0x1002)` **真写 `IA32_FS_BASE(0xC0000100)`** 并记进进程（任务切换时保存/恢复！）；非规范地址 `-EINVAL`；`ARCH_GET_FS(0x1003)` 写回用户指针；其它 `-EINVAL` |
| 160 | `setrlimit` | **`-EPERM(1)`**：没有配额可改（不假装成功） |
| 218 | `set_tid_address` | **真（最小）**：返回 0（没有 `clear_child_tid` 唤醒路径） |
| 228 | `clock_gettime` | **真（近似）**：用 `g_ticks64`（250 Hz）造值 —— `tv_sec = t/250`、`tv_nsec = (t%250) * 4000000`（**4 ms 粒度**）；`clockid` 0..3；其它 → `-EINVAL` |
| 231 | `exit_group` | **真**：**结束整个进程**（本内核 1 进程 1 任务，语义与 `exit` 一致） |
| 257 | `openat` | **真**：`open` 的现代入口（同一个 fd64 实现）；`dirfd` 忽略（只支持 `AT_FDCWD`）；相对路径要求以 `/` 开头，否则 `-EINVAL` |
| 318 | `getrandom` | **真（非密码学安全）**：ticks + TSC + xorshift 伪随机；单次上限 256B；越界 `-EFAULT` |
| 其它所有号 | — | **`-ENOSYS(38)`**，并且同一个号只打一次 `[SYSCALL] enosys nr=<n>`（防刷屏） |

`dup`/`dup2` 从"部分"变成真实现），其中 `rename`(82)/`rmdir`(84)/`rt_sigreturn`(15) 是显式 `-ENOSYS`，
13/14/37 是"只记录不投递"。已实现号里做不到的分支一律返回**具体负 errno**
（`-EBADF/-EFAULT/-EINVAL/-ENOMEM/...`），**绝不返回 0 假装成功**。

## 9. 进程与地址空间（批次 C：`kernel/proc64.h` / `kernel/proc64.cpp`）

### 9.1 进程模型（一页纸）

* **任务（线程）属于进程**。进程表（16 槽）+ 每个进程一个内核任务（16 KB 内核栈），
  `task64.cpp` 里只多存一个 `void* proc` 与三个"切换时要装载的数值"：`mm_cr3` / `mm_fs_base` /
  `syscall 专用栈顶`。切换点与 `TSS.rsp0` 完全同一处（`schedule64` / `task_exit64` / `task_start64`
  里的 `task_apply_ctx64()`）—— 这样调度器不需要知道 `Proc64` 的内部布局，既有语义/打点一行没动。
* **页表共享策略**：每进程自己的 PML4 页 + 自己的 PDPT 页。
  * `PML4[511]`（内核高半区）**原样复制**引导期那一项 → 内核代码/数据在**所有进程里共享同一批页表**；
  * `PML4[0]` 指向**新 PDPT**：`PDPT[0..3]` 照抄引导期（**前 4 GB 恒等映射共享同一批 PD** ——
    内核堆/页池/LFB 都是按物理地址直接访问的，这条链必须原样成立），`PDPT[4]` 起清 0 →
    **VA 4GiB..5GiB（用户窗口）每进程私有**，代价只有 1 个 PDPT 页 + 按需的 PD/PT。
* **CR3 切换点**：① 调度器切任务（上面那三处）；② 任务显式切（`proc64_switch_to64()` /
  `proc64_switch_to_kernel64()`）。切 CR3 本身就会刷新非全局 TLB 项（用户页 PTE 都没打 `PTE_GLOBAL`），
  所以**不额外 invlpg 全表**。
* **FS 基址（TLS）**：`IA32_FS_BASE(0xC0000100)` 是全局 MSR，进程切换时**必须保存/恢复**。
  落点与 `TSS.rsp0` 同一处（`task64_load_fs_base64()`，值来自 `proc->fs_base`）；
  `arch_prctl(ARCH_SET_FS)` 现在**真写这个 MSR**（glibc 的 TLS 全靠它）。
* **每任务 syscall 栈**：`SYSCALL` 不换栈，入口要自己切栈。批次 C 起每个任务在**自己内核栈顶下方
  4 KB** 开一块（原来是一块全局专用于栈）—— 否则 A 的 syscall 帧会被 B 的覆盖。栈布局（16 KB）：
  顶部 `[top-0xD0, top)` 是 ring3 中断帧（`rsp0 = top`）；`top-0x1000` 是 syscall 栈顶；
  `top-0x2000` 以下才是任务自己的内核 C 栈（`TASK64_ENTRY_RSP_RESERVE`）。

### 9.2 fork：**整页物理复制，不做 COW**（取舍写清）

`fork` 复制父进程用户窗口里**每一个已映射的 4 KiB 页**（新物理页 + `memcpy` 4 KB），并按父的
PD/PT 结构在子里重建同样的页表结构；叶子权限（含 NX）原样照抄；`brk`/`mmap` 记账与 `fs_base` 继承。
子进程的用户现场 = **父进程这一次系统调用的帧**（`rip` 是 syscall 的下一条指令、`rsp`/`rflags`/全部
GPR 都在里面），只把 `rax` 改成 0 —— 这正是 Linux fork 的"从同一点继续、返回值不同"，
而且 `task_switch_iret64` 弹的就是同一份 0xD0 布局，不需要任何手工拼装。

**为什么不上 COW**：COW 要"写时缺页 + 引用计数 + 页表项只读"三件套，缺页处理还得区分用户 COW 与
内核 `#PF`（要改 ISR 路径），而页池只有 ~384 MB、演示映像只有几页。整页复制的实现风险与调试成本
远低于 COW，语义上完全等价（父子互不可见）。页数上限 `PROC64_FORK_MAX_PAGES = 256`（≈1 MiB），
超了 `fork` 直接 `-ENOMEM` 并如实打点。

### 9.3 execve：在**当前进程里**换映像

`execve` 先把 `path`/`argv` 从**用户态指针**读进内核缓冲（逐个过 `user64_range_ok64`），
然后：释放旧映像（整个用户区 + 页表页）→ 复用 `elf64` 的装载逻辑（`elf64_load_for_exec64`，
它按调用方给的 `argv` 建初始栈与 auxv：`AT_PAGESZ/AT_PHDR/AT_PHNUM/AT_ENTRY/AT_UID/...`）→
重置 brk/mmap 记账 → **改写这一次系统调用的帧**（`rip`=新入口、`rsp`=新栈、`rax`=0、清 GPR、
`rflags=0x202`）→ `sysret` 直接回到新映像的 `_start`。

★ **如实标注的差异**：装载失败时本实现会按退出码 **127** 终止进程（Linux 会保留旧映像继续跑）。
理由：保留旧映像需要"先装到临时地址空间再原子切换"（影子地址空间 + 两份记账），
收益只是这一种边角场景。

### 9.4 wait4 / kill / 信号

* `wait4`：`task_sleep_ms64(2)` 轮询 + **5 秒有界超时**（超时 `-EAGAIN` 并打点）。
  **为什么不做等待队列**：调度器只有"睡到某个 tick"，没有阻塞/唤醒原语与等待队列对象，
  加一套要改刚修过回收竞态的 `task64.cpp`；轮询在有界场景下更划算。`status = (code & 0xFF) << 8`。
  ★ 被信号终止的进程在本内核里按"退出码 143（SIGTERM）/ 137（SIGKILL）"编码，**与 Linux 的
  "低 7 位放信号号"不同**（`[PROC64] kill/exit` 行里如实打出信号号）。
* `kill`：`SIGKILL(9)`/`SIGTERM(15)` → 立即终止目标（把它任务置 DEAD + 释放它的地址空间）；
  其它信号**只记录不投递**；不支持自杀（`-EINVAL`）。
* `rt_sigaction` / `rt_sigprocmask`：**只记录**（handler 地址、屏蔽字），`rt_sigreturn` 恒 `-ENOSYS`
  —— 本内核没有"用户栈上构造信号帧 + 恢复"这套机制，也没有 vDSO/restorer。**绝不假装投递**。

### 9.5 用户窗口"可用性"与两条引导路径（**实测结论，别把没验证的说成验证过**）

用户窗口要能用，必须往**引导期页表的顶层**写东西（给 `PML4[0]`/`PDPTE`/`PDE`/`PTE` 打开 U/S）：

| 引导路径 | 引导期页表 | 能不能建用户窗口 / 切 CR3 | 实测 |
|---|---|---|---|
| **BIOS**（`boot/loader64.asm`） | 我们自己建的 PML4（物理 `0x40000`，可写） | 能：每进程 CR3 + 用户窗口都成立 | QEMU/SeaBIOS：`[PROC64] init mode=isolated`，fork/execve/wait4/kill 全过（见 `tests/proc64_test.py`） |
| **UEFI**（`boot/efi/uefi64.c`） | **固件当前活动的 PML4**（EDK2 把页表页标成只读；且 `mov cr3` 在 VMware EFI 下已知会立刻复位） | **不能**：连给 `PML4[0]` 打开 U/S 都是 `#PF`（实测 `err=3`、`cr2=固件 PML4`） | QEMU+OVMF：`[USER64] user window NOT available`、`[PROC64] init mode=shared`、`[PROC64] cr3 isolation OFF ...`、`[PROC64] demo skipped`、`[APP64] ring3 launches skipped`，桌面照常起来 |

UEFI 下因此自动进 **共享地址空间模式**：`fork`/`vfork`/`clone`/`execve`/`wait4` 一律 `-ENOSYS`，
`brk`/`mmap` 退回共享窗口实现（与批次 B 行为一致），启动期的 ring3 演示整段跳过。
**串口与本文档都如实标注，绝不假装隔离成立。**

## 10. 离 glibc 还差什么（如实清单）

批次 C 之后**自有静态 ELF64**（`ld.lld -static -nostdlib`）能 `load → ring3 → fork/execve/wait4/kill → exit`，
但**发行版/glibc 程序仍然跑不起来**。差距按优先级：

1. **动态链接器与 PT_INTERP**：加载器只做静态装载（不做重定位、不看 `PT_INTERP`/`PT_DYNAMIC`），
   所以任何"依赖 ld.so"的 ELF 都进不来。要做：`PT_INTERP` 处理、把解释器也映射进同一地址空间、
   `AT_BASE`、ELF 重定位（REL/RELA、`R_X86_64_GLOB_DAT/JUMP_SLOT/RELATIVE`）。
2. **完整 TLS / vDSO**：`FS.base` 已经真生效（`arch_prctl` 写 MSR + 切换保存/恢复），
   但没有 `ARCH_SET_GS`、没有 per-thread TLS 区（`PT_TLS` 段、`__tls_get_addr`）、
   没有 vDSO（`clock_gettime` 等仍走真 syscall，能用但慢）、没有 `rseq`/`set_thread_area`。
3. **futex 真语义**：没有 `futex(202)`、没有 `CLONE_THREAD`，所以 pthread/stdio 锁、`
   std::mutex` 全都不可用；`clone` 只支持 fork 语义。
4. **信号投递**：只有"记录不投递"。要做：用户栈上的信号帧、`rt_sigreturn`、
   restorer/vDSO、`sigaltstack`、屏蔽字与 `pending` 的完整语义。
5. **socket / 网络 ABI**：内核有 e1000 驱动 + ARP/ICMP，但**没有** `socket/bind/connect/send/recv`
   这套 fd 层（也没有 AF_UNIX/inet 的协议族）。
6. **`/proc` 与 pty**：没有 `/proc`（只有 `readlink("/proc/self/exe")` 一个特例）、没有
   `/dev`（`/dev/null`、`/dev/zero`、tty）、没有 pty 与作业控制（`setpgid`/`tcsetpgrp`）。
7. **uid/gid 与权限模型**：**批次 P1c 起内核里已有真实的用户库与会话身份**（`kernel/userdb64.{h,cpp}`：
   `/etc/users.db` 加盐 SHA-256×1000；`su`/`sudo` 只改会话 euid，GUI 用户名/头像不变），但**权限位尚未拦截
   （P4）**：`getuid/getgid`(102/104) **仍恒 0**、`access` 忽略 mode、没有 `setuid/setgid/chmod/chown/umask`、
   也没有 `CAP_*`（syscall 侧对用户身份一无所知，身份只在终端/GUI/登录层可查）。
8. **文件系统能力（v3 目录树已落地，仍有边界）**：多级绝对路径 `/dir/sub/file`（`.`/`..`、大小写敏感）；
   名字 ≤31B、inode 总数 ≤512、路径 ≤128B / 16 段、目录深度 16；**没有符号链接/硬链接**、
   **没有 `link`/`symlink`/`fchmod`/`fchown`/`statfs`**；`rename`(82) 仍是 `-ENOSYS`
   （内核有 `vfs64_rename64` —— **同目录改名**，只改 inode 的 name/mtime/CRC，不动 `parent`；文件管理器的
   F2 重命名就走它，但没有接进 syscall 号段）；`rmdir`(84) 仍是 `-ENOSYS`
   （内核有 `vfs64_rmdir64` 只删**空目录**，但没接进这条号段）；`unlink` 只能删文件；
   单文件 **≤8 MiB**（批次 M：二级间接块；v2 旧卷仍 67584B）。v2 旧卷仍可挂载（按单层语义）。
9. **内存管理细节**：没有 COW、没有 `mremap`/`madvise`/`mlock`/`mprotect` 的段粒度语义、
   没有 `MAP_SHARED` 文件映射、`brk` 上限 64 KiB、`mmap` 只有 ~448 KiB 的窗口可用。
10. **时间/随机/其它**：`nanosleep` 是 4 ms 粒度、`clock_gettime` 由 tick 造、`getrandom` 是伪随机、
    `getrlimit` 是常量、`/sys`、`prctl`、`io_uring`、`epoll`、`signalfd`、`timerfd` 都没有。

**当前能验证到什么程度**：`tests/proc64_test.py`（BIOS 阶段 51 项 + UEFI 阶段 8 项）逐条对照
`[PROC64]`/`proc64:` 打点断言 —— 进程级地址空间、fork 的整页复制、execve 换映像、wait4 的退出码、
kill 的 SIGTERM→143、**每进程 CR3 互不相同**、**同一个 VA 父子各自读到自己的值**（隔离证据）。
glibc 相关的一条也**没有**验证过（没有它们需要的动态链接器/TLS/vDSO/futex），本文档如实列出上面的清单。
（`-EBADF/-EFAULT/-EINVAL/-ENOMEM/...`），**绝不返回 0 假装成功**。

### 4.2 FD 层与文件语义（批次 D：每进程 fd 表 + 引用计数对象；`kernel/fd64.h` / `kernel/fd64.cpp`）

**模型（一页纸）**：

* **fd 表按进程**：每张 `FdTable64` 有 **32 个槽**（fd = 3 + 槽位；0/1/2 是标准流，由 syscall/终端自己认）。
  进程结构（`kernel/proc64.h` 的 `Proc64`）持有一个 `FdTable64*`；任务经 `task_proc_of_current64()`
  找到自己的进程再拿到表。**没有进程上下文**时（任务 0 = 桌面/终端、安装介质内核、启动早期）
  退回**内核表** —— 终端文件命令（`ls/cat/write/touch/rm/mkdir/df/echo >` 与 `fdtest`）看到的就是内核表。
* **打开文件对象 + 引用计数**：fd 槽指向一个 `OpenFile64`（路径、flags、**偏移游标**、引用计数、
  目录缓存、pipe 端）。对象池 **64** 个、fd 表池 **20** 张、管道池 **8** 条（都是常量池，满了返回 `-EMFILE`）。

**fd 语义表（严格按 Linux；批次 D 把前三行从"部分/独立游标"改成了真语义）**：

| 操作 | 语义（实测打点见 `tests/fd64_test.py`） | 边界 |
|---|---|---|
| `open`（同进程两次） | 两个**独立**的 `OpenFile64` → **两个独立游标**（各读各的） | 多级路径 `/dir/sub/name`（v3；`.`/`..` 由 vfs64 解析）；`O_CREAT/O_TRUNC/O_APPEND/O_DIRECTORY` 支持 |
| `dup`(32) / `dup2`(33) | 新旧 fd 指向**同一个对象**（**共享偏移游标**），引用计数 +1；`dup2` 先关旧目标 | 目标 ≤2（重定向标准流）仍 `-ENOSYS`；没有 `fcntl`/`F_DUPFD` |
| `fork`(57) | **整张表逐槽共享**（引用计数 +1）→ 父子**共享偏移**；管道的两端也随之共享 | 没有 `CLONE_FILES` 的"另建一张表"语义 |
| `execve`(59) | **默认保留所有 fd**（Linux 语义） | **没有实现 `O_CLOEXEC`**（如实注明）；`close-on-exec` 无从设置 |
| `close`(3) | 引用计数 -1；**归零才真正释放对象**（打点 `refs=<n>`，归零打 `(object freed)`） | 关掉写端/读端会改变 pipe 的 EOF 判定（见下） |
| `O_APPEND`(0x400) | 每次 `write` 都先定位到文件**当前末尾**（写后游标 = 末尾）——先 `lseek` 到 0 也没用 | `lseek` 仍可改游标；只有写受 `O_APPEND` 影响（与 Linux 一致） |
| `lseek`(8) | `SEEK_SET/CUR/END`，**64 位偏移**，游标 0..8388608（8 MiB）；每次前先 `stat` 刷新大小（别的 fd 刚写过也看得到） | 目录/pipe → `-ESPIPE` |
| `pipe`(22) | **64 B 环形缓冲** + 读端/写端两个 fd；`fork` 后父子各持一端通信（`user/pipe64.asm`） | **没有阻塞/select/poll/信号语义**：写满 → 短写、完全无空间 `-EAGAIN`；读空且写端开着 `-EAGAIN`；写端全关 → 读 0（EOF） |

**文件系统侧（vfs64 = VimtuFS2 v3）**：路径是**多级绝对路径** `/dir/sub/file`（`name` 也接受，等价于
`/name`；`.` = 自己、`..` = 父目录，**根目录的父目录还是根目录**；大小写敏感、可打印 ASCII）；
名字 ≤31B（v2 旧卷仍 ≤27B）、整条路径 ≤128B、最多 16 段；单文件 **≤ 8 MiB（8388608 B）**
（= `VFS64_MAX_FILE_BYTES`：4 直接块 + 一级间接 + **二级间接**；v2 旧卷仍是 67584 B）；读写是**按偏移分块**的（`fs64_read_range64` / `fs64_write_at64`，推荐每次 ≤64 KiB，缓冲由调用方给）；`/` 只能当目录句柄打开；
**没有权限/属主、没有硬链接/符号链接**；inode 里带 **mtime**（RTC 打包 u32）与**类型判定 kind**
（目录/VAP64/ELF64/文本/二进制）。目录删除：内核 `vfs64_rmdir64` 只删**空目录**，非空必须先清空，
根目录永远不可删；这条号段（`rmdir`(84)）仍是 `-ENOSYS`。

**读写实现口径（为什么这么写）**：`vfs64` 没有 read-at-offset/部分写原语 →
每次 `read` 把整个文件读进一块全局缓冲再按游标切片（单次最多交给用户 4096B）；
每次 `write` 做一次**整文件 read-modify-write** 后**立刻整体落盘**（无脏页缓存）——
代价是每次写都读写整个文件，换来的是"多个 fd/多个进程同时写同一个文件"时语义仍然正确
（`O_APPEND` 的真值就靠它）。目录句柄第一次 `readdir` 扫一遍并缓存（16 条），之后 O(1)。

**打点**（自动验收 grep，格式勿改）：`[FD64] open path=.. fd=.. flags=..` / `[FD64] read fd=.. n=.. off=..` /
`[FD64] write fd=.. n=.. total=..` / `[FD64] close fd=.. refs=..` / `[FD64] pipe r=.. w=.. bytes=64` /
`[FD64] pipe read n=.. data=..` / `[FD64] dump table=kernel|proc used=..` / `[FD64] selftest PASS`。
终端 `fdtest` 是这条语义链的一键演示（独立游标 / dup 共享游标 / O_APPEND / pipe 环回 / fork 继承）。

### 4.3 VimtuFS2 **v3 目录树** 与**盘符/驱动器枚举层**（本批次新增；不含 UI）

这一节是"此电脑 + 文件管理器"的**地基**（UI 在下一批）：VFS 有真正的目录树、有 inode 时间戳与
类型判定；另有一层把"磁盘/分区/盘符"整理成表。**都在内核里，Ring3 号段没有新增调用。**

**① VimtuFS2 v3 格式（唯一定义点：`kernel/vfs64.h` 文件头 + `vfs64.cpp` 的 `VFS_LAY_V3`）**

* **卷版本 3**（超级块偏移 8 = `3`，inode 记录大小偏移 44 = `128`）；超级块 CRC32 覆盖 `[0,60)`、
  几何逐项重算校验（位图/inode 区/数据区必须严丝合缝），inode CRC32 覆盖 `[0,124)`。
* **v3 inode（128B）**：`type(1) namelen(1) rsvd(2) size(4) d0..d3(16) ind(4) parent(4)`
  `mtime(4) nlink(2) kind(1) rsvd2(1) name(31) 保留区 crc32(4)`；
  直接块×4 + 一级间接块（128 个块号）+ **二级间接块**（偏移 71 的 `dind`：128 个子块 × 128 块号）
  → **单文件 ≤8 MiB（8388608 B = 16384 块）**；映射能力 16516 块（8456192 B），对外上限刻意取整到 8 MiB。
  卷版本号仍是 3（老 v3 卷该字段恒 0 = 没有二级间接），inode 仍是 128B（保留区缩到 [75,124)）。
* **mtime 编码**：`(年-2000)<<26 | 月<<22 | 日<<17 | 时<<12 | 分<<6 | 秒`（正好 32 位；
  与 `rtc_get_date64` 的"月 1..12、年已加 2000"口径一致）；`0` = 未知；RTC 值不合法时回退
  `2025-01-01 00:00:00` 并打一行告警（保证 mtime 非 0）。
* **类型判定 `kind`**：目录 / VAP64（头 8B `VAP64\0\0\0`）/ ELF64（`\x7fELF`）/ 文本（扩展名
  `.txt/.md/.cfg/.log/.ini/.json/.c/.h` 或前 256B 可打印比例 ≥90%）/ 二进制；写文件时算好**存进 inode**，
  UI 直接读。**v2 旧卷没有这个字段** → 按扩展名保守判定（`.vap/.elf/.txt/...`，其余 = 普通文件）。
* **目录表示（取舍）**：名字就存在 inode 里，**目录没有数据块**——"目录" = `parent` 字段指向它的
  inode 集合。好处是少一层指针、少一类越界、格式一页纸写清；代价是条目上限 = inode 数（512）、
  查名字/列目录是 O(inode 数) 线性扫描（用"当前 inode 扇区"缓存把读盘次数降到 1/4）。
* **v2 兼容**：`v2` 卷（64B inode、名字 ≤27B、无 mtime/kind）**照常挂载**，按单层语义工作
  （v2 盘上所有条目 parent 都是 0，多级路径照样能解析，只是建不出子目录树）；新格式化一律 v3。

**② v3 新 API（`kernel/vfs64.h`；旧单层 API 全部保留为兼容包装，`fd64`/终端/`app64`/`elf64` 一行没改）**

| 类别 | API | 说明 |
|---|---|---|
| 遍历 | `vfs64_list64(path, out[], max, &cursor)` | **路径版 + 游标分页**（不一次读爆缓冲），返回条数，`0` = 结束 |
| 遍历 | `vfs64_opendir64/readdir64/closedir64` | 目录游标（内部静态流表 8 个），`readdir` 每次只扫一个 inode |
| 路径版 | `vfs64_stat64(path,&info)` | `type/size/mtime/parent/nlink/kind/name/index` |
| 路径版 | `vfs64_mkdir64` / `vfs64_create64` / `vfs64_write64` / `vfs64_read64` | **多级路径**（父目录必须存在） |
| 路径版 | `vfs64_unlink64`（文件）/ `vfs64_rmdir64`（**空**目录） | 非空目录一律拒绝并打点；根目录不可删 |
| 工具 | `vfs64_pack_time64/unpack/now/time_str`、`vfs64_kind_of_data64/by_name/kind_str` | 时间戳与类型判定（纯函数，UI 可直接用） |
| 只读 | `vfs64_probe_volume64(drive,lba,&volinfo)`、`vfs64_mounted_volume64(...)` | **不改挂载状态**的卷探测（盘符层用） |
| 验收 | `vfs64_tree_dump64(path,max_entries,max_depth)` | 有界打印目录树：`[VFS64] tree <路径> type= size= mtime=0x.. ymd=.. hms=.. kind= idx=` |

**路径规则（v3）**：绝对 `/dir/sub/file`；相对 `dir/file` 等价于从根开始（VFS 层没有 cwd）；
`//` 折叠、结尾 `/` 忽略、`.` = 自己、`..` = 父目录（**根的父目录还是根**，POSIX）；大小写敏感；
单段 ≤31B（v2 卷 27B）、整条 ≤128B、最多 16 段；段内必须是可打印 ASCII；所有 inode 号/块号/段下标
**先范围校验再用**，越界一律打点 + 返回 -1。

**③ 盘符/驱动器枚举层（`kernel/drive64.{h,cpp}`）**

* `drive64_scan64()`（幂等刷新）/ `drive64_count64()` / `drive64_info64(i,&info)` /
  `drive64_by_letter64('C')`。每项给：显示名、文件系统字符串、驱动器号（ata64 统一编号）、
  MBR 项号、起始 LBA、扇区数、总容量/可用容量（`total_known/free_known` 标明"已知/未知"）、
  是否可浏览、是否系统盘、卷版本、跳过原因。
* **枚举**：PATA 0..3 / AHCI 8.. / NVMe 16.. 的每块盘（`ata64_drive_count64`/`slot_to_drive64`）→
  读 LBA 0 的 MBR（4 个分区项，签名 `55AA` 才认）→ 每个分区做文件系统指纹：
  **VimtuFS2**（magic + `vfs64_probe_volume64` 的 CRC/几何校验）或 **FAT32/FAT16**（BPB 指纹）。
  盘尾备份 GPT **不重复解析**（内容与 MBR 一致；主 GPT 头按规范该在 LBA 1，而 LBA 1 是 loader 的）。
* **盘符规则**：**`C:` = 运行中的系统分区** —— 依据是 `vfs64` 当前**真正挂载**的那个卷的
  `(drive, start_lba)`（系统内核用 `app64_main_part_lba64(0)` = 读 drive 0 的 MBR `0x07` 项作挂载参数）；
  没挂载时退化为"drive 0 的 MBR `0x07` 项"，再退化为枚举顺序里第一个可浏览卷。
  其余可浏览的 VimtuFS2 卷按枚举顺序依次 **`D:`、`E:`…**（A:/B: 从不分配）。
  **ESP（type `0xEF`）/未知文件系统 / 未分区盘不占字母**，但仍列出并打点
  `[DRV64] skip lba=<n> type=<0xEF|unknown> reason=<esp|no-fs>`。
* **FAT 只识别不浏览**：ESP 会显示成"EFI 系统分区"、容量取 BPB（可用容量标"未知"），
  `browsable=false` —— 本内核只有 FAT32**写入器**，没有 FAT 读取/列目录。
* 打点（格式勿改）：`[DRV64] scan disks=<n> parts=<n> fs=<n>`、
  `[DRV64] letter=C: disk=<n> part=<n> fs=VimtuFS2 total_kb=<n> free_kb=<n>`、
  `[DRV64] skip lba=<n> type=<0xEF|unknown> reason=<esp|no-fs>`、`[DRV64] selftest PASS|FAIL mask=<n>`。

**④ ★ 多卷挂载 / 盘符切换（本批次新增：`vfs64` 卷槽表 + `drive64` 激活 + `vol` 命令）**

从这一批起，**不再只有 `C:` 能点进去**：每个可浏览的 VimtuFS2 卷都真的挂上来，按盘符切"当前卷"。

* **卷槽表（`kernel/vfs64.{h,cpp}`）**：`VFS64_SLOT_MAX = 4` 个槽，每槽独立保存一份卷几何
  （drive / 起始 LBA / 位图 / inode 区 / 数据区 / 布局）。系统卷固定 **0 号槽**（`vfs64_mount_system64`
  挂载并登记 = 盘符 `C:`），其余可浏览卷由盘符层按枚举顺序分到 1..3 号槽（`D:`/`E:`/`F:`）。
* **API**：`vfs64_mount_slot64(slot,drive,lba)`（挂进指定槽，**不改变当前卷**）、
  `vfs64_activate_slot64(slot)`（把"当前卷"切过去）、`vfs64_current_slot64()`、
  `vfs64_system_slot64()`、`vfs64_slot_used64/alloc/find/info`、`vfs64_slots_dump64()`。
  **旧 API（`vfs64_stat64/read64/write64/ls/opendir/…`）语义不变：它们作用于"当前卷"** ——
  所以终端/`fd64`/ring3 一行都没改。
* **缓存按卷键控（最容易踩的 bug）**：inode 扇区缓存键 = **(slot, drive, lba)** 三元组
  （`g_ino_cache_slot/drive/lba`），任何写盘都整体失效。切到另一块盘/另一个卷时**绝不**复用上一个卷的
  inode 字节（`tests/multivol64_test.py` 专门用"同一块盘上两个不同 LBA 的卷"覆盖这一条）。
* **按槽调用（固定系统卷）**：`vfs64_stat_on64/stat64_on64/read_on64/write_on64/mkdir_on64/create_on64/
  unlink_on64/rmdir_on64/ls_on64/list64_on64/tree_dump64_on64(slot, …)`。实现是**临时切卷守卫**
  （`Vfs64SlotGuard`）：只在这一次调用期间把当前卷换成 `slot`，函数返回前**原样切回**（LIFO；嵌套只打一行
  WARN，语义不乱）。中断上下文不会破坏它——恢复的一定是"自己进来时"那个卷。
* **谁必须用系统卷（不会写错卷的规则）**：`store64`（`/store.a`、`/store.b`，cfg 自动落盘）、
  `config64`、`update64`（`/update.pending`、`/update.done`）、`app64`/`elf64`/`proc64`（把内嵌示例应用
  装到 `/hello.vap`、`/hello.elf`、`/proc64.elf`、`/pipe64.elf`）、`sysstate64`（卷统计）**全部**改成
  `vfs64_*_on64(vfs64_system_slot64(), …)`。**用户正在浏览 `D:` 时，3 秒配置自动落盘仍然只写 `C:`** ——
  `tests/multivol64_test.py` 的"写卷安全"用例在浏览 D: 期间改配置触发落盘，然后用**宿主侧字节比对**证明：
  `D:` 卷整盘逐字节未变、`C:` 的 `/store.a` 能解析出刚写的键。
* **盘符层（`kernel/drive64.{h,cpp}`）**：扫描时给每个可浏览卷**分配/复用卷槽**（`DriveInfo64.slot`）；
  新增 `drive64_activate_letter64('D')`（切当前卷并打点 `[DRV64] activate letter=D: slot=1 … ok`）与
  `drive64_current_letter64()`；**第 5 个可浏览卷如实拒绝**：`skip reason=voltable-full`、不占字母，
  绝不顶掉已挂载的卷。`drive64_info64` 的可浏览条目改为**实时**容量（走卷槽现数位图）。
* **Explorer**：双击盘符卡片 = `drive64_activate_letter64` → 列**那个卷**的根目录
  （打点 `[UI] explorer enter letter=D: slot=1 ok items=2`）；历史记录回放会先按记录的盘符把卷对齐
  （`[UI] explorer volume sync …`），所以"后退/前进"跨盘也不会列错卷。
* **终端**：新增 `vol`（`vol` 列出所有盘符/卷槽/容量/当前卷；`vol C:`/`vol D:` 切当前卷并打点
  `[VOL] switch letter=D: slot=1`）；`df` 在原有"系统卷快照"之后追加**所有卷**清单
  （`[TERM] cmd df volumes=<n> current=<X:>`）。`ls/cat/write/touch/rm/mkdir/run` 依旧作用于**当前卷**。
* **验收**：`tests/multivol64_test.py`（108 条断言，`py -3` 跑）：两阶段安装出 `C:` → 宿主侧 Python 造第二个
  v3 卷（预置 `/docs`、`/readme.txt`、`/docs/notes.txt`）→ 终端 `vol`/`ls`/`cat`/`mkdir`/`write` 双卷独立 +
  Explorer 鼠标注入双击 `D:`/`C:` 卡片 + 写卷安全（D: 逐字节 + C: store 内容）+ 卷表满（4 块 AHCI 数据盘）+
  坏情况（`vol z`/`vol a`/`vol 1`）；全程禁止 `PANIC`/`TRIPLE FAULT`/`FAILED mask=`。

**⑤ 自检与验收**

* `vfs64_selftest64()` 新增 4 个位：bit8 多级目录树（mkdir `/efi` `/apps` `/apps/demo`、父目录不存在被拒、
  子目录里写文件、遍历 `/` 与 `/apps/demo`、stat64 的 parent/kind）、bit9 路径语义（`.`/`..`/`/../..` =
  根 + 对根的文件操作被拒 + 超长段/超深/非法字符）、bit10 mtime 与类型判定（含打包往返与越界拒绝）、
  bit11 代际几何（版本=3/inode=128B/CRC/55AA/几何重算）+ **重挂载持久化**（假盘内容保留，重新 mount
  后子目录文件与 mtime 不变）+ 空目录删除。真盘侧仍是**只读**探测（绝不在自检里格式化真盘），
  真盘的"建/删/重挂载"由 `tests/fs_tree_test.py` 的端到端流程覆盖。
* `tests/fs_tree_test.py`（新，84 条断言）：安装到 128MB 盘 → **格式化主分区得到 v3** → 多级 mkdir →
  子目录写文件 → **冷启动**后 `[VFS64] tree` 里 stat 到 size/mtime/kind、`cat` 读回、`rm` 删掉；
  同时断言盘符表（`C:` = disk 0 part 2、`D:` = 第二块盘、ESP 被 skip、`free ≤ total`、
  `drive64` 的容量与终端 `df` 在同一口径上一致）与坏路径被拒且不崩。

### 4.4 已知边界（别把没做的说成做了）

* glibc / 发行版二进制**没有验证过**：它们依赖的 TLS(FS.base) 真生效、信号投递、vDSO、`futex`、`clone`/线程、
  `/proc`、RELRO/multi-PT_LOAD 保护、IFUNC 重定位等大多不在这里。
  这里验证的是"自有静态 ELF64（`ld.lld -static -nostdlib`）能 load → ring3 → `syscall` → exit"。
* 用户态没有 `swapgs`/per-CPU `gs`，所以 SYSCALL 入口不能用 `gs` 取内核数据；ring3 里 `gs` 基址仍是内核的（用户程序不该依赖它）。
* `syscall` 指令路径因为"每个调用都打串口"，**不适合在循环里高频调用**（将来若要跑真程序，需要先给日志加节流）。
* 文件系统是 **v3 目录树、无权限、无硬链接**（单文件上限 **8 MiB**（批次 M 起），目录删除只支持空目录）；没有 `/proc`、
  没有设备节点；**pipe 已有**（64 B、无阻塞，批次 D 起），但 socket 不走 fd 层（`net64` 是内核自己的收发）。

## 5. 可执行格式一：VAP64（Vimtu64 自有）

**为什么自己定义格式**：本阶段只需要"装载一段 ring3 平铺二进制并校验完整性"，
32B 定长头 + 名字 + CRC32 就够；不做重定位 / 导入表 / 多段。

### 5.1 文件布局（唯一定义点：`kernel/app64.h`；打包器 `tools/make_vap.py` 必须逐字段一致）

| 偏移 | 长度 | 字段 | 语义 |
|---|---|---|---|
| 0 | 8B | `magic` | `"VAP64\0\0\0"`（5 个可见字符 + 3 个 NUL） |
| 8 | 4B | `version` | 结构版本 = **1** |
| 12 | 4B | `header_size` | 固定头字节数 = **32**（不含名字） |
| 16 | 4B | `entry_offset` | 代码入口在**文件内**的绝对偏移 = `header_size + name_len`（名字紧跟头后；`hello` 这个 6B 名字 → `38`）。**加载器不接受别的值** |
| 20 | 4B | `code_size` | 代码段字节数：**1..32768**（与 `user64_run_blob64` 的"代码最多 8 页"对齐） |
| 24 | 4B | `code_crc32` | `zlib.crc32(代码段)`（标准 CRC-32：反射多项式 `0xEDB88320`、初值/末异或 `0xFFFFFFFF`，与 vfs64/make_vap.py 同口径） |
| 28 | 4B | `name_len` | 名字字节数，**含结尾 NUL**：1..24（→ 可见字符最长 23） |
| 32 | `name_len` | `name` | 名字（NUL 结尾） |
| `32+name_len` | `code_size` | `code` | 代码段（**平铺二进制，入口在段首**，即第一字节就是第一条指令） |

**文件总长 = 32 + name_len + code_size**（加载器用这条等式做长度一致性校验）。

名字约束（`tools/make_vap.py` 在打包时就拒绝）：必须是可打印 ASCII（`0x21..0x7E`），**不能含 `/` 或 `\`**。

校验与拒绝理由（`app64.cpp`，串口会打 `[APP64] launch FAILED path=<p> reason=<...>`）：
`arg` / `vfs`（读盘失败）/ `size`（>64KB 缓冲上限或长度不一致）/ `magic` / `version` /
`name`（长度或 NUL 不合法）/ `crc` / `user64`（映射或进 ring3 失败）。

### 5.2 运行方式

1. 代码段被拷到 **`4GiB`（`USER64_CODE_VA64`）起的用户页**，映射为 **R/X**（只读可执行，不可写 —— 要写数据请用栈或 `mmap`）；
2. 栈用窗口里的 16 KiB 用户栈（R/W/NX）；
3. `iretq` 进 ring3，入口 = 代码段首字节；程序用 **`int 0x80`** 与内核通信；
4. `exit(2)` 或程序正常走完（后者会走到代码段末尾 —— 一定要显式 `exit`，否则行为未定义）后，内核回收用户页。

## 6. 可执行格式二：ELF64（`kernel/elf64.h` + `kernel/elf64.cpp`）

### 6.1 支持范围（加载器逐条校验，不满足就打 `[ELF64] reject reason=<...>`）

* 魔数 `\x7fELF`、`class=2`（64 位）、`data=1`（小端）、`version=1`、`machine=0x3E`（x86-64）；
* `e_type` = `ET_EXEC(2)` 或 `ET_DYN(3)`；`e_phentsize = 56`；程序头表整段必须落在文件内
  （`e_phoff + e_phnum*56 <= 文件长度`）；**`e_phnum ≤ 16`**（`ELF64_MAX_PHDR64`）；
* **不支持** `PT_INTERP`（动态链接器）、重定位、`PT_GNU_*` 特殊段；加载器**不做任何重定位**；
* **三项上限的归属（批次 M 写清）**：① **FS**：VimtuFS2 单文件 **8 MiB**（v2 卷 67584 B）；
  ② **用户窗口**：ELF 装载区 = 窗口低 64 KiB —— **能真正装进去跑**的映像远小于 8 MiB；
  ③ **读盘缓冲**：`ELF64_MAX_FILE_BYTES64` = 96 KiB（`.bss` 里），超过直接 `reason=size` 拒绝（不截断）；
* 每个 `PT_LOAD`：
  * 目标 `[p_vaddr, p_vaddr+p_memsz)` 必须**完整落在用户窗口的 ELF 装载区**（`4GiB .. 4GiB+64KiB`），否则拒绝（`outside-user-window` / `overlaps-user-region`）；
  * `p_filesz` 字节从文件拷进去，`p_filesz..p_memsz` 清零（`.bss`）；
  * 权限按 `p_flags`：`PF_R` → 加 `P|U`；`PF_W` → 加 `W`；`PF_X` → 不加 NX（不可执行段加 `PTE_NX`）。实现上先统一按 `P|W|U` 映射（否则只读段没法写内容），拷/清零完成后再逐页收紧；**同页多个段取权限并集**（所以各段之间请页对齐）。
* 用户栈：`USER64_STACK_VA64`（`4GiB+64KiB`）起 16 KiB（4 页，`P|U|W|NX`），按 **SysV ABI** 压初始栈：
  `[rsp] argc=1, argv[0]="/hello.elf", NULL, NULL(envp), auxv..., AT_NULL/0`；
  `auxv` 至少含 `AT_PAGESZ(6)` / `AT_PHDR(3)` / `AT_PHNUM(4)` / `AT_ENTRY(9)` / `AT_UID/EUID/GID/EGID(11..14)`；
  进入 `_start` 时 `rsp % 16 == 0`。

### 6.2 运行方式

* 进 ring3 走 `user64_enter_at64()`（同一个用户窗口、同一份 TSS.rsp0 逻辑）；程序用 **`syscall` 指令**与内核通信；
* `exit(60)` 或 `exit_group(231)` 后回收：逐页解除映射 + `page_free_64`（中间页表页保留）；
* 装载与运行是两步：`elf64_load64()` → `elf64_run_loaded64()`（终端与启动路径用合一的 `elf64_run64()`）。

## 7. 怎么编一个能在 VimtuOS 上跑的程序

### 7.1 方案 A：VAP64（`int 0x80` 自有 ABI，最省事）

以仓库自带的示例为准（`user/hello64.asm`）：

```bash
# ① 汇编成"平铺二进制"（NASM -f bin，org 0，入口在段首；只能 RIP 相对寻址）
nasm -f bin user/hello64.asm -o build64/hello64.bin          # 实际产出 202 字节

# ② 加 VAP64 头（32B 头 + 名字 + code CRC32），打包器自带回读自检
py -3 tools/make_vap.py build64/hello64.bin build64/hello.vap hello
#   → [VAP] wrote build64/hello.vap name=hello code=202 crc=0x........
```

**写自己的程序**：把 `user/hello64.asm` 复制成 `user/你的程序.asm`，改逻辑与名字，重复上面两步即可。
`exit(2)` 一定要调；数据放**只读**（代码页不可写），要写缓冲用栈（示例里的 `print_dec` 就是在栈上做十进制转换）。

### 7.2 方案 B：ELF64（`syscall` 指令，Linux 号段）

以 `user/hello_elf64.asm` + `user/hello_elf64.ld` 为准：

```bash
# ① 汇编成 ELF64 目标文件（.text/.rodata/.bss）
nasm -f elf64 user/hello_elf64.asm -o build64/hello_elf64.o

# ② 用仓库自带的链接脚本静态链接（脚本把映像钉在用户窗口里）
ld.lld -m elf_x86_64 -T user/hello_elf64.ld -o build64/hello.elf build64/hello_elf64.o
```

链接脚本的关键点（`user/hello_elf64.ld` 的注释里写得很清楚）：

* `. = 0x0000000100000000 + SIZEOF_HEADERS` —— 让第一个段从文件偏移 0 开始映到 4GiB，
  这样**程序头表本身也在映像里**，`auxv` 的 `AT_PHDR` 才有意义；**默认脚本会把 ELF 头放进 4GB 以内的独立段 → 一定会被加载器拒**；
* 各段之间必须 `ALIGN(4096)`（权限按页给）；
* `/DISCARD/` 掉 `.interp` / `.dynamic` / `.rela*` / `.got*` 等（加载器不做重定位，留着只会让映像非法或变大）。

### 7.3 关于用 C 写（**未验证，谨慎使用**）

仓库里**只带了汇编示例**。理论上可以用 freestanding C 走同一套流程
（`clang -target x86_64 -ffreestanding -nostdlib -static -mno-red-zone -fno-stack-protector ...` +
上面两个入口 ABI 自己写 `_start` 和 syscall 包装），但**本仓库没有 C 用户程序示例、也没有验证过**；
要这么干请自己加一个示例并补验收脚本。

### 7.4 怎么装进去

**当前只有一条路**：把程序**嵌进系统内核**，启动时由内核装进 VimtuFS2（幂等，已存在就跳过）。以 `build64.sh` 为准：

```bash
# VAP64：objcopy 变 ELF64 目标文件（符号名按输入路径生成，必须从仓库根执行）
objcopy -I binary -O elf64-x86-64 -B i386:x86-64 build64/hello.vap build64/hello_vap64.o
# ELF64：同一手法（只嵌进系统内核，安装介质内核不带 ELF64 加载器）
objcopy -I binary -O elf64-x86-64 -B i386:x86-64 build64/hello.elf build64/hello_elf64_elf.o
```

然后把这两个 `.o` 加进 `build64.sh` 的 `SRCS_OS` 链接列表（脚本里已有），重新 `bash build64.sh`。
启动时 `kernel64.cpp` 的 `os_boot_path()` 会：

1. `vfs64_mount(app_drive, app_lba)`（主分区起始 LBA 由 `app64_main_part_lba64(drive)` 从安装器写的 MBR 里解析出来；解析不到退回 `PART_MAIN_LBA`）；
2. `app64_install_builtin64()` → 装成 **`/hello.vap`**；`elf64_install_builtin64()` → 装成 **`/hello.elf`**；
   已经存在就打 `[APP64] install skipped (exists) /hello.vap size=<n>`（**不会重复写盘**）；
3. 串口留证：`[APP64] install ok path=/hello.vap bytes=<n> crc=0x<hex>`、`[ELF64] install ok path=/hello.elf bytes=<n>`。

> **诚实说明**：目前**没有"把任意文件拷进 VimtuFS2"的宿主侧工具**（批次 B 起终端 `write/touch/mkdir/rm`
> 写的**就是 VimtuFS2**，（多级路径、单文件 ≤8 MiB）；也没有图片/镜像注入脚本）。
> 所以"装应用"目前等价于"改内核嵌入的文件并重编内核"；给 VimtuFS2 写一个宿主编排工具是明确的下一步工作。

> **✅ 批次 O 起多了一条真通路：从 U 盘拷进来**（见 §7.6）—— 宿主侧不用改内核，只要把 `.vap`/`.elf`
> 放进一个 **FAT32 U 盘**，插着开机，在**文件管理器**里从 U 盘点 `Ctrl+C`、进 `C:` 点 `Ctrl+V` 即可。

### 7.6 从 U 盘装应用（批次 O：USB 存储，**只读**通路）

适用条件（如实）：**UHCI（USB 1.1）主控** + **直插根端口**的 U 盘 + **FAT32 卷**（块大小 512B）。
EHCI/xHCI 主控、hub 后面的 U 盘、2048B 块大小的盘都**不支持**（串口会打 `[USB64] not found` /
`unsupported interface` / `block_size != 512 -> not exposed as a block device`）。

宿主侧准备（Windows/macOS/Linux 都一样）：

1. 把 U 盘格式化成 **FAT32**（簇大小随便，1 簇 512B 的 35MB 小盘也认）；
2. 把要装的应用拷到根目录，例如 `MYAPP.VAP`（`tools/make_vap.py` 的产物）或 `MYAPP.ELF`；
3. 插到目标机器上，开机。

系统里（桌面）：

| 步骤 | 操作 | 会看到什么 |
|---|---|---|
| 1 | 串口/自检 | `[USBST] iface found class=08 sub=06 proto=50 ep_in=… ep_out=…` → `[USBST] inquiry vendor=… product=…` → `[USBST] capacity blocks=… block_size=512 … cap_mb=…` → `[USBST] read lba=0 count=1 ok` → `[USBST] selftest PASS mask=0` |
| 2 | 盘符 | `[DRV64] letter=D: disk=24 part=1 fs=FAT32 … ro=1`（U 盘 = 驱动器号 **24**，FAT32 一律**只读**） |
| 3 | 打开"此电脑" | U 盘那张卡片就是 `D:`（磁盘符 + 容量条） |
| 4 | 双击 `D:` 进去 | 看到 U 盘上的文件（**VFAT 长名也完整显示**）；状态栏标明只读 |
| 5 | 选中 `MYAPP.VAP` → `Ctrl+C` | `[UI] explorer clip op=copy n=1` |
| 6 | 点工具栏/导航回到"此电脑" → 进 `C:` → `Ctrl+V` | `[UI] explorer paste ok n=1 dst=/ skipped=0`；`C:` 根目录出现 `MYAPP.VAP`（同名会自动加 `(2)`） |
| 7 | 终端 `cat /MYAPP.VAP`（可选） | 读回同样的字节数（`cat` 单次最多显示 4096 B，超了会明确提示截断） |
| 8 | 终端 `run /MYAPP.VAP` / `run /MYAPP.ELF` | 按魔数分派：`VAP64\0\0\0` → `int 0x80` 路径；`\x7fELF` → `syscall` 路径 |

**不能做的事（如实）**：往 U 盘写（`write`/`mkdir`/粘贴一律被拒：终端在入口就按只读卷拦下、
管理器的 `Ctrl+V`/`Delete` 打 `[UI] explorer roact op=… ro=1`，最底下还有 `ata64_write` 的
`[USBST] write refused` 兜底）；U 盘上建/删文件；把系统装到 U 盘（安装向导的默认目标永远跳过它）。
文件只读方向是 **U 盘 -> 系统盘**；反方向（C: -> U 盘）会被拒。
### 7.5 怎么启动

在桌面终端里：

| 命令 | 行为 |
|---|---|
| `run hello.vap`（或 `run /hello.vap`） | 从 VimtuFS2 读出来 → 按**文件头魔数**分派：`VAP64\0\0\0` → VAP64 路径（`int 0x80`） |
| `run hello.elf`（或 `run /hello.elf`） | 同上，前 4 字节 `\x7fELF` → ELF64 路径（`syscall` 指令） |
| `elfrun hello.elf` | **强制**走 ELF64 加载器（不做魔数分派），用来单独验证 ELF 路径 |
| `run 别的名字` | 名字不带 `/` 会自动补成 `/名字`；VimtuFS2 是单层路径，所以只能找根目录下的文件 |

串口证据（这两条路径成功的判据）：

```
[APP64] load path=/hello.vap via=vfs64_read bytes=240 code=202 name=6 crc=0x........
[APP64] launch ok path=/hello.vap name=hello rc=0
hello from installed app (VAP64 on VimtuFS2)
[ELF64] load path=/hello.elf entry=0x0000000100000190 phnum=6 segs=4 size=<n>
[ELF64] enter ring3 entry=0x0000000100000190 rsp=0x0000000100010000
hello from ELF64 (syscall insn)
pid=<n> / open /hello.elf fd=<n> / read=<n> / sec=<n> / done (exit 60)
[ELF64] back to kernel (ring0) rc=0
[ELF64] launch ok rc=0 path=/hello.elf
```

（`run`/`elfrun` 打的是 `[APP64] run cmd path=<p> rc=<n>` / `[ELF64] run cmd path=<p> rc=<n>`；失败时 rc 为负并打印 `run: failed (see serial log)`。）

## 附 A：`update` / `preload` / `proc` 终端命令（批次 A 后半新增，均为真实现）

这三条命令在原 32 位终端里存在（`update` / `preload`）或属于批次 C 能力（`proc` = 管理真进程）；64 位
终端此前把 `update` / `preload` 留成"尚未支持"桩，本批次接真后**终端已没有任何"尚未支持"命令**。

### A.1 `update`（标记 -> 应用 -> 重启的机制闭环，**不是真正的升级包**）

* 标记文件：VimtuFS2 单层路径 `/update.pending`，内容是 ASCII 文本 `ver=<x.y.z>\n`（版本串只允许数字与 `.`，≤16 字符）。
* 应用动作（`kernel/update64.cpp`）：校验内容 -> `store64` 写 `update.applied=<ver>` 并 **flush 真落盘**
  -> sysstate64 ring log 一条 -> 写 `/update.done`（VimtuFS2 没有 rename，所以是"写新文件 + 删旧文件"）
  -> 自动软重启（`sysstate64_soft_restart64()`：优雅停止 + 落盘 -> 硬复位链）。
* 启动时检查（`os_boot_path` 里、`gui64_run` 之前）跑一次；终端命令：

  | 命令 | 行为 | 串口打点 |
  |---|---|---|
  | `update` / `update status` | 当前版本、store 里的 applied、pending/done 是否存在、载体与世代号 | `[UPDATE64] cmd status version=...` |
  | `update pending <ver>` | 写 `/update.pending`（测试与手工验证用） | `[UPDATE64] stage pending ver=... rc=0` |
  | `update apply` | 手动应用一次（store + `/update.done` + 删 pending）后**软重启** | `[UPDATE64] cmd apply -> soft restart` |

* **边界（务必别误读）**：这不是真正的升级包 —— 没有内核替换、没有差分/签名/回滚，也没有从网络或介质
  读取新版本；它只把 32 位那套"标记 -> 应用 -> 重启"的机制闭环做实了。

### A.2 `preload`（字形预光栅化 + 图标预缩放，带 rdtsc64 实测证据）

* 启动期（`gui64_run` 之前）跑一轮：三个 face 的 ASCII + 界面高频汉字 top 200（来源：`kernel/*.cpp`
  字符串字面量汉字的词频统计；≤ font 的 LRU 容量 256 才幂等）预光栅化；3 张桌面图标（128x128 -> 48x48）
  与开始图标（64x64 -> 24x24）预缩放（`gui64_preload_icons64()`，绘制路径自动改用缓存）。
* "首帧代表工作"= 预热前后各做一次**真实绘制**（一段界面文本 + 一个桌面图标），用 `rdtsc64` 量 cycles；
  数字是实测的（本机实测样例：before≈61.3M / after≈1.8M cycles，after < before）。
* 终端 `preload` 打印统计；`preload run` 再跑一轮（第二轮 `glyphs_new=0` = 缓存幂等）。串口打点：
  `[PRELOAD64] glyphs prewarmed=<n> ms=<n>` / `icons cached=<n>` / `first paint before=<n> after=<n> cycles`。

### A.3 `proc`（proc64 真进程：list / run / kill）

* 启动期多进程演示跑完进程就退出了，桌面起来时进程表是空的；`proc` 是运行期创建真进程的入口：

  | 命令 | 行为 |
  |---|---|
  | `proc list` | 打印进程表（pid/ppid/状态/线程数/CR3/名字）；串口 `[PROC64] cmd list rows=<n>` |
  | `proc run <name\|/path>` | `proc64_create64()` + `proc64_start_elf64()`（独立 CR3 + 独立任务）；内置 `spin` = 内嵌 `/spin.elf`（长命程序，永不退出） |
  | `proc kill <pid> [sig]` | `proc64_kill64()`（默认 SIGKILL=9）；串口 `[PROC64] cmd kill ... rc=<n>` |

* 任务管理器的"进程页"现在就是这张表（pid/ppid/名字/状态/CR3/线程数/CPU‰），回车 = `kill(SIGKILL)`，
  打点 `[UI] tmgr kill proc pid=<n> name=<s> sig=9 rc=<0|1>`，并真走 `[PROC64] kill ... -> exit code=137`。
* **已知缺陷（本批次不改 usermode64，works 在终端侧绕开）**：`usermode64.cpp` 的 in_ring3 位是**按任务槽位**
  的位图；ring3 进程被 kill 时不会从 `user64_enter_frame64` 正常返回，那一槽的位会残留，下一个复用该槽的
  任务进 ring3 会被 `[USER64] enter FAILED (frame) reason=2` 拒绝。`proc run spin` 因此带"占住脏槽再重试"
  （`term_spinpad` 内核线程 + 最多 4 次重试）。建议的根治：在任务回收/强杀路径清掉该任务的 in_ring3 位。

## 8. 一分钟自检清单（写程序时最容易踩的坑）

1. **VAP64 代码段是平铺二进制**：`nasm -f bin` + `org 0`，用 RIP 相对寻址，别假设自己被加载到某个固定低地址。
2. **VAP64 代码页是 R/X**：写全局变量会 #PF —— 数据放栈上，或走 ELF64 的 `.bss`/`mmap`。
3. **`int 0x80` 只支持 write(1)/exit(2)/getpid/ticks/sleep_ms**；要文件就用 ELF64 + `syscall`。
4. **ELF64 必须链接在 `4GiB .. 4GiB+64KiB`**，并用仓库的 `.ld` 脚本；段要页对齐；不要 `PT_INTERP`/重定位。
5. **路径是**多级**绝对路径**（`/dir/sub/name`，单段 ≤31B）；fd 表 32 项、单文件 ≤8 MiB（批次 M）、
   按偏移分块读写（缓冲区由调用方给，单次交给用户 ≤4096B）。
6. **没有 glibc / libc**：`printf`、`malloc`、`memcpy` 都要自己写（内核里也没有 libc 可借）。
7. **`syscall` 路径每个调用都打串口日志**，别写高频调用循环（现在只适合演示/小工具）。
8. **`exit` 必须显式调用**；VAP64 若走到代码段末尾、ELF64 若 `_start` 返回，都没有"正常结束"的语义。
9. **地址空间隔离已成立（批次 C）**：每个 proc64 进程有独立 CR3（`proc run` 建出来的进程就是）；但裸 `run`/`elfrun`
   仍跑在调用者的进程上下文里。用 `proc list` / 任务管理器进程页能看到每进程 CR3。
   ring3 槽位复用（kill 后同槽再进 ring3）在批次 B 已根治：task64 的 kill/reap/exit/force-remove 会清 in_ring3 位
   （`[USER64] slot release slot=.. in_ring3=1 -> cleared`），回归见 `tests/proc64_test.py` 的 4 轮同槽 kill+run 断言。
10. **验证手段**：自己加一个 `tests/xxx_test.py`（串口断言 + 必要时 screendump 像素断言），
    并把它加进 `tests/status_report.py` 的 `TESTS`/`CAPS` —— 这个项目里"能被脚本证明"才算完成。

## 附 B：批次 J 新增的文件操作 API（`vfs64_rename64` / 空间查询 / 按槽入口）

> 位置：`kernel/vfs64.{h,cpp}`（原语）+ `kernel/explorer64.cpp`（UI 与剪贴板）。
> 这一批**没有新增 syscall 号段**：文件操作由桌面应用直接调内核 VFS（与终端 `ls/cat/write` 同一层）。

| API | 语义 | 限制（如实） |
|---|---|---|
| `int vfs64_rename64(const char* old_path, const char* new_name)` | **同目录改名**：解析 `old_path` 拿到 inode → 校验 `new_name`（`1..31B`、`0x21..0x7E`、不含 `/`、不是 `.`/`..`）→ 同目录重名检查 → 改 `name` + `mtime` → 重算 inode CRC → 一次 `inode_store` 提交。同名（最后一段 == new_name）**幂等返回 0** | 不动 `parent`（**没有跨目录移动**）；根目录拒绝；重名返回 -1 + 打点（不覆盖）；失败打点 `[VFS64] rename64: <why>` |
| `int vfs64_rename_on64(int slot, const char* old_path, const char* new_name)` | 同上，但**显式指定卷槽**（`Vfs64SlotGuard`：调用期间临时切卷，返回前原样切回） | 槽非法/未挂载 → -1 + `rename_on64: slot=<n> not mounted` |
| `int vfs64_free64(uint32_t* free_blocks, uint32_t* free_bytes, uint32_t* total_blocks)` | 当前卷**数据区**空闲块/字节/总块数（走空闲位图统计；参数都可传 `nullptr`） | 未挂载/位图读失败 → -1；`free_bytes` 是"还能写多少字节"的**上限**（间接块另算） |
| `int vfs64_free_on64(int slot, …)` | 同上，按卷槽 | 同上 |

**文件管理器（explorer64.cpp）用它们做的事**（细节见 `docs/项目状态总览.md` 的【批次 J】）：

* **复制/粘贴**：源用 `vfs64_*_on64(源槽)` 读、目标按界面盘符写；写前用 `vfs64_free_on64(目标槽)`
  按"数据块 + 一级/二级间接块 + 子块 + 1 块余量"判空间（`vfs64_blocks_for_bytes64`），
  **不够就整条跳过（绝不写一半）**；单文件 >8 MiB（v2 卷 >67584 B）直接拒绝（不是截断）。
  文件内容是**分块复制**（每块 64 KiB：`fs64_read_range64` -> `fs64_write_at64`），大文件不再占大内存。
* **目录递归复制**：深度 ≤4、整棵 ≤96 条、单层一次列 16 条；拒绝把目录复制进自己的子树。
* **剪切**：复制成功后 `vfs64_unlink_on64`/`vfs64_rmdir_on64` 删源（先全部复制成功再删）。
* **删除**：文件 `vfs64_unlink64`、空目录 `vfs64_rmdir64`；**非空目录**先 `vfs64_list64` 判空，
  非空就如实提示"目录非空，暂不支持递归删除"（打点 `rc=1 reason=not-empty`）。
* **名字/长度校验**：`name_ok_pure()`（与 `vfs64` 的 `name_valid` 同口径）在提交前先挡一道；内联编辑框最多收 31 B。
* **重名策略**：粘贴/新建文件夹撞名自动追加 `(2)`、`(3)`…（**不带空格**：`0x20` 不是合法文件名字符）；
  重命名不自动改名（撞名 `rc=1`）。
* **配套补的键码**（`kernel/input.{h,cpp}`）：`KBD_KEY_DELETE=0xFA`（E0 53）、`KBD_KEY_F2=0xF9`（0x3C），
  以及只读的 `kbd_ctrl_pressed()/kbd_shift_pressed()`；Ctrl+字母仍折成控制字符（Ctrl+A=0x01/C=0x03/X=0x18/V=0x16）。

## 批次 K：fs64 分派层与 FAT32 只读语义

## 批次 N：引导日志的终端命令（`dmesg` / `boot verbose`）

两个命令都在 `kernel/terminal64.cpp`，数据源是 `kernel/console64.{h,cpp}` 的引导日志缓冲：

* `dmesg` —— 打印「头部保留 16 行（最早的长模式 / BootInfo / E820 等）+ `[CON64] … N lines dropped …`
  省略标记 + 16 KiB 环形缓冲里的最近若干行」，每行带 Linux 风格时间戳 `[    0.123456]`；
  同时**有界**地把前 16 行 + 后 16 行打到串口（前缀 `[CON64] dmesg[i]`，自动验收 grep 这个；
  全量只在屏幕上，避免 250+ 行刷串口拖慢桌面）。
* `boot verbose on|off` —— 写 `config64` 的 `boot.verbose`（默认 1）并**立即 flush 到 store64**，
  下一次冷启动生效：`0` = 不再滚屏，只打 `[CON64] verbose=0 skipped lines=N` 然后直接进桌面。
  `boot` / `boot verbose` 单独敲则打印当前值。

两个命令都打 `[CON64]` 行（`[CON64] dmesg lines=N head=N dropped=N trunc=N` /
`[CON64] boot verbose=… persisted=…`），端到端断言在 `tests/bootlog64_test.py`。

* **为什么有 fs64**：文件管理器/终端/FD 层需要的只是"列目录/查属性/读/写/卷信息/激活"这一小组操作，
  底层却有 `vfs64`（VimtuFS2，读写）与 `fat64`（FAT32，只读）两套实现。`kernel/fs64.{h,cpp}` 把
  "按卷类型分派"收在一处：上层只拿一个**统一卷号**（0..3 = vfs64 槽、4..7 = FAT 卷；-1 = 当前卷）
  调 `fs64_list64/stat64/read64/write64/...`，VimtuFS2 转 `vfs64_*_on64`、FAT32 转 `fat64_*`。
  这样"再加一种文件系统"不用在 UI/终端/FD 层到处加 if-else。
* **只读语义**：FAT 卷的写操作（write/create/mkdir/unlink/rmdir/rename）在 fs64 入口直接返回
  `-FS64_EROFS(=30)` 并打 `[FS64] reject vol=<n> ro=1 op=<...>`；`fd64_open_on64` 对只读卷上
  带写意图（WRONLY/RDWR/CREAT/TRUNC/APPEND）的打开返回 `-FD64_EROFS`（打点
  `[FD64] open FAILED … rc=30`），不会创建/截断任何文件。上层（explorer 工具栏/右键菜单）
  先按 `readonly` 置灰；键盘快捷键等漏网路径会打到 `[UI] explorer roact op=...` 并提示
  "只读卷（FAT32）"。
* **VFAT 长名支持范围**：0x0F 项按规范解析（顺序位 0x40、8.3 名字 checksum、最多 20 个 0x0F 项、
  UTF-16 -> UTF-8 含代理对）；校验和不符/顺序错乱整组作废并回退 8.3 短名；名字缓冲 256B；
  `8.3` 与 `LFN` 的写回冲突不做（只读侧只看 LFN 是否自洽）。路径解析大小写不敏感。
* **可用空间**：FAT 卷在挂载时读 FSInfo（free 字段）并缓存；FSInfo 无效则如实标 unknown
  （drive64 的 `free_known=false`），**不做实时 FAT 扫描**。VimtuFS2 仍是位图实时值。
* **终端命令**：`ls`/`cat`/`fatcheck` 在 FAT 卷只读可用（`fatcheck` 读文件算 CRC32 与构建产物核验）；
  `write/rm/mkdir/touch` 在 FAT 卷上明确报"只读卷（FAT32）"；`vol` 列表对只读卷标 `ro`。

## 批次 P1：Rust 模块（gui_rs）与 `rust` 终端命令

> 范围说明：Rust 模块是**内核侧**的（不新增 syscall 号段），但它给"应用层"提供的是**设计 Token / 主题配色的唯
> 一真源**；写 UI（含将来 ring3 应用）取尺寸/颜色时应以这里为准。

* **crate 结构**（`gui_rs/`，6 个源文件；`#![no_std]`、**无 alloc、无浮点**，小数一律千分比整数）：
  * `src/tokens.rs`：**33 个 Token**（圆角/模糊/透明度/双层阴影/动效/缓动/字号…），每个都有 `name`、`unit`（px/ms/千分比）
    与数值；`rust64_token_count64()/rust64_token_lookup64(name,len)/rust64_token_px64(id)/rust64_token_permille64(id)` 查询。
  * `src/theme.rs`：**7 套主题**（白色(默认)/暗色/蓝白渐变/粉白渐变/粉绿渐变/粉紫渐变/紫白渐变）
    + `Rgba` / `Rust64ThemeColors`（11 色）/ `Rust64Shadow`（近/远两层）；`rust64_theme_*` 查询与 `rust64_theme_set64()` 切换。
  * `src/panic.rs`：panic 钩子（内核注册 `rust64_panic_hook64`，Rust 侧 panic → 串口 + BSOD）。
* **链接方式**：`build64.sh` → `bash gui_rs/build_rs.sh`：用 **rustup shim 的绝对路径** rustc（MSYS2 自带 rustc 找不到 `core`），
  target `x86_64-unknown-none`，`--crate-type staticlib --emit obj`，`-C panic=abort -C relocation-model=static
  -C code-model=kernel` → `gui_rs/gui_rs.o`；**只加进系统内核**的链接行（安装介质内核不链 ——
  `tests/rust64_test.py` 用 nm/objdump + 字节搜证：系统内核有符号与 BUILD_TAG、安装内核一个都没有）。
  找不到 rustc / 目标 / 编译失败 = 构建**硬失败**（绝不静默跳过）。
* **ABI 约定**（`kernel/rust64.h`）：只传/只回 POD（`#[repr(C)]` 结构 + 定长整数）；字符串 = `*const u8 + len`（UTF-8，
  不带隐含 NUL）；绝不返回 Rust 引用/String/泛型；字段顺序即 ABI（加字段只能用 `reserved`）。
* **启动期自检**：`rust64_tokens_init64()`（保存/恢复当前主题，不改运行期状态）+
  `theme64_rust_crosscheck64()` 与 C++ 主题表交叉核对数量/名字/accent → `[RUST64] tokens ok themes=7 accent=#RRGGBB
  selftest PASS`；Rust panic 会打 `[RUST64] panic …` 并进内核蓝屏，**不会静默**。
* **终端命令**：`rust`（信息）/ `rust tokens`（列 33 个 Token）/ `rust set N`（切当前主题，同步 Rust 侧 current），
  打点 `[RUST64] term rust cmd=tokens|set|info theme=<i> accent=#RRGGBB tokens=33`。
* **如实说明**：Rust 主题表目前只有 11 个颜色，而 C++ `Theme64Tokens` 字段更全（Dock/按钮/选择框/壁纸等），所以
  "主题数量 / 名字 / accent"以 Rust 为准，**外壳绘制细节仍读 C++ token**；把全部绘制切到 Rust 表是后续工作。

## 批次 P1c：多用户 / 会话身份与终端命令（权限位属 P4）

> 面向"写程序的人"的要点：**内核里现在有真实用户，但 syscall 层还没有身份/权限** —— 见下。

* **数据与命令**（`kernel/userdb64.{h,cpp}` + `kernel/terminal64.cpp`，**没有新增 syscall 号段**）：
  * 用户库 `/etc/users.db` **v1 文本**：`VIMTU-USERSDB 1` + `U|<name>|<uid>|<home>|<hash_hex>|<salt_hex>|<avatar>|<theme>|<wall>|<lock_mode>|<flags>`；
    普通用户 uid≥1000、主目录 `/home/<名>`、桌面 `/home/<名>/Desktop`；root uid=0、`/root`、**不在登录界面**（flags HIDDEN）；
    最多 16 用户；首启自动建无密码引导用户 `vimtu`。
  * 口令：盐 16 B（`rdtsc` xorshift）**非 CSPRNG** + SHA-256(salt‖pw) + (1000−1) 轮 SHA-256(h‖salt)；**明文绝不落盘/进串口**。
  * 终端：`useradd/userdel/passwd/users/whoami/id/su/sudo/exit/loginctl lock`。`su - root` / `su -` / `sudo -i`
    **只提升会话身份**（euid=0；GUI 用户名/头像不变，打点 `gui_unchanged=1`）；`exit` 退回 GUI 用户；
    `loginctl lock` 回锁屏。`id` 会打印 `(no permission checks yet; P4)`。
* **对 ring3 / syscall 的影响（如实）**：
  * `getuid`(102)/`getgid`(104) **仍返回 0**；`access` 仍忽略 mode；没有 `setuid/setgid/chmod/chown/umask`/`CAP_*`；
    **权限位不拦截任何 open/read/write**（uid/gid/mode 检查是 **P4**）。
  * 会话身份只在**内存**里：软重启/断电后回到开机锁屏（只有普通用户），不跨重启；`userdel` 不删主目录。
  * 每用户桌面在**用户库/会话层**真实枚举（`/home/<名>/Desktop`），但 **GUI 桌面图标网格尚未按用户分目录**。
* **验收**：`tests/locklogin64_test.py`（88 条：锁屏 72/18px、背景清晰 vs 登录后模糊 20px、104px 头像、
  360×48 密码框 + 48×48 确认、ESC 反向、软重启仍锁屏、两用户桌面隔离、su/sudo/exit）。
