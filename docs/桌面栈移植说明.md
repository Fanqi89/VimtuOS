# 64 位桌面栈移植说明

> 目标：把 32 位系统里那套桌面与应用**全部原生化到 64 位**（纯 x86_64 长模式，不用
> 兼容模式、不跑 32 位用户态）。本文记录**做了什么、怎么验收、哪些没有做（以及为什么）**。

## 0. 成果一览

| 层 | 文件 | 行数 | 状态 |
|---|---|---|---|

## 1. 内存层：先把"没有堆"这件事解决掉

`kernel/mem_64.h` 原本 234 行**全是声明、零实现**——64 位内核连 `kmalloc_64` 都没有，
窗口状态、棋盘、终端缓冲全都无处安放。所以第一步是实现 `mem64.cpp`。
布局决策（64 位比 32 位多两个必须避开的区域）：

```
0x0007C000                 内核栈（entry64.asm: mov rsp, 0x7C000）
0x00100000..~0x02460000    内核映像 + .bss（含 fb 的 33MB 后备缓冲）
0x04000000..0x043F1200     安装载荷（仅"安装介质"内核用）
------------------------------------------------------------
内核堆   = [0x05000000, 0x08000000)   ← 80MB..128MB，固定 48MB
物理页池 = [0x08000000, mem_high)     ← 512MB 虚拟机实测 98272 页 / 384MB
页 bitmap = 64KB 静态数组（.bss）     ← 上限 2GB 页池，永不与任何区域重叠
```

* **堆固定不跟着 `_end` 走**：`_end` 会随代码增长，而 64MB 处躺着安装载荷；固定
  80MB 起可保证"安装程序内核"和"系统内核"行为一致、永不重叠。
* **页 bitmap 放进 `.bss`**，而不是像 32 位那样写在 `_end` 之后与堆同址——32 位那个
  缺陷会让第一次 `kmalloc` 就把块头写进 bitmap，页分配器元数据被静默破坏。
* 自检 `mem_selftest_64()`（启动期自动跑，串口打 `[MEM64] selftest PASS`）：16 字节对齐、
  多块不重叠、krealloc 保内容、释放后账面归零、反复分配不碎片化、坏指针防护。
  实测 68 次分配 / 68 次释放、`walkmax=1`（合并后空闲链表只剩 1 块，零碎片）。
* 顺带补了 **`memcpy/memset/memmove/memcmp/str*`**：64 位树里这些从来没有实现过，
  现在能链接只是因为还没有代码触发编译器生成这些调用；桌面一起来就会引用它们。

## 2. 接口契约：`gui64.h`

先冻结接口，再并行开发应用（这是这次能在同一轮里做完 5 个应用的关键）。

* **应用拆文件**：32 位把计算器/扫雷/设置/监视器全塞在 `gui.cpp` 里，64 位改成
  `calc64/mines64/settings64/taskmgr64.cpp` 各一个文件，只依赖 `gui64.h` 契约。
* **修掉 32 位的会话表缺陷**：32 位 `session_app_closed()` 按**槽位下标**查表、调用方传的是
  `Window::app_id`，于是 `APP_ID_TERM(3)` 会命中毒 TaskMgr 槽。64 位一切以 `app_id` 为键。
* **绘制约定**：应用在 draw 回调里用**屏幕绝对坐标**画，外壳负责 `fb_set_clip` 裁到客户区，
  再按脏矩形 `fb_flip_region` 提交。这与安装界面阶段的做法一致。
* **userdata 归属写进契约**：外壳**绝不** `kfree` 应用的 `userdata`，只调 `on_close` 回调
  （本次新加的 `WindowCloseFn`，5 个应用都提了这个需求）。两种回收方式并存都安全。

## 3. 外壳：脏矩形 + 光标重画（照抄安装阶段的有效经验）

* 整屏重绘会把鼠标包读慢十几倍 → 位移被聚合放大 → 光标乱飞。这条教训在安装界面已经付过
  学费，桌面直接沿用：**每次只重画受影响的小块**并局部提交。
  实测：鼠标移动只改 **303/349 像素（约 0.03% 屏幕）**，验证脚本会断言"变化 <3% 屏幕"。
* **光标不做 save-under**：每帧把光标区域连同底色重画一遍（后备缓冲里本来就有正确背景），
  省掉存/取逻辑也就没有残影 bug。
* 文字统一用 simhei 面（face 2）：它的子集含 ASCII + 常用汉字，中英混排不会出豆腐块。
* 图标用真实 128×128 RGBA 资源，但自写缩放 + **与后备缓冲做 alpha 混合**（驱动自带的
  `fb_blit_rgba` 是"对黑底混合"，直接铺在蓝色桌面上会发暗）。

## 4. 移植过程中抓到并修掉的 4 个真缺陷

| # | 现象 | 根因 | 修法 |
|---|---|---|---|
| 1 | 内存自检一开始就**整机挂死**（不是复位，是死循环） | 自检故意用"空闲链表头"当坏指针喂 `kfree`，而空闲块与已分配块**用同一个 magic**，于是它被当成合法块释放 → `blk->next = blk` **自环**，合并遍历永不退出 | 空闲块与已分配块用**不同 magic**（`BLK_MAGIC_64` / `BLK_FREE_64`）；`kfree` 只接受前者。顺带把"二次释放"和"释放空闲块"都变成可拦的 |
| 2 | 潜在三重故障 | `kmalloc/kfree/page_alloc` 里无条件 `sti()`：它在"IDT 尚未装载"的启动早期会把 PIT/PS2 中断放进来（拿不到向量表 → #GP → 三重故障），在中断处理里还会打开嵌套 | 改成 `irq_save64()/irq_restore64()`：进入时保存 IF，退出按原样恢复 |
| 3 | 日志里出现 `kfree: bad pointer` 让验收假失败 | 那是**自检故意喂的坏指针**在如实报警，不是故障 | 自检期间静音（`g_kfree_quiet`）+ 统计拒绝次数，把"守卫到底有没有拦"变成**硬断言**（必须恰好拦下 2 次） |
| 4 | `mouse_parse_test.py` 在 Windows 控制台报 `UnicodeEncodeError` | 脚本要打印 U+2212 减号，而控制台默认 GBK | 脚本内 `sys.stdout.reconfigure(encoding="utf-8")`（与算法无关，纯输出编码） |

## 5. 各应用与 32 位的差异（如实列出）

**共同点**：都在自己的 `draw/key/click` 回调里从 `w->userdata` 取状态（32 位多用全局变量 +
"当前实例"指针兜底），因此**多实例天然独立**；应用一律不写 `w->w/h`，改动走
`gui64_set_geom()/gui64_fit_window_to_client()`，外壳负责脏矩形。

| 应用 | 差异与改进 |
|---|---|
| 扫雷 | 计时改用 `PIT_HZ_64=250`（32 位曾按 100Hz 换算导致计时快 2.5 倍）；洪水展开改**显式栈**（高级 30×16 递归几百层会压爆内核栈）；首击安全 + "先标旗再首击"不再显示陈旧秒数；颜色全走 `rgb()`（32 位手写 `0x00RRGGBB` 会让 `0xFF0000` 变绿）；小格用 8×8 位图字体避免 TTF 行高溢出 |
| 计算器 | Q16.16 定点，`q16_mul` 用完整 64 位精度（32 位丢掉 `a1*a2` 项，导致 `0.5*0.5→0`）；其余分支与 32 位逐条对齐 |
| 终端 | 内容缓冲是 `uint16_t` **码点网格**（ASCII 走位图字体、CJK 走 `font_draw_glyph_cp`），中英混排可用；文件系统用**文件内最小 ramfs**（64 位还没有真文件系统）；`ps` 如实打印"1 个执行流（调度器未移植）"；`cfg/kill/top/hwinfo/lspci` 等依赖未移植子系统的命令**明确提示未支持**，不静默失败 |
| 设置 | 分辨率/缩放/语言**真能改**（`fb_set_mode`/`fb_set_zoom`/`gui64_set_lang_zh`）；**刷新率如实标注"不支持（显示层未移植）"**；无持久化（store 未移植），页面写明"硬重启回默认值" |
| 任务管理器 | 进程页数据来自真实的窗口表（`cpu_pct` 由外壳用 TSC 采样回调耗时、内存取 `mem_owner_bytes_64`）；性能页的内存/中断/帧率全实测；**磁盘项如实标注"驱动未包含在本内核"**（`ata64.cpp` 只编进安装程序内核）；启动项开关标明"只在本会话生效" |

## 6. 明确**没有**做的事（不是忘了，是依赖不具备）

| 项 | 为什么没做 |
|---|---|
| 刷新率读写（EDID/0x3DA/CRTC） | 64 位没有 `display.cpp` 那层（`disp_*` 全套未移植） |
| 设置/窗口几何/启动项**持久化** | `store.cpp`（`VCST` + ATA 读写）未移植；LBA 8009..8072 的保留区已在布局里留好 |
| 任务管理器列出"进程/线程/PID" | 64 位**没有调度器**（`switch64.asm` 就绪但未接入），没有任务表可枚举 |
| 应用内切分辨率后自动重排所有窗口 | 外壳已提供 `gui64_fit_window_to_client()`，但"逐个窗口重排"需要窗口自己响应；当前靠应用下次绘制时自适应 |
| 动态分配窗口标题以外的国际化资源 | 中英切换已可用，但字符串仍是编译期常量表（与 32 位一致） |
| 磁盘/文件系统浏览（"我的电脑"） | 无 ATA 驱动（系统内核不含）+ 无文件系统；窗口如实展示布局常量与说明 |

## 7. 怎么跑、怎么验收

```bash
bash build64.sh                       # 全量构建（系统内核现在 1,774,504 B，内核区上限 4MB）
python tests/desktop64_test.py        # 桌面栈验收：外壳 + 8 个应用 + 像素 + 脏矩形 + 异常日志
python tests/screenshot64.py          # 抓真机截图 -> docs/screenshots/desktop64.png
```

`desktop64_test.py` 的断言分 6 组（共 38 项）：

1. 等 `[GUI64] ready`；内存自检、外壳自检、`[OS] booted from installed disk`、`[OS] ready (idle)`
2. 像素：分辨率 1280×800、桌面主色占比、任务栏深色条、任务栏白色时钟文字、开窗前无标题栏
3. **脏矩形**：鼠标移动后变化像素 >20 且 <3% 屏幕（证明不是整屏重绘）
4. **8 个应用逐个打开**（Win 键开开始菜单 → 数字键选序号）并断言各自的开场日志
5. 开窗后标题栏像素 0 → 8811、任务栏出现窗口按钮、扫雷布局日志出现
6. 不得出现 `PANIC` / `TRIPLE FAULT` / `selftest FAIL` / `OOM` / `kfree: bad` / `FAILED mask=`

手工看界面（QEMU 有窗口）：

```bash
qemu-system-x86_64 -drive format=raw,file=build64/system.img -boot order=c -m 512 -vga std
```

`build64/system.img` 就是"一份完整的已装系统磁盘"（= MBR + loader64 + 系统内核 + 设置保留区），
所以可以直接引导它进桌面，不必先走一遍安装。VMware 里做法相同（新建 VM 时 `guestOS` 必须
选 **other-64**，否则长模式位被屏蔽）。

## 8. 下一步建议

1. **VMware 实测**：QEMU 已全绿，但用户的最终环境是 VMware（另有 `tests/vmware_install_test.py`
   覆盖 BIOS 全流程）。建议跑一次"装完 -> 进桌面 -> 开扫雷"的真机确认。
2. **④ 之后的收尾**：把 `ata64.cpp` + `store.cpp` 移植进系统内核 → 设置/窗口几何能持久化；
   任务管理器能显示真实磁盘。
3. **③ 调度器**：`switch64.asm` + `task_switch_iret64` 已就绪，接上后任务管理器才有真正的
   进程页，也才有"多任务"可言。
4. **UEFI 自动引导**那一步仍未打通（见 `docs/UEFI引导说明.md`），与桌面栈无关。
