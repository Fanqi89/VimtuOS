本文件记录 M1（64 位中断/时钟）调试到目前的**已证实结论**与**未解问题**，
便于下次接手时不必重走弯路。所有结论都是本机实测（QEMU 11.1 / TCG）。
本文件记录 M1（64 位中断/时钟）的调试过程与结论。**M1 中断路径已修通（见第 6 节）**，
所有结论都是本机实测（QEMU 11.1 / TCG 软件模拟）。

> 结论速览：根因是 `pt_regs64` 的**字段顺序写反**（把 CPU 压的 rip/cs/rflags 当成帧开头），
> 导致 `int_no` 读错 → PIT 中断被误判成除零异常。修正后 `[LM64] PIT IRQ OK ticks=12`。
> 诊断用的探针文件（`isr_probe64.asm`/`isr_dbg64.asm`/`isr_out64.asm`）已从构建中移除，
> 保留在仓库里备查；`build64.sh` 的 `VIMTU_PROBE_INT=1` 开关仍可用。

## 3. 用探针实测确认的事实（重要，别推翻重来）

诊断用的探针桩（`kernel/isr_probe64.asm`）走的是与正式桩**完全相同**的保存/恢复路径，
C 侧只打印一次帧内容。实测结果：

* **软件中断 `int $32` 正常投递**，帧内容完全正确：
  `cs=0x08`、`rflags` 为合法值（含保留位）、`rip` 指向内核地址。
* **硬件 IRQ0（PIT）正常投递**：帧里 `rip=0x0000000000104E83`（内核地址）、`cs=0x08`、
  `rflags=0x10202`（IF 置位）。
* **帧布局与 `pt_regs64` 一致**：CPU 在长模式下的入栈顺序是
  `[rsp+0]=rip, +8=cs, +16=rflags`（同特权级；特权级切换时 ss/rsp 在更高地址侧），
  中断桩在其上压 `int_no`(offset 0x78) / `err_code`(offset 0x80)，
  之后是 rax..r15（0x00..0x70）与 4 个段槽（0x88..0xA8 之前的 gs/fs/es/ds）。

结论：**IDT/门/桩/帧布局/PIC/PIT 本身都没有问题**。

## 4. 未解问题（下一步的唯一目标）

走**正式处理函数** `isr_handler64` 时，C 侧看到的帧是错位的：

    [H] int_no=0 err=7 rip=CCCCCCCCCCCCCCCD cs=0x10 rflags=0x10 rsp=0x10
    [H] frameptr=000000000007BEC0

特征：
* `int_no` 读出来是 0（实际应为 32），`err_code=7`（#GP 的错误码）；

### 3.1 追加实测（收尾时做强化的"帧转储"实验）

处理函数改成"打印前两条中断的完整帧后**正常返回**"（不再停机），实测输出：

    [X64] PIC remapped, IDT/TSS loaded, PIT 250Hz
    [H] int_no=0 err=0000000000000007 rip=CCCCCCCCCCCCCCCD cs=0x10 rflags=0x10
    [H] raw@000000000007BEC0: 0000000000000010 0000000000000010 0000000000000010
        0000000000000010 CCCCCCCCCCCCCCCD 0000000000000000 0000000000000007
        00000000CCCCCCCD 0000000000000000 0000000000000000 ...
    [PANIC] cpu exception 0

关键推论：

* `frameptr` 打印成功、`g_irq_total64++` 正常 —— 说明**桩的保存路径能跑到 C 侧**；
  [rdi+0] 的 `0x10`、[rdi+0x10] 的 `0x10` 恰好是 `mov ax,0x10; mov ds,ax; mov es,ax` 里的 0x10，
  **这是唯一能解释"四个 0x10"的来源**，说明 `isr64_common` 里那两条 `mov %eax,%ds / %es`
  确实执行了，且帧内容在到达 C 之前就已被污染（`int_no` 槽读出来是 0 而不是 32）。
* 与此同时，**探针路径在同一 0x7BFxx 栈区、同一保存序列下拿到的是完全正确的帧**
  （`rip` 指向内核、`cs=0x08`、`rflags` 合法）。

因此下一步的**第一优先实验**很明确：把 `isr64_common` 里那两条 `mov ds/es, ax` 去掉
（长模式下 ds/es 基址无效，内核里没有必要每条中断都重载段寄存器），再跑一次；
若仍复现，则用 `kernel/isr_dbg64.asm`（纯汇编处理函数，不经过 C）替换 `call isr_handler64`，
直接按偏移打印 `[rdi+0x78]`/`[rdi+0x80]`/`[rdi+0x88]`，二分定位"桩传参"还是"C 侧解释"。
* 帧里混入 `0xCCCC...`（编译器未初始化填充）与大量 `0x10`；
* 同一位置在探针路径下是**完全正确的帧**。

已排除：IDT 门（实测 sel=0x08 attr=0x8E）、IDT 基址（idtr.base 已打印且正确）、
段选择子（cs 实测 0x08）、栈本身（探针在同一栈上工作正常）。

**首要怀疑**：正式桩 `isr64_common` 里的
* `mov ax, 0x10; mov ds, ax; mov es, ax` —— 长模式下 `MOV Sreg, r/m16` 是否真被允许，
  以及它是否影响后续 `push` 序列（用机器码 `8e d8` 存在于映像中，见反汇编）；
* 或 `call isr_handler64` 前后的帧指针传递（`mov rdi, rsp`）。

**下一步建议**（按成本从低到高）：
1. 把 `isr64_common` 的做法改成"完全不碰段寄存器"（长模式下 ds/es 基址无效，
   内核里没有必要每条中断都重载），再测一次；
2. 若仍失败，用 `isr_dbg64.asm` 的纯汇编处理函数（不经过 C）替换
   `call isr_handler64`，直接打印 `[rdi+0x78]` 等偏移，二分定位是"桩传参"还是"C 侧解释"；
3. 用 GDB（`qemu -s -S` + `gdb`）在 `isr64_common` 处单步，直接看寄存器与栈。
