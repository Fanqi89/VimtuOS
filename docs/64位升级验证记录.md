# Vimtu64 64 位升级验证记录

本文件记录 **64 位（x86_64 长模式）升级** 的实测结论，只写实测通过的事实。
本项目现在**只有 64 位一条构建线**（`build64.sh`）：原先的 32 位构建（`build.sh`）已整体
退役到 `legacy32/`（见 `legacy32/README.md`），不参与构建。下表保留 32 位列**仅为历史对比**。

---

## 1. 构建线（现状）

| | 64 位（唯一构建线） | 32 位（已退役，见 `legacy32/`） |
|---|---|---|
| 构建脚本 | **`build64.sh`** | `legacy32/build32.sh` |
| 编译器 | **`clang++ --target=x86_64-elf`** | `clang++ --target=i686-elf` |
| 产物 | **`vimtu64-64.img` / `vimtu64-64.iso`** | `vimtu64.img` / `vimtu64-install.iso` |
| 引导 | MBR → **loader64 → x86_64 长模式** | MBR → loader → 32 位保护模式 |
| 内核链接 | **`kernel/linker64.ld` (ELF64)** | `kernel/linker_lld.ld` (ELF32) |
| 入口 | **`kernel/entry64.asm` → `kernel/kernel64.cpp`** | `kernel/kernel.cpp` 的 `_start` |
| 内核区 | LBA 9..8008 (**4.0MB**) | LBA 9..4008 (2.0MB) |

两者共用：`boot/boot.asm`（MBR）、资源生成脚本（字体/logo/图标）、`build/` 目录里的中间产物。

## 2. 镜像布局（唯一权威定义 = `kernel/memlayout64.h`）

    LBA 0          : boot.bin      (512B MBR，读 LBA1..8 到 0x9000)
    LBA 1..8       : loader64.bin  (实模式准备 + 32 位 ATA 读内核 + 进长模式)
    LBA 9..8008    : kernel64.bin  (最多 4,000 KB)
    LBA 8009..8072 : 设置持久化保留区 (64 扇区 = 32KB)
    = 8073 扇区 / 4,133,376 字节

长模式页表（loader 建，内核沿用）：PML4 0x40000 / PDPT 0x41000 / 4×PD 0x42000..0x45000，
恒等映射 0..4GB（2MB 大页）。内核栈 0x7C000。

## 4. 排障中发现的三个真实坑（已写进代码注释，避免重踩）

1. **QEMU 的 SeaBIOS 自己也往 0x402(debugcon) 写日志**（`SeaBIOS (version ...)`），
   所以 debugcon 是"固件日志 + 我们的日志"混合体；**串口 COM1 才是干净通道**。
   验收脚本因此把断言分成 `must_serial` / `must_debugcon` 两组。
2. **BIOS 阶段的横幅**（MBR 的 `Aurora32 boot`、loader 的 `Vimtu32/64 Loader`）走 INT 10h
   直写显存，既不进串口也不进 debugcon —— 不能用它们做自动断言，用 `dbg_str` 打的
   `L:edid ok` / `L:bootinfo` / `L:ata` / `L:lm64` 标记代替。
3. **长模式远跳必须用全局标号**：`jmp 0x08:.in64` 里的 `.in64` 会被 NASM 归到前一个全局
   标号作用域下（报 `symbol lm64_enter_long.in64 not defined`），必须写成 `lm64_in64`。

## 5. 已知限制（下一步要处理）

* loader 只恒等映射 **0..4GB**：超过 4GB 的物理内存目前不可直接访问，要由内核侧页表接管
  后再扩展（M1 的 paging 模块）。
* 本机 **VT-x 未启用**：QEMU 只能软件模拟（TCG）。真实固件环境的验收改走
  **VMware Workstation**（见 `docs/VMware验证指南.md`），一条命令跑完安装+启动验收。
* 装好的目标盘目前只用 **MBR + 自研布局**（引导分区 type 0xEF + 主分区 0x07）；
  UEFI 需要 GPT + FAT32 ESP，属 M3。
* **ISO 安装介质已可用**（`vimtu64-64.iso`，BIOS 光盘引导；QEMU + VMware 虚拟光驱都验过）；
  还没做的是「把 ISO 写进 U 盘后当**硬盘**引导」那条路（需要自研 hybrid MBR + unreal mode
  搬运高内存，见 `docs/ISO安装介质说明.md` 第 5 节）与 UEFI 启动。

### 三个真 bug（都已修 + 记录成因）

1. **按回车出来的是 Esc**（QEMU/VMware 都复现）
   * 现象：注入 `ret` 收到 `0x1B`；QEMU `ps2_keycode` trace 显示设备发的是
     **集 2** 码 `0x5a`（`set 2 xlate 0`），而驱动用集 1 表解码。
   * 成因：`kernel64.cpp` 里 `kbd_init()/mouse_init()` 被**执行了两遍**；第二次读 8042
     命令字节时缓冲里还留着鼠标的 ACK(0xFA)，写回 `0xFB` 把 bit6（集 2→集 1 翻译）清掉了。
   * 修复：初始化只做一次；`input.cpp` 读写命令字节前先排空缓冲并**强制 bit6=1**；
     键盘/鼠标 IRQ 共用一个按状态位 0x20 分流的排空函数（顺带修掉鼠标字节被当扫描码的隐患）。
2. **装完不自动重启**
   * 成因：`progress_tick()` 开头 `if (page != PAGE_PROGRESS) return;`，跳到完成页后
     永远走不到"等 2.5 秒重启"那段。
   * 修复：改成"复制阶段"条件判断，完成页仍每帧检查重启倒计时。
3. **VMware 里引导链静默停机（屏幕全黑、串口无输出）**
   * 成因：PAE 位读在 `CPUID.80000001h:EDX bit6` —— AMD 报、**Intel 不报**。
     QEMU 的 `qemu64` 是 AMD 风格所以一直通过；VMware 直通 Intel 主机 CPU 就判定
     "不支持长模式"并 `hlt`（而且停在只有 0x402 输出、VMware 看不见的路径上）。
   * 修复：PAE 改读 `CPUID.01h:EDX bit6`；32 位阶段加串口进度标记 + 失败时打印
     CPUID 实际数值（`L:pm ok` / `L:enter long mode` / `L:cpuid ok` / `L:paging ok`）。
