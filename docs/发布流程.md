# VimtuOS 发布流程与版本号规则

> 本文是**发布规则**的权威说明。每次对外发布都必须**新建一个标签 + 新建一个 Release**，不要复用旧标签。

## 1. 版本号规则（★ 用户新规则：**发布不再追加 `-betaN` 后缀**）

| 形态 | 版本号 | 用途 |
|---|---|---|
| **大版本** | `v0.4.3`、`v0.5.0`、`v0.6.0` … | 一批**大功能**落地时升大版本（次版本进位） |
| **小版本** | `v0.4.3`、`v0.4.4`、`v0.4.5` … | 修 bug / 加小功能时升小版本（修订号 +1） |

要点：
1. **每次发布，版本号必须变化**（这条照旧）：要么升小版本（`v0.4.3` → `v0.4.4`），要么升大版本
   （`v0.4.3` → `v0.5.0`）。★ **标签号里不再出现 `-beta` 字样。**
2. **`-betaN` 后缀已废止（本版起）**：标签、Release 名、`build64.sh` 的 `VIMTUOS_VERSION` 一律是
   纯 `MAJOR.MINOR.PATCH`（例 `0.4.3`）；历史的 `-betaN` 标签**保留不动**，见 §1.1。
3. **一次发布 = 一个新标签**，标签**只增不改**；已经发布过的标签**绝不复用**（旧标签不重新打包新构建）。
4. **每个 Release 保留属于自己的安装程序**：各版本的 ISO/IMG **长期挂在它自己的 Release 上、不要撤掉**——
   用户有权自由下载任意历史版本、自己挑版本用。
5. **二进制必须与该版本源码对应**：不许把新构建挂到旧标签上，也不许用旧标签冒充"最新版"；
   **发布新版本时，旧版本 Release 的附件一个都不要动**（新版本只动自己的 Release）。
6. **"预发布"语义怎么表达（不再用后缀）**：需要标注为预发布时，**只勾** GitHub Release 的
   **Pre-release** 勾选框（标签名与 `VIMTUOS_VERSION` 都不变）；没有对外发布意图的候选构建用
   `draft=true` 草稿，发布后把草稿删掉。★ 历史 `-betaN` Release 的 Pre-release 勾选**保持原状**。
7. **标签写法**：新发布一律用纯版本号 `v<MAJOR>.<MINOR>.<PATCH>`（例 `v0.4.3`）——**不带任何后缀**；
   历史上用过 `-betaN`（含点分写法 `v0.1.0-beta.1` … `v0.2.0-beta.5` 与 `v0.4.2-beta19`）的标签
   **保留原样、不重命名、不重打包**，见 §1.1。

## 2. 发布前的门禁（必须全过）

### ★ 第 1 条硬门禁（版本串）：发布前**必须先改 `build64.sh` 的 `VIMTUOS_VERSION` 并重建**

> 规则一句话：**本次发布标签号 == `build64.sh` 的 `VIMTUOS_VERSION` == 镜像内嵌串**（三者必须一致）。
>
> 发布动作的**第一步**（早于构建/验收/打标签/建 Release）：
> 1) 打开 `build64.sh`，把 `VIMTUOS_VERSION="0.4.3"` 这一类行改成**本次要发的版本号**
>    （★ 纯 `MAJOR.MINOR.PATCH`，**不带 `-beta` 后缀**）；
> 2) `bash build64.sh` 重建（EXIT=0）——**改完不重建 = 没改**；
> 3) 用串口证据核对内嵌串已变（见下面 ⑤：`[SET64] about version=…` 或终端 `ver`）。
>
> **为什么它是第一条硬门禁**：v0.3.3-beta15 与 v0.4.1-beta18 两次都漏了这一步 —— 标签是新的、
> 镜像里内嵌的还是上一版的串（beta15 内嵌 `0.3.2-beta14`；beta18 内嵌 `0.4.0-beta17`，
> 见 §1 第 9 条那段"未勾的一项"）。
> **这条不过 = 不许打标签、不许发 Release**：它不是"发布后检查清单"里的自查项，而是发布前的**否决项**。
>
> ★ **本版状态（`v0.4.3`）**：这一条按流程执行 —— `build64.sh` 的 `VIMTUOS_VERSION="0.4.3"` 已改并重建，
> **系统内核** `build64/kernel64_os.bin` 里实测**新串命中**（`0.4.3` **5** 次、`VimtuOS 0.4.3` **4** 次、
> 终端串 `VimtuOS Terminal v0.4.3` **1** 次，逐字节可检索；旧串 `0.4.2-beta19` **0** 次）——
> 如实标注：**安装程序内核** `build64/kernel64.bin` 里没有 `0.4.x` 字面量（**0 命中**），因为带版本串的
> `kernel/settings64.cpp` / `kernel/terminal64.cpp` 只编进系统内核；本门禁的判据就是系统内核的
> `[SET64] about version=VimtuOS 0.4.3 x86_64` 与终端 `VimtuOS Terminal v0.4.3 (64-bit long mode)`。
> beta15/beta17/beta18 连续三次的"未勾项"由此继续关闭（且从 `v0.4.3` 起标签号里不再有 `-beta`）。

### 其余门禁（在过了第 1 条之后按顺序执行）

#     设置页"关于" [SET64] about version=VimtuOS <版本> x86_64 build_tag=… bits=64
#     终端 `ver`    VimtuOS Terminal v<版本> (64-bit long mode)
#    ★ 血泪教训：v0.3.3-beta15 发布时漏了第 ①/④ 步 —— 标签是 v0.3.3-beta15，镜像里内嵌的

## 4. 通过 API 发布的要点（踩过的坑）

- **凭据**：本机已用 Git Credential Manager 缓存 GitHub 凭据，可用
  `$cred = ("protocol=https`nhost=github.com`n`n" | git credential fill); $tok = ($cred | Select-String '^password=').Line.Substring(9)`
  取 token（**不要打印到日志里**）。
- **建 Release**：`POST https://api.github.com/repos/Fanqi89/VimtuOS/releases`，字段
  `tag_name` / `target_commitish=main` / `name` / `body` / `draft=false` / `prerelease=true`（测试版）。
- **上传附件**：`POST https://uploads.github.com/repos/<owner>/<repo>/releases/<id>/assets?name=<文件名>`
  - 必须用 **裸 `application/octet-stream`** 上传，并**显式给 `Content-Length`**；
  - ⚠️ 不要用 PowerShell 的 `MultipartFormDataContent`：.NET 会给 multipart boundary 加引号，GitHub 会把整个信封当文件（附件莫名 +187 B）。
  - 首次上传返回 **422 往往是缺 `Content-Length`**。
- **校验**：上传后 `GET` 该 release，逐附件比对 `size` 与 `digest`（GitHub 给的是 `sha256:…`）与本地 `sha256sum` **完全一致**才算成功。
- **ISO 较大**（当前 ~56 MB），上传留足时间。
- **草稿**：草稿 Release（`draft=true`）不对外可见；草稿里挂的是临时候选构建，**正式发布后就把草稿删掉**，别让同名草稿长期悬着。

## 6. 附件与法律注意

- **只发源码时**：仓库不含第三方字体（`Fonts/`）与打包的交叉编译器（`tools/i686-elf/`）。
- **发二进制（ISO/IMG）时**：镜像里内嵌的字体子集必须是**可再分发**的（当前为 SIL OFL 的 Noto Sans / Noto Serif / Noto Sans SC，见 `docs/字体许可说明.md`）。
- **字体替换之前的老提交不得出二进制**：提交 `11cc67a`（`fonts: 内核内嵌字体换成开源字体…`）之前的提交内嵌的是商业字体子集
  （bahnschrift / ChaparralPro / simhei），**法律上不能公开分发** —— 即使那个标签还没有二进制，也**不要**直接用它构建后上传。
  给老版本补安装程序时，用**该版本线里"字体替换之后"的提交**构建（例：`v0.1.0-beta.1` 用 `11cc67a`），并在 Release 正文里**如实写清实际构建来源**；
  上传前做**字体自证**：在 ISO / IMG / 两个内核里检索字体名 —— `Noto Sans`/`Noto Serif`/`Noto Sans SC` 命中、`bahnschrift`/`Chaparral`/`simhei` **0 命中**
  （UTF-8 与 UTF-16BE 两种编码都查），并把结论写进正文。
