# VimtuOS 发布流程与版本号规则

> 本文是**发布规则**的权威说明。每次对外发布都必须**新建一个标签 + 新建一个 Release**，不要复用旧标签。

## 1. 版本号规则

| 形态 | 版本号 | 用途 |
|---|---|---|
| **正式版 · 大版本** | `v0.1.0`、`v0.2.0`、`v0.3.0` … | 一批**大功能**落地时升大版本 |
| **正式版 · 小版本** | `v0.1.1`、`v0.1.2`、`v0.1.3` … | 修 bug / 加小功能时升小版本 |
| **测试版** | 在上述版本号后追加 `-betaN`：`v0.1.0-beta1`、`v0.1.1-beta2`、`v0.2.0-beta3` … | 对外测试的预发布 |

要点：
1. **每次发布，版本号必须变化**：要么升版本号（大版本 / 小版本），要么递增 `-betaN`，或者两者同时
   （例：`v0.1.0-beta1` → `v0.1.1-beta2`）。
2. **`-betaN` 的 N 逐次递增、不重置**：`-beta1` → `-beta2` → `-beta3` → …（即使同时升了版本号，N 也继续往上涨）。
3. **一次发布 = 一个新标签**，标签**只增不改**；已经发布过的标签**绝不复用**（旧标签不重新打包新构建）。
4. **每个 Release 保留属于自己的安装程序**：各版本的 ISO/IMG **长期挂在它自己的 Release 上、不要撤掉**——
   用户有权自由下载任意历史版本、自己挑版本用。
5. **二进制必须与该版本源码对应**：不许把新构建挂到旧标签上，也不许用旧标签冒充"最新版"；
   **发布新版本时，旧版本 Release 的附件一个都不要动**（新版本只动自己的 Release）。
6. 测试版一律标为 **Pre-release（预发布）**，正式版才取消该勾选。
7. 写法统一为 **`-betaN`（不带点）**；历史上用过点分写法的标签（`v0.1.0-beta.1` … `v0.2.0-beta.5`）
   **保留原样、不重命名**，从下一版起统一按新写法。
8. 中文/英文说明都写在 Release 正文里，正文末尾附**本次附件的 sha256**。
9. **当前进度**：本次发布 **`v0.2.1-beta9`**（批次 N：开机滚屏引导控制台 boot console + `dmesg`）；
   下一版在它之上继续递增 `-betaN`（`v0.2.1-beta10` 或升版本号后再 `-betaN`）。
10. **例外（法律约束，见 §6）**：字体替换提交 `11cc67a` 之前的提交**不得发布二进制**（内核内嵌商业字体子集）。
   要给更老的版本提供安装程序，就用**该版本线里"字体替换之后"的提交**构建，并在正文里写清实际构建来源
   （样例：`v0.1.0-beta.1` 用 `11cc67a` 构建）。

## 2. 发布前的门禁（必须全过）

```bash
# ① 构建（唯一构建脚本）
bash build64.sh                 # EXIT=0；系统内核 < 4,096,000 B；loader ≤ 4096 B
# ② 全量验收（必须全 PASS，Windows 原生 Python）
py -3 tests\status_report.py --full
# ③ 状态核查（能力项计数要如实）
py -3 tests\status_report.py
```

只有"构建成功 + 全量验收 0 FAIL"才允许发布。

## 3. 发布步骤（照抄）

```powershell
cd C:\Users\fanqi\Desktop\VimtuOS\Vimtu64

# ① 提交并推送源码
git status --short              # 先看会提交什么（别把 build64/、Fonts/、tools/i686-elf/ 带进去）
git add -A
git commit -m "……"
git push

# ② 打标签并推送（★ 每次发布换新版本号）
git tag -a v0.2.0-beta.N -m "VimtuOS 0.2.0-beta.N"
git push origin v0.2.0-beta.N

# ③ 建 Release + 上传附件 + 校验（用 GitHub API）
py -3 <脚本>                    # 见 §4：正文字符串 + ISO/IMG 上传 + sha256 双向核对

# ④ 收尾：旧版本的 Release 一律不碰（不改正文、不加删附件），只回头确认它还在原样挂着
```

> **给历史版本补安装程序（特例，需谨慎）**：先读 §6 的字体约束 —— 只能用"字体替换之后"的提交构建，
> 上传前做字体自证，并在该 Release 正文里如实写清实际构建来源；补完之后 **`GET` 校验 `size` + `digest`**
> 与本地 `sha256sum` 一致，同时确认**别的 Release 的附件没有被改动**。

## 4. 通过 API 发布的要点（踩过的坑）

- **凭据**：本机已用 Git Credential Manager 缓存 GitHub 凭据，可用
  `$cred = ("protocol=https`nhost=github.com`n`n" | git credential fill); $tok = ($cred | Select-String '^password=').Line.Substring(9)`
  取 token（**不要打印到日志里**）。
- **建 Release**：`POST https://api.github.com/repos/Fanqi89/VimtuOS/releases`，字段
  `tag_name` / `target_commitish=main` / `name` / `body` / `draft=false` / `prerelease=true`（测试版）。
- **上传附件**：`POST https://uploads.github.com/repos/<owner>/<repo>/releases/<id>/assets?name=<文件名>`
  - 必须用 **裸 `application/octet-stream`** 上传，并**显式给 `Content-Length`**；
  - ⚠️ 不要用 PowerShell 的 `MultipartFormDataContent`：.NET 会给 multipart boundary 加引号，GitHub 会把整个信封当文件（附件莫名 +187 B）。
  - 首次上传返回 **422 往往是缺 `Content-Length`**。
- **校验**：上传后 `GET` 该 release，逐附件比对 `size` 与 `digest`（GitHub 给的是 `sha256:…`）与本地 `sha256sum` **完全一致**才算成功。
- **ISO 较大**（当前 ~56 MB），上传留足时间。
- **草稿**：草稿 Release（`draft=true`）不对外可见；草稿里挂的是临时候选构建，**正式发布后就把草稿删掉**，别让同名草稿长期悬着。

## 5. 发布后检查清单

- [ ] Release 页面：标签号正确、正文含本次变更与 sha256、附件齐全且校验一致
- [ ] 测试版勾选 **Pre-release**
- [ ] 仓库首页 README 的版本/体积/断言数字已同步
- [ ] `docs/项目状态总览.md` 已记录本次发布
- [ ] **旧版本 Release 的附件一个都没动**（每个 Release 各自保留自己的安装程序，用户可自由下载任意历史版本）
      —— 检查手法：`GET` 新旧两个 release，比对旧 release 的附件 `id`/`size`/`digest`/`updated_at` 与发布前一致。

## 6. 附件与法律注意

- **只发源码时**：仓库不含第三方字体（`Fonts/`）与打包的交叉编译器（`tools/i686-elf/`）。
- **发二进制（ISO/IMG）时**：镜像里内嵌的字体子集必须是**可再分发**的（当前为 SIL OFL 的 Noto Sans / Noto Serif / Noto Sans SC，见 `docs/字体许可说明.md`）。
- **字体替换之前的老提交不得出二进制**：提交 `11cc67a`（`fonts: 内核内嵌字体换成开源字体…`）之前的提交内嵌的是商业字体子集
  （bahnschrift / ChaparralPro / simhei），**法律上不能公开分发** —— 即使那个标签还没有二进制，也**不要**直接用它构建后上传。
  给老版本补安装程序时，用**该版本线里"字体替换之后"的提交**构建（例：`v0.1.0-beta.1` 用 `11cc67a`），并在 Release 正文里**如实写清实际构建来源**；
  上传前做**字体自证**：在 ISO / IMG / 两个内核里检索字体名 —— `Noto Sans`/`Noto Serif`/`Noto Sans SC` 命中、`bahnschrift`/`Chaparral`/`simhei` **0 命中**
  （UTF-8 与 UTF-16BE 两种编码都查），并把结论写进正文。
