# VimtuOS 发布流程与版本号规则

> 本文是**发布规则**的权威说明。每次对外发布都必须**新建一个标签 + 新建一个 Release**，不要复用旧标签。

## 1. 版本号规则

| 形态 | 版本号 | 用途 |
|---|---|---|
| **测试版（beta / 预发布）** | `v0.<大版本>.0-beta.<N>` | 每次发布**递增 N**：`v0.2.0-beta.2` → `v0.2.0-beta.3` → `-beta.4` → `-beta.5` → … |
| 正式版（将来） | `v0.<大版本>.<小版本>` | 例如 `v0.2.0`、`v0.3.0`；正式版发布时去掉 `-beta.N` |

要点：
1. **一次发布 = 一个标签**，标签**只增不改**；已经发布过的标签**绝不复用**（不要往旧标签上重新上传附件当"新版本"）。
2. 测试版一律标为 **Pre-release（预发布）**，正式版才取消该勾选。
3. 目前约定：**大版本号随"一批大功能落地"递增**（如 0.1 → 0.2 是进程/文件系统/安装链路/NVMe 这一批）。
4. 中文/英文说明都写在 Release 正文里，正文末尾附**本次附件的 sha256**。

## 2. 发布前的门禁（必须全过）

```bash
# ① 构建（唯一构建脚本）
bash build64.sh                 # EXIT=0；系统内核 < 4,096,000 B；loader ≤ 4096 B
# ② 全量验收（必须全 PASS，Windows 原生 Python）
py -3 tests\status_report.py --full
# ③ 状态核查（能力项计数要如实）
py -3 tests\status_report.py
```

只有"构建成功 + 全量验收 0 FAIL"才允许发布。

## 3. 发布步骤（照抄）

```powershell
cd C:\Users\fanqi\Desktop\VimtuOS\Vimtu64

# ① 提交并推送源码
git status --short              # 先看会提交什么（别把 build64/、Fonts/、tools/i686-elf/ 带进去）
git add -A
git commit -m "……"
git push

# ② 打标签并推送（★ 每次发布换新版本号）
git tag -a v0.2.0-beta.N -m "VimtuOS 0.2.0-beta.N"
git push origin v0.2.0-beta.N

# ③ 建 Release + 上传附件 + 校验（用 GitHub API）
py -3 <脚本>                    # 见 §4：正文字符串 + ISO/IMG 上传 + sha256 双向核对
```

## 4. 通过 API 发布的要点（踩过的坑）

- **凭据**：本机已用 Git Credential Manager 缓存 GitHub 凭据，可用
  `$cred = ("protocol=https`nhost=github.com`n`n" | git credential fill); $tok = ($cred | Select-String '^password=').Line.Substring(9)`
  取 token（**不要打印到日志里**）。
- **建 Release**：`POST https://api.github.com/repos/Fanqi89/VimtuOS/releases`，字段
  `tag_name` / `target_commitish=main` / `name` / `body` / `draft=false` / `prerelease=true`（测试版）。
- **上传附件**：`POST https://uploads.github.com/repos/<owner>/<repo>/releases/<id>/assets?name=<文件名>`
  - 必须用 **裸 `application/octet-stream`** 上传，并**显式给 `Content-Length`**；
  - ⚠️ 不要用 PowerShell 的 `MultipartFormDataContent`：.NET 会给 multipart boundary 加引号，GitHub 会把整个信封当文件（附件莫名 +187 B）。
  - 首次上传返回 **422 往往是缺 `Content-Length`**。
- **校验**：上传后 `GET` 该 release，逐附件比对 `size` 与 `digest`（GitHub 给的是 `sha256:…`）与本地 `sha256sum` **完全一致**才算成功。
- **ISO 较大**（当前 ~56 MB），上传留足时间。
- **草稿**：草稿 Release（`draft=true`）不对外可见；**不要长期留同名草稿**，避免下载到旧二进制。

## 5. 发布后检查清单

- [ ] Release 页面：标签号正确、正文含本次变更与 sha256、附件齐全且校验一致
- [ ] 测试版勾选 **Pre-release**
- [ ] 仓库首页 README 的版本/体积/断言数字已同步
- [ ] `docs/项目状态总览.md` 已记录本次发布
- [ ] 旧标签**没有被复用**（本次是新标签）

## 6. 附件与法律注意

- **只发源码时**：仓库不含第三方字体（`Fonts/`）与打包的交叉编译器（`tools/i686-elf/`）。
- **发二进制（ISO/IMG）时**：镜像里内嵌的字体子集必须是**可再分发**的（当前为 SIL OFL 的 Noto Sans / Noto Serif / Noto Sans SC，见 `docs/字体许可说明.md`）。
