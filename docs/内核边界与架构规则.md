# 内核边界与架构规则（架构宪法）

> 本文件是**规则**，不是状态报告。任何一批工作开工前先读它；越界的设计先在这里改规则，
> 而不是先写代码。
>
> 立规时间：本次任务（busybox 移植 + 日常工具集）—— 用户明确指令如下。

---

## 0. 一句话宪法

**内核不再添加新功能。新功能一律加在用户态。内核只允许"修复 / 健壮性 / 性能 /
用户态所必需的系统调用（ABI）补齐"—— 这一类改动统称「完善内核」。**

推论（照抄执行，不留解释空间）：

1. 任何"新能力"（新命令、新界面、新服务、新格式、新协议）**落地位置必须是用户态**，
   交付形态是**系统卷里的文件**（`/bin`、`/lib`、`/etc`……），内核镜像**一个字节都不加**；
2. 内核代码只能被**改动**，不能被**扩张**：可以修 bug、加校验、降复杂度、提性能、
   把已有能力以最小 ABI 暴露给 ring3；不可以加新子系统、新设备、新命令解析、新 UI；
3. 判定有疑问时**默认用户态**：先试着用现有 ABI 在用户态做完（哪怕多写几百行）；
   做不完再谈"补齐最小 ABI"，且**功能本身仍然留在用户态**；
4. 每批交付都必须能用**字节**证明上面三条：内核镜像不含新功能的字节（探针断言）、
   内核体积不因为"加功能"而上涨。

## 1. 判据清单

### 1.1 什么算「完善内核」（允许，且必须逐条说明理由）

| 类别 | 判据（同时满足） | 例子（本仓已有） |
|---|---|---|
| 修复 | 某个既有行为在**规格上**是错的；改动只让它变正确，不引入新能力面 | `wait4` 的 EAGAIN 处理、`fd64_readdir64` 目录类型判定、`unlink` 栈泄漏、xHCI 事件环 cycle 回卷 |
| 健壮性 | 新增的是**校验/边界/错误上报**，不是新语义；恶意/异常输入下从"崩"变成"明确拒绝" | `lx64_resolve_path64` 的长度/深度校验、`fd64` 越界拒绝、panic 时的看门狗暂停 |
| 性能 | 语义与 ABI 完全不变，只是更快/更小 | 目录句柄首次 readdir 缓存 16 条、`smp64` 自旋改让出 |
| 用户态所必需的 ABI 补齐 | ① 内核**已经有**这个能力（内部函数/结构存在）；② ring3 **没有**任何等价通路；③ 新增的是一个**最小暴露**（一个系统调用号 + 一层参数校验），**不含任何新算法**；④ 该能力的具体使用方式（策略、格式、命令语义）**全部在用户态** | `mmap`/`mprotect`/`brk`、`pipe`/`dup2`、`sigaction`/`sigreturn`、`pci_map_bar`、`shm_*`、`fb_map`/`fb_flip`、`arch_prctl`（FS.base）、`getrandom` |

ABI 补齐全网最低要求（写代码前先能背出来）：

1. 能不能用**已存在**的号段 + 已有的内核原语拼出来？能 -> 不许加号；
2. 加这个号以后，内核里**多出来的逻辑**是不是只有"参数校验 + 转发到已有函数"？
   如果多出来的是一段可执行策略 -> 它属于用户态，回去重做；
3. 这个号的**语义要在 `docs/应用层与系统调用说明.md` 的表里写清楚**，包括边界（不支持什么）。

### 1.2 什么算「新功能」（禁止加在内核）

只要满足下面**任意一条**，就是新功能：

* 引入了新的**用户可见语义**（新命令、新快捷键、新菜单项、新文件格式的解析/生成）；
* 引入了新的**设备/协议/服务的驱动或状态机**（哪怕只有几百字节）；
* 引入了新的**策略**（调度策略、权限策略、颜色主题、布局算法）—— 策略永远属于用户态；
* 让某个 ring3 进程**不再需要**读盘/读共享内存就能拿到新能力（等价于把用户态代码搬进内核）；
* 需要**新的常驻内核线程/定时器**才能工作（除非是"修复既有线程的调度/唤醒"）。

**反例（都是本仓历史上的越界，已按此规则外置或计划外置）**：

* 内核里那套 GUI（`gui64`/`explorer64`/`panels64`/`startmenu64`/`gfx64`/`img64`/`theme64`/`locklogin64`）
  —— "画窗口、摆图标、画主题、锁屏"全是策略，已经由 B-wm 搬出 Ring 3 合成器（`/bin/wm`），
  内核里那 8 个文件是**待清理的存量**（见第 2 节）；
* 内核里那些"应用"（终端、设置、任务管理器、用户库……）—— 应用属于用户态；
* 内核里那些非本机必备的驱动（USB/NVMe/AHCI/HDA/virtio-gpu/e1000）—— 属于"驱动服务"
  （`/bin/drvdemo` 那条线就是它的骨架）。

### 1.3 边界情况的裁决流程（照做）

1. **先假设用户态能做**。写一页纸：需要哪些已有系统调用？缺哪一个？
2. 如果缺一个 ABI：写出"最小 ABI 规范"——号、参数、返回值、错误码、边界，
   并证明"内核里已有对应原语"（给出文件名/函数名）。**功能代码仍写在用户态**。
3. 如果最小 ABI 也做不到（例如需要内核在中断上下文里做决策）：**停下来报告**，
   不要自行加。写清"为什么必须在内核、代价是什么、有没有二级替代"。
4. 以上任何一步都不改变"交付进系统卷"这一条。

## 2. 内核里"现存但应外置"的目标清单与顺序

数字来自 `tools/kernel_size_report.py`（本仓实测，内核 `.text+.rodata+.data` = 3,300,329 B
分项合计；平整度字节 `build64/kernel64_os.bin` = **3,297,680 B**，余量 **798,320 B**）：

| 桶 | 文件数 | 字节 | 占比 | 现状 |
|---|---|---|---|---|
| 核心（不可外置） | 8 | 412,109 B | 12.5% | `vfs64/proc64/fd64/syscall64/task64/elf64/mem64/fs64` —— 这些是"内核"本身 |
| 设备驱动（模块化/用户态候选） | 8 | 205,725 B | 6.2% | `xhci64/usb64/ahci64/hda64/ata64/nvme64/virtio_gpu64/e1000_64` |
| **GUI 专用（→ Ring 3）** | 8 | **578,180 B** | 17.5% | `gui64/explorer64/panels64/startmenu64/gfx64/locklogin64/img64/theme64` |
| **内置应用/外壳（→ Ring 3）** | 13 | **749,796 B** | 22.7% | `terminal64/settings64/taskmgr64/userdb64/desktopops64/config64/icons64/mines64/session64/calc64/preload64/update64/sysstate64` |
| 内嵌资源 blob（→ 系统卷） | 8 | 827,509 B | 25.1% | `font_simhei_z(733,584) iconpack_bin(49,192) kaisi_png(font_mono_z/font_bahnschrift_z/icon_start_mini/font_fallback_z/ap_trampoline64` |
| 其它平台基础 | 29 | 527,010 B | 16.0% | `kernel64/fat64/console64/hwui64/store64/drive64/panic64/font/usermode64/sig64/display64/wl64/input64/edid64/net64/app64/hwinfo64/smp64/acpi64/input/apic64/fb/gui_rs/x86_64/pci64/isr_stubs64/switch64` |

> 明细里 `font_simhei_z`（733,584 B）和 `iconpack_bin`（49,192 B）是**目前最大的一块**，
> 两者相加 782,776 B —— 单它们就占内核 23.7%。**内嵌资源已经外置过一批**
> （logo + 3 个图标 + icon_start_mini 的 64x64 原图 = 356,992 B，见 build64.sh 的
> `tools/assets_pack_win.py` 那一步与 `kernel/icons64.h` 的说明），剩下这两块同理外置。

### 外置顺序（按"改动面 / 收益比"从高到低；**一次只做一桶**）

1. **资源 blob（第 1 顺位，收益 ~810 KB）**
   * `font_simhei_z`（733,584 B）：改成 `/etc/font_simhei_z.bin` + 内核只留"读卷"的路径
     （资源外置的现成范式：`kernel/icons64.h` + `tools/assets_pack_win.py`）。
   * `iconpack_bin`（49,192 B）、`kaisi_png`、`font_mono_z`、`font_bahnschrift_z`、
     `font_fallback_z`：同一批外置。
   * 验收：内核字节净减 ≥ 800,000 B；字体/图标显示**逐像素**与改前一致（截图哈希）。
2. **内置应用/外壳（第 2 顺位，收益 ~750 KB）**
   * 顺序：`terminal64`(245,598) → `settings64`(162,900) → `taskmgr64`(87,366) →
     `userdb64`(60,541) → `desktopops64`(58,474) → `config64`/`icons64`/`mines64`/
     `session64`/`calc64`/`preload64`/`update64`/`sysstate64`。
   * 交付形态：`/bin/<app>.elf`（Ring 3 进程）+ 内核只保留"窗口/输入/合成"的原语
     （`wl64`+`display64` 已经是这条路的骨架，`/bin/wm`、`/wmclock.elf`、`/wmpanel.elf` 是样板）。
   * 注意：`terminal64` 里的 **shell 服务协议**（`sh64_serve64` 的"代列目录"）在外置前必须先有
     ABI 替代 —— 见第 3 节第 1 条。
3. **GUI 专用（第 3 顺位，收益 ~578 KB）**
   * 顺序：`gui64`(131,216) → `explorer64`(110,850) → `panels64`(98,498) →
     `startmenu64`(74,231) → `gfx64`(57,375) → `locklogin64`(56,734) → `img64`(29,596) →
     `theme64`(19,680)。
   * 与第 2 顺位是同一条路（合成器在 Ring 3），所以实际执行时**2 与 3 交替做**：
     每搬一个应用，顺手把它依赖的那部分 GUI 原语也搬走（剩下的原语只留"表面/缓冲区/提交"）。
4. **设备驱动（第 4 顺位，收益 ~205 KB）**
   * 顺序：`xhci64`+`usb64`(73,338, 一块) → `ahci64`+`ata64`(54,782, 一块) → `nvme64`(22,337) →
     `virtio_gpu64`(17,411) → `e1000_64`(8,474) → `hda64`(29,383)。
   * 交付形态：Ring 3 驱动服务（`pci_map_bar` + `shm_*` 已经就位；`/bin/drvdemo` 是骨架）。
   * **注意**：驱动外置会让"每次 IO 先切到用户态" —— 这一桶的收益必须在**性能验收**里
     被证明可接受（否则只做 HDA/virtio-gpu 这种低频设备）。
5. **内嵌资源收尾 + 内核自检瘦身**：`panic64` 的自检文本、`net64`（无用户态网络栈时的占位）
   等，最后处理。

### 迁移验收口径（每条**必须全绿**，缺一条就算没做成）

1. **内核字节净减**：`tools/kernel_size_report.py` 的平整度字节（`kernel64_os.bin`）
   **严格下降**，降幅与该桶的清单字节量级一致；`tests/a42a64_test.py` 的三层预算断言
   **只允许"下调上限"，不允许上调**；
2. **行为不变**：该功能的**用户可见行为逐字节/逐像素一致**（截图哈希、串口输出逐字节比对、
   文件内容逐字节比对）；
3. **回归全绿**：`sh64 / musl64 / dynlink64 / tcc64 / lua64 / make64 / tar64 / gzip64 /
   edit64 / wm64 / a42a64 / desktop64 / gui_modern64 / busybox64` 全过，且**不许削弱断言**
   （抖动先复跑，不改判据）；
4. **体积纪律**：搬出去的东西在内核镜像里搜不到（64B 高熵探针 = 0 命中）；
5. **文档同步**：`docs/应用层与系统调用说明.md` 的号段表与 `docs/项目状态总览.md` 的能力表
   同步更新，`docs/发布流程.md` 的检查清单逐条打勾。

## 3. 本批（busybox）用到的"缺口 → 裁决"实例（按第 1.3 节的流程走过一遍）

| 缺口 | 裁决 | 本批做法 |
|---|---|---|
| ring3 没有 `getdents(217)`；目录枚举在内核里**有**（`fd64_readdir64`），但只对内核自己开放 | 按第 1.1 节判据，这是**用户态所必需的 ABI 补齐**（加号以后内核里只多"参数校验 + 转发"）。但本批用户指令明确"不碰 kernel/**" -> **不改内核，先报告** | 用户态替代：构建期把卷的目录树导出成 `/etc/vimtu.dirs` 索引，`user/busybox/vimtu_dirent.c` 把 busybox 的 `opendir/readdir` 接到索引上。**如实标注**：索引是构建期快照，本次开机里新建的文件不会被 `ls` 看到 |
| ring3 没有 `/proc`（`ps`/`free`/`uptime` 拿不到进程表与内存信息） | 同上：要么补 `/proc` 合成（属于"内核里新增一块只读文件系统" -> 偏"新功能"，需要单独立规），要么把进程表以最小 ABI 暴露给用户态（更符合宪法） | **如实标 GAP**：applet 装进去了，但列不出东西/明确报错 |
| ring3 没有 `statfs(137)`（`df` 拿不到卷容量） | "用户态所必需的 ABI 补齐"（内核已有卷几何：`vfs64` 超级块） | **如实标 GAP**（`df` 明确失败，不是 PANIC） |
| 用户态没有 TCP/IP（`socket/connect/...` 全缺） | 网络栈**整体在用户态**做（这才是宪法要求的），内核只该补"网卡寄存器映射 + 中断投递"这类最小 ABI | **如实标 GAP**：`wget`/`ping` 构建并通过参数校验/明确报错，不假装成功 |
| `mkdir` 大小写、symlink 缺失（多入口） | 纯用户态问题 | 包装程序：`/bin/<applet>` = 4.7 KB 的 `execve("/bin/busybox", argv, envp)` |

## 4. 发布前的检查清单（与 `docs/发布流程.md` 的清单联用）

* [ ] **本批是否给内核加了新功能（应为否）** —— 若为"是"，停下来改设计；
* [ ] 本批所有交付物**都在系统卷里**，并且内核镜像里搜不到它们的高熵探针；
* [ ] 内核体积：`kernel64_os.bin` 只减不增（除非本批是"补齐最小 ABI"，且已在报告里逐条论证）；
* [ ] `docs/应用层与系统调用说明.md` 的号段表与本次一致；
* [ ] 回归全绿且**没有削弱任何断言**。
