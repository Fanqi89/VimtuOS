# VimtuOS 混合驱动架构（VimtuOS Unique Hybrid Driver Architecture）

> **本文档记录的架构由项目发起人 Fanqi89 主导设计，是 VimtuOS 独创的底层契约。**
> 它不是对 Linux 的模仿，也不是对 Windows NT 的照搬 —— 业界有 NT 这类"混合内核"，
> 但 VimtuOS 的两条边界是自己定的：
> **① 15 MiB 的内核空间扩容边界；② AHCI/NVMe 留 ring0、文件系统协议层剥到 ring3 的特定切分比例。**
> 这两条是本项目对外申明的核心特色，代码注释、README 与本文档以同一口径描述它们。

---

## 0. 一句话

**把"要延迟"的留在 ring0，把"会崩"的赶到 ring3，两边的数据通路必须是零拷贝。**

---

## 1. 切分线（谁在 ring0，谁在 ring3）

| 组件 | 位置 | 理由 |
|---|---|---|
| 中断控制器（APIC/IOAPIC/PIC）、定时器、ACPI | ring0 | 中断延迟与确定性；任何用户态往返都来不及 |
| **AHCI / NVMe 控制器本身**（HBA 寄存器、命令队列、PRDT、完成中断） | ring0 | 直接摸寄存器 + 响应完成中断；一次往返就该交货 |
| 基础显卡核心（帧缓冲、模式设置、DMA/PRIME 基础原语） | ring0 | 合成器每帧都要它，且它必须能在没有用户态调度时也活着 |
| PS/2 键盘鼠标、USB xHCI/EHCI 核心 | ring0 | 同上（输入延迟直接决定手感） |
| VimtuFS2（本机原生文件系统） | ring0 | **例外不是特权**：它是本项目的"自家格式"，解析器就在内核里、格式与内核同步演进；见 §5 的坦白 |
| **ext4 / NTFS 等外部复杂协议** | **ring3** | 解析逻辑巨大、易被畸形镜像打崩；崩了只需重启服务进程 |
| 应用（终端/编辑器/浏览器/办公/包管理器…） | ring3 | 常规 |

**为什么不是"全在 ring0"（宏内核）**：一个 ext4 的内核态解析 bug = 整机蓝屏/复位。VimtuOS 的纪律是
"**攻击面与内核边界对齐**" —— 外部协议（来自别的系统的镜像）永远不进 ring0。

**为什么不是"全在 ring3"（纯微内核）**：把 AHCI/NVMe 挪到用户态，每次 I/O 都要两次 IPC 往返 + 调度延迟，
在 TCG/低端机上直接表现为"读盘比蜗牛还慢"。VimtuOS 要的是"**兼顾极致性能与绝对稳定**"，
所以切的不是"驱动全都不许在内核"，而是"**控制器在内核、协议在用户态**"。

## 2. 15 MiB 内核空间边界（v0.9.31 落地）

### 2.1 磁盘侧

```
LBA 0                : boot.bin            MBR = **Stage 1**（只负责把 Stage 2 读进内存）
LBA 1..64            : loader64.bin         **Stage 2**，容量 32 KB（v0.9.32 前只有 8 扇区 = 4 KB）
LBA 65..30784         : 内核容量 15 MiB      ★ 硬闸门 = 15,728,640 B（30,720 扇区）
LBA 30785..32583     : 原始区（1,799 扇区） 演示程序 / 中文字体 / 图标包 blob
LBA 32584..32647     : store 裸盘降级槽（64 扇区，与主分区起点重叠，仅降级用）
LBA 32648..          : 主分区（VimtuFS2 卷）
```

- **唯一定义点**：`kernel/memlayout64.h`（`ML64_LOADER_SECTORS=64`、`ML64_KERNEL_SECTORS=30720`）；
  `ML64_KERNEL_LBA = 1 + ML64_LOADER_SECTORS`、`PART_BOOT_SECS = ML64_KERNEL_SECTORS + ML64_RAW_SECTORS`
  全部派生自它，三处实现（`build64.sh` / `boot/boot.asm` / `boot/loader64.asm`）只许对齐不许另写一份。
- **Stage 1 / Stage 2（v0.9.32）**：MBR 用两次 INT 13h 把 64 扇区（32 KB）的 Stage 2 读进
  0x9000 与 0x10000（分两块是为了不跨 64 KB 物理边界），再跳过去。Stage 2 因此**不再有 4 KB 焦虑**
  （容量 32,768 B，实测 4,090 B，余量 28 KB）。⚠️ **UEFI 链没有这个限制**：`BOOTX64.EFI` 把
  `UEFI64.BIN` 读到 0x06000000，上限 256 KB（`boot/efi/stub.c` 的 `LOADER_MAX`），UEFI64.BIN 现为 40 KB。
- **原始区搬出容量之外**：老布局把 blob 塞在内核区尾部，于是"内核预算 = (原始区起点-9)×512"，
  每加一个 blob 内核就小一圈。现在内核固定拿满 15 MiB，原始区独占其后。
- **loader 只读真实大小**：构建期把内核字节数折成扇区数写进 loader 的 `'KSNT'` 回填槽
  （`tools/loader_patch64.py`，紧跟签名 4 字节 = 512B 扇区数 + 2048B 光盘扇区数），
  所以"15 MiB 容量"不会变成"每次开机白读 12 MB"。

### 2.2 内存侧（四段互不重叠，两头都有闸门）

```
0x00100000 + 15MiB = 0x01000000   内核**容量**上界（内核二进制本身必须 ≤ 15 MiB）
~0x02C8B000                       __bss_end（实测 45.5 MB，含 fb 的 33 MB 后备缓冲）
0x04000000..0x06000000            载荷暂存区（安装介质把 system.img 整块读到这里）预留 32 MB
0x06000000..0x06040000            UEFI64.BIN（平铺长模式引导器）
0x07000000..0x0A000000            内核堆 48 MB —— **下限**；运行期起点 = max(0x07000000, ALIGN(__bss_end))
0x0A000000..                      物理页池（到 E820 上界；512 MB 机上 90,080 页）
```

- **构建期闸门**：`build64.sh` 用 `nm` 读 `__bss_end`，断言它 **不越过** 载荷暂存区起点
  （越线会让安装介质内核清 BSS 时把载荷抹成 0，症状是"装完的盘内容全 0"且日志一个字都不留）。
- **运行期闸门**：`kernel/mem64.cpp` 启动时打一行
  `[MEM64] layout bss_end=… payload=[…] heap=[…] pool=[…] guard=ok|FAIL`，
  四段关系任一条不成立就如实 `guard=FAIL`。
- **堆跟着内核走**：`heap_base = max(下限, ALIGN_UP(__bss_end, 2MiB))` —— 内核长得再大也不会被自己的堆覆盖。

## 3. 零拷贝契约（ring3 驱动 ↔ ring0 块设备）

**死命令：不允许大量内存拷贝。** 三层机制：

1. **共享内存页**：`shmget/shmat`（Linux ABI 号段）把页池里的物理页映射进用户地址空间；
   内核侧 `page_alloc_64()` 返回的就是物理地址（0..4GB 恒等映射，PA == VA），可直接填进 DMA 描述符。
2. **DMA 直投**：AHCI 的 PRDT / NVMe 的 PRP 指向的必须是物理地址 —— 共享页天然满足，
   所以 ring0 只要把"命令队列项"写进共享区，ring3 侧填数据指针，控制器直接把盘上的字节搬进用户页。
3. **描述符而非负载**：跨边界传的是 {缓冲区地址, 长度, 结果状态}，不传数据本身。

现状（如实）：`shmget/shmat/shmdt` 与 `proc64.cpp` 的共享内存对象已实现并有 ring3 验收
（`tests/ipc64_test.py`、`tests/proc64_test.py`）；**ext4/NTFS 的 ring3 协议服务进程尚未开始写**
（本批只完成它依赖的地基：15 MiB 内核空间 + 有界堆 + 共享内存 + 块设备 ring0 控制器）。

## 4. 层级定位：从"混合驱动"到"混合内核"

| 层级 | 特征 | 现状 |
|---|---|---|
| 混合驱动架构（Hybrid Driver Architecture） | 控制器 ring0 / 协议 ring3 + 零拷贝 IPC | **正在实施**（地基已落地，协议服务未写） |
| 混合内核架构（Hybrid Kernel Architecture） | 保留宏内核的高效 syscall 主干 + 微内核式 IPC 消息机制与可恢复服务 | 规划中 |

**执行顺序（不可跳步）**：

1. **内核空间扩容到 15 MiB**（v0.9.31）：容量、loader 真实长度、内存四段边界、构建/运行期闸门 —— 完成。
2. **ring3 驱动注册与块设备总线**：用户态服务进程向内核注册"我处理哪类协议"，内核按分区类型把
   请求路由给它；服务崩溃可重启、可回退到"只读安全态"。
3. **零拷贝数据通路**：共享页 + DMA 描述符（§3）。
4. 之后再谈"整体混合内核"（把更多子系统做成可重启服务）。

## 5. 诚实的边界（不许吹）

- **VimtuFS2 仍在 ring0**。它是本项目自家格式，与内核同版本演进；把它剥到 ring3 的价值（防畸形镜像）
  远小于代价（每次元数据操作都要 IPC）。**我们不假装自己是纯微内核。**
- **ext4/NTFS 的 ring3 驱动目前只有设计，没有代码**。本批交付的是它依赖的地基。
- **"零拷贝"当前的取证范围**：共享内存原语与页池 PA==VA 已可验证；**尚无一个真实的 ring3 块设备
  驱动跑过 DMA 直投**，所以"读盘不慢"这句现在只是架构承诺，不是实测结论。下一批必须用
  ext4 服务进程在真实镜像上证明（含吞吐对比：同样 64 MiB 顺序读，ring3 路径 vs 内核 VimtuFS2 路径）。
- 15 MiB 只是**容量上限**，当前内核实测 3,165,616 B（v0.9.31 构建），余量 12.5 MB —— 留着给后续
  驱动与协议层用，不是"已经用掉 15 MB"。
