# 桌面帧预算：拖动窗口的帧成本拆解与优化（v0.10.2 批次）

目标：`/lib/wm.elf`（Ring 3 合成器）拖动窗口时不要再被自己拖住，一帧要落进 16 ms 预算。

**结论先说**：日志预算这一刀把拖动从 **5.7 fps 提到 14.8 fps**（同一夹具、同一台机），
`wm64_test` 89/89、`wmfull64_test` 41/41 全绿；但**还没到 60 fps**，而且卡点已经不在
合成器算法上 —— 实测卡在**内核给用户态的共享内存/帧缓冲映射是"按页切换的小窗口"**：
碰一个新 4 KiB 页要 15 µs ~ 3 ms，一帧要碰几百页。§5 给出全部原始数字与下一步。

---

## 1. 夹具与测量方法（可复现）

`$scratch/p1_wmperf.py`（本轮新建）：

1. 复制 `build64/wm64_test.img`（`wm64_test` 用的夹具盘）→ 起 QEMU（`-vga std`，1280x800）；
2. 等 `[WM] map` / 两块 surface / `[WM] place` / 首帧；
3. 光标按 `plan_move` 走到 `wmclock` 标题条（600,360）按下左键 → 收到 `[WM] drag begin`；
4. 用一个 TCP 连接按固定间隔灌 `mouse_move`（默认 8 ms 或 16 ms 一包，**不是** 30 ms ——
   夹具自己不能把帧率钉住）；
5. 同时用 6 ms 轮询把串口**逐行打到达时间戳**；
6. 统计 `[WM] drag begin` ~ `[WM] drag end` 之间的：帧数、`[WM] frame` 的
   `dirty=/px=/us=/flip_us=/bg_us=/t_ms=`、日志行数与按 tag 的分布。

`t_ms=` 是 v0.10.2 新加的**客人侧时间戳**（`vimtu64_ticks()*4`）；主机侧时间戳只有 6 ms
分辨率，帧周期必须看客人的。

## 2. 改动前（v0.10.1 内核 + v0.10.1 wm）

```
drag_wall_s            = 1.400

drag_move_lines        = 44       <-- 44 个鼠标移动事件
frames                 = 8        <-- 真正上屏的帧 → 5.7 fps
px_med                 = 23552    <-- 每帧重画像素（两块窗口面积之和）
us_med                 = 644      <-- 合成（含背景回填）
flip_us_med            = 447      <-- 内核 backbuf→LFB
period_ms_med          = 85.46
```

一帧 85~175 ms，而像素活儿只有 ~1.1 ms。**多出来的时间不是画出来的。**

## 3. 找到的四个真因

### 3.1 每个鼠标事件打 11 行日志（占单帧成本 ~95%）

日志出口是 COM1：`dbg64_putc()` 每字符一次 `outb`，QEMU 里就是一次 VM exit → 实测
**≈1.4 ms/行**。一次拖动的事件链每步都打：

```
[SYSCALL] nr=1 ...            ← 用户态 printf（还被拆成多条 128B write）
[WL64] seatpost / seat event  ← 内核投递 + 客户端 dispatch
[WM] route / drag move / ack  ← 合成器自己的
[WMCLOCK] seat n=..           ← 客户端
[WL64] move id=.. pos=..      ← 27 号挪窗（保留：几何证据）
[WL64] export i=0/1 ...       ← 每轮循环两块 surface 各一行（连空闲都在刷）
[FB64] flip / [WM] frame ...
```

### 3.2 每个输入批次之后又整窗重画一遍（双份 paint + 双份 flip）

`wm.c` ⑪ 有一段"外壳刚把光标画进我们窗口里 → 立刻整窗重画"，它不判断本轮 ⑨ 是否已画过。
日志里 `us=0 flip_us=0` 的帧就是这条路径（原来连计时都不做）。

### 3.3 脏矩形是"旧位置 ∪ 新位置"的包围盒，三趟全走包围盒

背景回填（bbox）→ 窗口 blit（bbox）→ 内核 backbuf→LFB（bbox）。拖 10 px 时 bbox 已经是整窗。

### 3.4 逐像素实现

* `wm_bg_restore()` 每像素调 `wm_bg_at()`（算偏移 + 判跨 2 个 shm 对象 + 取基址）；
* `wm_blit_slot()` 每像素指针乘法；
* 半透明混合每通道一次 `/255`。

## 5. 改完之后的实测

### 5.1 第一刀（打点预算 + 去重画 + 行级 memcpy + 60 Hz 节拍）

同一夹具、同一台机：

```
稳态拖动（180 事件 / 16 ms 一包，~3.9 s）
  frames                 = 56        → 14.4 fps（改前 5.7）
  console_lines_in_drag  = 375
  us（窗口 blit）中位     = 288~804 µs
  flip_us 中位           = 286~700 µs
  bg_us（背景回填）       = 3,300 µs（44,928 px）/ 44,000 µs（73,008 px）
  内核对齐：`[WM] frame .. t_ms=` 的 dt 中位 336 ms，min 60 / max 676
```

### 5.2 第二刀（2 MiB 大页映射）—— **落地了，但判据没达标**

改了内核（见 §6），日志可证大页真的生效：

```
[FB64] backbuf pa=0x0000000000A00000 huge=1
[FB64] map huge pid=25 blocks=1 va=0x0000000140000000 pa=0x0000000000A00000
[SHM64] create pid=25 id=5 size=2097152 pages=512 huge=1 pa=0x000000000A200000
[SHM64] map   pid=25 id=5 slot=0 va=0x000000013E800000 pa=0x000000000A200000 pages=512 huge=1 u=1
[SHM64] create pid=25 id=6 size=1998848 pages=488 huge=1 pa=0x000000000A400000
[SHM64] map   pid=25 id=6 slot=1 va=0x000000013EA00000 pa=0x000000000A400000 pages=488 huge=1 u=1
```

判据（`[WM] bench`，8 次取最小，排除抢占；`cks=` 非 0 证明拷贝没被编译器删掉）：

```
改前：bgfull_us   = 519,413 / 565,080     （单次测量）
改后：bgfull_us_min = 460,538 / 501,288   ← **目标 < 20,000 没达到**
      copy4k_us_min = 4                   （4 KiB 拷贝本身正常）
拖动帧率：14.4 fps → 17.5~19.6 fps（+25%，不是 60）
```

### 5.3 足迹扫描：断崖在 256 KB 与 1 MiB 之间

`[WM] bench scale`（快照 → 帧缓冲，真实的拷贝方向，每档 6 次取最小）：

```
us_4k=68   us_64k=1110   us_256k=4726   us_1m=108493   us_3m=389189
     ↑ 16x 尺寸 → 16x 时间（线性）     ↑ 4x 尺寸 → 23x 时间（断崖）   ↑ 又线性
```

换算成每字节：4 KB~256 KB 是 **17~18 ns/byte**；1 MB 以上是 **103 ns/byte**（5.7 倍差）。

同一台机、同一个进程里，**写自己的 .bss** 只要 **1 ns/byte**（`copy4k_us_min=4`，方向是
快照→bss）；而**写共享帧缓冲**是 17~103 ns/byte。也就是说：

* 大页把页表项数量从 1000 个压到 2 个，**没有**改变拷贝成本 → **不是 TLB/页表问题**；
* 成本与"访问的是不是外部共享内存"强相关，并在 ~256 KB~1 MB 处出现断崖。

这已经不是合成器能修的东西，也不是大页能修的。下一步必须先回答"为什么写共享页比写自己的页慢
17~100 倍、为什么 512 KiB 附近有断崖"。**本轮到此为止，如实记录，不假装达标。**

## 6. 本批已落地的内核改动（2 MiB 大页）——以及它没解决问题的原因

已实现并验证"映射是对的"：

| 改动 | 位置 | 证据 |
|---|---|---|
| `page_alloc_2mb_64()`：2 MiB 对齐 + 512 页连续的物理块（位图按对齐扫描） | `kernel/mem64.cpp` | `[SHM64] create … huge=1 pa=0x0A200000`（2 MiB 对齐） |
| `user64_map_phys_2mb64()`：直接写 PD 项（PS=1，不建 PT），要求 va/phys 双对齐且在 4 GiB 直映内 | `kernel/usermode64.cpp` | `[SHM64] map … huge=1 u=1` |
| 页级查询助手认识大页（`is_user` / `page_flags` / `unmap_page` 三处；否则 fb_map 自检会判失败） | `kernel/usermode64.cpp` | 修前 `[WM] FAILED fb_map rc=-4`，修后正常 |
| shm 对象 ≥1 MiB 走 2 MiB 块，整块 512 页填满（1,998,848 B 那种"差 24 页"的对象也能整块映射） | `kernel/proc64.cpp` | `id=5 pages=512` / `id=6 pages=488` 两行都 `huge=1` |
| fb 后备缓冲 2 MiB 对齐 + 按大页映射（尾部不足 2 MiB 的仍走 4 KiB） | `kernel/fb.cpp` / `kernel/syscall64.cpp` | `[FB64] backbuf pa=0xA00000 huge=1`、`[FB64] map huge blocks=1` |

**发版口径（重要）**：两个大页开关目前**默认关闭**，代码与判据都保留在本仓库里：

```c
kernel/proc64.cpp    static const int SHM64_HUGE_ENABLE = 0;   // shm 对象的 2 MiB 块分配
kernel/syscall64.cpp static const int FB64_HUGE_ENABLE  = 0;   // fb_map 的 2 MiB 大页
```

关掉的原因（不是"没做"）：打开它们之后 `wm64_test` 出现两条**像素级**回归 ——
⑤ 点击后开关区域读回 `0x000000`、⑦ 交回时 `erased=13672`（打开前是 `erased=0`）。
⑦ 随 fb 大页关闭而转绿；⑤ 最终定位到**启动基准自己**：它在首帧之前把 4 MiB 快照回填进
帧缓冲 8 次、又做了 3 MiB 的足迹扫描（从 2 MiB 的 shm 对象里读，越过对象边界），等于在
首帧前把屏幕涂了一遍。基准现在由 `/etc/wm_bench` 探针文件触发，发版路径零副作用，
`wm64_test` 回到 **89/89**。

也就是说：**⑤ 不是大页的锅，⑦ 是**。把 `FB64_HUGE_ENABLE` 重新打开前，必须先让 ⑦ 绿；
这条已经写进 `kernel/syscall64.cpp` 的注释里。

**为什么没解决问题**：见 §5.3 —— 成本与页表项数量无关，与"是不是外部共享页"和"足迹是否超过
~512 KiB"有关。下一轮的第一件事不是继续改合成器，而是查这个（候选：QEMU 对 guest 共享页的
写处理、该映射的 PAT/UC 属性、kernel 侧对 fb 页的某种逐写副作用）。

## 7. 下一步（按收益排序，已按 §5.3 更新）

1. **查清"写共享页 17~103 ns/byte + 512 KiB 断崖"**。验收判据现成：
   `[WM] bench scale` 的 `us_1m` 应从 108,493 降到 < 5,000；`[WM] bench bgfull_us_min` 应 < 20,000。
2. 若确认是缓存属性/映射属性：把 fb/shm 的映射属性与 kernel 自身页对齐（现在是 PTE 层面不同）。
3. 合成器侧再谈 scroll-move（拖动只重画两条露出的边）——只有 (1) 落地后才有意义。
4. 帧节拍已经是 16 ms；PIT 250 Hz 的 4 ms 粒度换 1 ms 可再贴近 16.6 ms（小事，收益有限）。
