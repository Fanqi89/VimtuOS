## 3. 磁盘 / 分区：真实读 + 真实写（kernel/ata64.cpp + kernel/part64.cpp）

`ata64.cpp` 是安装程序专用的精简 ATA PIO 驱动（主/从 4 个驱动器，LBA28）：

* `ata64_identify()`：型号 + 总扇区数，识别 ATAPI（光驱不列为安装目标）
* `ata64_read/write()`：读写任意 LBA（PIO 轮询），`ata64_read_sector/write_sector` 是单扇区包装
* `probe_disk()`：解析 **MBR**（4 项）与 **GPT**（保护性 MBR → LBA1 头 → 分区项），
  分类显示 ESP / Microsoft 保留分区 / 基本数据分区，并算出"未分配的空间"

`part64.cpp` 是安装引擎（**每一件事都真的落到盘上**）：

| 界面按钮 | 真实动作 | 串口证据 |
|---|---|---|
| 新建 | 写标准布局的**混合 MBR**：P1 = 引导分区（type `0xEF`，**活动**，LBA 9 起 8000 扇区）+ P2 = 主分区（type `0x07`，LBA 8009 起）；目标盘够大（≥ ~17MB，主分区还能留 8MB）时**再加 P3 = EFI 系统分区**（type `0xEF`，盘尾 5MB），P2 收缩到 ESP 之前 | `[PART] 新建分区表 OK drive=8 boot=9+8000 main=8009+112790 esp=120799+10240` |
| 删除 | 清掉对应 MBR 分区项（16 字节全 0）并重写 55AA 签名 | `[PART] 删除分区 OK drive=1 index=2` |
| 格式化 | 清分区**首 64 扇区**（不整盘擦，避免久等）；主分区（`0x07`）用真文件系统 **VimtuFS2**（超级块 + 位图 + inode + 数据区）。**ESP（盘尾那个 0xEF 项）拒绝格式化**（抹掉它 UEFI 就起不来了） | `[PART] 格式化 OK drive=1 index=2 start=8009 sectors=24759` |
| 安装系统 | 从安装介质的**载荷**（magic `VIMTUPAY`）整盘复制到目标盘：每帧 128 扇区（64KB），进度 = 已写扇区 / 总扇区 | `[INSTALL] 开始安装：src=0 dst=1 sectors=8073` / `[INSTALL] 完成：已写 8073 扇区，分区表已更新` |
| 安装收尾（新增） | ① 在盘尾格式化 **FAT16 ESP**（512B 扇区、SPC=1、2 份 FAT、512 项根目录、真 FAT16 簇数区间）② 写 `EFI/BOOT/BOOTX64.EFI`（内嵌的 PE 桩字节）+ `UEFI64.BIN`（内嵌的平铺引导器）+ `KERNEL64.BIN`（**直接读目标盘 LBA 9..8008 的 4MB 内核区**，不占安装程序内核体积）③ 写盘尾**备份 GPT**（项1 主分区 / 项2 ESP）+ 混合 MBR | `[FAT64] selftest PASS` / `[INSTALL] esp: lba=120799 sectors=10240 fat_ok=1` / `[INSTALL] esp files: BOOTX64.EFI=2560B UEFI64.BIN=36864B KERNEL64.BIN=4096000B` / `[INSTALL] gpt written (main + esp), pmbr ok main=8009+112790 esp=120799+10240 backup_hdr_lba=131071` |
| 完成 | 界面 100% + `[SETUP] 安装完成 100%（真实写入 8073 扇区）` → 2.5 秒后 `[SETUP] 自动重启（8042 复位）` | 见左 |

### 3.1 安装时建 ESP + GPT（让装好的盘 UEFI 也能启动）

为什么需要：以前安装只写"MBR + 固定 LBA 引导区"，固件在盘上找不到任何 FAT 卷，
所以**装好的盘在 UEFI 机器上根本不出现在启动菜单里**。现在安装收尾会补齐：

* **FAT16 ESP**（盘尾 5MB）—— 内核实现在 `kernel/fat64.{h,cpp}`：把构建期
  `tools/make_esp.py` 的卷格式算法原样搬进内核（**同样的卷参数**：512B 扇区 / `SPC=1` /
  1 个保留扇区 / 2 份 FAT / 512 项根目录 / 簇数硬断言落在 `[4085, 65525)`）。
  限制（写清楚）：只支持根目录 + 最多 2 层子目录、**簇链连续分配**、8.3 短名、只新建不覆盖。
* **混合 MBR**：`0xEF` 引导区（活动，9+8000）+ `0x07` 主分区 + `0xEF` ESP（盘尾）。
  不写 `0xEE` 保护项 —— EDK2 见到 `0xEE` 会放弃 MBR 解析路径，而我们要保留
  "MBR 里找 `0xEF` 分区"这条老固件兜底路径。
* **盘尾备份 GPT**：主 GPT 头的规范位置是 LBA 1，而那里是 `loader64.bin`
  （`boot/boot.asm` 从 LBA 1 读 8 扇区）—— 两者不可兼得，所以只写备份头 + 备份项数组。
  UEFI 规范要求"主头无效时使用备份头"，EDK2（OVMF / VMware EFI）实测如此，
  且启动后 LBA 1..8 的 loader 字节**没有被固件改写**（`tests/esp_install_test.py` 有这条断言）。
* **ESP 里的内核**：`KERNEL64.BIN` = 目标盘 LBA 9..8008 的整块 4MB（= `kernel64_os.bin` + 补零）。
  安装程序内核因此**不需要**内嵌系统内核副本（内核区上限 4MB，装不下两份）。
  `boot/efi/uefi64.c` 也相应把 `SYSTEM.IMG`（安装载荷）改成**可选**：装好的盘上没有它，
  跳过并写 `U:missing SYSTEM.IMG (optional, skipped)` + 介质描述符 `kind=0`（系统内核不用载荷）。
* **小盘怎么办**：`disk < 8009 + 8MB(主分区) + 5MB(ESP) + 33(GPT备份) ≈ 17MB` 时不建 ESP，
  只写老 MBR 布局（BIOS-only），串口打 `[INSTALL] esp skipped (disk too small) sectors=…`。
  既有的 16MB 回归目标盘走的就是这条路径，字节级断言原样保持。
* **FAT16 写入器自检**：安装程序启动时先跑 `fat64_selftest64()`（`[FAT64] selftest PASS`）：
  坏参数被拒（卷太小 / drive<0 / 未格式化就写文件）+ **内存卷**上 format→mkdir→写 3000B 文件→
  沿簇链逐字节读回 + BPB/FAT[0]/FAT[1]/目录 `"."`/`".."`/两份 FAT 一致 的逐项核对。
  自检**只碰内存卷**（后端显式切换，真盘调用走 `fat64_format64`）—— 曾经因为后端切换写在
  format 内部，自检把 drive 0 的介质盘格式化掉了（实测把 ISO 前 2.5MB 覆盖成 FAT16 卷，
  串口侧看不出来），现在 `tests/usb_boot_both_fw_test.py` 末尾有"介质字节未改动"的 sha256 断言兜住。

宿主侧字节级验收（`tests/esp_install_test.py`）：MBR 三项 / 备份 GPT（头与项数组 CRC）/
ESP 的 FAT16 卷（`tools/fat_check.py` 规范体检）/ 三个文件与本地构建产物逐字节一致，
然后**UEFI（OVMF）与 BIOS 各从同一块装好的盘启动进桌面**。

### 踩过的驱动坑（都有注释，别再踩）

1. **驱动器选择字节必须是 0xE0**（bit6 = LBA 模式）。写 0xA0（CHS）时 IDENTIFY 照样成功，
   但随后的 READ/WRITE 会被设备以 **ABRT（错误寄存器 0x04）** 中止 ——
   表现为"识别正常、读盘全失败"。
2. **首扇区读失败不能把磁盘标成"不存在"**。空盘/未格式化盘读 LBA0 可能失败，但设备是好的；
   一旦清掉 present，整个驱动器会从列表消失，看起来像"没接硬盘"。
3. **`ata64_diag()` 不要在运行期调用**：它发 IDENTIFY 但不读走那 256 字数据，
   会把设备留在"命令被中止"的状态，导致随后的 sector0 读取失败。

排障入口：`ata64_dbg_st[8]` / `ata64_dbg_err` / `ata64_dbg_polls` / `ata64_dbg_reason`
（读失败时 `probe_disk()` 会把它们打到串口）。

## 4. 安装介质布局（build64.sh 生成，三方一致）

```
vimtu64-64.img （16266 扇区 = 7.9MB，可直接写 U 盘 / 作 VMware 磁盘）
vimtu64-64.iso （约 14.9MB = 7.1MB ISO9660 + 6MB 附加分区，**安装盘三合一**：
                 ① BIOS 光盘 El Torito ② U 盘/裸盘 hybrid MBR ③ UEFI（GPT + FAT16 ESP）；
                 引导桩 + loader + 安装程序内核 + 系统镜像 + UEFI 引导器都在里面，
                 详见 docs/ISO安装介质说明.md 与 docs/UEFI引导说明.md）
  LBA 0            boot.bin        MBR 引导扇区
  LBA 1..8         loader64.bin    实模式准备 + 进长模式 + 64 位 ATA 读内核
  LBA 9..8008      kernel64.bin    安装程序内核（-DVIMTU_INSTALLER_MEDIA=1）
  LBA 8009..8072   设置持久化保留区（64 扇区）
  ---- 以上 8073 扇区 = 一份完整的"系统磁盘映像"（build64/system.img）----
  LBA 8192         载荷头（magic "VIMTUPAY" + 扇区数 8073 + 载荷 LBA 8193）
  LBA 8193..16265  载荷本体 = system.img 的副本（里面是 kernel64_os.bin，
                   即**系统**内核，启动时走 [OS] 路径而不是安装程序）
```

同一套源码编译两遍：带 `-DVIMTU_INSTALLER_MEDIA` 的是安装程序，不带的是装到硬盘上的系统。
安装时把 LBA 0..8072 整段（含 boot.bin + loader64 + 系统内核 + 设置区）复制到目标盘，
所以装完的盘就是一份自洽的可启动映像。

## 5. 串口按键通道（COM2，无人值守安装）

`kernel/setup64_keys.h`：轮询 COM2(0x2F8) 的接收缓冲，收到的字节**原样当按键**投给向导
（与真实键盘同一个 `handle_key` 路径），串口留 `[SETUP] com2key=0x..` 证据。

为什么需要它：自动验收时 QEMU 靠 monitor `sendkey`、VMware 想发键只能抢窗口，
而 **VMware Workstation 自带的 VNC 服务器是只读的**（实测发 KeyEvent 客人收不到），
真机更没法脚本点按；走串口后 QEMU / VMware / 真机三类环境用同一条路径。
真机上只要另一台机器接一根串口线，就能把整个安装流程跑完（类似 Windows 的 unattend）。

约定：回车 `0x0D`/`0x0A`、Esc `0x1B`、字母数字即字符，方向键用内部码
`0xFD`(上)/`0xFE`(下)/`0xFB`(左)/`0xFC`(右)。

## 7. 键盘/输入相关的两个真坑（M2 实测）

1. **8042 命令字节被写坏 → 键盘变扫描码集 2**：`kbd_init()` 原来直接读命令字节、`|0x01` 写回。
   如果此刻输出缓冲里还留着鼠标初始化产生的 ACK(0xFA)，就会把 0xFB 写回去 ——
   bit6（集 2→集 1 翻译）被清掉，键盘从此送集 2 码，用集 1 表解码就成了
   "按回车出来的是 Esc"（QEMU trace 实证：`sendkey ret → ps2_put_keycode 0x5a set 2 xlate 0`）。
   修复：读写命令字节前先排空输出缓冲、写的时候**强制 bit6=1** 并清掉保留位；
   同时删掉 `kernel64.cpp` 里重复的第二遍 `kbd_init/mouse_init`（诱因就是它）。
2. **键盘 IRQ 不能吃鼠标字节**：两个 IRQ 现在共用一个"按状态位 0x20 分流"的排空函数，
   避免鼠标包字节被当成扫描码投递（实测收到过根本不存在的按键 0x01/0x03）。
